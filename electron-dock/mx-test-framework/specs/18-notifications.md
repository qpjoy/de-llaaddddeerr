# 18 · 通知

> 五件待办的第一件。为什么排第一：定时任务一旦跑起来，**没有通知就等于没跑**——
> 早上不会有人主动去开看板，出了问题也是几天后才发现。

---

## 1 · 先说清楚"通知"是什么

最容易做错的版本是"每次跑完发一条"。定时任务每天跑，群里每天一条"执行完成"，
两周后所有人静音这个群。等真出问题时，没人看。这叫**告警疲劳**，
它比没有通知更糟，因为看板还显示着一切正常。

正确的规则只有一句：

> **只在状态跃迁时通知，不在有结果时通知。**

| 发生了什么 | 通知？ | 去哪 | 为什么 |
| --- | --- | --- | --- |
| 上次通过 → 这次失败（**新失败**） | ✅ 一条 | 业务群 | 这是新信息 |
| 连续失败第 2、3、30 次 | ❌ 静默 | — | 看板已经写着了，重复说只会训练人忽略这个群 |
| 失败 → 通过（**恢复**） | ✅ 一条 | 业务群 | 不说，之前静音的人永远不知道可以放心了 |
| `blocked`（浏览器起不来、依赖装不上、Pod 被驱逐） | ✅ 一条 | **运维群** | 不是产品问题，是基础设施问题，找的是另一批人 |
| `blocked` 连续第 2 次起 | ❌ 静默 | — | 集群坏一周不该发一周 |
| `expired`（桌面任务没人认领） | ❌ | — | 那是"没人开电脑"，是排队设计在正常工作，不是失败 |
| flaky | ❌ 实时 | 周报 | 实时报 flaky 就是在制造噪声 |

**"新失败"的比较基准是同一个任务的上一次已完成执行**——同一个任务，不是同一个套件。
一个套件上挂着"每小时 mock"和"每晚 real"两个任务时，它们是两路独立信号，
一路翻红不该让另一路闭嘴。

---

## 2 · 消息里有什么

内容由读消息的人在 30 秒内要做的判断决定：**是不是我的、有多严重、去哪看**。

```
❌ 新失败 · 罗盘 / 罗盘 Web mock · 每晚
任务：罗盘 Web mock · 每晚
结果：21/23 通过，1 失败，1 未执行
  · LP-FE-AUTH-001 未登录访问内页应跳转到登录
    expected 302 but got 200
本次：aaaabbbbcccc
上次通过：111122223333
http://mxt.internal:30879/runs/trun_xxx
```

几个刻意的取舍：

- **错误只取第一行**，不贴堆栈。告警是指路牌，不是报告。要看堆栈就点链接。
- **最多列 5 条失败**，剩下的写"还有 N 条未列出"。20 条失败刷屏没人看得完。
- **"上次通过"的 commit** 是整条消息里最有用的一行——它把排查范围缩成一个
  commit 区间。
- **"未执行"单独列出**。一次执行可以是绿的，同时悄悄跳过了目录里一半的用例。
  这正是平台要盯的东西，所以它进告警。
- **入库前脱敏**。断言消息里粘进 `authorization: Bearer ...` 是常事，
  那东西不能进群。

## 3 · 通用接口：适配器

每个渠道类型只需要实现同一个形状：

```js
{ kind, validate(config), build(message, config) -> { url, headers, body } }
```

`build` 是**纯函数**——它返回一个"要发的请求"，而不是去发。这样：

- 每个适配器都能不联网测试
- 投递、重试、超时、出队这些逻辑只存在一个地方（`dispatch.mjs`），
  不会每加一个渠道就重写一遍

已实现三个：

| kind | 说明 |
| --- | --- |
| `webhook` | 通用 JSON POST。**这是让上面这张表不封闭的逃生口**——邮件网关、工单系统、内部转发服务、自研机器人，任何有 HTTP 端点的东西都能接，不用改平台代码。配了 `secret` 会带 `x-mxt-signature`（和 GitHub 同样的 HMAC 形状，多数转发服务已经认识） |
| `feishu` | 飞书自定义群机器人 |
| `wecom` | 企业微信群机器人 |

**邮件怎么办**：没有内置 SMTP 适配器，因为那需要引一个依赖（nodemailer），
而这个项目此前只有一个运行时依赖。两条路：

1. 用 `webhook` 打到你已有的邮件网关（多数公司都有）——**推荐**，零改动
2. 真要原生 SMTP：在 `adapters.mjs` 里加一项，大约 30 行 + 一个依赖。
   接口就是为这个留的

## 4 · 为什么先写库再发送（outbox）

通知不是在收到结果的那个请求里发出去的。它先写进 `mxt_notifications` 表，
由调度器每分钟一跳时投递。

两个理由，都是从相反做法的后果推出来的：

1. **同步发会让执行机等在别人的聊天服务器上。** webhook 慢一点，
   就变成"测试跑得慢"；webhook 卡住，就烧掉这次执行的租约。
2. **发完就忘（fire and forget）会在重启时静默丢消息。**
   "结果记下来了但没人被通知到"是比没有通知更糟的结果，因为看板看着很正常。

先写库还有第三个好处：**当有人说"我没收到消息"时，有一行记录可以查**——
`GET /api/v1/notifications` 能看到每条的状态、重试次数、最后一次的错误。

投递失败会在后续的 tick 重试，**最多 4 次**然后标 `failed` 并留下原因。
不无限重试：一个半年前就删掉的 webhook 不该变成一个永久的后台错误，
而且得让人看得见它为什么停了。

## 5 · 怎么用（详细步骤）

### 5.1 部署（不需要额外配置）

`manage.sh deploy` 会自己从节点 IP 和 NodePort 推导出通知里要用的链接地址，
并在部署时打印一行 `notification links will point at http://...`。

只有当那个地址不是使用者实际访问的地址时（例如前面加了反向代理），
才需要在 `.env.internal` 里显式指定：

```bash
MXT_PUBLIC_URL=https://mxt.example.internal
```

> 为什么要单独一个变量：平台内部已有 `MXT_SELF_URL`，但那是集群内部名字
> （`http://mx-test-framework`），发到群里点不开。
> 原本这是一个需要人记得配的变量，但"忘了配"的表现是**告警照常到达、只是没有链接**——
> 一个要等到有人真去点链接时才会发现的问题。所以改成自动推导。

### 5.2 拿到机器人地址

**飞书**：群设置 → 群机器人 → 添加机器人 → 自定义机器人 → 复制 webhook 地址。
如果开了"签名校验"，把密钥也复制下来。

**企业微信**：群设置 → 群机器人 → 添加 → 复制 webhook 地址。

### 5.3 在 MXT 里登记渠道

```bash
curl -X POST "$MXT_URL/api/v1/notification-channels" \
  -H "authorization: Bearer $MXT_ADMIN_TOKEN" -H "content-type: application/json" \
  -d '{
    "name": "罗盘测试群",
    "kind": "feishu",
    "config": { "url": "https://open.feishu.cn/open-apis/bot/v2/hook/xxx", "secret": "yyy" },
    "app": "luopan",
    "events": ["failure", "recovery"]
  }'
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `kind` | `feishu` / `wecom` / `webhook` |
| `app` | **不填就是所有应用**。运维群通常不填，业务群填自己的应用 |
| `events` | 不填就是全部三种。**运维群建议只填 `["blocked"]`**，业务群填 `["failure","recovery"]` |

登记时会用适配器校验地址——把企业微信的地址填进飞书渠道会**当场报错**，
而不是几天后在一次真实告警时静默失败。

### 5.4 发一条测试消息

```bash
curl -X POST "$MXT_URL/api/v1/notification-channels/<渠道 ID>:test" \
  -H "authorization: Bearer $MXT_ADMIN_TOKEN"
```

它**走的是和真实告警完全相同的那条路**（入队 → 调度器投递），
所以最多要等一分钟。这是故意的：一个走另一条代码路径的测试，
证明不了真实那条路能通。

### 5.5 确认送达

```bash
curl "$MXT_URL/api/v1/notifications" -H "authorization: Bearer $MXT_ADMIN_TOKEN"
```

看 `status`（`pending` / `sent` / `failed`）、`attempts`、`lastError`。

## 6 · 需要斟酌的点

**① 渠道地址本身就是凭据。** 飞书机器人 URL 的 token 是路径的一部分，
拿到 URL 的人就能往群里发消息。所以读取渠道列表时**只返回域名和"有没有密钥"**，
不返回完整地址。这意味着**你填进去之后就看不到了**，请自己留一份。

**② 运维群和业务群要分开。** `blocked` 是基础设施问题（浏览器起不来、
Pod 被驱逐、依赖装不上），发给业务同学他们既看不懂也处理不了；
反过来 `failure` 发给运维也是噪声。这就是 `events` 字段存在的原因。

**③ 别给一个任务配太多渠道。** 同一条失败发到三个群，等于三份告警疲劳。

**④ 调度器是单副本的。** 现在的实现假设只有一个进程在投递
（`30-server.yaml` 把副本数钉死为 1）。如果将来要多副本，
`listPendingNotifications` 这条查询要改成 `FOR UPDATE SKIP LOCKED`，
否则同一条消息会被发多次。这条写在代码注释里了。

**⑤ 200 不等于送达。** 飞书和企业微信都会用 HTTP 200 + body 里的错误码
表示失败（比如签名不对是 `19024`）。只看状态行会把没送到的消息标成已送达。
实现里检查了 body 的 `code` / `errcode`。
