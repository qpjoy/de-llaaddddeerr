# ADR-0007：框架与命令在 MXT 里指定，用例代码归测试团队自己的仓库

状态：已接受（2026-09-01）
补充：[ADR-0003](0003-git-owned-case-source-of-truth.md)（用例以 git 为真相源）——
**那条不变**，变的是"哪个 git 仓库"。

## 背景

平台要支持多语言多框架（pytest / Cypress / Playwright / k6）。接入点放哪：

- **A**：放业务项目里，各项目自己产出 JUnit，MXT 只收结果
- **B**：放 MXT 后台，建任务时直接指定框架与命令

之前的实现是 A 的变体：MXT 存 `engine` / `runnerImage` / `command`，
但 `command` 被限制成只能调用**被测仓库里的具名入口**
（`pnpm run x` / `make x`），理由是"执行命令也是测试代码，要走 PR"。

## 三件被混在一起的事

争论卡住是因为下面三件事被当成了一件：

| # | 问题 | 答案 |
| --- | --- | --- |
| 1 | **谁决定怎么测**（用什么框架、跑哪些用例） | 测试团队 |
| 2 | **执行配置放哪**（框架、镜像、命令、工作目录） | **MXT 后台** |
| 3 | **用例代码放哪** | **git**——但不必是业务仓库 |

把 2 和 3 绑在一起，就会得出"要动业务仓库"的结论。它们是可分的。

## 决策

### 一、执行配置在 MXT 后台指定，命令不再限制词表

`command` 放开成任意 argv：`["pytest","-q","--junitxml=out.xml"]`、
`["npx","playwright","test","--reporter=junit"]`、`["k6","run","script.js"]`
都可以直接在后台填。

保留的只有两条：

- **argv[0] 不能是 shell**（`sh`/`bash`/`powershell`…）。参数不经过 shell，
  把 argv[0] 交给 shell 等于把刚去掉的解析放回去。需要管道就在测试仓库里写个脚本。
- **参数不能含控制字符**。它们会破坏 argv 传递，并允许伪造日志行。

### 二、suite 可以有自己的测试仓库

新增 `suite.repoUrl` / `suite.defaultBranch`（迁移 007），为空时回落到应用的。

于是测试团队可以在**自己的仓库**里写 Playwright/pytest 代码，
**业务仓库一行都不用改**——不需要加 package.json script，不需要 Makefile，
不需要往别人的仓库提 PR。

### 三、用例代码仍然必须在 git 里

ADR-0003 的理由一条都没弱：review、diff、blame、回滚，以及
**"检出 v2.0.0 就得到 v2.0.0 的用例"** 这条版本绑定。
变的只是"哪个仓库"，不是"要不要仓库"。

## 理由

**"谁决定怎么测"这个问题，测试团队是对的。** 业务开发不一定关心测试质量，
更不该成为测试策略的守门人。让测试同学为了改一个 pytest 参数去等别人 review，
是这个平台本来要消除的摩擦。

**而"用例代码进 MXT 数据库"解决不了版本绑定。** spec 依赖选择器、路由、接口形状。
应用在 v2.0.0 时，MXT 里存的是哪一版用例？要么另造一套版本系统（它永远会和 git 不同步），
要么放弃"这次结果对应哪版用例"这个问题的答案。
**测试团队自己的 git 仓库同时满足两边**：他们完全自主，且版本绑定天然成立。

**原来的命令白名单本身就不自洽。** 它限制 `command` 只能调具名入口，
**却完全不限制 `runnerImage`**——管理员填任意镜像，入口点就是任意代码。
所以那条白名单挡不住有意的人，只挡得住正当用法。真正的信任边界是
**admin 角色 + 沙箱容器 + 审计**，不是一张批准词表。

**沙箱是真的**：容器没有 service account token、egress 受 NetworkPolicy 限制、
工作区是随 Pod 消失的 emptyDir、run token 只作用于这一次执行。

## 两类用例的归属线

不是所有用例都该搬到测试仓库。判据是**这条用例需不需要知道应用内部**：

| 用例类型 | 放哪 | 为什么 |
| --- | --- | --- |
| 共享 fixture / mock / 类型的用例 | **业务仓库**（同一 commit） | 分开就会漂移。罗盘现有 23 条 Cypress 用例有 9 份 fixture，属于这一类，**不要动** |
| 黑盒 e2e、接口、性能、桌面冒烟、LLM 评测 | **测试团队仓库** | 只碰对外表面，分开没有漂移风险，且测试团队完全自主 |

新接入的项目默认走第二类。

## 关于 AI 生成用例

[ADR-0003](0003-git-owned-case-source-of-truth.md) 要求 agent 产物走 PR，这条保留，
但成本因为本 ADR 大幅下降：**PR 提到测试团队自己的仓库，是测试同学 review 自己 agent 的产出**，
不再需要等业务开发。

人工核对这道闸门不能省。理由和当初一样：
**一个没人 review 过的绿色用例，只证明代码没崩，不证明业务对。**
agent 越好用，这道闸门越重要——生成速度上去之后，唯一还能保证"测的是正确的东西"的就是它。

## 后果

- 后台新建套件时要填的东西变多了（引擎、镜像、仓库、分支、目录、命令），
  但每一项都是测试同学自己能决定的，不需要问任何人。
- 业务仓库的接入成本降到 **0**：注册应用时填它的地址，用例写在别处。
- `suite.repoUrl` 为空时行为完全不变，已有的接入方式继续有效。
- 私有测试仓库同样用 `MXT_GIT_TOKEN`。凭据作用域要覆盖测试仓库。
- 命令放开之后，**suite 的创建与修改必须进审计日志**。这是替代白名单的那道保障，
  目前还没实现。

## 被否决的方案

- **用例代码存进 MXT 数据库**：丢掉版本绑定与 review/diff/blame，
  换来的只是"不用开仓库"这一点便利。
- **继续要求业务仓库提供具名入口**：把测试团队的自主权交给了业务开发的排期，
  且与不受限的 `runnerImage` 自相矛盾。
- **保留命令白名单并同时限制镜像**：能自洽，但会把"支持任意框架"这个目标
  变成"支持我们预先想到的框架"，与平台定位冲突。
