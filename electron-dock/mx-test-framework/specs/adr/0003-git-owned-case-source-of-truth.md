# ADR-0003：用例代码以 git 为真相源，平台做注册与调度

状态：已接受（2026-08-12）

## 背景

用例由 Agent 离线生成（已定）。剩下的问题是：生成的 spec 代码放哪里、由谁发起生成。
两种设想：

- **A**：在仓库里生成 → review → 合并；平台从仓库读，只负责执行。
- **B**：平台前置用 Agent 生成各个 case，存在平台里，然后运行。

## 决策

**spec 代码与 catalog 永远存在被测应用的 git 仓库里。平台不存储可执行的测试代码。**

生成动作可以从两处发起，产物路径完全相同：

- 开发者在仓库里跑 `mxt gen`
- 运维在平台 UI 点"生成用例" —— 平台起一个带仓库写权限的 job，跑同一个 `mxt gen`，
  **产出 Pull Request**

平台侧存的是 catalog 的**投影**（`mxt_cases`），通过 `catalog:sync` 从仓库同步，
用于调度、drift 检测和报告。它是只读副本，不是真相。

## 理由

**测试的价值来自"人确认过它测的是正确的东西"。** 一个没人 review 过的绿色用例，
只证明代码没崩，不证明业务对。把 spec 放进 git 就自动获得了 review、diff、
blame、回滚和"哪次提交改了这个断言"的追溯——这些正是判断一次结果是否可信所需要的。
平台自建一套代码存储，要么重新实现这些，要么放弃它们。

**平台执行未经审核的代码是权限问题。** runner 在真实 worker 上跑，`system` kind 的
worker 还有 GUI 和网络访问。如果代码可以在平台上直接生成并执行而不经过 PR，
那么任何能点这个按钮的人就获得了 worker 上的任意代码执行权。PR 是这条路径上
唯一的人工闸门。

**代码与被测对象必须同版本演进。** spec 依赖选择器、路由、接口形状。它跟应用代码
放在同一个 repo、同一个 commit 里，才能保证"检出 v2.0.0 就得到 v2.0.0 的用例"。
存在平台里就需要另造一套版本绑定机制，而它永远会和 git 不同步。

**这也是 09 号文档已经写下的原则**："CLI、Admin UI、runner job 都应写入同一套
`test.runs` 和 `audit.events`，不要出现本地脚本通过但后台不可追溯的分裂。"
把代码留在 git、把执行记录留在平台，正是这条原则的具体形态。

## 后果

- 平台"生成用例"按钮的产出是 PR，不是可以立刻执行的用例。这在 UI 上要说清楚，
  否则会被理解成功能没做完。
- 平台需要仓库写权限（或至少 PR 创建权限）才能支持从 UI 发起生成。
  这个凭据的作用域要限死到指定仓库的指定分支前缀。
- `catalog:sync` 是显式动作（CI 合并后调用或平台定期拉取），不是 run 的副作用。
  一次 run 里少了个用例，只会被标成 `notRun`，绝不会悄悄从目录里删掉。
- 被测应用仓库需要装 `mxt` CLI 作为 devDependency。

## 被否决的方案

- **平台内建 case 编辑器与代码存储**：丢掉 review/diff/版本绑定，换来的只是
  "不用开 PR"这一点便利。
- **平台生成后直接执行，事后补 review**：把人工闸门放在执行之后，闸门就没有意义了。
- **纯低代码/表格化用例定义**：真实的 E2E 需要处理 SSE 流、轮询状态机、
  条件等待（compass 的 `agent-task-lifecycle` 和 `ai-chat` 就是），
  表格表达不了，最终会长成一门更差的编程语言。
