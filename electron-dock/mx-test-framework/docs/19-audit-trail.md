# 19 · 审计轨迹

> 五件待办的第二件。它存在的唯一理由：[ADR-0007](adr/0007-test-code-ownership.md)
> 放开了命令白名单，并把 **"admin 角色 + 沙箱容器 + 审计"** 写成了替代品——
> 而三者里的审计当时并不存在。这是在还那笔账。

---

## 1 · 为什么放开白名单之后必须有审计

原来的规则是 `command` 只能调用被测仓库里的具名入口。放开的理由是它**不自洽**：
它限制 `command`，却完全不限制 `runnerImage`，而任意镜像的 entrypoint 就是任意代码。
所以那条白名单挡不住有意的人，只挡得住正当用法。

但放开之后，"谁能建 suite"就等于"谁能决定在真实机器上跑什么代码"。
这件事本身没问题——CI 系统都是这样的，Jenkins 管理员也能跑任何东西——
**问题在于事后无法追溯**。审计补的就是这一条：

> **谁，在什么时候，把命令改成了这个，之前是什么。**

---

## 2 · 记什么，不记什么

一个什么都记的审计日志是没人读的日志，而没人读的日志不是控制手段。
所以范围刻意收窄到两类：

| 类别 | 记录的动作 |
| --- | --- |
| **决定"在真实机器上跑什么代码"** | `suite.create`（命令 / 镜像 / 仓库）、`app.create`（仓库 / 分支）、`package.publish`（被下载并执行的安装包）、`runner.register`（哪台机器能领任务） |
| **决定"谁能做上面那件事"** | `member.role_change`、`channel.create` / `channel.delete`（改通知去向是让变更不被发现的方式） |

**刻意不记的**：

| 不记 | 为什么 |
| --- | --- |
| `catalog:sync` | 高频，且真相在 git 里，那边已经有 diff 和 blame |
| 执行结果 | `mxt_runs` / `mxt_run_cases` 已经是完整记录 |
| 报告查看、列表读取 | 只读操作，量大，取证价值接近零 |

## 3 · 审计表不能变成第二个密钥库

这是实现里最需要小心的一点。被记录的对象里有带凭据的：
通知渠道的 webhook 地址、执行机刚签发的 token。
**一个存了凭据的审计表，就是一个没有访问控制、保留期还极长的密钥库。**

两层防护：

1. **调用点先处理**。通知渠道先过 `redactChannel`；执行机注册**根本不把 token
   传给审计**，只传机器的元信息。
2. **通用兜底**。`scrub()` 递归遍历，任何键名匹配
   `/token|secret|password|credential|apikey|authorization|cookie/i`
   的值都替换成 `[redacted]`。

第二层存在的理由是：第一层依赖"每个调用点的人都记得"，
而这个假设会在半年后新加一个调用点时失效。**错一次的代价高到值得付通用扫描的成本。**

一个细节：`redactChannel` 里那个"有没有配签名"的布尔字段叫 `signed` 而不是
`hasSecret`——后者会被 `scrub` 的 `/secret/` 命中，把一个本来安全且有用的布尔值
变成 `[redacted]`。过度脱敏不危险，但会丢信息，所以改的是字段名，不是放宽规则。

同理，`[redacted]` 而不是直接删掉键：**"这里设了一个密钥"本身就是变更的一部分**。

## 4 · 几个刻意的取舍

**① 只追加，没有修改和删除。** API 里没有 `PATCH /audit/:id`，也没有 `DELETE`。
**一个能被编辑的日志不能作为任何事情的证据**，所以这两个路由的缺席就是功能本身。

**② 审计写失败会让整个请求失败。** 不是"尽力而为"。理由：两个写操作都落到同一个
数据库，"审计写失败但业务写成功"的窗口极窄；而当一个安全控制无法被记录时，
**大声失败是正确的默认值**。尽力而为的审计会在最需要它的时刻退化成没有审计。

**③ 客户端地址优先取 socket，不信 `X-Forwarded-For`。**
无条件信任那个 header，等于让调用方自己往审计轨迹里写任意来源地址。
只有在 socket 地址拿不到时（反向代理场景）才回退到 header。

**④ 删除操作先读后删。** `channel.delete` 要记录"删掉的是什么"——
删完之后就没有东西可以描述了。

**⑤ 只有 admin 能读。** 记录里含配置 diff，它说明的是平台怎么接线的，
viewer 不需要知道。

## 5 · 怎么用

```bash
# 全部
curl "$MXT_URL/api/v1/audit" -H "authorization: Bearer $MXT_ADMIN_TOKEN"

# 只看 suite 的变更
curl "$MXT_URL/api/v1/audit?resource=suite" -H "..."

# 某个应用的全部变更
curl "$MXT_URL/api/v1/audit?app=luopan" -H "..."

# 某一条 suite 的完整历史
curl "$MXT_URL/api/v1/audit?resource=suite&id=ste_xxx" -H "..."
```

实际输出长这样：

```
18:06:51  runner.register      by 服务管理员  from 127.0.0.1
18:06:51  channel.create       by 服务管理员  from 127.0.0.1
18:06:51  suite.create         by 服务管理员  from 127.0.0.1
    command = ["pytest","-q","--junitxml=junit/out.xml"]
    image   = python:3.12-slim
18:06:51  app.create           by 服务管理员  from 127.0.0.1
```

| **suite / task 的修改（PATCH）** | 目前只有 create 进审计，因为**平台还没有 suite 的修改接口**——改配置要删了重建。等加 PATCH 时，`before`/`after` 的结构已经就位 |
