# 数港系统页面与功能测试流程

版本：2026-10-20（取消超管登录后的专属码校验，并下线数港登录页的邀请码注册/首次开通入口，保留独立子账号方案）。适用基线须包含 Hub migration159 及当前 Hub/DataPort 实现；执行时记录实际部署提交。本文为手工验收流程，不代表用例已通过；历史执行记录不替代本轮修订用例。

## 1. 测试范围与执行原则

覆盖数港公共页面、控制台全部页面和弹窗，以及完成业务闭环所需的 Hub 数港管理页面、统一 Auth 超管登录与数港独立子账号能力。超管和已有 MX 关联身份由 Launcher/Auth 管理，新员工密码/会话由 Hub 的数港业务 schema 管理，企业成员、角色、订单、订阅、额度、工单由 Hub 管理，支付事实由 mx-pay 管理；必须从页面发起操作，再核对业务结果，不能用“接口返回 200”代替整条链路通过。

原型作为布局、字号、间距和交互的对照；正式系统的角色、价格、数据、支付状态和权限以实际业务合同为准，不复制原型假数据。原型只读，不在原型上创建账号、领取套餐或执行真实业务。

执行分三层，结果分别记录，不能互相替代：

| 层次 | 环境和操作 | 能证明什么 |
| --- | --- | --- |
| 页面对照 | 本地合成数据，同视口对照原型 | 视觉、交互、空态和异常展示；不能证明真实授权和交付 |
| 完整功能验收 | 隔离测试企业，真实 DataPort/Hub/Auth 与测试数据库；查询供应商和支付使用受控测试通道 | 登录、权限、持久化、计量、通知和交付闭环 |
| 生产发布后检查 | 已授权账号只读检查页面、已有记录和版本 | 发布与读取正常；真实付款、查询、重置和权限修改须另行明确安排 |

主流程先在完整功能验收环境执行。没有测试支付通道、供应商替身、专用账号或可控时间等前置条件时，相关用例记为“阻塞”，不能通过改浏览器响应或数据库造成功状态来宣称闭环通过。本文没有授权执行生产写操作。

## 2. 开始前准备

### 2.1 环境检查表

- [ ] 记录数港、Hub、Auth、Pay 的访问地址、部署提交、部署时间、浏览器版本；测试环境页眉或测试记录能明确辨认环境。
- [ ] 本轮按 Hub → DataPort 发布，Hub 已应用 `159_dataport_local_accounts.sql`、154及此前迁移；无需为本轮部署 Launcher/Auth 或执行旧账号 Secret 初始化。见[独立子账号发布说明](local-employee-accounts.md#部署)。
- [ ] 运维确认账号服务、加密配置、SSO、数据库和服务间连接就绪；沿用持久化加密密钥。只确认就绪，不把实际密钥、Admin Token、Cookie、密码写入测试报告。
- [ ] 测试查询通道可返回完整、部分、无数据、未知、限流和故障等结果，能统计调用次数；不连接真实收费供应商做默认回归。
- [ ] 测试支付通道可控制待支付、支付成功、失败、回调延迟、重复回调及交付失败。没有该能力时先执行下单和只读用例，支付闭环单独标记阻塞。
- [ ] 测试人员有独立浏览器配置或无痕窗口隔离不同账号；至少两个窗口可同时操作。不要在同一个 Cookie 会话中冒充两个角色。
- [ ] 原型与实际应用均能打开；桌面视口统一 `1440×1000`、浏览器缩放 `100%`，手机视口 `390×844`。等待字体加载后再截图。
- [ ] 测试截图、导出文件和录屏存放工作区 `screenshot/system-functional-YYYYMMDD/`，不放入代码仓库。含敏感字段的证据先遮盖。

### 2.2 测试账号与企业

使用独立测试数据，例如前缀 `qa_dp_YYYYMMDD`，不要默认使用 goodmorning、taku、root 或实际客户账号。企业及初始 owner 由测试管理员按既有配置方式预先准备；当前没有数港独立平台管理员角色，超管专属码配置页已移除。

| 代号 | 账号/身份 | 准备用途 |
| --- | --- | --- |
| A-O、B-O | 企业 A、B 的有效 owner | MX 登录直接进入已授权企业、企业管理、跨企业隔离 |
| A-M | 企业 A 固定 admin | 可管理普通员工的部分操作，不能据此推定拥有 owner 权限 |
| A-Q | 企业 A analyst | 查询、批量、历史、导出、本人工单 |
| A-F | 企业 A billing | 购买、订阅、账单；不授予查询权限 |
| A-V | 企业 A viewer | 查看历史、用量、文档和本人工单；不能查询、导出历史 |
| A-C | 企业 A 自定义角色成员 | 按角色增减权限，测试即时生效及最小授权 |
| A-S | 企业 A 可停用的普通托管成员 | 密码查看、重置、停用、已有会话失效；不可用其他用例的唯一管理员代替 |
| MX-E | 已有 MX 普通账号，尚未加入 A | 测试关联邀请，不改变原密码、资料和其他应用准入 |
| A-B | 同时属于 A、B 的普通成员 | 切换企业、成员停用只影响单一企业 |
| P | Hub 既有 Admin Token 管理会话 | 测试 Hub 工单处理及已授权商品配置，不作为客户权限测试账号 |

每个账号另记实际角色、memberId、tenantId 和启停状态；只登记脱敏标识，不在本文填入凭证。P 与所有客户账号使用不同浏览器会话。

2026-10-20 数港超管登录页仅提供已有 MX 账号密码登录，不提供邀请码注册或首次开通兑换。未开通数港的账号由管理员处理，保留 Auth 应用准入与有效企业归属检查；Hub 团队邀请用于加入企业，不能代替应用准入。登录后的 Hub owner 专属码校验已于 2026-10-19 取消。员工由超管创建数港独立子账号，其他应用与 Launcher 邀请策略保持。

## 5. 首次完整业务验收顺序

先按此顺序完成一次跨页面闭环，再执行后文边界用例。每一步记录编号、时间、操作人、业务对象 ID、预期/实际和证据；前一步失败导致后续无法操作时，后续记阻塞并关联缺陷。

| 步骤 | 页面操作 | 必须跨页面核对的结果 | 对应详细用例 |
| --- | --- | --- | --- |
| 1 | 预先绑定的 A-O 完成 MX 登录，直接打开数港 | 直接进入企业 A，无专属码校验；无企业成员身份不能读取业务，不新建平台管理员 | AUTH-01～08、PLAT-01～03 |
| 2 | A-O 打开“我的订阅”，确认零元试用后领取 | 无支付跳转；只有一份试用订单/订阅；查询页与账户菜单额度一致 | SUB-01～03 |
| 3 | A-O → 企业账号，创建托管 A-S，分配 analyst；查看一次初始密码，A-S 独立窗口登录 | 仅创建一个数港独立成员，不创建 MX 身份；首次必须改密，重登后可查询，不可管理成员/Key/账单；密码不进入日志 | MEM-01～05、ROLE-01 |
| 4 | A-S 查询一个受控 IP，回看历史，再导入含重复及错误行的小 Excel | 只执行允许的有效查询；画像、历史、调用次数、订阅消耗可逐笔对应；回看不再次扣次 | QUERY-01～08、BATCH-01～06、USAGE-01 |
| 5 | A-S 在画像点“报错”，核对带入 IP/请求编号并提交工单 | 仅一份已提交工单；A-V 看不到该工单，A-O 可查看本企业工单 | TICKET-01～05 |
| 6 | P 打开 Hub 工单页，按企业/标记找到工单，回复并置为处理中，再关闭 | A-S 收到两次对应更新，消息点“查看工单”打开同一详情；A-V 不收到私人工单通知 | PLAT-04～08、MSG-01～05 |
| 7 | A-F 购买测试付费套餐，通过受控支付完成，再查看订单和订阅；A-O 查看用量 | 同一订单付款与权益只交付一次，页面区分已支付/已开通；A-F 仍不能执行查询 | SUB-04～09、BILL-01～06 |
| 8 | A-O 创建 Key，签发替代 Key，再手动撤销旧 Key | 旧/新 Key 授权集合一致；替代不自动撤销旧 Key；撤销不删历史 | KEY-01～06 |
| 9 | A-O 新建自定义角色分给 A-C，再减少一项权限；刷新/切回 A-C 页面 | 页面和操作收紧；直接路由/旧页面请求均不能绕过；B 企业看不到 A 的角色 | ROLE-02～08、ISOLATE-01～04 |
| 10 | A-O 重置 A-S 托管密码，A-S 验证旧密码/旧会话和新密码；随后停用 A-S | 旧凭据与会话失效；Key 保留且有独立检查提示；其他企业会员不受影响 | MEM-08～13、AUTH-10 |
| 11 | A-O 到日志按测试 IP、员工账号、请求编号检索并导出；核对消息已读 | 关键操作可追溯、租户正确、导出不泄漏凭证；个人已读不影响他人 | AUDIT-01～06、MSG-03 |
| 12 | 各角色退出并重新打开直接路由；复查桌面和手机核心页面 | 无私有数据残留、无错误导航、弹窗及表格可用；完成执行表和缺陷复测 | AUTH-09、UI-01～10、RES-01～07 |

建议初次执行使用小批量数据；500 行边界只解析验证，不因验证上传上限而默认执行 500 次收费查询。

## 6. 详细功能用例

以下“核对记录”指测试后台只读记录或获准的脱敏接口响应。需要核对写入次数、幂等、权限拒绝时，可由测试协作人员查看服务端记录；不以 SQL 直接修改结果代替页面操作。每一行作为独立用例登记实际结果。

### 6.1 公共页面、登录与企业授权

| 编号 | 前置/角色 | 页面操作 | 预期结果 |
| --- | --- | --- | --- |
| AUTH-01 | 匿名 | 打开首页、定价；输入合法 IP 点查询；关闭登录弹窗后重开 | 公共内容正常，无私有数据；业务动作引导登录；弹窗区分企业超管 MX 和数港子账号入口，关闭重开可用 |
| AUTH-02 | 有数港准入的普通 MX 账号 | 输入正确账号密码登录；再用错误密码登录一次 | 正确登录回到原目标；错误凭据明确提示、可重试，无残留假登录态；不新增第二个 MX 身份 |
| AUTH-03 | A-O 新 MX 会话，未配置过专属码 | 登录后直接打开查询、Key、企业账号路由 | 直接读取真实权限并显示对应导航，无“验证企业超管身份”页面，不要求 owner code/session 记录 |
| AUTH-04 | A-O，有/无历史专属码记录的测试企业 | 分别登录读取授权页面；访问原 challenge 接口 | 旧码是否配置均不影响进入；原接口不可用，不新建许可或码，其他企业无权访问 |

## 10. 通过标准、复测与清理

### 10.1 首次系统验收完成标准

- 第 5 节跨页面主流程在记录的同一组部署版本上走通，三端身份、权限和业务对象能关联。
- 第 3 节每个固定角色、至少两种自定义角色均实际操作；页面隐藏、直接路由与服务端拒绝都验证。
- 企业/成员隔离、owner 验证、密码边界、计量、支付幂等和消息隐私相关用例无未解决失败；P0/P1 为零。
- 主要页面及弹窗完成桌面/手机原型对照；字号、企业列表列距、新建子账号小字、客服入口等既有问题逐项留证；未通过项有明确缺陷，不写“基本一致”。
- 受限能力、未接入能力、阻塞与未执行项写清楚；支付或供应商闭环阻塞时，只能结论为“页面/部分功能通过”，不能宣布全系统已验收。
- 修复后复测原失败步骤及相邻角色/企业分支，不能仅跑一次脚本或截图覆盖缺陷；自动测试与构建报告作为补充证据单列。

### 10.2 后续修改的回归选择

每轮至少重跑：AUTH-02/03/09、ROLE-01、QUERY-01/07、TICKET-01、PLAT-05、MSG-01/03、ISOLATE-01/03、UI-02/07/08、RES-03/04。无对应测试环境时如实阻塞。

修改账号/权限时加跑全部 AUTH、MEM、ROLE、ISOLATE；修改查询/计量时加跑 QUERY、BATCH、USAGE、API 及订阅门禁；修改商品/支付时加跑 SUB、BILL、CONFIG、KEY 门禁；修改工单/消息时加跑 TICKET、PLAT、MSG、相关日志；修改公共 CSS 时所有 UI 页面与桌面/手机弹窗都回归。该最小集合不替代首次全量验收。

### 10.3 测试后恢复

1. 保存脱敏证据和最终结果；凭证不进入测试文件、截图、工单正文或 Git。
2. 按批次登记清理专用测试邀请、临时 Key、成员状态及自定义角色；已有业务历史/审计按测试环境保留策略处理，不直接删除来掩盖失败。
3. 撤销不再使用的测试 Key，恢复受控故障和测试商品配置；不改生产商品、客户角色或持久化加密密钥。
4. 确认测试支付与真实支付分开，记录未结测试订单/占用状态；不要通过未实现的退款流程“清理”真实款项。
5. 关闭测试管理员会话，确认生产没有因本轮测试意外产生写入；如有，列出事实与待处理项交业务负责人。
