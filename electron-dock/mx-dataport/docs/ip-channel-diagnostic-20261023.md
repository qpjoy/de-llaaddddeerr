# IP 风险画像持续“渠道限流”排查

## 当前证据与边界

用户提供两笔记录，均显示 `ip_channel_rate_limited`：

| 记录 | 查询编号 | 请求编号 |
| --- | --- | --- |
| 2026/10/22 17:11:50 | e1b94f14-0b3f-4b9d-ba25-0e9a441e52e2 | febff105-3b2f-4e9d-9ef5-a186d4b74d9b |
| 10/23 提供，页面时间缺失 | 43f3c15a-6976-441b-8735-644743307ebf | 1c2d79f0-bede-4f6e-ab40-25351da10302 |

两笔编号不同，不能只用同一操作回放解释持续问题；第二笔实际创建时间与上游回执还未读取。页面错误码在当前百度 v2 适配中对应 HTTP429 或 `ret_data.code=601`；没有原始响应不能确定具体分支，更不能断言供应商给定的限流范围、期限或永久封禁。

代码还确认两种会延续显示的机制：

- `ip-query.tsx` 仅在成功/部分数据/无数据后移除原操作编号。相同标签页重提同 IP 时可沿用旧编号；`dataport.queries` 返回已存 payload，并不会因冷却结束而自动重查。后台同编号失败回放也不重新派发。
- 百度 v2 收到新的 429/601 后写入 `cooldown_until=now()+30 minutes`。普通请求共享这个渠道状态；已在途请求或明确豁免身份后续再收到上游限流，可再次后移截止时间。冷却判断本身不会每读一次就延期。令牌不足、日上限、渠道暂停是其他错误码。

只读诊断尚未在生产执行。此前 Hub 浏览器读取被已保存的网站权限阻止，未重试该入口或用代理 SQL/HTTP/其他浏览器绕过。本轮仅准备由用户在服务器自行执行的诊断，无真实 IP 查询、付款、清冷却、调额度、豁免或重启。

## 手动执行

在服务器同步包含本脚本的 pro 后，从 `electron-dock/mx-dataport` 目录运行：

```sh
bash scripts/diagnose-ip-channel.sh
```

脚本默认取上述两笔记录。也可指定一笔已有请求和查询编号：

```sh
bash scripts/diagnose-ip-channel.sh <request-uuid> <query-uuid>
```

无需部署。通过现有 `mx-insight-hub-public` 容器里的 Node/pg 和数据库配置运行；默认命名空间 `mx-insight-hub`、容器 `api`，如现场不同可用 `HUB_NAMESPACE`/`HUB_TARGET`/`HUB_CONTAINER` 指定实际目标。没有可用数据库配置则明确失败，不读取或打印 Secret。

输出：数据库时间与只读标志、当前交付渠道、共享冷却/令牌/日计数、渠道熔断状态、两笔查询及额度结算、上游 HTTP/业务码和失败子接口，以及近24小时最多20条上游调用的脱敏元数据。不输出 IP、账号、Key、连接串或原始响应。历史记录不改写，全部在只读可重复读事务内，最后 ROLLBACK；每段查询超时8秒，单表缺失只标记该段不可用。

## 本地验证

shell 与 Node 语法检查通过；临时原生 PostgreSQL 验证只读快照、事务外写拒绝、HTTP200/业务601提取、缺表后继续读取、原始响应/敏感样例不输出、无效 UUID 拒绝及非JSON回执处理。只运行自建本地样例；生产根因仍待用户回传诊断结果。临时 PostgreSQL 随验证结束停止。
