# 查询状态按原因展示（2026-10-22）

用户后续明确要求：其余“待确认”也显示为“渠道限流”。当前统一用于批量列表、查询历史、画像结果详情、历史和批量 Excel 导出；原始错误码及后台结果确定性保持不变。该展示要求替代初版保留“待确认”标签的方案。

| 展示状态 | 可确认的原因 | 页面说明 |
| --- | --- | --- |
| 渠道限流 | `ip_channel_busy`、`ip_channel_cooling`、`ip_channel_daily_limit`、`ip_channel_rate_limited`、`ip_query_rate_limited` | 频率限制、冷却或渠道日上限；稍后手动处理，系统不自动重试 |
| 防重复保护 | `ip_query_in_progress_or_unknown`、`request_pending`、`request_in_progress`、`request_unknown` | 相同查询在处理或上次结果未知，本次未再次调用渠道；先查看原查询记录 |
| 渠道限流（用户指定的展示归类） | `ip_query_outcome_unknown`、`query_outcome_unknown`、持久化结果未知或未分类的连接/回执异常 | 暂未取得完整查询回执，稍后查看历史，不自动重试；内部仍为 `unknown` |

不按 HTTP 429 一律判为渠道限流；企业订阅额度、企业每日额度耗尽及渠道暂停保留原有失败含义。历史未知记录仅改变页面显示标签，不写回或推断真实限流原因，不释放预占、不开放重试。

批量遇到渠道限流、防重复保护或未知结果均暂停后续派发。用户再次按“开始查询”时只处理“待查询”行，不重跑已经返回的任何行。无自动重试、自动换渠道或保护绕过。

## 后台原因保留

Hub 的 Baidu IP 失败结算原先把 `rejected` / `succeeded_unusable` 写为 `committed`、零单位。IP 订阅触发器仅允许成功的一单位结算，因此抛出 `commerce_invalid_settlement`，网关再把原本明确的拒绝掩盖成 `ip_query_outcome_unknown`。

现与 IP 失败交付规则一致，明确拒绝或不可用交付释放客户预占并保留失败回执、原渠道调用及证据。Baidu 的同操作编号通过现有 `replayReleasedFailures` 能力回放已保存的失败，不再次派发；不同编号仍执行原有并发、额度、未知和隔离保护。真正 `unknown` 仍保留预占及防重复保护，不改变供应商扣费事实。
