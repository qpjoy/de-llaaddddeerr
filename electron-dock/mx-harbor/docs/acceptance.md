# Harbor 验收与上线操作规划

日期：2026-10-11。以下是完整商业闭环验收要求；首批认证、权限读取和部署工具的实际完成项见 [实施与部署说明](implementation-and-operations.md)。支付及线上验收尚未完成。架构与依据见 [全局方案](architecture-and-rollout.md)。

已确认：所有账号首次进入 Harbor 需邀请或管理员开通；¥1 仅用于管理员付款验收，沿用年度商品完整权益。没有面向普通用户的 ¥1 试用套餐。

## 当前可执行：邀请码准入与共享权限

本节针对已实现的登录、准入和只读权限，不要求先付款。不要用 Root 的 Hub 管理员视角证明普通客户权限；准备两个普通验收账号 A/B 和两个测试空间 T/U。

1. 先完成 `enroll → Launcher/Auth deploy → Harbor deploy`。若 Hub 还没发布 Portal 版本，再发布 Hub；本次登录 UI 修复没有新增 Hub 改动。`/ready` 成功和 `/status` 的 `configured` 只能证明本地服务/配置就绪。点击登录应自动完成短暂 SSO 往返并回到 Harbor，出现可填写的账号、密码和首次进入邀请码。停留在接入错误时先完成 Auth 发布，不要改注册模式解决客户端错误。
2. 在 Launcher **Internal → 用户中心 → 注册与邀请**，默认保留“邀请码注册”，**Hub 注册方式**保留“开放注册”，**Harbor 注册方式**选择“邀请码注册”并保存。默认“关闭注册”仍是全局关闭开关；不要因此关闭 Hub。
3. 创建两枚单名额邀请码，**邀请用途**选择 **“Harbor 注册与首次进入（仅开通 Harbor）”**，设置期限。普通“统一账号注册”邀请不能代替。保留邀请码明文给测试用户，不写入报告。
4. A 使用一个已有的普通 Hub 账号，在 Harbor 的“登录”页先不填邀请码，应该被拒绝；补入第一枚专用邀请码后成功。退出、再次不填邀请码登录应成功，邀请码已用名额仍是 1。再用另一个未开通账号兑换已满的码，应拒绝。已有 Auth/Hub 会话也不能绕过首次准入。
5. B 在“邀请码注册”页填写新账号、密码、确认密码及第二枚专用邀请码。成功后在 Launcher 用户中心只出现一份统一账号；应用访问只新增 Harbor，不能因为邀请而获得 H2I/Luopan 网络准入、Hub 管理或数据产品。另测无效/过期/已撤销的邀请码应失败。
6. 管理员替代开通：在已有账号的**应用访问**设置中显式开通 `mx-harbor`；若曾禁止 Harbor，需同时解除该项禁止。显式禁止优先于允许。该账号之后无需邀请码。不要修改该账号的其他应用访问项。
7. 将 A 作为普通成员加入空间 T（例如 viewer），B 加入 U；给 T 按 Hub 现有方式配置测试产品/文档权限。用 A 分别登录 Hub 客户界面和 Harbor，选择同一空间，核对 **空间权限、API Keys 前缀、我的接入/订阅、已有订单、接口文档**。对比应是同一 member/tenant、同一角色和原权益，而不是另建一套。Harbor 只显示客户功能，不能显示供应商/排障/商品管理。
8. 在 Harbor 浏览器开发者工具 Network 查看 `/bff/v1/session`、`/bff/v1/api-keys`、`/bff/v1/commerce/tenants/<T>`、`/bff/v1/documentation?path=%2Fdocs%2Fopenapi.json` 的响应，仅核对脱敏标识。用 A 请求 U 的 commerce 路径必须为 403/404，不能返回 U 的数据；匿名文档请求应为 401，`/bff/v1/runtime` 等管理路径为 404。这里不要使用管理员 token 或另一人的 cookie。
9. 在 Hub 撤销 A 在 T 的 membership/对应产品权限，刷新 Harbor 相关页面并核对最新接口响应：空间/文档/产品可见性同步收紧。邀请码只解决进站，不能恢复产品权限。随后在 Launcher 禁止 A 的 Harbor 访问，已有 Harbor 会话下一次服务请求也应被拒绝；Hub 本身的授权保持原样。最后按验收记录恢复测试设置。

API 域名兼容可以先核对文档中的 `servers` 指向 Harbor；实际带 Key 查询需要固定测试额度后再做，不能把一次真实供应商查询混进页面刷新测试。当前只读页面和上述身份验收不证明支付、购买、IP 网页查询或完整文档目录 UI 已完成；¥1 订单/支付交付按后文商业闭环另验。

验收留证：策略截图、邀请码已用名额（不含明文）、同一 member/tenant 的脱敏对照、越权/撤权 HTTP 状态与 requestId。用户自行进行生产注册/授权；自动回归使用本机临时数据库。

## 1. 发布顺序

1. 完成纯 UI 包与原型对照，固定可重复的页面/组件 fixture。
2. 在隔离 Auth、Harbor、Hub、Pay 与临时数据库中实现和验证。先测兼容的应用策略、身份关联及有限客户 API，再接支付来源与返回目标。
3. 对现有 Hub 登录/注册/接口、MX-H2I 登录/联网及 Luopan 进行回归；用例结果分别记录“模拟”“真实隔离数据库/HTTPS”“生产受控验收”，不能互相替代。
4. 部署兼容版本与 additive migrations；Harbor 新准入和新销售保持关闭。旧 Hub client、SSO 会话、数据库绑定和已创建订单继续可用。
5. 登记 Harbor 独立 Auth client/域名，发布 Auth 新客户端与应用策略，确认所有副本使用一致配置。该步骤单独预检，不把 Harbor 日常发布绑定到 Launcher 发布。
6. 登记 `mx-harbor` Pay 应用范围、Hub 商业支付来源及 Harbor 返回目标，核对实际 HTTPS、服务端私网连接、Pay 签名通知与凭据范围。
7. 发布 Harbor 工作负载和精确网关规则，检查客户入口、匿名文档保护、回调、无 Hub URL 依赖及禁止管理路由。
8. 管理员开放 Harbor 邀请，执行一组专用账号/空间验收，再创建并支付一笔真实 ¥1 验收订单。
9. 验收成功后按产品发布清单开放普通销售。后续数据产品逐项接入，不以隐藏管理导航替代后端隔离。

Harbor 以 `deploy` 一键完成幂等迁移、更新和自动重启；旧 `migrate` / `restart` 均为完整部署的兼容别名，`status` 只读。SSO/Hub 未接入不阻塞 Harbor 迁移与发布，相关接口在运行时返回明确的不可用状态，接入配置就绪后重新发现；详见实施说明。商业支付来源和完整上线顺序尚待后续实现与验收，不能仅运行 deploy 就开放销售。

## 2. 管理员将如何开通与验收

以下是目标操作流程；“Harbor 接入/验收”是拟新增的 Internal 窄管理入口，不是当前已存在的菜单。

1. **Internal → 统一认证 → 接入应用**：登记 Harbor HTTPS origin、固定 callback 与独立应用身份；客户端秘密仅安全交给 Harbor 后端。
2. **Internal → 用户与账号 → 注册与邀请**：保持 Hub 为开放注册，Harbor 设为邀请码注册、显式准入。全局默认保持当前兼容设置，不为了关 Harbor 而关闭统一新注册总开关。
3. 创建 Harbor 专属邀请码，设置名额和期限；或者为已有 MX 账号显式开通 Harbor。邀请码不赋予 H2I/Luopan、Hub 平台管理、支付管理或产品权益。
4. 测试用户从 Harbor 登录/注册并兑换。核对 Launcher 用户中心中的同一账号；已有用户复用 Hub 原 member/space，新用户按明确个人空间规则开通。
5. **Internal → Harbor 接入/验收**：经受保护管理合同选择验收空间、真实年度商品修订及 Harbor 来源，创建 ¥1 验收订单。显示实际金额、原商品价格、完整期限/次数及目标空间，操作留审计。既有 Hub 页面与默认验收操作保持原样。
6. 用户在 **Harbor → 我的订阅/订单** 打开同一订单，核对 ¥1 与完整年度权益后进入支付宝付款。客户不能自行创建验收价订单。
7. 支付完成返回 Harbor。页面分别显示“付款已确认”和“服务已开通”；若业务交付未完成则保留处理中，不能提示用户再买一笔。
8. 核对 Pay 同一订单已 paid，Hub inbox/订单/订阅/授权只交付一次；在 Harbor 看到有效期与本期调用次数。在 Hub 用同一有准入资格的账号检查同一空间，核对权益一致。
9. 执行一个明确授权的 IP 查询，并用 **Harbor 域名**调用同一产品 API；核对相同 tenant/Key 计量、真实返回及文档权限。具体生产调用数量在执行前固定，页面刷新、历史回看、测试失败不自动增加供应商调用。
10. 保存订单 ID、支付 ID、事件 ID、requestId、应用来源及脱敏验收证据。不要把凭据、邀请码明文、完整支付 URL 或敏感查询结果写进公共报告。

首轮使用没有现有订阅的专用空间。若选已有有效订阅的空间，年度权益按当前续订规则顺延，这是正确行为，不能为验收重置原额度。

## 3. 验收矩阵

| 编号 | 场景 | 必须证明 |
| --- | --- | --- |
| UI-01 | DataPort、UI gallery、Harbor 同视口对照 | 首页/侧栏/IP 页/定价结构/账号菜单/订单的布局、色彩、字体、滚动行为一致；业务内容来自真实合同 |
| UI-02 | 桌面、短屏、390px 手机 | 无横向溢出；上拉菜单、弹窗、键盘焦点和手机侧栏可用；新模块沿用组件风格 |
| UI-03 | 未授权/加载/失败/空结果 | 不闪现管理导航，不把错误当空数据，不显示原型合成风险为真实结果 |
| IAM-01 | Hub 开放、Harbor 邀请、平台默认兼容 | 分别生效；Hub 现有注册仍可用；旧管理客户端省略字段不抹掉 Harbor 策略 |
| IAM-02 | 已有 Hub 用户无 Harbor grant | 即使持 Auth 会话，仍要求邀请/管理员开通；不能通过直接 callback/托管页/原生 API 绕过 |
| IAM-03 | 新账号与已有账号兑换 | 新账号只建一个用户；已有账号不重建；只有一次应用授权和名额消费；不存在登录/兑换循环 |
| IAM-04 | 过期/撤销/跨应用邀请码、并发最后名额 | 全部按当前服务端策略处理；客户端伪造 source/appId、伪造注册 proof 无效 |
| IAM-05 | 飞书/外部注册入口与回调 | Harbor 不可发起；Hub/H2I 原流程正常；已有统一账号不因历史身份来源被错误注销 |
| IAM-06 | 相同用户跨 Hub/Harbor、双端并发首次登录 | 一个原 member/个人空间，原 membership、Key、余额/权限不变；audience/client 区分仍严格 |
| IAM-07 | 同名/同邮箱不同账号、错误 issuer/audience | 不自动合并、不扩大授权；多个历史绑定候选进入显式处理 |
| IAM-08 | 退出、停用、撤权、Auth 故障 | Harbor 本地退出边界正确；撤权后旧会话受限；Auth 故障保留会话但不伪造认证成功 |
| IAM-09 | 新 Harbor 账号尝试 H2I/Luopan | 原 SDK 登录/网络租约不因 Harbor 邀请而获得权限；管理员另行授权仍按原规则执行 |
| IAM-10 | 原 MX-H2I 用户回归 | 密码/飞书登录、token/lease、续约/重连与联网按原测试包保持；没有改 WG/DNS/PAC/地址/peer |
| IAM-11 | 管理员账号进入 Harbor | 仅实际空间客户权限；不自动 platformAdmin；不会反向清除 Hub 已有平台管理授权 |
| PERM-01 | 用户 A 请求 B 的 tenant/consumer/Key/订单/历史 | 在 Hub 服务端拒绝；BFF/URL 参数和浏览器隐藏都不是唯一保护 |
| PERM-02 | viewer/analyst/billing/admin/owner | 按目标空间原角色执行；不能把 A 空间 owner 用到 B；billing 不发 Key |
| PERM-03 | 已授权 consumer + 不含对应 scope 的 Key | 查询拒绝；多个 consumer 的零散权限不能拼出单一受保护产品/文档权限 |
| PERM-04 | HTML 文档、直链、OpenAPI、示例下载 | 全部经过同一过滤；匿名不能读完整文档；撤销授权后不可用缓存继续读取 |
| PERM-05 | 直接请求隐藏管理 API | 供应商/渠道切换/采购/运维/Admin Token 入口不在 Harbor 路由和权限合同中 |
| PERM-06 | 历史访问与 Key 选择 | 复用真实 Key 身份；遵守现有 Key 级历史范围；不能为跨站方便而返回整个空间所有历史 |
| PAY-01 | 普通用户指定 amount=100/acceptance/其他 payment app | 服务端拒绝；普通商品保持原售价；验收价只能由授权管理操作创建 |
| PAY-02 | 管理员创建 Harbor 验收订单 | 原商品修订和完整年度权益快照不变，仅本单 100 分；目标空间与 Harbor 支付来源持久绑定 |
| PAY-03 | 重复点击、创建响应丢失、Pay 连接中断 | 原 request key/业务订单/支付订单恢复，不另建、不双扣；不因未知响应释放或重建 |
| PAY-04 | 伪造/重复/乱序/迟到事件、金额/币种/app 不匹配 | 不错误发权益；保留真实支付事实和需处理证据；通知鉴权不依赖 Auth |
| PAY-05 | Hub 事务提交前失败、提交后 ACK 丢失 | 前者回滚后可恢复，后者只返回原回执；inbox/订单/订阅/授权原子，一次交付 |
| PAY-06 | test/live 与 Hub/Harbor 应用隔离 | test 不发 live 权益；Harbor Pay 凭据不能读/写其他应用订单；不同来源 worker 不抢错事件 |
| PAY-07 | 同支付宝 APPID、多业务应用、旧订单 | 不复制重复渠道；新 Harbor return 归 Harbor；旧 Hub return/商户身份/原签名通知保持 |
| PAY-07b | Harbor 查看旧 Hub 未完成订单 | 按原空间权限只读；不在 Harbor 启动会返回 Hub 的旧 checkout，不改历史返回快照；已付权益共享 |
| PAY-08 | 回跳伪造成功、回跳未发生、陌生订单定位参数 | 不从浏览器落款；服务端按当前成员空间解析；无回跳也能靠事件交付 |
| PAY-09 | Pay/Hub/Harbor 分别不可用 | 已购调用不依赖 Pay；Pay 持久保留交付事件；Harbor 不可用不影响 Hub；状态真实可恢复 |
| PAY-10 | 原年度续订、验收空间已含订阅 | 按既有顺延，不重置原次数/有效期；普通业务原钱包和历史流水不变 |
| API-01 | Hub 与 Harbor 同 Key、同 path/input | 合同响应、错误、游标、幂等和计量一致；切域名不扩大权限或重复扣费 |
| API-02 | 最后一次额度跨域并发、过期、未知结果 | 共用同一原子额度；错误释放/未知保留沿用 Hub；不自动回退钱包或供应商 |
| API-03 | 查看历史、切 Tab、刷新权限、刷新支付页 | 不隐式触发 IP/供应商请求或重复购买；历史不重复计量 |
| API-04 | 文档示例、邀请、返回、错误、资源与下载 | 不依赖 Hub 域名；保留必要的兼容技术字段，不对签名数据/历史响应做字符串替换 |
| OPS-01 | 独立 Harbor 一键 deploy、重复执行与回滚预案 | 自动迁移后重启一次并验证就绪；重复执行保留数据和凭据，不重启 Launcher/Hub/Pay，不改变 H2I 运行配置和数据库 |
| OPS-02 | 网关、来源头、CSRF、入口限速 | 明确可信代理；不接受任意 Host 生成 URL；Cookie 写请求不能跨源；管理路径外部拒绝 |
| OPS-03 | 新增 schema/策略回滚、混合版本 | 旧数据/客户端兼容；新 Harbor 开关可独立关；不在旧 Auth 副本忽略策略时开放入口 |
| OPS-04 | 已付款后回滚 Harbor | 保留 Pay 通知、Hub 事件消费与原订单查询；不撤掉处理存量付款所需的服务 |

## 4. 必须保留的证据

- UI：原型版本/文件哈希、相同 fixture、视口截图、交互结果及可接受差异说明。
- 身份：脱敏后的 issuer/client/audience/member/tenant 关联，准入与撤销审计；不记录密码或 token。
- 业务：SKU 修订、订单/事件/订阅/用量标识及前后数量，证明未重复开通/扣费。
- 兼容：Hub 原端点合同结果；MX-H2I/Luopan 原回归结果及实际线上未受影响的受控检查。未做真实联网检查时明确标“未验证”。
- 部署：实际集群/namespace、迁移状态、镜像与配置修订、所有副本状态、网关配置校验和回滚版本。不能把 deploy 脚本成功模拟当作生产成功。

只记录检查结果，不把真实供应商调用写进每次构建/自动回归。测试需要真实账务语义时使用一次性 PostgreSQL 和签名模拟支付；最终真实 ¥1 支付由用户操作完成。

## 5. 停止放量与恢复

出现跨租户越权、错误身份绑定、普通用户可创建验收价、付款应用串单、重复权益或影响 H2I 时，停止 Harbor 新准入/新销售并保留全部证据。不要关掉已有 Pay 通知/交付消费来“回滚付款”。

页面问题先回退 Harbor Web；身份问题拒绝未完成的新绑定，不重置 User Center；支付未知状态保持原订单并核对签名来源；数据调用未知结果遵循 Hub 现有隔离/恢复合同。不得自动换供应商重付费请求、重算历史金额或删除受益空间以清理验收数据。

上线前安排一次备份与恢复边界检查：Harbor 会话丢失只要求重登，不能丢用户/空间；Hub 业务恢复须与 Pay 事件事实核对，不能因两库恢复点不同重复交付或漏记。复用现有恢复规范，不把此次新站上线扩张为所有中心的基础设施重建。
