# Hub 商城、订阅权益与 IP 风险画像 v2

日期：2026-10-07。已按商城体验、空间共享订阅、¥1 验收和管理员切换交付渠道的补充需求修订。迁移 130 后的新购买以本版为准；迁移前的调用者订单及订阅保持原快照。

## 决策与中心边界

先在 Hub 增加一级菜单「商城」，商业代码放在独立的 `server/commerce` 与 `hub_commerce` schema。现在没有必要增加一个需要独立部署、鉴权、值班的新服务。模块从第一天就用稳定商品 ID、业务订单、权益和支付事件契约隔离，未来两个以上应用需要共同销售、组合商品、统一促销时，再抽为 mx-commerce。

| 领域 | 所有者 | 不应承担的职责 |
| --- | --- | --- |
| 账号、登录、应用入口 | Launcher/Auth；Internal 是操作中心 | 不存订阅额度、不判断付款到账、不依赖供应商健康 |
| 商品、SKU、销售价、购买订单、续订、赠礼凭证 | Hub Commerce；未来可独立 | 不持有支付宝私钥、不认定支付事实 |
| 收款、支付渠道、支付订单、验签、支付事件、对账 | 独立 mx-pay | 不理解 IP 次数、不写 Hub 权限或钱包 |
| 数据产品、渠道、授权、额度执行、查询记录 | Hub | 不因 Pay 暂时不可用停止已购产品调用 |
| 发票、财务统计 | 原业务申请与独立财务投影 | 不阻塞支付和权益事务 |

商城和数据产品工作台是两个入口：商城回答“买什么”，工作台回答“已经拥有的服务怎样使用”。销售价格不是供应商采购价格，商品上下架也不是供应商运行开关。

## 商品和数据产品模型

产品定义稳定能力，例如 `ip_risk`；渠道是版本化交付，例如 `baidu-v2`、`legacy-v1`；SKU 是价格、期限、额度和受益空间的不可变购买快照。新商品购买的是产品能力，不绑定某家供应商。管理上分三个面：上游供应商管理 API 与运行策略；数据产品管理交付渠道；商城管理商品介绍、价格与上下架。

首个 SKU 保留内部标识 `ip-risk-baidu-annual-100k` 以兼容已有订单，用户看到「IP 风险画像 · 年度版」。人民币 **33,999 元**（整数 `3399900` 分），12 个日历月，总额度 **100,000 次成功交付**。订阅绑定所选空间；空间就是 Hub 的租户（tenant），无需用户再绑定或创建调用者。空间内获授权的调用者和 Live Keys 共用一个年度计数，不能每个 Key 再获得 10 万次。有效无数据也属于成功交付，错误不消费，结果不确定的请求冻结额度等待核对。一次 IP 计一个客户单位；上游 base/overall 请求分别记供应商证据，不重复计入客户次数。批量逐项计量，重复 IP 不默默去重。

付款交付把产品授权合并到空间服务配置及已有有效调用者、Live Keys，保留其原有授权与限额；后续新调用者按既有空间授权继承机制接入。空空间自动准备专用产品调用者；用户明确点击「开始使用」时，按现有 Key 管理权限签发受限网页访问 Key。空间共享不等于所有成员获得 Key 管理权限，成员角色与 API 鉴权仍适用。旧调用者订阅继续限定原调用者，迁移不扩张它的授权范围。

到期或用尽停止新查询；不自动转钱包扣费，不跨年结转。年套餐没有自动续费授权，续订是新的用户购买。已有有效期内的续订从当前结束时间顺延，新一周期的额度到新周期才生效；已过期则从本次交付开始。提前用尽时需要明确购买增量包或另一个即时生效的套餐，不把“续订”误当作立即解锁新额度。日历月按 UTC 保存，月底取目标月最后一天，界面显示本地时间及精确失效时刻。

后续计费形式在商品层表达：按次钱包计费、预付次数包、订阅含量、订阅加超额。每种模式必须明确计量单位、期限、超额动作、并发/QPS、是否含缓存命中、退款规则，不能用一个模糊的“套餐价格”隐式改变旧客户政策。

## 用户发现、购买与可见性

所有已登录用户可进入商城看已发布商品。商品卡突出产品用途、好处、售价、服务期与调用次数，使用现有主题下的产品视觉；不展示上游名称、上下架状态或大段限制提醒。详细期限、调用、到期与续订规则放详情页，购买确认只选择使用空间，规则可展开查看。管理 Token 增加「商品管理」页签，集中编辑、上下架、验收价和交付渠道。公开销售说明可以展示；可运行工作台、完整受保护接口文档、真实查询、历史记录仍按产品权益与调用授权检查。前端隐藏菜单不是鉴权。

已购用户在数据产品看到可用服务；过期后「我的购买」仍保留订单、用量与续订入口，历史查询不重新请求供应商。已有 v1 人工授权客户保持原有入口与合约，不因新增商城批量撤权。管理 Token 可以管理商品和渠道；普通登录的全局角色不自动获得供应商密钥访问。

购买流程：

1. 商城选择 SKU → 确认使用空间、价格、期限与调用次数。由服务端读取当前上架修订，浏览器不能指定金额、额度或权限。
2. 创建 Hub 购买意图，持久保存商品快照、受益对象、请求幂等键、环境、支付源/应用/渠道。重复点击只返回原意图；不同参数复用请求键报冲突。
3. 同一个业务订单请求 mx-pay。超时保留原意图，以原业务订单查找/重试，不另建订单。
4. 打开 mx-pay 提供的支付宝收银台。付款后的浏览器跳转仅是订单定位信息，不能证明付款成功。
5. Hub 接收并核对支付中心的已付款事件：支付源、应用、环境、业务订单、客户、金额、币种、渠道和发起者全部匹配。
6. 在 Hub 一个数据库事务中提交 inbox、购买订单交付状态、订阅周期、授权和审计；成功提交后 ACK 支付中心。重复投递只返回原交付回执。
7. 回到「我的订阅」，查看订单付款状态、本期调用次数与剩余有效时间。已开通后刷新会话的产品目录，提供「开始使用」和「接口文档」。点击开始使用只准备受限访问身份，不重新激活或重置订阅期限。

支付中心不可用时，商城仍可查看历史订单；已购产品可继续使用。商品上下架由管理员控制，与供应商运行开关分开；服务未就绪时查询明确提示，不派发上游、不扣钱包。停止销售应下架商品，不能依赖供应商开关代替销售状态。已收款但暂时停用仍保留权益，不能丢订单。商品下架不撤销旧订单快照和已购权益。价格调整不改已创建订单；后台保存须修订检查并记审计。

## ¥1 验收流程

Admin Token 登录 → 数据商城 → 商品管理 →「创建 ¥1 验收订单」→ 选择验收空间并确认。仅该订单按 100 分请求 mx-pay，正式商品售价仍为 3399900 分；订单不可变快照记录验收用途及原售价。普通用户不能调用验收价接口，也看不到验收入口。

空间所有者在「我的订阅」找到同一订单，打开支付宝收银台完成实际 ¥1 付款。Hub 核对支付事件后自动发放该商品完整服务期与次数。再点击「开始使用」，验证画像查询、本期次数、历史回看与接口文档。此验收订单产生真实权益，建议选择专门验收空间；已有有效空间订阅时仍按续订规则顺延。不要为测试临时修改公开商品售价，也不要用模拟到账替代真实付款验收。

## 百度 v2 与旧渠道

`/tmp/david-baidu/ip_query.py` 是网页接口参考，不是带采购凭据的正式商业 API SDK。固定源是百度云 `afd-ip-threat/act/v1/ipage`；参考结构有 base、overall、location、other。样例并不保证地理字段齐全。首期以 base + overall 为明确交付组合，定位/机构扩展应单独验收后加入，不自动补查。

新增空间产品接口 `POST /api/v1/data/ip/risk/service`，接受 `ip` 或 `ips`，统一返回逐项结果。授权能力为 `ip.risk.subscription.query`，订阅计量为 `ip.risk.subscription.product`。管理员在商品管理中配置交付渠道，初始使用现有 v1；可手动切换到已接入的百度 v2 网页渠道，客户不重买、不换接口地址。普通订阅查询不暴露渠道选择。一次批次固定一个渠道，切换只影响新请求；原幂等请求与历史仍返回原结果。

原 v1、v2 和多渠道比较接口继续各自检查原有能力与计费，不通过购买空间订阅获得这些原始接口权限。旧 v2 调用者订阅继续使用原渠道和原年度计数；管理员配置空间产品渠道不会迁移旧订阅或重解释历史。

不把百度 Web Search 的凭据或开关复用于 IP。IP 渠道显示固定 API 目录、字段覆盖、启停、频率/日限额、失败/限流状态与实际请求数。当前网页接口没有商业 API Key，明确标为无需商业凭据，不虚构密钥输入。后续取得正式商业 API 的接口文档与凭据后，另接版本化适配器并验收，再允许管理员选用；不是将密钥填到现有网页适配器即完成接入。产品接口和空间订阅独立于交付供应商，不授予任意上游原始接口权限。

限流在数据库跨副本协调，失败时不自动换渠道。HTTP 失败、业务 601、无数据、部分字段、未知结果分别记录；限流后的新请求应遵守冷却。参照脚本的本地 JSON 计数不能直接当作多副本额度真相。缓存若采用，须标注原始观测时间；历史/幂等回放永不重复扣额度。未实测的网页接口只能标为参考契约，不能称为商业 SLA 或已通过线上验收。

Web Search 可以有已授权渠道的有序候选集，在派发前按健康选择；已派发、可能计费的未知请求不能自动回退造成重复采购。允许失败后重试的供应商必须有“明确未计费”的证据与总预算。IP 空间产品固定使用管理员选定渠道，不从 Web Search 继承自动候选策略。

## IP 画像界面

保留 Hub Neon Void 和风险画像优先的工作台。首屏：产品说明、本期调用次数/年度上限与剩余有效时间、单个或批量 IP。普通空间订阅只展示产品服务；管理员及原渠道授权保留相应调试入口。结果区优先展示 IP 与原始等级，再按实际返回展示归属地、运营商、场景、机构、经纬度和数据更新时间；空值标「未提供」，不补造 v1 缺少的字段。风险标签按上游明确的分类保留子标签、等级和观察日期。

风险环只是等级标识，不把没有统一量纲的分数伪造成百分比。没有真实坐标不画地图；有坐标也不加载未经授权的地图服务。查询时间、数据更新时间、标签观察时间分别表达。未购买展示商品介绍和购买按钮；已购买展示调用次数、剩余有效时间与续订，查询、历史和文档使用同一身份。

界面补充（用户确认）：订阅按服务期表达，不做钱包式的“查询一次扣一次”提示，不把未使用次数展示成待消费余额。主指标是“本期已调用 / 年度上限”和“有效期还剩多少天”；准确到期时间与处理中的请求为次要信息。底层仍对成功交付严格计数，以保证年度调用上限。

## 赠送、礼品卡和手动激活（后续阶段）

三者应分开：自用默认到账即激活；“延后激活”购买的是有兑换截止日的待激活权；“赠送”购买的是一次性可兑换凭证。不要先给购买者激活，再转移用过的订阅。

赠送订单保留付款人、商品快照与购买时间，受益人兑换时才确定。生成高熵一次性 token，数据库只存摘要；链接不包含付款信息或身份。接收者登录后明确选择个人/企业账户并确认，事务内锁凭证、检查期限/撤销/已使用状态，再创建唯一权益与审计。重复兑换返回同一回执；两人竞争只有一人成功。

企业购买者可以代购给自己有授权的账户；跨账户赠送必须由接收人确认，不根据邮箱或昵称自动合并身份。分享链接只是 bearer 凭证，不等于邮件送达。兑换前可撤销并重发，已兑换不可自由转让。赠送退款要先冻结未兑换凭证；已兑换/部分使用进入人工处理，退款事实仍由 Pay 管理。礼品卡储值属于余额负债，和固定产品礼品不是同一种商品，另设账本与会计规则。

建议顺序：P0 自用自动交付与按期续订 → P1 次数包与产品运营 → P2 未激活固定商品礼品 → P3 跨应用销售与储值卡。首期不出现看似可用却没有后台契约的赠送按钮。

## 迁移、隔离和验收

迁移 129 新增 Hub schema、固定商品种子与百度渠道。迁移 130 将当前 IP 商品修订为绑定空间的产品权益，清除原种子的供应商介绍，并默认产品交付 v1；保留已有商品售价、上下架、自定义描述和限流策略。旧订单及订阅快照不改，不自动给旧租户授新权益。迁移记录防止重跑覆盖管理员的新渠道选择；不重算旧账单、不改 Pay 数据库、不动 Launcher/MX-H2I 用户、网络或数据库。

必须验证：重复购买请求、价格修订、跨租户读写、伪造金额、test/live 隔离、重复/乱序/伪造支付事件、提交后 ACK 丢失、并发最后一次额度、明确失败释放/未知冻结、到期拒绝、历史不扣量、v1 兼容、无渠道自动重试、迁移重跑不覆盖运营修改。真实支付与供应商验收要与隔离数据库和模拟 HTTP 测试分别报告。

## 本次实施结果

- 已实现面向客户的「发现服务」「我的订阅」和商品详情；Admin Token 单独显示商品编辑、上下架、¥1 验收订单及产品交付设置。用户商品页无上游名称、运营状态或大段限制文案，订阅显示本期调用次数与有效时间。
- 新购买为空间共享订阅，复用原支付订单、支付事件核对及事务内自动交付。空空间无需先建调用者；开始使用时准备受限访问 Key。已实现产品稳定 API、默认 v1、管理员切换到百度网页 v2；不因切换重发历史或重计次数。
- 迁移 `129_commerce_ip_risk_v2.sql` 与 `130_commerce_space_subscriptions.sql` 由既有 migrate/deploy 流程执行，正式种子为 ¥33,999 / 12 个月 / 100,000 次。隔离数据库已验证旧订单跨升级重试、原消费范围保持、共享年度最后一次并发竞争、现有及新建调用者继承、迁移重跑保留管理员价格/上下架/渠道选择。
- 本期商品编辑器发布 IP 风险画像空间订阅 SKU。通用按次商品、增量包、跨产品组合、赠送/兑换、自动退款和独立销售中心仍是后续范围；正式百度商业 API 仍待接口文档及凭据。产品能力与客户授权继续复用现有管理面。
- 最新服务端回归：2,249 项通过、0 失败，69 项因外部环境条件跳过；另外启用临时 PostgreSQL 的 68 项支付/IP/商城专项测试全部通过、无跳过。覆盖重复支付交付、ACK 丢失、test/live 隔离、越权、年度并发额度、失败释放、未知保留、到期、迁移幂等与 v1 兼容。构建、TypeScript 与能力目录检查通过。
- 浏览器验收使用隔离 Hub + Pay 数据库及本地签名付款事件、模拟 v1/v2 响应，不产生真实付款或供应商调用。桌面 1440×1000 与手机 390×844 验证明暗主题、空间选择、Admin Token ¥1 下单、原订单收银台链接、空空间开通、默认 v1 查询、管理员切 v2 后继续使用、历史不增量、受保护文档及无页面横向溢出。Browser plugin not available，因此使用本机 Playwright/Chromium。无页面运行错误；未登录 SSO 探测的 401 与测试服务 favicon 404 属于测试环境已知请求。

与参考界面的差异：保留 Hub 现有主题；百度 base + overall 没有提供的机构/精细定位显示为未提供或不展示，未添加地图 SDK；风险等级不转换成虚构评分。所给百度网页无法通过本次网页读取工具直接渲染，界面依据用户截图与 `/tmp/david-baidu` 样例核对。

本次尚未部署生产、向生产数据库执行迁移、真实付款或实测百度在线接口。最终线上验收应分别验证已配置支付源的原订单跳转/到账与百度网页渠道可用性；不能以本地模拟通过代替线上服务验收。本次未修改 Launcher/MX-H2I 登录、网络配置或 mx-pay 核心实现。
