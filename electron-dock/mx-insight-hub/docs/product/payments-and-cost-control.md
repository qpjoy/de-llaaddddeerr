# Hub 支付、充值与成本管控

更新：2026-10-02。本文区分仓库已实现、需要运营配置和未来规划；不代表线上已部署、商户已签约或发生过真实交易。

## 1. 已确认的业务决策

用户已确认首期使用“支付宝收款码 → 用户提交流水号 → 管理员核实 → 租户共享钱包入账”，付款确认后提交公司抬头、税号、收票邮箱，工作人员人工开票。

所有 Key 继续消费所属租户的原有钱包。充值不改变计费模式、套餐、价格、倍率、授权、用户角色、Key secret、登录或联网状态。新增支付模块不是另一套身份中心。MX-H2I V2 仍由 Internal 管理操作面与全部配置；Luopan 仍是独立 Launcher 测试产品。

当前交付重点是 **用户到 Hub 的充值闭环**。不提前实施渠道代收分账、供应商自动付款、税务开票接口或对外展示站。

后续定位为 **公司统一支付中心**：其他应用通过独立 mx-pay API 下单、查询和接收付款结果；Hub 钱包充值是其中一个业务场景。公司财务是另一个业务领域，可接入统一平台入口。独立 API、应用/环境凭据、付款事件拉取/确认和一键迁移部署已实现，见 [mx-pay 当前运行说明](../../../mx-base/mx-pay/README.md)；Hub 仍走下文 P0 内嵌路径，尚未切换存量。

2026-10-02 补充：产品入口可以在 Hub，目标交易服务应由 mx-pay 独立部署，Hub 充值也通过同一契约接入。存储、Kubernetes 发布、退款/折扣/财务分层及迁移依据见[支付中心服务边界与稳定性](../architecture/payment-center-service-boundaries-and-reliability.md)；该文更新下一阶段的架构优先级，不改变下文标注的 P0 实现现状。

用户已补充机器性能较好且可扩展，正式方案按“独立 PostgreSQL + 至少两个 Kubernetes 工作节点”规划；API/worker 分布、数据库复制、控制面和故障验收见上述架构文档第 5.4 节。此为规划资源基线，尚未部署或迁移。

界面目标为支付中心独立管理台与财务看板，Hub 保留租户余额/充值/发票入口。统一账号仍沿用 Launcher User Center，本地成员与产品角色保留；内网登录到公开身份入口、影子成员表达和存量租户平滑过渡见[平台身份与产品控制台规划](../architecture/platform-identity-and-product-consoles.md)。当前不开放注册，不替换已有身份绑定。

## 3. 现在能完成的链路

1. 平台管理员在 **充值与发票 → 收款设置** 填写稳定收款账户标识、支付宝实际显示的收款人、PNG/JPEG/WebP 收款码和付款说明，显式开启正式收款。默认关闭；测试流程无需凭据。
2. 租户 owner/admin 登录原 Hub，在充值页选租户、正式/测试环境和金额。正式首期仅 CNY，单笔 ¥5–¥100,000；整数分保存，最多两位小数。页面显示现有正式余额及冻结额。
3. 创建订单，服务端固定租户、币种、金额、环境、渠道、收款人和收款码快照；客户端不能指定 paid 状态。重试相同请求编号复用订单，换金额不能复用该编号。
4. 用户核对收款人、扫码并在支付宝中填写订单金额。**静态码不能保证支付宝自动带出金额**；Hub 会明确显示金额，但自动预填需后续官方订单支付接口。
5. 用户填写付款人和交易流水号，点击“我已付款，提交核实”。这只把订单变为待核实，余额不变。
6. 平台管理员在财务工作台查询待核实订单，到收款账户查真实账单，填写实际流水、实收总额、到账时间、手续费（未知可留空）和核实说明，并确认该笔未由旧人工充值重复记账。
7. 实收总额必须与订单一致。确认事务同时写支付订单、现有 `billing.credit_ledger_entries` 和不可变操作记录；原钱包触发器增加余额。返回不确定时按原请求编号重试，不能创建一条补偿充值掩盖未知结果。
8. 确认后用户可提交公司信息申请开票。管理员人工开具、交付发票，再登记号码和交付说明，或退回让用户重新提交。**本系统当前不生成税务发票、不发送邮件**。

少付/多付、已取消订单的迟到付款、重复付款、支付争议：首期转人工异常处理，不根据相近金额或尾数自动匹配，也不自动充值差额或退款。待核实订单不允许用户取消；管理员退回后可补正。取消只是停止申请，不代表资金退回。

已有人工充值入口保留，用于历史合同/特殊账务调整。付款订单必须在支付工作台确认，不能再在旧入口手工加一次余额。历史人工充值没有可靠支付渠道身份，系统不能承诺自动识别所有历史重复；上线前必须核对未结单。

## 4. 模块、部署与数据边界

| 层 | 职责 |
| --- | --- |
| `mx-base/mx-pay` | 不依赖产品的订单规则、金额/环境校验、状态转换、幂等指纹；后续放官方渠道适配器 |
| `Hub/server/payments` | Hub 会话与租户范围、PG/内存存储、将支付结果记入现有租户钱包、操作审计 |
| `Hub/src/pages-payments.jsx` | 充值、订单详情、公司开票申请、管理员收款配置/核账/开票工作台 |
| 原 billing 与 provider cost | 继续负责消费预占/结算/释放、计划价格、上游采购证据，不由支付模块替代 |

P0 随 Hub 一起部署，复用 PostgreSQL 同库事务，没有新增公网端口。`mx-pay` 暂无独立部署命令；Docker 增加命名构建上下文 `mx_pay`，已有 Hub Compose、Kubernetes 构建入口已接入。`mx-base` 的 GPU/静态服务生命周期不变。

下一阶段独立支付服务应有自己的凭据、部署、支付数据库和健康状态，但不能成为 Hub 登录、存量数据读取或 MX-H2I 网络就绪条件。拆服务后采用：渠道事件 inbox → 支付订单/outbox → Hub 幂等入账 inbox → ack；付款状态与 `pending_credit` 等业务交付状态分别记录，不做不受控 HTTP 双写。common 提供连接/迁移/可靠任务原语，支付表与业务钱包分别属于 mx-pay 和 Hub；正式目标优先使用专用支付 PG，不能将共享实例分库称为完整故障隔离。

### 当前数据库（迁移 122）

| 表 | 关键约束 |
| --- | --- |
| `mx_pay.settings` | 正式人工收款配置，版本校验；账户标识保存后固定；新配置仅用于新订单 |
| `mx_pay.orders` | 租户外键；整数分；明确 live/test；索引化状态/发票状态；租户+环境+创建请求编号唯一 |
| `mx_pay.events` | 创建、提交、确认、取消、退回、开票、配置的操作事件；只追加；每订单操作请求编号唯一 |
| `mx_pay.test_credits` | 独立测试入账流水；每订单唯一；只追加；绝不写正式钱包 |
| `billing.credit_ledger_entries` | 复用正式账本，`mx-pay:<order UUID>` 同时作为幂等与外部引用，链接订单和钱包 |

订单以固定结构 JSONB 保存快照，并以生成列建立筛选/唯一索引，避免内存全量过滤。正式支付身份是 **environment + provider + merchant_account_id + trade_no**；跨租户也不能重复入账。核心订单身份和已入账金额/结算信息受数据库触发器保护，发票流程可继续更新。按租户和订单加事务锁，并复用原钱包锁及余额触发器。

查询必须显式指定环境；租户订单/详情由当前会话所属租户验证，API Key 不能管理充值。没有新增或扩大任何旧身份权限：租户财务操作复用 owner/admin 的 `consumer.write`，全平台核实、配置和发票登记复用 platform admin。普通 viewer/analyst 不展示充值入口。专职财务角色及审批分工列入 P1，不要求给财务人员永久使用共享 Admin Token。

查询返回 `private, no-store`，收款码只接受体积受限的内嵌栅格图片，不请求外部图片 URL。公司信息只保存在受权订单/事件中，不放 localStorage、URL 或公开 API。列表不带收款码；详情操作记录展示最近 100 条并说明上限。平台共享 Token 的 actor 如实标为 admin-token，不假装实名经办人。

内存模式仅本机演示，页面刷新可读回，服务重启丢失；不适用于真实收款。正式必须使用 PostgreSQL、备份、HTTPS 和受控部署配置。

### 测试与正式共存

同一数据库、同一代码、订单明确 `environment`，但测试支付只写 `test_credits`。原正式钱包不加环境字段，也不批量迁移历史流水。测试入账显示“不可消费”，测试发票只为流程验证，财务筛选和导出始终带环境。当前 **mock 不是支付宝官方沙箱**，没有对支付宝发起任何请求。

未来 API Key 的 test/live、供应商 sandbox/live 和支付 test/live 是三条独立维度，不能仅看到测试充值就允许它调用真实收费上游。需要真实沙箱消费时另建隔离的测试钱包和预算策略，不给正式钱包注入测试资金。

## 5. 支付宝与微信资质路径

核查时间 2026-10-01；具体准入、经营类目、远程收款能力和费率以当前账户签约页面/支付宝审核结果为准，不能把“有二维码”当成“有网站支付资格”。

| 方式 | 能实现的体验 | 准备事项与限制 |
| --- | --- | --- |
| 个人/商家静态收款码 | 显示金额、人工付款、人工核账 | 官方帮助说明个人/企业支付宝账户可申请收钱码，但不等于任何个人码都允许网站远程经营收款，更不等于有自动查询/回调 API |
| 个人经营收款/小微进件 | 依获批产品提供经营收款能力 | 是否免营业执照、可用场景、额度、渠道接口权限应逐项向支付宝确认；不能承诺无执照即可开通网站自动支付 |
| 企业/个体工商户官方支付 | 固定订单金额、官方收银台/二维码、验签通知、查单、账单、退款 | 先准备营业执照、法人/经营者身份、同主体收款账户、结算账户、联系人、真实服务内容；按选定网站/APP/当面付产品补网站域名/备案等资料并签约。线上充值须选实际场景支持的产品，不把当面付当作通用线上接口 |
| 官方沙箱 | 验证签名、通知、查单和对账流程 | 单独应用/网关/密钥/测试账户；不会带来真实收入。下一阶段实现 |
| 微信支付 | 官方 Native/JSAPI/H5 等适用场景 | 提交对应主体资料、银行账户并申请商户号，按具体产品申请权限；公众号/小程序绑定和域名要求另核查。后续实现 |

央行通知对明显经营活动要求按特约商户管理，并对个人静态码远程非面对面收款设有限制。**不能把普通个人转账码长期公开在网站上当成商业支付通道**。首期代码支持人工收款，但上线前仍应确认收款码的经营/远程使用范围；尚未具备时使用 mock 流程。公司开票还需确认实际销售方、收款方、合同和税务处理的一致性。

- [支付宝收钱码申请与账户条件](https://cschannel.alipay.com/mobile/helpDetail.htm?help_id=201602661432)：支持个人和企业账户申请，不构成远程网站收款或 API 接入授权。
- [支付宝经营服务接入](https://render.alipay.com/p/c/zhifuisv/3.html)、[网页/移动应用开发入口](https://open.alipay.com/module/webApp)：应用创建、产品开通、资料和配置入口；不同产品分别审核。
- [央行银发〔2021〕259号全文（北京市政府转载）](https://www.beijing.gov.cn/zhengce/zhengcefagui/qtwj/202204/t20220407_2655822.html)：个人条码与经营收款、远程收款边界。
- [微信支付商户接入指引](https://pay.wechatpay.cn/static/applyment_guide/applyment_detail_public.shtml)、[JSAPI 权限申请](https://pay.wechatpay.cn/doc/v3/merchant/4012791854)：商户主体材料和按产品开通。

## 6. 财务与成本模型

必须分清四种数：客户支付总额、租户可消费额度、实际消费收入、供应商与基础设施成本。充值成功不自动等于已实现收入；具体收入和开票时点由财务按实际服务/合同确认。

### P0 已有证据

- 客户订单总额、实际收到的总额、到账时间、实际流水、核实人/说明、渠道手续费或“未知”、钱包入账编号。
- 现有消费账本继续记录冻结、扣费、释放、未知结果；付款页可跳转用量与账单。
- 财务工作台按正式/测试、订单状态、开票状态、完整订单号筛选，分页浏览并导出**当前页** CSV。合计明确只统计当前页，不称为全量月报。
- 每张订单申请一次全额开票；退回可重新提交，已开具不能覆盖。发票内容/税率由财务决定，首期不硬编码税率，不把赠送额度开成实付票据。

这支持人工核账，不包含渠道账单自动下载、自动匹配、银行到账证明或总账会计系统。用户输入的流水号不是支付凭证；管理员人工确认是首期的支付事实来源。

### P1 计划：完整对账与财务权限

1. 原始渠道账单导入/官方下载：保留文件哈希、账期、时区、商户、币种、导入批次；文件去重，不能重复记账。
2. 建立支付总额/手续费/渠道净额/银行结算额四方核对，区别交易日和结算日。未知费用保持未知；不得按“行业常见费率”填零或推算实际值。
3. 对账差异类型：Hub 有单渠道无款、渠道有款 Hub 无单、金额不符、重复支付、迟到支付、退款未同步、手续费差、结算延迟。保存经办人、复核人、处理理由和关联证据。
4. 分离 `finance.read / receipt.confirm / invoice.manage / refund.approve / payment.configure`；高额入账、退款、收款账户变更双人审批。采用原 Launcher 登录 + Hub 财务角色，不建立第二套登录。
5. 后台异步全量导出，固定快照/时间范围、限定权限和过期下载，避免把“当前页导出”误当月度关账。
6. 开票申请与消费订单可拆开：余额充值、实际服务消费、退款/红字票须避免重复开票。支持合并/拆分开票前，先引入可开票金额的预留与余额。

### 成本与毛利管控

| 成本/账务 | 现状及下一步 |
| --- | --- |
| 上游逐次调用采购成本 | 沿用请求级采购价证据、供应商原币种及实际/估算标记；调用前冻结/准入，结果未知保留待结算，不盲重试 |
| 客户 API 收入 | 沿用不可变计划版本、消费冻结/扣费；充值不自动换计划、启用收费或扩大授权 |
| 支付手续费 | P0 人工登记已知手续费，未知不填零；P1 以账单核准，记录毛额与净额 |
| LLM/Embedding/清洗/存储 | 现有调用/资源控制继续有效；逐步按 token、任务、CPU/GPU 时间、存储量、流量和缓存命中归集可证明的实际量；没有计量不要虚构单价 |
| 免费、赠送、折扣、渠道佣金 | 与实付款分账；赠送不自动形成现金收入或可退款额度。价格/佣金规则要版本化 |
| 多币种 | 原币种保存，不能把 USD 采购直接减 CNY 销售额声称毛利。汇总时另存汇率来源、时点和换算报表，不改原始流水 |
| 风险准备 | 退款、拒付、未知付款、供应商未知结果单独列待处理项；余额告警不是交易失败证据 |

成本上限保持现有语义：当前请求有正确范围且足额的 enforced 正向钱包冻结时，不因 Hub 月采购/补贴阈值而错误阻断；免费/补贴请求仍走相应硬预算。供应商额度、速率、并发、健康、合同/价格证据等控制继续有效。支付入账本身不触发任何上游调用。

## 7. 自动支付、渠道与供应商的后续阶段

### P1：支付宝官方支付

先确认商户主体与对应产品，使用官方沙箱验证，再启用生产。订单接口保持不变，增加官方 channel adapter 输出 checkout URL/QR。服务端生成金额与商户订单号；回跳页面只展示结果，不作为入账依据。

验签通知/主动查单必须检查应用、收款商户、商户订单号、渠道交易号、币种、总额、成功状态和环境；校验后用同一结算事务。原始通知受限存储 + event ID/交易唯一约束；重复、乱序与未知结果可恢复。超时不得假定未支付并创建新交易；按原订单做受控查单。

新增公网入口只开放固定支付通知路径，经 HTTPS 验签后进入 mx-pay；不公开 Internal 管理 API、收款配置或 Launcher 认证接口，不为支付更改 MX-H2I 路由/DNS。证书、密钥和 webhook secret 分环境加密保存；普通接口只返回 configured 状态。公网路由及正式商户启用另行实施。

### P2：Creem、微信、爱发电和退款

- Creem：相同订单抽象、HMAC-SHA256 原始报文验签和 event 去重；test/live 分离；付款成功、退款/拒付、订阅支付为不同事实。先核实它对销售方、结算币种、税务与开票责任的协议，不假定与国内直连支付宝相同。
- 微信：选择适用的 Native/JSAPI/H5 产品，实现平台证书/公钥验证、API v3 通知解密和对应订单/退款对账；未获相应产品权限不能直接上线。
- 爱发电：适合作为补充渠道。保留 server-side 分页查单、时间水位、有界重试与订单映射，轮询延迟不能伪装即时到账，也不能仅凭浏览器轮询返回决定付款。
- 退款：原订单关联、剩余可退实付额、已消费/冻结额度检查、申请与审批、渠道退款单、未知结果、退款通知及发票红冲。原支付与消费流水不删除，以反向流水核算；不把余额调整等同已退款。

### P3：下游代理/渠道

先区分“代理自己向 Hub 买额度再给客户供货”和“代收终端客户资金再分账”。首种可先复用独立渠道租户、合同价和佣金账；后者需要支付机构支持的服务商/特约商户/分账产品和相应协议，不能自己做资金池或用一张个人码代收所有商户。

预留业务关系：`channel_id`、终端客户租户、合同版本、资金所属主体、销售归属、佣金规则版本、结算单及付款单。订单受益租户由授权关系推导，不能由客户端任意填写。渠道价、客户售价、供应商采购价分别存证。渠道不能查看其他渠道成本、账单或给任意租户加钱。

### P4：上游供应商付款

将供应商采购合同/应付账单、已用调用成本、供应商预存余额、我方付款和供应商确认分开。建立 `supplier_account / payable / payment_instruction / payment_execution / settlement`，有审批、预算、商户校验及幂等。供应商充值与客户钱包不互相挪用。

现有余额监控先只作告警；后续自动补款需运营明确开启、单笔/日/月限额、允许供应商账户和审批规则。未知结果先查证，不能连续自动补款；支付适配器不直接持有无限制自动转账权限。

## 8. 对外 DataHarbor 与一套数据

对外展示站可以拥有独立视觉和产品目录，但登录后充值、订单、发票及消费应请求相同 Hub 合同，身份绑定同一 member/tenant，不复制账户余额与业务订单。内网和公网是访问入口，不是两套业务环境；公开部署不能把 internal API 路径直接暴露为无需授权的服务。

将来接入对外站时抽取稳定的客户支付 API/BFF，继续鉴权并绑定租户；页面共享组件或契约测试保持金额、状态与错误语义一致。可以给订单记录入口来源用于归因，但来源不决定 test/live。首期没有更改 `/tmp/dataharbor` 或发布任何公网网站。

## 11. 公司统一支付中心与其他应用接入（规划，2026-10-02）

### 11.1 产品定位与当前差距

其他应用可以把 Hub 支付中心作为统一收款与财务入口。应用保留自己的产品、定价、用户登录和业务交付；mx-pay 独立提供支付订单、统一收银台、渠道适配、付款事实、通知及支付对账，Hub 提供业务接入与综合财务界面。域名/品牌可以统一，交易路由应直接到 mx-pay，不能强制经过 Hub 程序；不要求每个应用再部署一个收款服务或复制一套财务数据。

**当前只能调用第 9 节的控制台充值接口，尚无面向其他应用的机器接口。** 当前创建订单必须绑定 Hub 租户，确认付款必然写入该租户的正式钱包或测试账本；因此不能把这些路由原样作为通用商品支付 API。现有数据 API Key 也没有充值管理权限。不得把平台 Admin Token 发给接入应用、客户端或网页以绕过这个差距。

| 概念 | 职责与边界 |
| --- | --- |
| 接入应用 `application_id` | 标识哪个系统发起业务订单、接收结果；从应用凭据推导，不能靠请求参数冒充 |
| 客户/租户 | 标识付款对应的业务客户；应用内客户编号与 Hub 租户不是同一个概念。只有 Hub 钱包充值必须绑定已授权的受益租户 |
| 销售主体与收款账户 | 公司实际销售方、获准使用的商户账户和渠道；由管理员预先配置应用可用范围，客户端不能指定任意收款人 |
| 应用业务订单 | 商品、套餐、数量、优惠、履约对象与服务内容；由应用后端生成并固定价格版本，浏览器报出的金额不是可信售价 |
| Hub 支付订单 | 应收金额、币种、环境、收款渠道、渠道流水、付款状态与支付事件；统一的付款事实来源 |
| 业务交付 | 充值钱包、开通会员、交付报告等；由对应业务处理器执行。支付成功和交付成功分别记录 |

例如 DataHarbor 为同一 Hub 租户充值，入账仍进入原钱包；另一个应用出售 ¥99 的会员，mx-pay 记录 ¥99 的收款，通知该应用开通会员，不额外生成 ¥99 的 Hub API 余额。所有应用共享支付能力，不等于所有应用客户自动共享钱包。

### 11.2 应用接入流程

下述为完整目标流程；当前独立 API 与人工核实/拉取事件子集以 mx-pay README 为准。统一支付动作由独立 mx-pay 执行；Hub 以业务应用身份处理自己的充值入账。

1. 在支付中心登记应用与 test/live 服务端凭据；当前通过受控凭据文件配置，未来增加管理 UI、销售主体/额度/回跳/通知策略与轮换流程。
2. 用户在应用中正常登录并选择商品。应用后端校验用户、价格与资格，建立稳定业务订单，再向 mx-pay 下单。Hub 钱包充值还需验证该应用对受益租户的明确授权关系。
3. mx-pay 持久化支付订单并返回订单身份、状态和付款展示信息。当前由业务后端转交必要信息；独立浏览器收银台会话/地址尚未实现。
4. 管理员以独立核实凭据核对到账后，mx-pay 同事务提交付款事实和待交付事件。官方验签回调/查单后续补充；用户点击、应用回跳或普通应用凭据都不能声明已付款。
5. 应用当前主动拉取事件，在本地同事务提交 inbox 与业务交付，再确认稳定业务流水；失败保留事件。Hub 接入需保留原钱包幂等引用。签名推送与查单 worker 后续按同一契约扩展。
6. 支付工作台查询支付资金事实，财务工作台管理票据、审批和核算；平台入口集成各工作台。当前独立服务已有受限 API，完整人类工作台与 Launcher 身份接入未实现。应用仅能查询本应用、本环境范围。

统一收银台可使用短时、不可枚举的订单访问凭证，使其他应用用户不必另建一套 Hub 登录。该凭证只允许查看必要付款信息和提交该订单的付款申请，不能查询钱包、财务事件或操作其他订单；不能携带 Admin Token、应用密钥、税号或邮箱。需要申请发票时通过应用后端验证客户归属，再签发对应的受限操作会话。回跳地址与通知地址来自应用注册配置，不能由任意订单请求传入任意 URL。

### 11.3 建议 API 契约（下列路径尚未实现）

本节保留原网关/完整能力草案；已经实现的独立服务接口为 `/v1/orders`、`/v1/events` 等，详见 mx-pay README。不得把下述路径当成当前可调用路由，或将完整退款/通知能力当成已交付。

使用独立、版本化的 `/api/v1/payments` 路由和应用鉴权，不扩权现有数据 API Key，也不暴露 `/internal/v1/admin/payments`。目标路由由网关直接转到独立 mx-pay Service，Hub 自身通过业务适配器调用。即使位于内网，应用之间仍按凭据和授权隔离；公开部署只增加经过审核的路由。

| 方法/路径草案 | 用途与限制 |
| --- | --- |
| `POST /api/v1/payments/orders` | 应用后端下单；必带 `Idempotency-Key`，应用身份和环境从凭据推导 |
| `GET /api/v1/payments/orders/:paymentId` | 查询本应用订单的付款与交付状态，返回稳定版本和更新时间 |
| `GET /api/v1/payments/orders?businessOrderId=...` | 响应丢失时按本应用业务单号找回唯一订单；禁止跨应用枚举 |
| `POST /api/v1/payments/orders/:paymentId/invoice-requests` | 受权应用代客户提交开票资料；仍需实际付款和可开票金额校验 |
| `POST /api/v1/payments/orders/:paymentId/fulfillment-ack` | 应用报告已完成/失败的交付结果；只改交付状态，不改付款事实 |
| mx-pay → 应用预注册通知地址 | `payment.paid` 等签名事件；后续退款和拒付使用独立事件类型 |

创建请求包含 `businessOrderId`、`orderKind`、`amountMinor`、`currency`、商品/价格版本摘要和应用内客户引用；`hub_wallet_topup` 额外需要通过授权校验的 Hub 租户绑定。`applicationId`、销售主体、正式/测试身份、收款账户和 `paid` 状态不能作为任意可写字段。接入应用只能在事先允许的产品与金额范围内下单；Hub 不把商品单价当作渠道凭证。

幂等范围为 **应用 + 环境 + 业务订单号**，并独立保存请求编号与请求指纹：相同身份、相同参数返回原订单，不同金额/币种/受益人返回冲突。更换请求编号不能让同一业务订单重复收款。请求超时先找回原订单；支付尝试与业务订单分开记录，在上次支付结果未知时不能无条件创建第二次扣款。通道流水唯一范围继续是 **环境 + 渠道 + 收款账户 + 流水号**，不能加入应用编号后放松为“每个应用可入账一次”。

应用 API 使用 HTTPS 和专用服务端凭据，凭据绑定应用、环境及最小权限，例如 `payment.order.create/read`、`payment.invoice.request`、`payment.fulfillment.ack`。凭据校验值不可逆保存；应用通知签名密钥单独加密保存并支持轮换。任何接入应用都没有 `receipt.confirm`、收款配置或给任意租户加余额的权限。应用服务端密钥不能嵌入 Electron 包、浏览器、移动端或静态站点；这些客户端调用其受控后端或受限收银台会话。

### 11.4 通知、交付与数据模型

付款状态与交付状态分开：可以出现“已付款、待开通/开通失败”，不能因为通知失败把付款改回未支付。付款提交和待通知事件在同一数据库事务内写入 outbox；独立 worker 有界重试，失败进入可查询、可人工重放的队列。重放仍使用原事件身份，不产生第二笔收款。

通知含 `eventId`、`eventType`、`applicationId`、`environment`、`paymentId`、`businessOrderId`、金额/币种、付款事实及版本。使用独立密钥对时间戳与原始请求体签名；应用校验签名、时效、环境、订单、金额并按事件去重。传输采用至少一次投递，不承诺恰好一次；每次重投刷新传输时间与签名，事件编号保持稳定。应用先持久化 inbox 再返回成功，由自身事务完成交付及回执任务；HTTP 2xx 只表示事件已被可靠接收，不等于商品已经交付。乱序事件按状态机和版本处理；定期对账可按原单查询修复遗漏，不通过重复充值补偿。

在 mx-pay 独立支付库内增加应用登记/凭据、业务订单归属、销售主体/账户绑定、支付尝试、交付回执及 outbox/inbox；Hub 钱包和业务 inbox 留在 Hub 库。实际迁移另行设计、审核与验收；**迁移 122 尚无这些表或字段，仍是 Hub 同库 P0**。新订单快照应有明确版本，保留原支付订单为付款事实来源。历史充值按 `hub_wallet_topup` 兼容解释，不重写原始金额/流水/审计快照、不重新确认已付款订单、不再次触发钱包入账。通用商品支付不能继续强制每个买家拥有 Hub 租户；该约束需在新增契约和存储适配中明确处理。

切换前 P0 的付款与钱包保持现有同库事务；切换后 Hub 与其他应用一样通过 outbox/inbox 交付，Hub 业务 inbox 与钱包入账在 Hub 本地事务完成。应用只保留自己的业务单、支付编号和幂等接收/交付记录，不再维护第二份独立的“实收总账”。测试与正式可共库，但应用凭据、商户/通道配置、订单、通知、交付与报表都必须区分环境；测试付款不得开通正式会员、交付正式收费服务或增加正式钱包余额。

### 11.5 财务与实施顺序

财务按应用、销售主体、收款账户、环境、币种、订单类型和时间查询，渠道到账仍按实际收款账户统一对账，避免每个应用各算一份银行实收。客户归属和收票资料按授权可见；消费成本、商品收入确认与现金实收分开记录。未来应用利润报表必须基于各应用实际交付/消费、采购与费用证据，不能只把充值金额减去采购调用金额。

先覆盖公司自有应用收款。下游独立商户代收分账、上游供应商付款沿用第 7 节的独立阶段；它们不是给应用新增下单权限就自动具备的能力。多销售主体也须有各自的收款、开票和账务归属配置。

建议下一轮先用一个接入应用打通 `mock 下单 → 收银台 → 付款确认 → 签名通知 → 幂等交付 → 查询与对账`，再验证人工收款通道；应用接入建设可以先于支付宝官方 API。首个验收应覆盖跨应用/跨租户拒绝、环境隔离、同业务单并发重试、通知丢失/重复/乱序、应用离线后恢复、密钥轮换和财务归属。Hub 原充值流程及 MX-H2I 登录/联网仍须通过回归。当前这一轮只补充规划，没有新增机器接口、签发凭据、开放公网路由或修改现有登录。

下一阶段优先把 Hub 充值作为第一个独立 mx-pay 接入方，再增加第二个应用；先完成独立存储/队列/发布验收，再扩大渠道与财务功能。退款由应用决定资格并冻结业务额度，mx-pay 校验资金上限并执行；折扣由应用算价，支付保存最终金额；综合财务报表与发票作为独立扩展消费资金与业务证据。完整次序和现有部署限制见[稳定性规划第 2、7、9、12 节](../architecture/payment-center-service-boundaries-and-reliability.md)。
