# 数据浏览中心高级搜索：RAG 可行性与交互方案

日期：2026-09-16。状态：评估与建议，未启用新搜索模式、模型调用、历史向量化或部署变更。

## 结论

值得分阶段完善。建议保留账号大盘、内容大盘、热点线索，增加独立的 **高级搜索** Tab，以“检索内容证据 → 查看关联账号 → 按需生成带引用回答”为主流程。第一阶段接入已有 ES 全文搜索；第二阶段开放受控混合召回；第三阶段增加可选 RAG 回答。不要把普通浏览、精确统计或既有接口转发改成每次都经过 Agent。

RAG 是“检索后，把证据交给模型生成回答”；向量检索是召回方式之一。二者不是同一个功能，RAG 也可以只使用全文检索返回的证据。ES 全文搜索和向量搜索可以组合，没必要为了 RAG 再引入一套向量数据库。LangChain 官方也区分检索与生成，并将固定两阶段 RAG 与多轮 Agentic RAG 分开；前者更适合本次需要的有界线上体验。[官方说明](https://docs.langchain.com/oss/javascript/langchain/retrieval)

**推荐采用，暂不直接全量开放。** 当前底座可复用，但现有检索管线接口尚有过滤、证据回查、降级、预算和覆盖率缺口。仅加一个 Tab 并直接调用现有 `semanticSearch()` 不足以达到稳定业务搜索的标准。

本次核对的是仓库，不是线上运行状态。截图中的 39,628 个账号不能推算向量规模；需要统计可检索内容数、正文完整率、平均切片数、更新频率、向量覆盖和真实查询量。仓库 `package.json` 当前没有 LangChain/LangGraph 依赖，已有固定 runner 不等同于已安装这些框架。

## 相对全文检索的实际收益

| 用户问题 | 首选路径 | 可获得的改善与限制 |
| --- | --- | --- |
| 找账号 ID、品牌名、商品型号、原文短语 | 精确条件 / 全文检索 | 可解释、稳定，向量不应稀释精确约束 |
| “退款一直没到账”，原文写“售后迟迟不处理” | 全文＋语义混合 | 有机会找出用词不同但含义相近的记录；模型质量要用中文样本评估 |
| “哪些账号近期讨论售后问题” | 内容混合检索 → 按平台＋账号 ID 聚合 | 用命中内容证明关联；不将少量命中推断为账号长期身份或完整画像 |
| “这些投诉主要集中在哪些问题，有什么原文依据” | 混合检索 → 可选 RAG 回答 | 对选定证据归纳并逐项引用；模型不能证明未检索到的材料不存在 |
| “过去 30 天总共有多少投诉，增长多少” | 已定义分类口径＋确定性统计 | top-K 语义结果不能推算总体数量/比例/增长；未建立分类与基线时说明不支持 |
| 图片里的文字、视频讲了什么 | OCR / ASR 等独立抽取后检索 | 当前只有 title/body 的 embedding 看不到图片或音轨；不能声称多模态已覆盖 |
| “可能发生什么舆情” | 独立信号与时间序列评估 | RAG 只能整理已有证据，不能自动获得预测能力 |

全文检索本身也可使用同义词、分词改进和字段权重，不能把所有收益归因于向量。建议对比“当前 PG 子串 / ES balanced / 混合检索”三个基线，避免把接入 ES 的收益误算成 RAG 收益。RRF 可以融合不同检索器的排名，但候选范围和排序仍须评估，分数不是概率或可信度。[Elastic RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

## 高级搜索 Tab 的页面设计

导航建议：`账号大盘 ｜ 内容大盘 ｜ 热点线索 ｜ 高级搜索`。保留现有风格；面向用户的名称不必直接写技术缩写 “RAG Search”，在说明中写“全文、语义检索与引用回答”。

| 区域 | 控件与行为 |
| --- | --- |
| 查询栏 | 输入检索词或描述；明确点击“搜索”才执行；进入 Tab、切换结果分区或打字不调用模型 |
| 搜索方式 | “全文匹配”“语义＋关键词”；第一阶段默认全文。通过评测且语义覆盖可用后，可将高级搜索默认设为混合，普通大盘保持原行为 |
| 检索范围 | 平台、数据集、对象类型、内容形态、发布时间、来源标签；从账号详情进入时携带固定的平台＋账号 ID，可显式解除 |
| 生效条件 | 展示已应用条件；自然语言解析只在后续显式“解析条件”操作使用。解析结果可编辑，服务端校验后再检索 |
| 覆盖与状态 | 展示本次模式、统计时间、向量覆盖范围及不可用原因；缺少正文/OCR、索引延迟、词法降级都需可见 |
| 结果分区 | “内容证据”“关联账号”；内容默认。账号结果由本次命中内容聚合，每个账号展示代表内容及命中数，跳转现有账号详情 |
| 内容结果 | 复用封面、作者、发布时间、类型和指标；新增命中片段及“关键词命中 / 语义召回”依据，全文详情沿用既有页面 |
| 回答区域 | 搜索成功后出现独立按钮“基于这些结果生成回答”，默认关闭；可先勾选证据。生成失败不清空列表 |
| 引用 | 每个结论链接到 Hub 内容详情与具体片段；显示覆盖范围、时间和无法回答的部分，不生成无来源分数 |
| 导出 | 全文结果遵守自身查询语义与导出上限；语义导出只包含本次冻结候选与证据，明确“候选集导出”；回答与原文证据分开 |

例如输入“近一个月讨论退款困难的内容”，第一版可以先由用户设置“近 30 天”并搜“退款困难”；自然语言的日期不会偷偷变成硬过滤。后续解析器输出可见条件后，再执行“退款困难”的语义＋关键词查询。

该入口连接账号和内容，但不合并两个大盘。浏览大盘解决“有什么、多少条、按条件管理”；高级搜索解决“找相关证据、阅读和归纳”。与左侧检索管线也不是重复：前者是使用入口，后者负责构建状态、模型版本、覆盖率和故障诊断。

### 总量、分页不能退回含糊状态

- 原两个大盘继续显示 PG 当前范围的精确总量及页数。
- 高级全文模式的总数来自同一 ES 查询及其索引覆盖，不与 PG 子串总数混用；PG 降级明确提示模式和统计口径变化。
- 语义模式显示“本次召回 X 条内容 / 涉及 Y 个账号，候选上限 K”，另显示“筛选范围内可检索规模 / 语义覆盖”。后者不是语义命中总数。
- kNN/RRF 返回有界候选，不能声称存在类似全文过滤那样的精确全库相关总数。候选可冻结后分页，页数只针对本次候选集；扩大 K 属于重新检索。
- 对需要全量导出/总体统计的用户，提供回到内容大盘并保留硬条件的入口，同时提示语义描述未转换为全库分类条件。

## 建议请求链路与接口边界

固定链路：校验身份与 Zod SearchIntent → 服务器施加范围 → 全文召回，按模式并行加入 query embedding＋kNN → 当前记录回查 → 按 canonical ID 去重、RRF/可选重排 → 内容证据 → 可选账号聚合 → 按需引用回答。

1. 第一阶段只服务现有 Hub Admin Token。拟增 `POST /internal/v1/admin/data-browser/search` 和独立 `/answer`，这是接口建议，当前尚未注册。公共 listener 继续无此入口，不扩张租户授权或复用付费转发调用。
2. SearchIntent 仅有 query、显式 mode、受控 filters、有限 topK/结果分区；拒绝任意 DSL、索引名、SQL、scripts、URL 和客户端 ACL。自然语言生成的条件也要走同一校验，Zod 只能证明结构，不能证明含义正确。
3. 全文分支必须覆盖 content 索引，不能只搜索已经成功向量化的 chunk；否则“没有向量”的大量旧数据会悄悄消失。
4. 两条检索分支使用一致的硬过滤；向量过滤尽量在 kNN 内执行。服务端按主键批量回查 PG 当前 revision、删除、可见性和必要字段，在输出与模型上下文之前再次校验。缺权限或版本不一致的证据丢弃/重取，不能只依赖异步删除投影。
5. 当前 chunk v1 缺少账号 ID、对象/内容类型、标签与可见性字段；完整过滤需要新增受控投影或其他有界执行策略。不能把全库候选取回 Node 后无限筛选，或在权限过滤不足时发送上下文给模型。
6. 融合前将词法记录和语义切片统一成 canonical ID；同一长文多个切片不应挤占全部名额。保留每条证据的片段、source revision、模型空间与排序来源；账号聚合仅使用当前候选，并限制单账号代表条数。
7. 回答接口接收服务器签发或保存的搜索快照引用及所选证据 ID，不接受浏览器自造原文。执行前重新检查授权/revision。生成输出校验结构、引用存在性和支持关系；不支持的结论拒答。引用存在并不自动意味着结论有依据。
8. 内容属于不可信材料，不能改变工具、权限、系统提示或预算。模型不获得采集、转发、发布、登录或修改数据的工具。查询和正文只发送给显式批准的 Sequence，日志不记录密钥或无限正文。
9. 模型调用继续走既有 Node Sequence 路由。LangChain JS 可用于模型/文档适配，LangGraph JS 可承接后续有状态多步研究；第一版固定检索不必为调用图引入完整运行平台，更不需要 Python 服务。

### 现有调试路径必须补的具体缺口

| 当前代码事实 | 业务化处理 |
| --- | --- |
| `semanticSearch()` 仅接受 platform / datasetId 过滤 | 补齐上述统一过滤，不静默忽略日期、账号或标签 |
| 两路都在 chunk 索引查询；chunk 只在有向量后投影 | 加 content 全文兜底，分别说明全文/向量覆盖率 |
| 缺少 embed 时返回 lexical-only；embed 或 kNN 报错会使当前请求失败 | 分支级超时/错误隔离，全文先可用；不能把所有失败都改成空结果 |
| 当前 route 直接取 body.size；只有简单 query 必填检查 | 新入口严格 Zod 长度/类型/size 上限、并发/令牌预算和取消 |
| 返回切片 `_source`，按切片 ID 融合 | 统一安全投影、当前记录批量回查、按内容去重，增加证据和覆盖元数据 |
| 无查询时点的模型空间过滤和完整业务快照 | 校验当前模型锁；不兼容存量隔离；跨请求冻结有限结果且绑定身份/条件/版本 |
| embedding 与普通 projector 是同 Pod 独立循环 | 循环隔离不能隔离 CPU/内存/连接；历史回填前拆分资源并加任务 claim/预算 |

## 额外负担与控制办法

负担主要来自“处理多少文本、多少查询”，不是 Tab 本身。没有测量生产使用率，不能保证开启后零影响。代码可以不依赖登录链路，但共享 PG、ES 和宿主机资源仍可能间接影响其他业务。

| 来源 | 开销 | 建议 |
| --- | --- | --- |
| 首次与增量向量化 | 文本读取/切片、Embedding tokens、PG 写入/WAL、ES HNSW 构建 | 先选数据集和近期完整正文试点；后台低优先级、可暂停、token/日预算；禁止部署时自动全量向量化 |
| 语义查询 | 一次 query embedding＋kNN，额外延迟和 QPS | 仅显式语义模式；按查询＋模型空间缓存 query vector，结果缓存另绑定授权/条件/索引版本 |
| 重排 | 每次候选与问题的推理开销 | 初期可不启用；离线证明收益后只处理少量候选，超时回退原排名 |
| 回答生成 | 输入证据 token、输出 token、模型延迟 | 单独按钮、有限证据与总 token，默认不自动回答；独立并发额度 |
| 存储 | PG chunk/text/vector 与 ES 文本/向量/图结构，备份与重建临时空间 | 限定 eligible corpus、淘汰失效表示、独立容量监控；不要另建重复 PG ANN 索引 |

仓库的共享 ES manifest 是单副本、12 GiB heap、32 GiB memory limit、8 CPU limit；projector 的 limit 是 2 GiB / 4 CPU。这些是配置上限，不是生产空闲资源，也不证明多个产品同时使用时有余量。当前代码使用 ES `int8_hnsw`；量化降低检索向量的内存需求，但 ES 仍保留原始向量，磁盘不会同比缩小。[Elastic 容量说明](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/approximate-knn-search)

仅用于估算的例子：100 万切片 × 1024 维 × 4 bytes ≈ **3.81 GiB 原始 float32 向量**。当前 PG 保存一份，ES 也有其向量存储；int8 数值本体约 0.95 GiB，另有 HNSW 图、文本、元数据、数据库行/索引、WAL 和备份。不能把 0.95 GiB 当全部内存或全部磁盘；一条内容可能有多个切片。

成本用实际合同价格计算，不预设供应商单价：

- 初次 embedding ≈ 合格内容的切片 token 总量 × 每百万输入 token 单价 / 1,000,000。
- 日常增量 ≈ 新增/正文变化 token＋查询 embedding token；首次历史回填可能远大于日常成本。
- 回答成本 ≈ 回答次数 ×（问题＋证据输入 token 费用＋输出 token 费用）；重排另计。

当前 materialize 按 canonical revision 判定失效；将来应增加文本 hash＋chunker/model-space 版本，指标数字变化但正文没变时复用已生成向量，并正确更新投影 revision。当前 chunker 的 320 token 是软目标，超长无标点句子会整体保留；生产化要补硬 token/字符上限和确定性长句拆分。

后台拆分还需防止重复付费：增加 claim/lease、模型请求预算和可追踪状态，再扩容 Worker；不能仅把副本数加大。暂停新增 embedding 时，删除/撤销投影仍要继续。为 PG 连接、ES 并发、分词和模型调用分别设界限；峰值压测中若普通查询或 outbox 延迟明显回归，先暂停回填/生成，而不是提高公共接口超时。

### 初始试点预算（建议值，待测量调整）

- 选 1–2 个正文质量好的数据集，先最多 1 万条内容；近期 30 天只是候选范围，仍受总量/token 上限约束。
- 全文与向量各取最多 100 个候选，融合去重后保留最多 50 条；单条最多保留 2 个证据片段。
- 按需回答最多 10 条证据，总输入上限 8k tokens，单次输出上限 1k；模型不支持该上下文时进一步下调。
- 语义查询初始 2 个并发槽位，回答 1 个；所有 API 实例合并计算额度，不能仅按进程叠加。后台构建独立预算。
- 产品目标先设为检索 p95 ≤ 3 秒、回答总预算 ≤ 20 秒，均是验收目标，不是当前已测速度；超时保留可用全文结果。
- 明确开关 `全文 / 语义 / 回答 / 历史回填` 四者独立。页面查询绝不隐式触发外部补采。

## 增量、旧索引与升级

1. 新增高级搜索 UI 不需要全量 ES 重建。
2. 首次要覆盖历史语义检索，所选历史文本必须至少生成一次对应空间的向量；可分批完成，覆盖未齐时全文分支继续覆盖旧数据。
3. 只改提示词、候选窗口、RRF 参数不必重新 embedding；新增展示字段依情况增量补投影。新增可检索 multi-field 不会自动填充旧文档，不能以 mapping 存在推断历史覆盖。[Elastic mapping 说明](https://www.elastic.co/docs/manage-data/data-store/mapping/update-mappings-examples)
4. 补充 chunk 的账号/类型/标签字段需要更新投影和受控回填。复用 PG 已存向量，无需为相同文本＋模型重新调用 Embedding；按缺失表示与当前 revision 分批，不改 canonical 真相。
5. 换模型、维度、语义预处理或不兼容切片规则，要新表示空间和新 chunk generation。当前模型锁应继续拒绝原地混写，先设计迁移；不能仅改默认 Sequence 就宣称完成升级。
6. 旧版本继续服务，新版本低峰限速构建、追平增量、校验删除/权限/coverage、评测后切换。支持可回滚的读指针，保留有界旧版本；按数据量评估，不承诺一夜完成。

## 分阶段投入与放行条件

| 阶段 | 交付 | 放行条件 |
| --- | --- | --- |
| A：统一全文体验 | 高级搜索 Tab、复用 ES profile、统一硬条件、命中高亮、详情/导出；诊断全文覆盖 | 筛选和权限一致；无语义/模型配置也可用；大盘及公共搜索无回归 |
| B：受控混合检索 | 表示版本、覆盖状态、分支降级、当前 PG 回查、按内容去重、账号证据聚合，受控增量 embedding | 中文离线评测有净收益；无越权/已删内容泄漏；正常负载下普通查询和投影延迟不回归 |
| C：按需引用回答 | 固定两阶段 RAG、快照引用、引用核验、拒答、取消/预算/运行记录 | 引用支持关系和事实准确率达到评测门槛；供应商故障不影响检索列表 |
| D：可选研究工作流 | 多轮改写、对比、深度研究与持久化恢复 | 有明确研究需求和增益，再引入完整 LangGraph 执行治理；不进入默认搜索 |

不把大规模历史向量化、全库 AI 画像或 Agent 自动改接口放进 A 阶段。建议先完成 A 和 B 的基础门槛，再决定 C 的实际投入；若基线 ES 已满足业务，B/C 可以继续保持关闭。

建议准备约 100–200 个实际问题及人工标注相关内容，覆盖账号/型号精确词、中文改写、长文、多平台、无答案、空正文、日期/标签约束、删除与权限变更。比较 Recall@20、nDCG@10、人工相关率、重复率、无答案表现、成本与 p95；分类型报告，不能只给总平均。初始放行门槛可用：语义问题 Recall@20 相对 ES 基线提升至少 10%，精确查询无明显退化；测试集中越权/删除泄漏为零。该阈值是建议，不是已达成结果。

回答另评估引用支持率、未支持断言、时间混淆和拒答质量，不用模型自评代替人工样本。线上 canary 同时监控大盘/公共读取 p95、ES 拒绝率/page cache、PG 连接等待、outbox lag、embedding tokens 和成本。建议以普通读取 p95 相对基线增加超过 10% 作为暂停试点的初始信号，并结合流量变化判断。
