# 高级搜索、后台向量化与容量边界

2026-09-16。此文对应当前代码实现。**用户最后确认：线上全量重建和全库向量化由用户在数据中心手动启动，本次未部署、未启动线上任务。**

## 两个入口

数据浏览中心新增“高级搜索” Tab，原账号、内容、热点及总量/导出保持原路径。

- 全文：AND / OR / 连续短语，可选 ES 模糊纠错，标题/正文高亮。AND/OR 由受控 DSL 构造，用户输入不作为任意 ES 查询语法执行。
- 语义 + 全文（RAG）：两路各取最多 100 个候选，向量路预过滤平台、数据集、类型、作者、来源标签和日期，按 canonical record 去重后 RRF 融合。AND/OR 只约束全文分支；筛选范围约束两路。
- 内容证据与关联账号两种结果视图。账号按本次命中内容的作者归组，不是全库画像。
- 搜索本身不调用 Chat；选择 1–10 条证据后点击“生成引用回答”，才使用显式配置的 Chat 默认 Sequence。请求/响应由 Zod 校验。来源材料是不可信数据，不授权模型执行工具。
- 每次搜索保存 10 分钟证据快照。生成前后都检查来源 revision/projectionRevision 和删除状态；未知引用、失效快照、改动来源、无效 JSON 拒绝展示。只校验引用存在性，不能保证模型每个结论均被引文支持，界面说明这一边界。
- 高亮私有标记转为 React 文本与 `<mark>`，不解释来源 HTML。结果 JSON 导出标注“本次候选”，不冒充全库导出。
- 语义排名不提供虚假的全库页数；准确总量与翻页保留在原账号/内容大盘。

全文失败返回明确错误；语义分支失败则标明“本次仅全文”，不伪装混合结果。严格 HanLP 调用失败不会改用 jieba/bigram。明确选择的连续短语使用 ES 原文分析字段，不调用 HanLP；它不是故障时自动切换的替代方案。

## 数据中心操作顺序

1. 在 Agent 中心配置并验证 Embedding Provider / Sequence，显式设为 Embedding 业务默认。Chat 业务默认用于可选回答。模型、维度必须符合现有 Embedding 锁；不会偷偷选择目录第一项。
2. 正常 deploy 执行 migration 086，建立队列、租约/预算/快照表与 outbox 触发器，并部署独立 retrieval Worker。默认后台向量化关闭；不会自动扫描历史全库。迁移锁等待上限 2 秒，锁冲突应重试部署，不无限阻塞已有写入。
3. 在“向量化与 RAG 索引”保存并发/每日预估 token 预算并启用；这只允许处理已入队增量，不隐式开始全库回填。
4. 如需严格重建全文及已存向量的 ES 投影，使用原“搜索索引重建”。该流程从 PostgreSQL 重建、追增量并原子切换 alias，不删除当前可读索引。**ES 重建不等于调用模型生成向量。**
5. 点击“全库向量化 / 补齐索引”，阅读范围和费用说明并确认。后台开始 UUID 游标扫描。启动会检查在线 Worker、Embedding 维度、目标 ES 映射及 HanLP；失败不创建任务，不调用替代分词器。
6. 查看在线 Worker、等待/执行/已处理/需重试、今日预留 token、全库扫描阶段和最近失败。计数最多缓存 30 秒。可暂停新任务；取消回填也会暂停队列，保留已有任务供恢复。失败投影解隔离后可显式重试。

全库范围是已入库 canonical 的**可检索文本**：标题+正文至少 24 字符。不会新采集图片、视频，不自动做 OCR/ASR。短文本仍可全文检索。只有真正入 canonical/outbox 的外部平台结果、清洗结果、数据产品采集结果才进入向量队列；纯转发但未规范化入库的响应不会自动成为可搜索数据。

当前 chunk schema 为 v2，增加平台类型/作者/标签过滤与 `embeddingSpace`（模型＋维度）；content 维持 v6。chunker v2 为超长无标点文本增加有界切分。历史旧 chunker 需要重切、重新向量化，未来仅 ES 投影变化应复用 PostgreSQL 向量。模型升级需新空间/索引、分批迁移与切换，不能把不同模型向量混算。

## 后台处理与隔离

canonical 入库事务写入既有 outbox，触发器只对相同 record ID 合并一个持久任务，记录最高 projection revision；事务回滚时队列同步回滚。**它增加一次短小的数据库写入成本，并非零开销**，但同步响应路径不执行切片、HanLP、模型调用或 ES bulk。原公开转发、鉴权、计费和 MX-H2I 链路不依赖 retrieval Worker 就绪。

独立流程：领取 record → 切片并保留来源修订 → Embedding → PostgreSQL 持久向量 → 严格 HanLP → ES。ES 失败不会重付已落库向量的模型费用；同文本的 revision 更新可复用向量。崩溃恰好发生在模型已计费但结果尚未落库时，重试可能再次产生费用，这是至少一次交付的限制。

- PostgreSQL `FOR UPDATE SKIP LOCKED`、唯一 record 任务、3 分钟租约、30 秒续租、随机租约 token；完成/失败只承认未失效的持有者。新 revision 抵达运行中任务会递增 version，旧任务结束后重新待处理，不吞掉更新。
- 默认 K8s 2 个 retrieval 副本、每副本同时处理 1 个 record；全局并发默认 2，上限 16，不能只改 UI 就超过实际 Worker 副本数。滚动更新、PDB 保留一个副本。Compose search profile 也包含独立 retrieval 服务。
- 历史任务优先级低于增量；每 5 秒最多播种 250 条。回填完成按该轮播种的 version 判断，持续新入库不会让历史任务永远无法结束。
- 失败退避，普通失败最多 8 次进入隔离；预算、暂停、未配置模型等等待条件不会耗尽业务失败次数。Worker 丢失租约停止发起后续阶段；当前来源锁和 ES 外部版本防止旧写覆盖新修订。
- 删除有独立优先标记，暂停/Embedding 不可用时仍可处理删除。搜索还会回读主库验证，ES 延迟不能复活删除记录。
- 预算按调用前预估 token 预留，包含失败尝试，不等于供应商精确 token 或金额硬上限；供应商限额仍需单独设置。达到预算保留队列，次日按 UTC 恢复。

## 读写分离与 100 QPS

已实现工作负载/连接池隔离：原 Public API 与原查询池不变；新增检索池每 Admin 实例最多 4 连接，Worker 每实例最多 5，连接等待 1.5 秒、SQL 5/15 秒。共享数据库的 CPU、I/O、WAL、ES heap 仍会相互影响，这不是物理数据库隔离。

暂不引入 PG 只读副本：队列写入、预算、租约和来源失效校验需要主库的一致性。后续可把统计、历史资料、候选 hydration 移至副本；**最终引用有效性校验仍走主库**，或采用可证明已追平的 LSN 门槛。

前台检索全局 16 个租约槽，生成回答 2 个；API 本地还有 16 个检索准入限制，繁忙返回 429，不无限等待。HanLP 查询词缓存 256 项/60 秒，查询向量缓存 256 项/60 秒并合并相同在途请求；配置切换导致 router 变化时清空向量缓存。ES 候选范围 100、kNN candidates 200、ES 查询预算 4 秒、query embedding 8 秒、回答模型 20 秒。

**尚未证明 100 QPS。** 100 次普通公开请求/秒不等于 100 次模型检索/秒，更不等于 100 条待索引记录/秒。应分别测：

| 场景 | 必须测的实际负载 | 放量前的依据 |
|---|---|---|
| 原接口 100 QPS | 存储命中、外部转发、批量返回、幂等重放的真实比例 | P95/P99、错误率、鉴权/计费一致性 |
| 增量写入 | QPS × 每响应记录数 × 变化比例 × 每记录切片数 | 每秒处理量大于到达量，最老待处理年龄不持续增长 |
| 高级检索 | 全文/语义比例、query cache 命中率、ES 分片/过滤分布 | 16 / 平均请求秒数只是并发理论上限，不能当吞吐保证 |
| 全库回填并行 | 正常业务持续读写 + 低优先级向量任务 | API 延迟、PG WAL/连接、ES 拒绝率、HanLP 429、模型限速 |
| 故障恢复 | 杀 Worker、PG 连接丢失、ES/HanLP/模型失败、删除与更新交错 | 不吞更新、不重复实体、不引用旧数据，恢复后队列可消退 |

先做 10→25→50→100 QPS 的独立压测窗口，再调整副本和额度。普通接口 100 QPS 达标不代表 RAG 100 QPS；回答生成仍为独立低并发通道。全库预估至少统计有效文本数、平均切片、抽样预估 token、模型额度/吞吐和索引空间，不根据“191.7 万记录”直接猜总费用。

2 个 Worker 是进程容错，不是宿主机/数据库高可用。当前 Internal 是单节点部署：PG 主从/备份、ES 副本跨节点、故障域、存储恢复目标需另立基础设施计划；PDB 无法防止单机断电。

## HanLP 容量

检查 mx-common 当前实现：每模型进程以 semaphore 控制推理，默认单 forward；Torch/OMP/MKL 默认 16 线程，部署限额 16 CPU / 8 GiB。**128 核/100GB 宿主机不代表单模型会占满所有 CPU**，还要扣除 PG、ES、其它任务资源。

本次 Worker 把最多 16 个片段请求合并为 HanLP batch，严格校验 provenance，错误重试/隔离，不降级分词。增量全文 projector 仍独立；现有 ES 查询分析和高级 AND/OR 查询也会使用 HanLP，不能假设“读取绝不用 HanLP”。缓存可减少重复查询分析。

扩容应先测单模型 batch 长度与 P95，再评估多个独立模型副本。不要直接提高同一模型实例的并发 forward（线程安全与内存竞争尚未证明），也不要把全库 bulk 并发直接设成 128。本次未改 mx-common 的线上副本或线程参数。

## 回滚注意

先暂停 retrieval 并保留 PostgreSQL 队列/向量，不删除新表或索引。不要单独回滚到旧 projector 镜像并放任它启动：旧版内置全库 embedding 循环，没有本次预算与手动启用门槛。优先回滚 UI/API、保留已验证的新版 projector/retrieval；完整回滚要先评估旧循环、索引 alias 和 chunker 兼容性。部署仅准备结构与增量服务，不把回滚当作隐式全库重跑。
