# 高级搜索、后台向量化与容量边界

## 2026-09-30：自建 Embedding 的查询优先与合批

`mx-base/mx-embedding` 原先在整个后台请求期间持有锁，同时到达的搜索会立即得到 429。新版本使用有界队列和跨请求 micro-batch：RAG 查询在后台批次之间优先，连续四个查询批次后让后台推进；单次 GPU forward 无法抢占。Hub 明确传递 interactive/background HTTP 调度提示，经业务默认 Embedding Sequence 路由，不改变请求正文、模型、维度或查询指令。不启动重建、不增加预算、Worker 并发或模型进程，MX-H2I 登录和联网不变。

先升级模型服务，再升级 Hub Admin 和 Worker；旧服务忽略提示、旧客户端按后台处理，支持滚动部署。模型服务默认仍每批最多 4 文本、单请求最多 16 文本/8192 token、512 维，查询总时限 6 秒，Hub 查询 embedding 保留 8 秒总时限。满队列/超时仍可能限流，不能保证服务在显存不足或单次 GPU forward 过慢时可用。其余 ES/网络失败仍需独立定位。

压测命令、计数含义和共享 vLLM 显存注意事项见 [mx-embedding 运维](../../../mx-base/mx-embedding/README.md#吞吐与查询延迟验收)。同时记录 Hub 全文/RAG 的端到端 P95、成功率及 Worker 各阶段耗时，不能把模型服务 QPS 当作入库记录/秒或日增量完成率。

## 2026-09-30 后续：自建模型自动增量与负荷保护

后台向量化启用且未暂停时，canonical 新增/更新通过现有 outbox 事务触发器自动合并入队；无需每日手动启动。固定历史初始化保持一次明确操作，后续增量优先。截图中的日预算与当日预留均为 1,000,000 token，在线 Worker 为 2、任务并发上限为 1：增量已经触及预算，并且最多一条记录同时执行。110,519 条待处理不能仅凭截图全归因于算力不足；也可能包括预算延期、历史任务、重试与待投影。2 条「需重试」应查看具体失败码，不能用提高预算掩盖。token 是近似工作量，不是记录数或算力配额。

新增明确选择的 **按负荷持续处理（自建模型）**：

- Admin `dailyTokenBudget: 0` 表示继续累加每日预留量，但不因每日 token 总量停止增量。正数仍为原日限额（1,000–10 亿）；每天 UTC 00:00 / 北京时间 08:00 切换统计日。它不自动修改模型、Provider/Sequence、并发上限、初始化额度或运行范围。
- 保存持续模式或提高日额度后，预算延期的 pending 任务重新进入调度；不重置已消耗用量，不启动历史扫描，不改动来源及现有向量。暂停/关闭仍阻止新模型预算预留；初始化仍按固定版本清单和独立总额度执行。
- Worker 每约 5 秒只读采样主机 CPU 时间差与内存可用量，Linux 使用 `MemAvailable` 避免把文件缓存误当内存耗尽；若可读取 cgroup v2，另测容器 CPU 配额使用与内存上限。CPU ≥85% 或内存 ≥90% 时暂缓新工作；CPU ≤70%、内存 ≤80% 且连续两个样本稳定后自动继续。缺少必需主机指标时等待，首次启动先采样。检查发生在领取前及记录内各阶段/模型批次之间；已发出的调用正常收尾。
- 模型/依赖可识别的 429、502、503、504 会让该 Worker 退避 30 秒起、最长 5 分钟。直接 429 或 ProviderRouter 全部返回 429 的任务继续自动重试，不计入永久失败次数；其他依赖错误仍沿用原有有界重试。退避只影响后台 Worker，不更改公共请求路由/重试或 Provider 配置。
- 集群数据库租约及配置并发上限继续生效，每个 Worker 一条记录。资源等待不会消耗 token 或永久失败次数；任务保留、稍后再调度。删除投影继续，不受此负荷门槛阻断。UI 提示日预算等待、实际可承接并发、主机/容器指标、资源恢复状态及优先队列/普通历史回填待完成量。队列拆分按调度优先级统计；优先队列也可能已被初始化清单覆盖，不等同于额度归属。

上线步骤：正常迁移执行 `120_retrieval_continuous_budget.sql`，仅放开 0 的含义，**不修改现有日额度或启用状态**。等待 Admin 与全部在线 retrieval Worker 更新并上报新指标（旧/过期 Worker 会阻止启用持续模式），在 数据中心 → 向量化 选择持续处理，保持「启用后台向量化」且取消暂停，保存一次即可。无需再次点全库向量化。先按现有并发观察；只有在已测资源与依赖余量允许时调整上限，实际并发不超过在线且可承接任务的 Worker 数。

日清目标依赖平均处理速度高于平均新增速度，且有余量消化积压；解除日限额不能创造算力。当前监测能看到 Worker 主机与可读取的容器资源，**不代表远端模型 GPU、其他节点、ES 磁盘或数据库 I/O 的完整容量**。远端依赖仍以其限流/错误和已有等待指标判断；高负荷暂停会延长追平时间。实际 ETA 仍以已确认的完成进度采样，不伪造保证。涉及的内核含义参考 [cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html) 与 [Node.js OS CPU 时间](https://nodejs.org/api/os.html#oscpus)。

## 2026-09-30 后续：默认 RAG 与 Unicode 摘要修复

高级搜索按用户最新要求改为 **RAG → 全文 → 全部**，页面默认 RAG：

| 页面选项 | API mode | 行为 |
|---|---|---|
| RAG（默认） | `semantic` | query embedding + 向量 kNN；仅检索已有向量，不混入全文候选 |
| 全文 | `fulltext` | Elasticsearch 全文检索；AND/OR 依照完整词项，保留短语与模糊纠错 |
| 全部 | `hybrid` | RAG 与全文两路候选经当前版本核验后，以 RRF 合并排名；任一路可独立命中 |

「全部」不是先 RAG 后全文的串行顺序，也不表示导出全库。这里 RAG 是用户选择的语义检索入口名称，生成引用回答仍需要选择证据后明确点击。打开页面或切换模式不会调用模型；仅显式搜索时才执行对应检索。原有 API 调用省略 `mode` 仍按 `fulltext` 处理，以免既有调用者隐式增加模型调用。仅语义失败明确报错；全部模式的语义分支不可用时仍保留明确的全文降级提示。

修复一个会随候选内容变化而出现 `internal_error` 的缺陷：原实现用 UTF-16 `slice` 截断 300 单位预览与 1600 单位片段，恰好切开 emoji/扩展汉字时产生孤立代理码，导致 `retrieval.search_snapshots.evidence` 写入 PostgreSQL jsonb 被拒绝（`22P02` / `Unicode low surrogate must follow a high surrogate.`）。现在在边界保留完整字符，仍遵守原长度上限，来源正文不修改；给引用回答的 1000 单位片段也使用同样规则。查询与范围标识中的 NUL/非法代理码在入参阶段返回 400，不再到快照写入时才失败。

通过本地 PGlite PostgreSQL 内核复现旧截断的 `22P02`，并验证三种模式的真实 jsonb 快照写入、读取、引用回答与租约释放。该验证使用合成数据与检索/模型替身，不连接生产服务。用户随后提供的 Hub Admin 日志确认，截图请求 `01ac2371-d7d2-4cc9-bc40-422378db2977` 及另一请求 `f13ab22f-39b9-4501-93fe-47da9ecfe946` 均为相同的 `22P02` / `Unicode low surrogate must follow a high surrogate.`，与本地复现一致。此次仅更新 Hub 高级搜索及回归，不部署、不重建索引，不改变 MX-H2I 登录或联网。

## 2026-09-30：完整词召回与向量质量对照

入口是 **数据浏览中心 → 高级搜索**。数据中心的「检索与筛选 / Balanced」仍走原有 canonical 搜索，不调用本高级搜索 API。以下改动只作用于 Admin 的 `/internal/v1/admin/data-browser/advanced/*`，不改变公开搜索、模型配置、后台预算、数据或 MX-H2I 登录/联网。

- 修正 AND/OR 下的中文误召回：HanLP 完整词项为主要路径；原文 `title/body` 只以连续短语独立召回。此前并列的 standard `multi_match` 会把中文拆为单字，长文中散落的「售、后、退、款、困、难」可能满足 AND。现在不再以这种路径放行；不删除合法的单字查询，也保留中英混合词项。模糊纠错限定在完整词字段。
- 高亮对每个完整查询词或整句短语建立原文 `match_phrase`，不把 HanLP 预分词字段的不同字符偏移套回原文。仅语义命中没有字面高亮是正常情况；模糊纠错产生的变体也可能没有精确词项高亮。
- 增加「仅语义（向量对照）」模式 `mode: semantic`：只走 query embedding 与 kNN，不调用全文分支或 HanLP。服务不可用时明确报错，不自动改成全文；现有 hybrid 仍可明确降级到全文。三种模式沿用同一硬筛选、当前版本/删除校验、证据快照和按需引用回答。
- 增加可选 `minSimilarity`（余弦相似度，−1 到 1；默认 `null`）。它传入 kNN 的 `similarity`，融合与快照前再次核对，不拿 RRF 分数当相似度。UI 留空不设下限；全文模式不接受非空下限。混合模式下，下限只约束向量分支，全文候选仍可独立进入结果。不存在对所有模型都有效的默认阈值，也不显示相关概率。
- 「本次检索依据」显示实际查询词、融合前经版本核验并去重的两路候选数、交集、模型/维度和本次阈值；JSON 导出保留实际模式、降级和检索依据。记录数只描述本次有界候选，不是全库向量覆盖率。区分语义未请求、不可用、没有有效候选和有候选；ES 成功但零语义候选时明确提示。
- 查询词项超过 64 个时明确拒绝，避免静默截断 AND 条件。候选上限保持 100；不增加模型调用次数，不引入付费重排，不为了凑满页数放宽条件。结果标题改为「候选证据」，不把进入 top-K 等同于相关性已验证。

这些是查询侧改动，复用现有 `content-v6` / `chunk-v2` 字段及已存向量；不需要重新 embedding、索引迁移或全库重建。引用存在性仍不等于结论被来源支持。

### 如何比较质量

1. 选一个向量覆盖已确认的数据集，固定日期/平台/条件和候选数；同一问题分别运行全文、仅语义、混合，分别导出结果。比较时记录模型空间、阈值、查询时间；持续入库和不同覆盖范围会影响结果。
2. 先准备 10–20 个已知答案的问题，再扩展为 100–200 个带人工相关记录标注的问题。包含精确词、中文同义改写、长文、无答案与范围限制。下面是**合成测试示例**，不是生产检索结果：

| 问题 | 应相关的例子 | 应排除的例子 |
|---|---|---|
| 售后拖延、退款困难 | 商家的售后持续拖延，退款困难 | 销售后，拖车延误；退场贷款，困境难解 |
| 退货后迟迟收不到钱 | 东西早已寄回，十天了钱还没有到账 | 仅讨论贷款、经济困境的新闻 |

3. 检查前 10 条相关率、已标注相关记录的 Recall@20、排序质量及请求耗时。无答案问题也需人工判断；不能认为 kNN 返回了候选就表示库里有答案。
4. 仅在同一模型与标注集上调整相似度下限，记录误召回减少和相关内容丢失的取舍。下限过高会漏掉同义改写；混合模式仍可能有低相似度但正确的全文命中。用「仅语义」隔离观察这一影响。
5. 最后选证据生成回答，逐条核查引用与结论。检索和回答分开评分，测试替身与单元测试不代替真实模型的效果验收。

本地回归包括查询约束、高亮 DSL、向量独立检索、相似度门槛、快照证据、失效来源、空结果和故障降级。另有 `tests/server/advanced-search-es.integration.test.mjs`：仅在显式设置 `MX_RETRIEVAL_TEST_ES_URL` 为可丢弃的本地 ES 时运行，创建随机测试索引并清理；用合成分词/向量证明旧查询误召回、实际 ES 完整词高亮及余弦过滤。不读取生产环境连接、不调用模型或 HanLP。当前机器 Docker 未运行，该 ES 集成检查按环境跳过；尚不能据此宣称生产质量达标。

## 两个入口

数据浏览中心新增“高级搜索” Tab，原账号、内容、热点及总量/导出保持原路径。

- 全文：AND / OR / 连续短语，可选 ES 模糊纠错，标题/正文高亮。AND/OR 由受控 DSL 构造，用户输入不作为任意 ES 查询语法执行。
- 语义 + 全文（RAG）：两路各取最多 100 个候选，向量路预过滤平台、数据集、类型、作者、来源标签和日期，按 canonical record 去重后 RRF 融合。AND/OR 只约束全文分支；筛选范围约束两路。
- 内容证据与关联账号两种结果视图。账号按本次命中内容的作者归组，不是全库画像。
- 搜索本身不调用 Chat；选择 1–10 条证据后点击“生成引用回答”，才使用显式配置的 Chat 默认 Sequence。请求/响应由 Zod 校验。来源材料是不可信数据，不授权模型执行工具。
- 每次搜索保存 10 分钟证据快照。生成前后都检查来源 revision/projectionRevision 和删除状态；未知引用、失效快照、改动来源、无效 JSON 拒绝展示。只校验引用存在性，不能保证模型每个结论均被引文支持，界面说明这一边界。
- 高亮私有标记转为 React 文本与 `<mark>`，不解释来源 HTML。结果 JSON 导出标注“本次候选”，不冒充全库导出。
- 语义排名不提供虚假的全库页数；准确总量与翻页保留在原账号/内容大盘。

全文失败返回明确错误；语义分支失败则标明“本次仅全文”，不伪装混合结果。严格 HanLP 调用失败不会改用 jieba/bigram。明确选择的连续短语使用 ES 原文分析字段，不调用 HanLP；它不是故障时自动切换的替代方案。

## 数据中心操作顺序

1. 在 Agent 中心配置并验证 Embedding Provider / Sequence，显式设为 Embedding 业务默认。Chat 业务默认用于可选回答。模型、维度必须符合现有 Embedding 锁；不会偷偷选择目录第一项。
2. 正常 deploy 执行 migration 086、087，建立队列、租约/预算/快照表、固定初始化清单与 outbox 触发器，并部署独立 retrieval Worker。等待 Admin 和全部 retrieval Worker 完成升级后再点击新初始化任务。默认后台向量化关闭；不会自动扫描历史全库。迁移锁等待上限 2 秒，锁冲突应重试部署，不无限阻塞已有写入。
3. 在“向量化与 RAG 索引”保存并发/每日预估 token 预算并启用；这只允许处理已入队增量，不隐式开始全库回填。
4. 如需严格重建全文及已存向量的 ES 投影，使用原“搜索索引重建”。该流程从 PostgreSQL 重建、追增量并原子切换 alias，不删除当前可读索引。**ES 重建不等于调用模型生成向量。**
5. 设置“本次初始化 token 总额度”，默认 10 亿，0 表示不限额。这是本次任务的累计额度，不按日重置，也不改变每日增量额度。点击“全库向量化 / 补齐索引”并确认后，以单条 MVCC 快照语句保存可检索记录 ID、正文版本和投影版本；清单捕获最多 60 秒，失败整体回滚，不产生半个任务。后台按固定清单扫描，不再扫描变化中的全库。启动检查 Worker、Embedding 维度、ES 映射及 HanLP；失败不开始任务，不调用替代分词器。
6. 查看在线 Worker、等待/执行/已处理/需重试、今日预留 token、全库扫描阶段和最近失败。计数最多缓存 30 秒。可暂停新任务；取消回填也会暂停队列，保留已有任务供恢复。失败投影解隔离后可显式重试。

全库范围是已入库 canonical 的**可检索文本**：标题+正文至少 24 字符。不会新采集图片、视频，不自动做 OCR/ASR。短文本仍可全文检索。只有真正入 canonical/outbox 的外部平台结果、清洗结果、数据产品采集结果才进入向量队列；纯转发但未规范化入库的响应不会自动成为可搜索数据。

新记录使用每日预算。初始化范围内的记录若发生更新或删除，旧版本显示为“版本变化 · 转增量”，新版本也使用每日预算；这不是“该记录向量化成功”。初始化按“已处理 + 转增量 = 锁定范围”结束，不等待新增数据。捕获阶段的并发可见性差异在分批入队时再次校验。已在途的旧版本模型调用仍可能计费；新调用不会借用旧版本额度。额度不足可在原任务更新额度并继续，不重建清单。

每日预算耗尽的增量留在队列，UTC 次日（北京时间 08:00）后可继续；当天提高每日预算并保存也会唤醒预算等待任务。初始化额度单独累计，所以初始化完成后无需把每日预算“改回”，也不会因历史消耗导致当天增量停摆。升级前任务继续采用原规则。详见 [初始化与容量检查](initialization-and-capacity.md)。

当前 chunk schema 为 v2，增加平台类型/作者/标签过滤与 `embeddingSpace`（模型＋维度）；content 维持 v6。chunker v2 为超长无标点文本增加有界切分。历史旧 chunker 需要重切、重新向量化，未来仅 ES 投影变化应复用 PostgreSQL 向量。模型升级需新空间/索引、分批迁移与切换，不能把不同模型向量混算。

## 全文重建在 `extensions` 解析失败时的恢复

2026-09-17 修复：历史扩展字段可能包含超长正文或序列化 JSON。`flattened`
把叶子值作为一个关键词索引，未设置长度上限时可能触及 Lucene 的 32,766 字节限制，
产生 `document_parsing_exception`。中文、emoji 及控制字符转义会让错误预览特别长；
仅凭预览不能判断是非法 JSON，需查看底层 `caused_by`。

- content v6 的 `extensions` 增加 `ignore_above: 4096`。超限叶子值不参与该字段的
  关键词检索/聚合，原有投影值仍完整保存在 ES `_source`，PostgreSQL canonical、
  revision 和原始归档均不改写。标题、正文的全文索引和严格 HanLP 分词保持原逻辑。
  此处不是截断内容，也不是跳过失败记录。
- 这是可原位更新的映射参数，不升级 schema、不清空历史进度。恢复已有的未完成索引时，
  先更新其映射，再从 PostgreSQL 保存的最后成功批次游标继续；仅更新模板不会修复已有索引。
  若映射更新冲突，任务停止，保留游标和当前读别名。
- 全量重建和增量 projector 的错误摘要保留索引、记录 ID、HTTP 状态及优先排列的
  底层原因，省略巨大的值预览，避免 2,000 字符的持久化上限截掉诊断信息。

上线修复后，由操作员在数据中心重新检查并显式启动严格重建。同一索引槽和同一分词
后端的未完成任务会续接已保存的批次；失败批次会重放，不承诺从单条失败记录精确续接。
首轮完成前不会把读别名切到部分索引。不要为此清空 PG 记录、删除当前服务索引或改动
MX-H2I 登录/网络配置。截图中的磁盘约 90% 使用率是另一个容量问题：重建仍需容纳第二份
投影，应先确认预检空间；本次映射修复不会释放磁盘，也不会降低 ES 水位保护。

参考：[Elastic flattened 参数](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/flattened)、
[ignore_above 与字节长度限制](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/ignore-above.html)。

## 后台处理与隔离

canonical 入库事务写入既有 outbox，触发器只对相同 record ID 合并一个持久任务，记录最高 projection revision；事务回滚时队列同步回滚。**它增加一次短小的数据库写入成本，并非零开销**，但同步响应路径不执行切片、HanLP、模型调用或 ES bulk。原公开转发、鉴权、计费和 MX-H2I 链路不依赖 retrieval Worker 就绪。

独立流程：领取 record → 切片并保留来源修订 → Embedding → PostgreSQL 持久向量 → 严格 HanLP → ES。ES 失败不会重付已落库向量的模型费用；同文本的 revision 更新可复用向量。崩溃恰好发生在模型已计费但结果尚未落库时，重试可能再次产生费用，这是至少一次交付的限制。

- PostgreSQL `FOR UPDATE SKIP LOCKED`、唯一 record 任务、3 分钟租约、30 秒续租、随机租约 token；完成/失败只承认未失效的持有者。新 revision 抵达运行中任务会递增 version，旧任务结束后重新待处理，不吞掉更新。
- 默认 K8s 2 个 retrieval 副本、每副本同时处理 1 个 record；全局并发默认 2，上限 16，不能只改 UI 就超过实际 Worker 副本数。滚动更新、PDB 保留一个副本。Compose search profile 也包含独立 retrieval 服务。
- 历史任务优先级低于增量；每 5 秒最多播种 250 条。回填完成按该轮播种的 version 判断，持续新入库不会让历史任务永远无法结束。
- 失败退避，普通失败最多 8 次进入隔离；预算、暂停、未配置模型等等待条件不会耗尽业务失败次数。Worker 丢失租约停止发起后续阶段；当前来源锁和 ES 外部版本防止旧写覆盖新修订。
- 删除有独立优先标记，暂停/Embedding 不可用时仍可处理删除。搜索还会回读主库验证，ES 延迟不能复活删除记录。
- 预算按调用前预估 token 预留，包含失败尝试，不等于供应商精确 token 或金额硬上限；供应商限额仍需单独设置。每日增量额度按 UTC 恢复；初始化额度为任务累计值，达到后需显式提高或改为 0。二者均保留队列。

## 读写分离与 100 QPS

已实现工作负载/连接池隔离：原 Public API 与原查询池不变；新增检索池每 Admin 实例最多 4 连接，Worker 每实例最多 5，连接等待 1.5 秒、SQL 5/15 秒。共享数据库的 CPU、I/O、WAL、ES heap 仍会相互影响，这不是物理数据库隔离。

暂不引入 PG 只读副本：队列写入、预算、租约和来源失效校验需要主库的一致性。后续可把统计、历史资料、候选 hydration 移至副本；**最终引用有效性校验仍走主库**，或采用可证明已追平的 LSN 门槛。

前台检索全局 16 个租约槽，生成回答 2 个；API 本地还有 16 个检索准入限制，繁忙返回 429，不无限等待。HanLP 查询词缓存 256 项/60 秒，查询向量缓存 256 项/60 秒并合并相同在途请求；配置切换导致 router 变化时清空向量缓存。ES 候选范围 100、kNN candidates 200、ES 查询预算 4 秒、query embedding 8 秒、回答模型 20 秒。

**尚未证明 100 QPS。** 100 次普通公开请求/秒不等于 100 次模型检索/秒，更不等于 100 条待索引记录/秒。应分别测：

| 场景 | 必须测的实际负载 | 放量前的依据 |
|---|---|---|
| 原接口 100 QPS | 存储命中、外部转发、批量返回、幂等重放的真实比例 | P95/P99、错误率、鉴权/计费一致性 |
| 增量写入 | QPS × 每响应记录数 × 变化比例 × 每记录切片数 | 每秒处理量大于到达量，最老待处理年龄不持续增长 |
| 高级检索 | 全文/语义比例、query cache 命中率、ES 分片/过滤分布 | 16 / 平均请求秒数只是并发理论上限，不能当吞吐保证 |
| 全库回填并行 | 正常业务持续读写 + 低优先级向量任务 | API 延迟、PG WAL/连接、ES 拒绝率、HanLP 429、模型限速 |
| 故障恢复 | 杀 Worker、PG 连接丢失、ES/HanLP/模型失败、删除与更新交错 | 不吞更新、不重复实体、不引用旧数据，恢复后队列可消退 |

先做 10→25→50→100 QPS 的独立压测窗口，再调整副本和额度。普通接口 100 QPS 达标不代表 RAG 100 QPS；回答生成仍为独立低并发通道。全库预估至少统计有效文本数、平均切片、抽样预估 token、模型额度/吞吐和索引空间，不根据“191.7 万记录”直接猜总费用。

2 个 Worker 是进程容错，不是宿主机/数据库高可用。当前 Internal 是单节点部署：PG 主从/备份、ES 副本跨节点、故障域、存储恢复目标需另立基础设施计划；PDB 无法防止单机断电。

## HanLP 容量

检查 mx-common 当前实现：每模型进程以 semaphore 控制推理，默认单 forward；Torch/OMP/MKL 默认 16 线程，部署限额 16 CPU / 8 GiB。**128 核/100GB 宿主机不代表单模型会占满所有 CPU**，还要扣除 PG、ES、其它任务资源。

本次 Worker 把最多 16 个片段请求合并为 HanLP batch，严格校验 provenance，错误重试/隔离，不降级分词。增量全文 projector 仍独立；现有 ES 查询分析和高级 AND/OR 查询也会使用 HanLP，不能假设“读取绝不用 HanLP”。缓存可减少重复查询分析。

这不是把字符串拼成一篇：HTTP 发送 `texts: string[]`，Python 调用 `_tokenizer(inputs)` 并逐项返回；模型内部还可分 mini-batch。当前向量 Worker 每次领取一个 record，同一 record 最多 16 个 chunk 合批；大量单 chunk 短记录可能仍是每个模型请求一个字符串，不存在跨 Worker 的全局批合并。两副本和模型往返延迟可能先于 HanLP 成为瓶颈，需用只读诊断及实际小批端到端时间区分。

扩容应先测单模型 batch 长度与 P95，再评估多个独立模型副本。不要直接提高同一模型实例的并发 forward（线程安全与内存竞争尚未证明），也不要把全库 bulk 并发直接设成 128。本次未改 mx-common 的线上副本或线程参数。

## 回滚注意

先暂停 retrieval 并保留 PostgreSQL 队列/向量，不删除新表或索引。不要单独回滚到旧 projector 镜像并放任它启动：旧版内置全库 embedding 循环，没有本次预算与手动启用门槛。优先回滚 UI/API、保留已验证的新版 projector/retrieval；完整回滚要先评估旧循环、索引 alias 和 chunker 兼容性。部署仅准备结构与增量服务，不把回滚当作隐式全库重跑。
