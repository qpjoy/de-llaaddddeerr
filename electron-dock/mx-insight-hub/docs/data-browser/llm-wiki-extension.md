# LLM Wiki 扩展预案

2026-09-16。当前交付是 RAG，本页只规划后续扩展，不启动 Wiki 编译任务。

[Karpathy 的 llm-wiki 原始方案](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 将原始材料、持续整理的知识页和处理指令分开，强调在摄入时维护知识，而不仅在查询时拼接片段。它可以减少反复组织材料的工作；是否优于当前 RAG，要在 Hub 的实体歧义、事件变化和来源撤回任务上实测，不能当作已验证结论。

Hub 的拟议结构：

1. **原始事实**：继续以 canonical record/revision、lineage 和来源归档为准。网页/评论中的指令属于材料，不拥有执行权限。
2. **派生知识页**：新增独立 `knowledge.pages` / `page_versions`，包含 topic/entity key、正文、claims、引用的 record+revision、有效时间、编译模型/提示/策略版本、审核状态和冲突说明。不能回写覆盖 canonical。
3. **依赖关系**：`knowledge.dependencies` 记录页面→原始修订、页面→页面，更新/删除事件只让受影响页面失效并进入独立编译队列；限制依赖深度，检测循环。不允许检索快照的 10 分钟留存替代长期证据归档。
4. **受控编译**：Node.js 的独立 Worker，预算/租约/重试复用本次模式但独立任务类型和额度。摄入→取原文→提取 claims→冲突检查→引用校验→候选版本→发布。未来采用 LangGraph.js checkpoint，可在人工审核处暂停；无需让普通搜索承担完整 Agent 循环。
5. **联合检索**：本次输出保留 `evidenceKind='canonical'`、`evidenceVersion='hub.canonical-evidence.v1'` 与来源修订。未来新增 `wiki-page` evidence contract，以单独召回器加入融合结果，并追溯到原始事实。UI 必须区分来源事实与模型综合页。

删除/权限变更优先于重新编译：先隐藏失效 Wiki 版本、删除或屏蔽对应索引，再排队重建，不能在等待模型期间继续公开旧结论。历史知识页保留审计，但不能继续作为有效证据。

先选一个有明确来源范围的小专题：比较关键词、当前混合 RAG、RAG+Wiki 三组在同一批问题上的证据召回、事实正确率、引用支持率、更新延迟、冲突保留和总 token 成本。长尾单次查询可能不值得预编译；反复查询、稳定专题、跨文档总结更适合作为候选。通过评测才扩大，不迁移原有转发和登录链路。

本次不引入 Wiki 页面表、不自动合并账号、不自动发布热点结论，也不将知识页直接送入在线 API 路由决策。
