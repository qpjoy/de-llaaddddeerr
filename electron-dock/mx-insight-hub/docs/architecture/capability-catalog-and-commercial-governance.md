# 能力目录、采购成本与客户套餐协同方案

- 日期：2026-09-23。
- 状态：**Implemented locally**。管理流程、增量迁移和回归已实现；尚未执行生产迁移或部署。第 11 节记录实际落地边界。
- 范围：MX Insight Hub。保留现有 API、权限、价格快照、账本、游标和幂等合同；MX-H2I / Launcher 的登录、联网和部署依赖不变。
- 依据：当前代码、用户反馈及文末关联文档。截图用于识别体验问题，不作为生产账务已对账的证据。

## 1. 结论

沿用现有计费内核，补齐统一能力登记和管理工作流。**不需要先重建所有业务分类，也不应让分类直接决定价格、授权或调用路由。**

Hub 已有采购成本与客户售价分账、不可变套餐版本、消费者级套餐分配、租户钱包、Key 权限快照、逐请求幂等和上游调用证据。问题主要是产品、接口、授权、费率模板与数据源清单各自维护映射，新增能力容易只接通其中几处。现有统一采购价功能也主要是批量复制价格，尚不是可继承且能保留例外的供应商基础价方案。

目标管理流程：接入一次能力 → 登记接口/来源/计量规则 → 审阅采购与销售价格 → 发布产品模板 → 为客户选择套餐和授权包 → 按既有链路签发或更新 Key。客户只看到 Hub 服务和成交价；供应商身份、采购价、凭据与路由证据留在受限管理面。

## 2. 为什么一次请求出现多行余额流水

当前页面逐行展示 `credit_ledger_entries`，不是逐笔消费摘要。通常一笔付费请求包含两步：

| 步骤 | 可用余额变化 | 冻结余额变化 | 含义 |
| --- | ---: | ---: | --- |
| 请求冻结 | -¥0.10 | +¥0.10 | 请求执行前占用额度 |
| 成功扣费 | ¥0.00 | -¥0.10 | 从已冻结额度结算 |
| 确定失败时释放，代替成功扣费 | +¥0.10 | -¥0.10 | 原路退回可用额度 |

例如可用余额 ¥100、冻结 ¥0，冻结后为 ¥99.90 / ¥0.10，成功后为 ¥99.90 / ¥0。实际消费 ¥0.10。不能把两行的 `amount` 相加为 ¥0.20。结果未知时保留冻结，等待既有对账流程；不能因为前端超时就退款或重试。

数据库已有每个 usage request 唯一客户 charge、幂等账本条目，以及每个 charge 唯一终态 capture/release 约束。截图符合正常冻结/结算模式，但仅凭截图不能确认某个账户的全部历史请求都没有重复业务提交或未结算冻结。

建议界面默认显示“消费记录”：按 `customer_charges` 一笔一行，展示业务、平台、调用者、时间、成交金额、状态和 requestId。展开后展示冻结/结算/释放链路；“原始账本”保留独立审计视图，充值和人工调整单独呈现。消费列表必须在服务端按 charge 分页，不能把截断的一页原始流水在浏览器中拼成完整消费。聚合搜索的父请求可作为分组入口，金额只汇总子消费，不新增父扣款。

依据：`src/pages.jsx` 的“余额流水”、`server/stores/memory-store.mjs` 的客户 charge 预留/结算、`migrations/056_commercial_billing_ledger.sql`、`migrations/080_unpriced_customer_operations.sql`。

## 3. 当前已经具备什么，缺什么

| 领域 | 当前已实现 | 本次核对发现的缺口 |
| --- | --- | --- |
| 数据源目录 | 稳定目录 ID、业务分类、覆盖/实施/字段/运行状态分轴；已有只读接入清单 | 目录分类不是执行登记；部分能力仍手动补清单 |
| 上游管理 | 按供应商/operation/release 管理接口、凭据、采购价格、预算、运行状态 | 统一价批量写到各操作；缺少明确的基础价继承与例外保留流程 |
| 客户价格 | 产品费率模板、已发布套餐组合、一次编译为不可变价目表 | 产品模板与其他能力清单分散；缺少完整性检查及直观产品价格概览 |
| 授权 | 租户服务配置、消费者授权、Key 范围与运行配置独立 | 产品快捷勾选与新能力容易不同步；开户跨页操作较多 |
| API/产品 | 标准业务 API、受约束的兼容接口、产品页面及权限过滤 | API、产品入口、文档和价格模板没有共同登记校验 |
| 聚合搜索 | 当前 Key 范围、逐源子请求、受限并发、不透明续页和重放保护 | 来源发现主要按授权/合同，不是完整的运行可用性与价格预检；没有查询前费用预览 |
| 计量 | Hub 请求、上游调用、采购成本、客户 charge、钱包 journal 分开记录 | 管理页面缺少统一解释和关联入口，容易把不同计数当成同一个指标 |

已确认的同步遗漏：小红书费率模板 v2 已包含阅读量与评论，但 `server/data/source-connections.mjs` 的小红书接入条目尚未登记 `social.posts.analytics` 和 `social.comments.list`；`src/pages.jsx` 的“小红书画卷权限”快捷勾选也没有这两项。它们不表示底层 API 未实现，却会让管理员误以为一次产品配置已经包含全部功能。

## 4. 现在怎样方便设置小红书价格

现有产品模板 `xiaohongshu` v2 有六项，均为 **CNY 0.10 / 请求基础价**：

| 业务 | 计费键 |
| --- | --- |
| 笔记搜索 | `social.posts.search` |
| 正文与标签 | `social.posts.resolve` |
| 用户资料/搜索 | `social.users.resolve` |
| 用户笔记 | `social.users.posts` |
| 详情与阅读/曝光指标 | `social.posts.analytics` |
| 一页笔记评论 | `social.comments.list` |

这是当前代码模板，不代表某个线上客户已经绑定该版本，也不代表供应商成本是 ¥0.10。最终成交价还受套餐及租户倍率影响。

1. 在“套餐与配额”选择调用者，用“追加小红书费率”将模板放入当前套餐草稿，保留其他业务费率；或在发布窗口选择“小红书笔记画卷”产品模板。
2. 核对最终价格和额度，发布一个可复用的标准套餐版本。不同客户可直接分配同一已发布版本；只有价格、额度等合同条款不同时才创建差异版本。
3. 按业务需要授予平台及具体 capability，再签发/更新原 Key 的权限快照。套餐存在不等于已经授权。
4. 检查供应商操作的实际运行就绪状态。统一采购价与客户套餐是两个入口，采购价格不需要按客户重复维护。

套餐绑定 **consumer**，同一 consumer 下的 Key 共用价格；钱包、计费模式和专属倍率是 **tenant** 级。若同租户的不同调用者需要不同优惠，应使用各自套餐，不用租户倍率冒充调用者专属折扣。发布新版本不会自动更新旧分配。

当前“未配置客户价格”按免费处理，照常检查授权和用量；不能通过此次目录迁移静默改成拒绝或收费。新开户界面应逐项明确显示“收费 / 明确免费 / 未配置，当前按免费”，让管理员在发布时看见遗漏。

## 5. 建议的关联模型

复用现有对象，在它们之间建立稳定、可校验的关联，而不是再造一个包办所有状态的目录表。

| 对象 | 管什么 | 不直接决定什么 |
| --- | --- | --- |
| 业务分类 / 平台目录 | 场景、平台、负责人、覆盖说明与筛选 | 价格、授权、供应商是否可调用 |
| 业务能力登记 | 稳定 operation ID、对象类型、API 合同、权限要求、计费键、搜索语义 | 客户实际授权和运行开关 |
| 产品模板版本 | 能力集合、产品展示、推荐授权范围、销售费率模板 | 现有 Key 范围和客户合同 |
| 连接器 release / 绑定 | 平台 + 操作 + 请求形状 → 可执行的供应商接口或工作流 | 客户售价 |
| 采购价版本 | 供应商、端点/计费单位、计费判定、币种、证据与生效日期 | 客户售价和消费者授权 |
| 销售套餐版本 / 分配 | 最终客户费率、额度、来源与绑定调用者 | 采购预算、上游凭据和运行放量 |
| 授权与运行策略 | 租户/调用者/Key 的可用范围及服务就绪状态 | 目录分类与历史合同价格 |

这些关系不是一对一：多个公开路径可复用一个能力/计费键；一次能力调用可产生多次上游调用；一个逻辑平台可按业务选择不同供应商；同一能力可属于多个产品。公共目录 capability 与执行 capability 也不能按相同名称自动等同。

第一阶段以已有合同注册表为权威，新增统一的关联 manifest 和校验器，生成产品展示、接入清单、权限快捷选择及费率完整性报告。manifest 只引用注册过的 handler 和 release，不接受任意 URL/脚本。不要直接从 `BILLING_FEATURES` 反推权限：免费能力和兼容权限未必有销售价条目。

运行请求继续使用既有鉴权与计费索引。套餐发布时展开成完整、不可变价目表；未来路由发布时同样编译为固定快照。不要在高并发请求中递归解释产品组合或遍历分类树。

## 6. 采购基础价与计量标准

### 两套价目必须独立

- 采购价：平台运营统一维护，按供应商合同记录；所有客户的调用复用这份依据。允许端点例外、不同币种和不同计费判定。
- 销售价：产品基础模板 + 已审核的客户合同差异，发布时固化。供应商调价不自动改客户售价，客户折扣也不改采购成本。
- 当前系统仅支持按 `request` 的客户计价。按条、任务、token 或其他单位必须另做合同与账本扩展，不在目录迁移中伪装成已支持。

建议把现有“统一采购价目与预算”演进为“供应商基础方案版本 + 端点例外”。批量操作先展示影响清单，默认保留人工例外和手动暂停。新增端点仅在其计量、计费判定及合同适用范围已核验时应用基础方案；未知成本进入待配置，不用 0 或其他接口的价格猜测。

当前预算按供应商、月份及币种累计调用/预留成本，操作策略提供阈值。现有正数 `enforced` 客户冻结有专门的采购/补贴阈值豁免规则；本阶段保留原语义，也保留限速、配额、凭据、熔断、幂等及合同约束。后续如调整预算层级，须独立评审，不能把目录同步顺带变成所有请求的新拦截器。

### 报表至少区分五个量

| 指标 | 权威来源与口径 |
| --- | --- |
| 逻辑业务请求 | 业务 requestId；聚合父/子分开展示，重放单独标记 |
| 实际上游调用 | `external_platform.provider_calls` 中按供应商/端点归属的调用证据，不按 API 访问日志或返回帖子条数推算 |
| 上游确认计费调用 / 成本 | `billed=true` 与成本快照；`billed=null`、未知金额单列，不能当免费或确定已扣费 |
| 客户已结算消费 | 客户 charge 的 capture/charged 金额；免费、冻结、未知、释放分别列示 |
| 钱包账本条目 | hold/capture/release/充值/调整事件，用于审计，不称作“调用次数” |

例如一次笔记搜索可能包含搜索与内容补全等上游步骤，客户仍按已发布的一次业务请求费率结算；采购则记录各实际步骤。反过来，合法缓存交付可能不产生新的上游调用，客户是否收费仍依既有合同。不能简单把“每个客户请求”当成“一次 TikHub/JustOne 调用”。

采购成本分币种保存和汇总。需要毛利参考时，另附有日期的显式汇率快照和未计价项，不能将 USD 成本与 CNY 收入直接相减，更不能让估算汇率进入钱包结算。

## 7. 聚合搜索按什么标准执行与收费

当前实现是对当前 Key 获准且合同支持的逻辑来源发起子查询，实时每个继续中的来源取一页、并发最多 3；父请求不额外计费，每个子请求走其原有计费链路。加载更多继续各来源的原游标，未知或已结束来源不自动重查。既有实时结果合并不等于已经实现跨平台统一热度/相关度排名。

建议补齐查询计划，按以下顺序决策：

1. **业务匹配**：平台、内容类型、关键词、排序、过滤与 freshness 是否能由已核验合同表达。新闻、笔记、商品不能只因在相同大类就使用同一个查询。
2. **授权和运行条件**：同时满足调用者/Key 范围及服务策略。发现接口提供的是观察快照，派发时仍重新校验，避免预览与执行之间状态变化。
3. **固定路由**：同一平台/操作/请求形状选一条批准的路径；同一平台有多个供应商不意味着都查询。先满足字段质量和语义，再考虑延迟、成本等策略。派发后未知结果不自动切换供应商重复购买。
4. **价格说明**：展示本批逻辑平台数、每源页数、客户套餐版本及预计费用。价格未知与按既有规则免费的条目明确区分；不把“搜索 19 个平台”说成固定一次费用或 19 倍小红书价格。
5. **结果口径**：返回逐源成功/空结果/不可用状态、时间和字段完整性。不同平台的阅读、曝光、点赞不能互相替代，也不直接合成同口径热度；缺失值仍是 null。

第一期保留“父请求不另收费，子请求按各自合同收费”。预览不承诺新的资金上限；如后续开放 `maxCost`，必须由服务端对计划及全部子请求实施一致的预留/结算约束，再对外宣称硬上限。不能仅增加一个前端估价数字。

历史模式仍查询 Hub 已存数据，不触发上游采集，其价格遵循对应存量查询合同。按条计费、综合热度排行、智能最低成本路由都是独立产品能力，不能借聚合入口悄悄改变既有行为。

## 8. 如何自动迁移已有能力

自动迁移的是**已经可证明的事实和稳定关联**，不是从名称推测价格、授权或可用性。

1. 从现有固定合同、执行注册表、产品访问配置及采购操作清单生成带版本/hash 的库存快照；按稳定 ID 关联目录。人工名称、分类、覆盖结论和来源证据保留。
2. 输出 dry-run 差异：新增登记、缺失映射、冲突、未知计费键、未核验采购价格、产品与 Key 快捷范围遗漏。关联不明确的项进入待处理，不猜测绑定。
3. 幂等写入实现登记与关联，标明 `origin`、版本、首次/末次发现时间；重新执行无重复对象。源代码移除能力时标记待退役，不删除历史账务或旧合同。
4. 将已有采购价迁入等价版本，保存每个端点/操作的现行金额、币种、计费证据、人工例外与运行状态。无法无损合并的差异保留，不强行整理成一个平均价。
5. 以影子方式比对“旧解析结果”和“新登记投影”，覆盖全部现有产品和旧 API。比对通过后才切换管理展示，运行执行仍沿用旧路径。
6. 产品费率、授权包和采购基础方案的新增版本作为可审阅草稿。对旧客户，只有显式套餐分配/授权动作才生效；不追补历史账务，不自动扩大 Key 快照。

迁移失败或回滚只撤回新登记/投影，不修改已发布价目表、已使用的价格快照或不可变账本。未来开户流程把“选择产品、选套餐、检查权限/就绪状态、提交”组织在一个入口，但每个步骤仍明确归属、可审计、可重入；某步失败时从该步继续，不能重复发布套餐或充值。

## 9. 实施顺序与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| A：先减少混乱 | 消费记录与原始账本分开；小红书目录/快捷权限补齐；产品价格概览；现有映射完整性校验 | 一笔成功请求一行消费，底层仍保留两步；旧 Key/套餐未扩权或改价；分页不丢结算事件 |
| B：统一登记 | 能力关联 manifest、生成投影、dry-run 和幂等迁移工具；采购基础方案及例外模型 | 重跑无重复；保留人工分类/价格/暂停；兼容旧路径与存量合同；未知证据如实显示 |
| C：简化开户 | 产品授权包 + 标准套餐选择 + 运行就绪汇总 + 原 Key 更新流程 | 新客户复用套餐；部分完成可续办；已有 Key 只在明确提交后变化；租户级开关影响清楚 |
| D：聚合搜索可解释 | 查询计划/价格预览、逻辑来源筛选、逐源结果与费用汇总 | 不产生预览采购；无父/子重复收费；权限撤回仍生效；原游标/重放不重复派发 |

金额与权限修改测试用隔离账本、模拟上游及 PostgreSQL 事务回归；覆盖并发余额预留、成功/失败/未知、重复请求、部分聚合成功、币种不同与版本变更。界面验收覆盖桌面/窄屏、套餐复用、逐笔消费展开及权限缺失/运行阻断，不使用真实付费上游来测试 UI。

以上为设计与验收要求；实际实现和发布步骤见第 11 节。生产套餐、采购价、预算、授权和历史账务未在开发验证中修改。

## 11. 2026-09-23 实施记录与发布边界

已实现：

- 消费记录：服务端按 charge 游标分页，一笔请求一行，展开完整 hold/capture/release。原始账本折叠保留，充值和调整仍在其中审计。此视图不重写账本。
- 统一登记：`server/data/capability-catalog.mjs` 从现有路由、供应商操作和共享产品模板生成带 hash 的清单。基础快照包含 77 条接口/清洗路径、287 个供应商操作和 3 个可复用定价产品；数据库中动态清洗分类可追加路径。目录的人工分类、名称和覆盖证据保留。
- 产品工作台：在套餐页选择产品，显式补齐调用者缺失权限、复用已发布套餐、追加产品费率到草稿、进入原 Key 管理。套餐分配替换整份套餐，界面先说明影响；Key 不随调用者补权自动扩权。小红书六项能力由同一产品定义生成权限快捷选择、销售模板及目录映射。
- 采购基础方案：按供应商保存不可变版本和逐操作绑定。预览列明保留/更新范围；提交验证预览 hash 和操作修订，逐项沿既有审计接口应用。部分失败如实返回并可重新预览续办；手动暂停和独立价格保留。新端点仍需人工核验合同、价格与日期。
- 聚合预览：`POST /api/v1/data/aggregate/preview` 接受与查询相同的参数，返回本批来源、页数、当前成交价格、套餐版本和已知就绪状态。预览不产生业务用量、余额冻结或上游调用，不锁价或提供硬费用上限。实际查询仍重新鉴权和计价。
- 聚合父收费修正：原有 canonical 价格被配置时存在父、子均报价的边界。104 与新服务配合，使新实时父请求只记录编排/配额，客户采购仅在子请求结算；历史存量查询保持原价。历史消费和原请求重放不改写、不追补。

实施中采用的简化：现有逐操作采购价直接作为受保护的独立配置保留，**不猜测哪些旧价格本来属于同一基础方案，也不自动复制成新的生效采购版本**。管理员第一次预览时可逐项明确纳入基础方案；以后该绑定的修订一致才继续继承。分类目录继续表达业务覆盖，运行鉴权与计费继续沿用原内核。本阶段不实现按条/token 计费、自动最低价供应商选择、跨币种毛利或 `maxCost`。

发布步骤：

1. 用目标库的只读连接执行 `npm run check:capability-catalog` 查看差异（未安装 104 时报告待迁移）；无数据库连接时仅生成源码清单。
2. 按既有备份/发布流程执行 `npm run migrate`。104 创建管理元数据表并调整新聚合父请求计量触发器；随后在迁移事务锁下同步登记。同步可重入，源码移除项标记 retired，不删除历史。
3. **迁移完成后再启动新服务**，检查消费页、目录登记差异、产品授权/价格及供应商基础方案预览。既有客户无需重新注册或更换 Key。
4. 已有采购价、客户套餐、调用者和 Key 的任何变更均由管理员后续显式操作；仅发布此改版不会修改它们。发布基础采购版本也不会改变客户售价。

消费查询复用既有租户/时间索引，部署迁移不对大账本执行额外阻塞式索引构建。开发使用内存隔离账本与模拟上游；PostgreSQL 实库迁移验收必须在目标测试库完成后再安排生产发布。


本机验收记录：相关服务端回归 109 项通过，PostgreSQL 实库用例 1 项因未配置测试数据库跳过；类型检查与生产构建通过（保留已有 bundle 大小提示）。浏览器验证了逐笔消费展开、标准套餐分配、目录评论能力映射、采购基础方案 v1→v2 预览/发布、聚合费用预览；390px 窄屏表格只在容器内部滚动，整页无横向溢出。全程使用内存数据与模拟上游，没有真实采购或生产配置变更。
