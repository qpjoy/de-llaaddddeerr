# 04 准入、并发与全局资源

状态：
- 第 2 节是对现有代码的核对；
- 第 3、4 节是设计，未实现。

## 1. 两类控制，不要混用

| | 准入（保护上游） | 资源互斥（自建引擎） |
|---|---|---|
| 目的 | 控制打到供应商的并发和频率，保护额度 | 同一个真实资源同一时间只做一件事 |
| 超发的后果 | 短暂多打几个请求，可以接受 | 两个爬虫同时跑，可能触发反爬，结果不可信，**不能接受** |
| 宕机丢失少量状态 | 可以接受，租约到期自动恢复 | 不可接受，必须人工核实 |
| 实现 | PG 租约，异步提交 | PG 行约束 + 部分唯一索引，同步提交 |
| 例子 | 图 4「Hub 限速与等待队列」（TikHub） | [03](03-self-hosted-engines.md) 的引擎单执行槽 |

## 2. 图 4 的限速在当前架构下的实际效果

**源码依据：**
- `server/core/process-share.mjs`：按 `max(1, ceil(配置值 / 进程数))` 把上限分给每个进程；
- `server/external-platforms/admission-runtime.mjs`：并发和等待队列属于各个网关对象，放在进程内存里；
- 每分钟请求数用 PG 的 `external_platform.provider_rate_buckets` 令牌桶，所有进程共享。

Public 现在是 4 个进程（PostgreSQL 模式）：

| 图 4 的配置 | 实际效果 |
|---|---|
| 网关实例总并发 16 | 每进程 4 个，合计 16 |
| 单调用者并发 8 | 每进程 2 个，合计 8。Node cluster 按**连接**分配请求，不保证均衡，所以可能提前触顶 |
| 队列最大等待请求数 32 | 每进程 8 个，进程之间不互相均衡 |
| 供应商每分钟请求数 50 | PG 共享令牌桶，**全局精确** |
| 队列最长等待 10 秒 | 不变，只是一次短 HTTP 等待，不是持久任务的期限 |
| **把总并发改成 1** | 每进程至少 1 个，**实际最多 4 路并行** |

**其他限制：**
- 不同 TikHub 网关对象各自计数。它们读同一份供应商配置、共享每分钟请求数，但没有一个覆盖所有 TikHub 接口的全局并发计数。
- 部分明确授权的内部身份可以豁免业务准入。
- 截图里显示「修订 #0、沿用部署默认值」（10 秒 / 32）；本地代码的默认值已经是 30 秒 / 256（`DEFAULT_CONCURRENCY_QUEUE`）。线上数据库里实际生效的值**未核实**。
- **图 4 只管 TikHub**，不管直接调 Night-All 的搜狗请求。自建引擎要单独控制。

**结论：** 现在仍然有效，单个 Pod 内总量也正确。但它是业务准入，**不能拿来实现「只能单线程执行」**。

## 3. 多副本、多节点后的问题

`processShareOf` 只知道一个 Pod 里有几个进程，不知道有几个副本。Public 从 1 个 Pod 变成 R 个 Pod 后：

- 总并发 = 配置值 × R；
- 等待队列 = 配置值 × R；
- 每分钟请求数仍然正确，因为它在 PG 里。

**所以 Public 加副本之前，并发和等待队列必须全局化**（[01](01-topology-and-multinode.md) S2 的前置条件）。

| 方案 | 做法 | 判断 |
|---|---|---|
| 按副本数再分一次 | 读取副本数，用配置值 ÷（副本数 × 进程数） | 需要额外的部署配置或访问 k8s API；滚动更新期间副本数会变；负载不均时浪费名额。**不采用** |
| Redis 全局信号量 | 租约放在 Redis ZSET | Hub 目前**完全没有用 Redis**，引入它等于在请求路径上加一个新依赖。**暂不采用** |
| **PG 租约信号量（推荐）** | 和现有每分钟请求数桶同一种做法：短事务 + `synchronous_commit=off` | 不新增依赖；跨进程、跨副本、跨节点都正确；崩溃时最多丢失最后几个租约，到期后自动恢复 |

## 4. PG 租约信号量设计（拟定）

```sql
CREATE TABLE external_platform.admission_leases (
  lease_id uuid PRIMARY KEY,
  provider_key text NOT NULL,
  consumer_id uuid,
  holder text NOT NULL,            -- pod/进程标识，便于排查
  expires_at timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON external_platform.admission_leases (provider_key, expires_at);
```

**领取**（一个短事务）：

1. `SET LOCAL synchronous_commit = off`；
2. 用 `pg_advisory_xact_lock` 把同一供应商的计数串行化；
3. 删除这个供应商已过期的租约；
4. 只有当「供应商总数 < 总并发」并且「该调用者的数量 < 单调用者并发」时才插入租约；
5. 返回 `lease_id`，拿不到则返回空。

**释放与续期：**
- 请求结束后按 `lease_id` 删除，同样异步提交。
- 租约有效期 = 上游超时 + 安全余量。
- 上游调用很长时，中途续期一次。

**等待：**
- 拿不到租约的请求在本进程里排队，在 `maxWaitMs` 内带抖动地退避重试（50–200 ms）。
- 收到释放通知时提前唤醒；释放时发 `NOTIFY admission_release`。
- 每进程等待数仍然有上限，避免内存无限增长。

**开销（估算）：** 每个请求多两个短事务。因为是异步提交，不用等落盘；单个供应商的串行锁在 100 QPS 下每次远小于 1 ms。

**降级：** PG 不可用时，请求本来就无法预留额度，会直接失败，所以不需要单独的降级路径。

**范围：**
- 「网关总并发」和「单调用者并发」改为全局；
- 「等待队列」继续是每进程的有界队列；
- 图 4 页面的文案要改成「全集群合计」。

## 5. 自建引擎的互斥

- 不放进准入信号量，单独由引擎行的 `active_job_id` 加 `WHERE status='running'` 部分唯一索引保证（见 [03](03-self-hosted-engines.md) 第 2 节）。
- **同步提交**，unknown 时不会因为租约到期而自动释放。
- **为什么不用 Redis 或 BullMQ 的「全局并发 1」：** 它们只能保证 Hub 这一侧不并发派发，证明不了上游已经停止。最终要靠任务身份和停止证据。

## 6. 验证清单

1. 单 Pod 4 进程：并发压到配置值 + 4，实际在途数不超过配置值（全局化之后）。
2. 2 个副本：在途总数不超过配置值；每分钟请求数不变。
3. 杀掉一个持有租约的进程：租约在有效期后自动释放，没有永久占用。
4. 修改总并发后：所有进程在一个刷新周期内生效，不会回退到旧修订。
5. 自建引擎：4 个进程、多个副本同时领取，同一时间只有一项是 running。
