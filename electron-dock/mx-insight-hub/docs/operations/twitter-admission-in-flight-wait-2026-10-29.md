# Twitter 搜索 409：同查询仍在执行，Hub 改为先等待（2026-10-29）

## 现象

Delta 策略“admin_政情·爱泼斯坦文件最新动态”的 Run `#109977` 调用 v2 搜索（Twitter raw），Hub 返回：

- `409 search_admission_blocked`，请求 `a19f3831-5ad9-44f7-bbdd-73ba26573c7c`
- `dispatchState=not_started`、`automaticRetryAllowed=true`、`retrySameRequest=true`
- `retryAfterSeconds=177`，`blockingRequestId=4954dc7f-5242-4c8d-b671-1db739495170`

Delta 收到后结束本次 Run，不重试，并发出 ERROR 告警。本次没有调用供应商，也没有计费。

## 原因

这不是冷却时间。2026-10-28 已经删除了“未知结果冷却”和“已结束的未知结果阻断新 key”。保留下来的只有**执行中去重**：同一个 API Key、同一平台、同一查询文本，如果有另一个请求正在执行，新请求要等它结束，避免同时为同一页付两次钱。

`4954dc7f` 就是那个仍在执行的请求。`retryAfterSeconds` 是它剩余的租约时间（最多 300 秒）。生产的预留租约是 180 秒，所以剩余 177 秒说明它大约只比本次请求早几秒开始。这是推算，可以在诊断中心搜 `4954dc7f` 核对它的开始、结束时间。

为什么会撞上：Delta 所有策略共用一个 Hub Key，而 Hub 判断“相同”只看查询文本，不看时间窗口。不同策略只要关键词相同、几乎同时调度，就会互相挡住。

修改前，Hub 立刻返回 409；Delta 自 `3a5413e`（10-28）起不再重试，于是这一次采集失败并告警。数据不会缺：失败 Run 的窗口不会前移，下一次调度会补采。

## 修改：Hub 先等，再放行

`server/data/search-protocol.mjs`：

- v2 新请求如果只是被**仍在执行的同查询请求**挡住（即 `search_admission_blocked` 且 `dispatchState=not_started`），Hub 在服务端每秒检查一次，最多等 40 秒。挡住它的请求一结束，就自动放行本次请求，调用方只会看到这次请求慢了一些。
- 等待期间本次请求不派发、不预留、不计费。
- 40 秒后对方仍在执行：返回和以前完全一样的 409。调用方断开连接时立即停止等待。
- 40 秒是内置值，不新增 env。取值见下节。
- 只等这一种情况。同 key 保护、`request_in_progress`、`request_outcome_unknown`、`idempotency_conflict`、熔断和限流都照旧立即返回；带 `X-MX-Insight-Retry-Of` 的人工重试也不等待。
- 路由层的 Twitter 等价查询检查（写法不同、编译后相同的查询）同样返回 `search_admission_blocked`，同样会等待。

API 文档（`data-search-v2-docs.mjs`、`openapi.yaml`、`docs/integrations/data-search-v2.md`）已注明这次等待。

### 为什么等 40 秒，而不是一直等到 Delta 超时

- 一次 Twitter 搜索通常 3–6 秒（10-19 的 11 笔样本为 2.6–5.7 秒），最长受 Hub 自己的 30 秒供应商超时限制，再加几秒保存。40 秒足够等到最慢的那个请求结束，再等也基本等不到结果。
- 本次请求等完之后还要自己执行，最慢同样约 30 多秒。40 秒加上这段，仍在 Delta 的 90 秒超时之内。
- 如果一直等到 Delta 超时：对方在第 80 秒左右结束时，Hub 会开始付费采购，而 Delta 几秒后就断开了。结果是钱花了、数据没人收，Delta 看到的是超时（结果未知），比一个明确“未开始”的 409 更糟。
- 这个上限不会中断任何正在进行的采购，只是停止排队并明确告诉 Delta“这次没开始、没扣费”。

### 为什么同一个 Key 还要等

这不是对这个 Key 的权限、额度或频率限制。Hub 不会同时发出两个**完全相同的供应商请求**，所有 Key 都一样，派发层也有同样的去重。Twitter 的供应商请求里不含时间窗口（窗口在交付时由 Hub 过滤），所以两个关键词相同的策略，第一页发出的是一模一样的请求。

只去掉准入这一层并不能让它们并行：第二个会在派发层被挡下，报 `request_in_progress`，而且那时已经预留，比现在更糟。两层都去掉，就是同一页同时付两次钱，而且第二个也不会比等 3–6 秒更快拿到结果。所以由 Hub 排队等待，对 Delta 来说只是慢了几秒，不会再看到拒绝。

### 没有改的

- 不同时为同一查询派发两次请求：执行中去重仍在，只是由 Hub 自己等待，不再交给调用方。
- 多个相同查询同时到达时，它们会依次执行；排在后面、等待超过 40 秒的仍会收到 409。
- 不需要改 Delta，也没有改 MX-H2I、登录或联网。

## 测试

- 新增 `tests/server/data-search-v2-admission-wait.test.mjs`：对方结束后自动放行且只派发一次；等待用完后返回原 409，同一 key 之后仍可使用；调用方断开时停止等待且不派发；其他拒绝不等待。
- HTTP 路由测试新增：默认配置下对方 300 毫秒后结束，本次返回 200；把等待设为 0 时仍返回原来的 409 结构。
- 用 PGlite 0.2.17 跑完整服务端套件，失败项仍是原有 45 项；类型检查和公开文档测试通过。

## 部署

```bash
MX_INSIGHT_SYNC_LAUNCHER=0 MX_SMOKE_DATA=0 bash scripts/manage.sh ops internal-production deploy
```

部署后，同关键词的策略同时调度时，只要先到的请求在 40 秒内完成，就不会再出现这条告警。如果仍然出现，说明先到的请求执行超过了 40 秒，在诊断中心搜告警里的 `blockingRequestId`，看它的执行时长。
