# 用量统计增量汇总（2026-11-08，迁移 182）

## 背景

2026-11-08 Internal 部署时，所有工作负载已上线，但 smoke 调用 `GET /internal/v1/admin/dashboard` 返回 503。原因是 `PostgresStore.usage()` 的全平台账单汇总（请求表关联账单表，再按计费项和币种分组）超过了事务内 5 秒的语句时限。smoke 之后的默认 Key、供应商凭据导入和补默认价格因此都没有执行。

用量统计原来每次读取都要扫描全部请求历史，`usage_requests` 每行还带着响应体，数据越多越慢。以下几处都受影响：

- 平台仪表盘（全历史）：管理后台总览页、Launcher 健康汇总读取 `/ops/summary` 的 `requests` 和 `units`、部署 smoke。
- 按租户、调用者、Key 的用量：管理后台用量页、Key 详情、租户自己调用 `/api/v1/usage`。
- 按 Key 查看最近请求：请求很少的 Key 要沿全局的 `created_at` 索引扫过大量别人的请求。

## 做法

**记录变化。** `usage_requests` 和 `billing.customer_charges` 上的触发器在变化所在的同一事务里，向 `reporting.*_deltas` 追加一行很小的带符号变化记录：旧状态记 −1，新状态记 +1。会触发记录的变化包括新增、状态、计量单位、上游延迟、平台、能力、归属、创建时间。变化表没有索引和唯一约束，并发写入互不等待，也不给请求路径增加索引写入。账单变化按它所属请求的租户、调用者、Key 和小时归类，与原来的关联查询口径一致。

**合并成小时汇总。** Admin 进程每 30 秒把已提交的变化合并进 `reporting.*_totals`。合并在一条语句里完成：删除变化行，同时累加到汇总表，读取方要么看到合并前，要么看到合并后。净值为 0 的分组会被删掉。如果发现汇总出现负数，状态退回 `pending`，读取改回历史查询，并重新构建。构建与合并用同一把 advisory lock，Admin 滚动发布时也只有一个进程在执行。

**读取。** 在同一个只读快照里，把三部分相加：

1. 完整 UTC 小时内的汇总；
2. 尚未合并的变化行；
3. 时间筛选首尾不满一小时的部分，直接读原始请求，用调用方给的精确边界。

返回的行与原来的历史查询完全相同，包括字段、顺序、平均延迟的取整方式，也同样是实时的。只有汇总状态为 `ready` 且定义版本匹配时才读汇总，否则继续使用历史查询；历史查询仍保留账单直读和仪表盘分段降级。

**最近请求。** 带租户、调用者或 Key 筛选时，先从汇总中找出包含这个归属最新 50 条请求的那些小时，再只在这些小时内读取原始请求。时间筛选首尾不满一小时的部分不计入 50 条，所以读到的范围只会多不会少，结果与原查询一致。不带归属筛选时仍按原方式读取。

**首次构建。** 部署后 Admin 进程在后台执行一次完整构建，整个过程在一个 REPEATABLE READ 事务里：按历史数据算出小时汇总，并删除这个快照已经包含的变化行。快照之后才提交的变化保留下来，之后再合并，所以不会重复计数，也不会漏算。构建的语句时限是 30 分钟，且不使用并行 worker。构建失败时，30 分钟后重试，期间统计照常走历史查询。

## 验证

- `tests/server/usage-rollup-postgres.test.mjs`（真实 PostgreSQL），每个阶段都与 `usage(filters, { rollup: false })` 的历史查询结果做完全相等比较：
  - 构建前、构建后、有待合并变化时、合并后；
  - 请求移到别的小时（它的账单跟着移动）；
  - 已提交请求改为结果未知；
  - 运营对结果未知的账单做对账；
  - 只有能力、没有平台的请求。
  - 比较时覆盖平台、租户、调用者、Key 四种范围，每种都搭配整点、非整点、同一小时内、起止颠倒、只给一端的时间窗口。
- 同一文件还验证了：
  - 构建期间仍未提交的事务只计一次；
  - 稀疏 Key 和高频 Key 的最近请求；
  - 后台任务在构建失败后会等待一段时间再重试。
- `tests/server/usage-report-bounds.test.mjs`：读取汇总同样先设置本地资源限制，任一条语句被取消时整体回滚，不返回部分结果。
- 反向对照：人为把汇总中的一行加 1，汇总路径立即读出差异，说明比较确实经过了汇总路径。

## 压测（本机 PostgreSQL 17，100 万请求）

测试数据：

- 100 万条请求、100 万条账单，其中请求表 3.3 GB（响应体约 1.5 KB）。
- 请求分布在 180 天内；1 个大租户（3 个 Key）占 90% 的请求，另有 20 个小租户。

### 首次构建

约 30 秒，同时清掉了导入期间积累的 290 万行变化。小时汇总约 17 万行，两张汇总表连同索引约 130 MB。

这批数据让每个 Key 在每个小时都有请求，是汇总行数最多的情况。生产环境汇总行数主要随时间增长，请求量增长时增加得慢得多。

### 读取耗时

缓存已热；各路径先完整执行一遍，再取下面这一次的耗时。新旧两条路径的结果做严格深比较，全部一致。

| 场景 | 历史查询 | 增量汇总 |
| --- | --- | --- |
| 全平台（仪表盘 / Launcher） | 1391 ms | 216 ms |
| 大租户全部历史 | 1754 ms | 86 ms |
| 小租户 Key 全部历史 | 246 ms | 35 ms |
| 大租户最近 24 小时（非整点） | 23 ms | 6 ms |
| 全平台最近 30 天 | 726 ms | 55 ms |

本机整张请求表都在内存里，所以历史查询的数字明显好于生产；生产库是共享的，数据也不在缓存中，那次超过 5 秒就是这个原因。历史查询每次都要扫描约 3.3 GB 的请求表和账单，并随请求量线性增长。增量汇总全平台读取约 200 MB 的汇总表；按租户或 Key 读取时走索引，只读这个归属的汇总行。

### 写入代价

- **耗时**：用 `track_functions` 计时，真实的预留→提交路径上，两个统计触发器每次调用约 19 µs，每个请求合计 0.076 ms，约占请求耗时的 0.25%。同一路径上原有的账单预留触发器每次调用约 448 µs。
- **WAL**：每个请求写 6 行变化，之后被合并删除，共约 1.4 KB；本机测得每个请求的总 WAL 约 25–30 KB。
- **合并**：2000 个请求产生的 9600 行变化，合并用了 33 ms。

## 运维

- 查看状态：`SELECT * FROM reporting.usage_rollup_state;`。`ready` 表示在读汇总；`pending` 表示在读历史查询，等待 Admin 构建。
- 强制重建：`UPDATE reporting.usage_rollup_state SET status = 'pending';`。Admin 下一轮会重建，重建完成前读取自动改用历史查询。
- 如果绕过触发器批量写入或修复了 `usage_requests` 或 `billing.customer_charges`（例如 `session_replication_role = replica`、`DISABLE TRIGGER`），之后必须强制重建。正常的 pgBackRest 物理恢复和 pg_restore（触发器在导入数据之后才创建）不受影响。
- 待合并的变化行数：`SELECT count(*) FROM reporting.usage_request_deltas;`。Admin 长时间停止时这张表会变大，读取会变慢，但结果仍然精确；Admin 恢复后会分批合并。
- 不新增任何环境变量或部署配置，节奏与上限都内置。不涉及 MX-H2I 登录和联网。
