# Hub 通用并发等待（2026-10-13）

此前的等待机制只覆盖小红书主网关的搜索、详情和官方接口，以及 PGY 的专用调度。企业、通用供应商网关、独立用户资料/作品和 IP 网关在本地并发满时仍可立即拒绝。企业请求 `7443d5db-d9b0-4d99-b204-eacd4e92df6c` 的网关账本确认是这类派发前拒绝，详见 [取证记录](enterprise-qixin.md)。

本次让这些缺口复用 `ConcurrencyAdmissionQueue`：

| 链路 | 当前处理 |
| --- | --- |
| 企业全部固定目录接口 | 每网关实例 10 并发、每 consumer 10；满额等待 |
| 通用网关 | 电商搜索/资源、账号搜索、原生转发、社交内容、热榜、Hub 直连 raw/data-search、Facebook、Web Search 等待现有并发名额；Twitter 标准补页首次采集的缺口于 2026-10-15 补齐，已保存余量仍可直接交付 |
| 独立小红书 user-info/crawl | 该实例共享队列；为用户名解析、资料、作品完整调用链保留执行时间 |
| IP 单次、批次、渠道和订阅产品 | 保留每实例 3 并发、60 RPM，满额等待；沿用原批次 60 秒截止 |
| 小红书主网关/PGY | 保留已有队列、前台保留名额、专用间隔及原策略 |

队列默认每实例最多 **32 个等待请求、等待 10 秒**。实际等待时间还受原 reservation 剩余时间限制，必须预留完整上游超时预算和 5 秒保存余量。IPSearch 预算 15 秒；百度 IP 两次子请求及两次内部等待合计预算 40 秒。未知执行预算不能进入等待后盲目派发。

这是 HTTP 请求内的短时排队，不是重启后自动重放的后台任务。复用同一实现不意味着所有供应商共用一条队列：容量跟随原有网关实例，同一供应商不同实例及不同 Pod 不共享进程内计数。现有数据库派发去重、供应商 RPM、采购预算和熔断仍各自生效；本次不宣称核验了供应商允许的最大并发，也不提高其他供应商的限制。媒体代理和 Night-All 远端自身调度不在此队列范围。

## 派发边界

- 未满时按原路径执行；已允许的存量回退仍可立即交付。等待者按可准入顺序处理，某 consumer 自身满额不会阻塞有名额的其他 consumer。
- 等待中保留原客户预占，释放派发去重租约；不预占供应商采购预算、RPM 或新增 provider call。队列自身不持有数据库连接。
- Twitter 标准补页首次采集等待保留原交付去重租约，防止相同请求在等待期另行采集；出队使用同 owner、同期限重新检查未知结果及隔离保护。该队列只接收尚未持有已采集页的请求。已有付费余量遇到新采集繁忙时直接提交短页，不先释放预占。
- 出队重新检查当前 Key/consumer/tenant、授权交集、已发布套餐、凭据、操作开关、熔断和派发去重；原请求期限不会因等待而延长。允许缓存的链路可复用等待期间生成的新鲜结果。
- HTTP 断开会取消尚未派发的请求并清理等待项。已经派发的调用仍保存证据和完成原结算；已有多步工作流继续遵守原合同，不因断开产生隐式重复调用。
- 超时、队列满和取消释放客户预占，不开始供应商调用。未知结果保护和已交付幂等回放不变，没有新加自动付费重试。

## 错误与诊断

企业排队满示例（HTTP 429）：

```json
{
  "code": "external_platform_busy",
  "message": "Hub 处理企业数据请求时等待队列已满，尚未调用上游，请稍后重试",
  "details": {
    "platform": "enterprise",
    "layer": "hub",
    "stage": "concurrency_admission",
    "reason": "concurrency_queue_full",
    "upstreamDispatched": false,
    "retryAfterMs": 1000
  }
}
```

等待超时使用 `concurrency_queue_timeout`；供应商真实响应、RPM、熔断、预算、授权错误继续保留各自分类。`retryAfterMs` 是重试建议，不保证届时有名额。客户端应保留原请求身份，核对当前结果后再按业务意图重试，不能把请求失败统一当作免费重放。

Twitter 标准补页保留原 `503 / external_platform_busy`，文案明确 Hub Twitter 等待超时或队列满，
附 `admissionMode=bounded_wait`、具体原因、当前/最大并发与退避建议。
默认仍为该实例总并发 3、单 consumer 2；没有提高采集速率或重试已派发的失败。
事故证据、版本边界和验证见 [Twitter 并发拒绝](twitter-busy-2026-10-15.md)。

请求诊断读取最新非幂等回放的 gateway 记录，仅在 usage 的 released 请求缺少 HTTP 且错误一致时补出状态，返回 `responseStatusSource=gateway_request`。仍优先显示已保存 usage 状态；不会伪造响应正文或可复现能力。数据库查询限定请求 ID、单行结果、只读一致性事务和超时，复用已有 usage_request_id 索引。
