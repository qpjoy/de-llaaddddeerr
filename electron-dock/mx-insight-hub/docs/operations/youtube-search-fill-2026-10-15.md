# YouTube 短页、补页预算与缺失指标

日期：2026-10-15。本记录说明本轮源码调整与本地验证，不表示生产已发布或原截图已完成归因。没有新发起付费搜索。

## 已核实的旧行为

用户截图显示 YouTube 返回 19 条、`partial` 和 `DATA_PROVIDER_CALL_LIMIT_REACHED`，截图没有完整 Hub 请求 UUID。仅凭这些字段无法确认实际部署版本、当次去重、游标状态或供应商总调用次数。

| 位置 | 调整前的实际含义 |
| --- | --- |
| Night-All `lib/shared/schemas/data-search.js` | HTTP `maxProviderCalls` 默认 1，显式范围 1–3；路由校验后将默认值交给分页服务 |
| Night-All `paged-content-search-service.js` | 内部构造兜底默认 3；`positiveInt(..., 20)` 中的 20 是构造配置钳制上界，并非默认采购 20 次 |
| 同一分页服务 | `pageFetches` 统计底层页面获取；与可能包含重试、候选端点的 `meta.providerCalls` 分开 |
| 标准搜索 `fetchInput` | `disableAutoDetails=true`、`includeDetails=false`、`includeComments=false`；不会用 19 次详情补采解释 19 条帖子 |
| Hub `HubService.search` / `NightAllAdapter.search` | 公共合同不接收 `maxProviderCalls` / `maxRetries`，转发体不注入 20 次预算 |
| Hub `night-all-pagination.mjs` | 保护原 Key／查询／页大小／合同游标，控制 15 个公开页；不设置上述补页次数 |

旧 warning 只在当前输出少于 `pageSize`、内部页面获取数达到该次预算且上游仍有后续时产生。它不证明账户余额、供应商总配额或真实 HTTP 429，也不单独证明返回条数有丢失。

本地合成验证使用真实 HTTP 请求 schema 与分页服务：`pageSize=20`，模拟一个包含 19 条且仍有后续的成功上游页，恰好调用一次页面获取，得到 19 条、`partial` 和同名 warning；断言详情与评论附采关闭。该结果证明旧默认值足以产生这种现象，不冒充原截图的已保存凭证。此前 [9 月故障记录](search-request-diagnosis-2026-09-23.md) 中的默认 3 指内部服务兜底，需结合 HTTP schema 默认 1 阅读。

## 本轮调整与保留边界

取消 Hub Twitter、Facebook、Bilibili、抖音、快手、知乎标准逻辑页默认最多 3 次派发的限制，同时取消 Night-All 普通标准搜索 HTTP 默认 1 次／内部默认 3 次的补页限制。不会只把默认值从 1 调到 3。调用方直接向 Night-All 显式传入的 `maxProviderCalls` 仍生效；既有成本估算不能越过这一预算。Hub 公共请求字段和价格合同不增加此控制项。

补页仍先消耗已取得的余量，按原供应商和游标读取后续并去重，达到 `pageSize` 即停止。以下边界继续生效：

- Hub 原生补页既有 15 个上游页／公开页边界，以及 Night-All 兼容路径的 15 个公开页边界、游标身份与有效期；公开页数不能当作供应商真实调用数。
- 原请求截止时间、归档字节、当前授权、采购预算和速率准入。
- 真实上游 429／失败、无后续、重复游标和无分页进展；原有明确 429 保底规则不扩展到其他失败。
- 已派发的未知结果保留预留与锁，不能为补满页面重采，不能把未知结果降为可重试短页。

Night-All 新增的 120 秒检查只在已完成一次页面获取后、准备开始后续获取时停止派发，不取消在途供应商请求，也不是端到端响应保证。Hub `NIGHT_ALL_TIMEOUT_MS` 默认仍为 60 秒；慢响应仍可能先进入既有 unknown 流程。本轮没有延长该超时、缩短预留保护或自动重试。连续 3 个页面没有新增 ID、但游标仍前进时，Night-All 返回 `partial`、`DATA_PROVIDER_NO_PROGRESS` 和可继续的游标；新增 ID 会重置此计数。这是无进展保护，不是总获取次数上限。已经重复的原生游标则终止该上游续取，已取得的余量仍可交付。

因此 `pageSize` 仍是结果上限，短页与 `partial` 仍可能正确出现。取消本地默认补页次数不删除供应商返回的真实限制，不把历史 warning 改写为成功，也不增加详情／评论／账号采集。

新 YouTube 标准投影将未提供的点赞、评论、分享、浏览、收藏保留为 `null`；明确观测到的数字零保留为 `0`。产品卡片将 null 显示为“未提供”。兼容 raw 的既有默认值与字段保留，不用新映射重写旧已保存响应；无法从历史零补回当时没有保存的非零数值。

## 幂等、游标与结算

原幂等键及请求指纹、Key／查询／页大小／路径／供应商绑定、已归档余量与已交付 ID 去重继续生效。已保存交付在原窗口内精确重放，包括旧 19 条、warning 与失败；原未知状态继续保持。`stable` 与 `fresh` 的既有重放语义不变；不要用相同幂等键反复 POST 代替状态核对。新公开页继续使用新的幂等键并原样回传游标。

Night-All 已有 `maxProviderCalls=1` 游标在新调用省略预算时，可按原完整上下文恢复；查询、业务身份、平台、页大小、重试参数、供应商与端点检查仍然有效。显式传入预算时仍严格匹配。旧游标快照不改写，新游标按当前上下文保存。

一个 Hub 逻辑请求沿用原客户报价与一次结算；每笔实际派发仍分别记录上游凭证并遵守采购准入。补页不能绕过操作状态、配额或钱包，也不自动恢复历史 unknown／隔离记录。详情、评论和账号接口的既有合同不因本轮默认补页调整改变。

## 不重搜取得原请求证据

产品展示的结果底部显示完整“请求 UUID”；展开“完整响应与请求证据”可读取响应顶层 `requestId`。已保存 HTTP 响应头的 `x-mx-insight-request-id` 也可定位业务使用记录；普通 `x-request-id` 可能是 HTTP 关联 ID，不能直接当作用量账本 UUID。幂等键是另一项身份，不能替代请求 UUID。

Admin 可以在既有使用记录中按原 Key 与时间范围查找，再读取 `GET /internal/v1/admin/request-diagnostics/{requestId}`；该诊断使用 READ ONLY 事务，不发起业务采集。公共请求状态 GET 虽不采购，但会调用过期预留清理，不能宣称数据库严格只读。

修改默认补页逻辑不需要再发一次真实搜索来确认截图。要对这笔“19 条”做精确归因，才需要原已保存响应与可关联的 Night-All 页面／调用凭证，核对部署版本、`pageInfo`、调用计数和去重。没有原 UUID 或凭证时只能确认代码机制，不能认定该截图的具体供应商限制或费用。

## 发布与验收

YouTube 内容搜索当前仍走 Night-All；本轮没有把它迁移为 Hub 原生关键词路径。Hub 工作流／文档调整与 Night-All 分页 schema、服务和指标映射需要分别发布到实际运行位置。单独发布 Hub 不会更新 Night-All 的默认值或补回已经丢失的指标。

Hub 发布仍由操作者在完整同步源码后执行：

```bash
MX_INSIGHT_SYNC_LAUNCHER=0 MX_SMOKE_DATA=0 bash scripts/manage.sh ops internal-production deploy
```

此命令不发布 Night-All。Night-All 使用其现有发布流程；两者均不隐含真实付费查询验收。保留原授权、价格、历史响应与账单，不改 MX-H2I 登录、联网或 Launcher。运行时变更和本地回归结果以本轮实际完成的测试记录为准；原截图的请求凭证尚未取得。

本地验收：Night-All 8 个相关文件共 142 项通过、0 跳过，包括真实请求 schema 的 19＋1 补齐、8 平台超过 3 页、显式预算、旧游标隔离、循环游标、无进展与超时检查，以及现代 null／真实零和兼容 raw。Hub 工作流 177 项通过、3 项原有真实 PostgreSQL 环境测试跳过；通过项包含实际 PGlite 计费触发器、超过 4 份采购归档的原子提交、回滚和一次结算。文档与 API 相关测试 19 项通过。全部使用本地合成数据与隔离存储，没有请求真实供应商。
