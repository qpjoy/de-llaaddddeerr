# Facebook 按业务独立暂停

用户确认按“内容搜索 / 账号内容 / 账号资料 × Facebook”分别暂停，互不牵连。此改动仅在本地完成，未部署、未修改线上策略、未调用付费供应商。

## 管理入口

进入“策略搜索 → 管理”，选择业务接口与 Facebook：

| 业务 | 设置 | 范围 |
| --- | --- | --- |
| 内容搜索 | 现有“暂停新搜索” | 保持原 Facebook 搜索策略及作用范围 |
| 账号内容 | “业务状态 → 暂停新采购” | crawl 新采购及需继续采购的分页，包括前置账号解析 |
| 账号资料 | “业务状态 → 暂停新采购” | user-info 新采购 |

账号内容和账号资料仍固定使用 JustOne，不在本次引入供应商切换。保存必须填写原因，并以当前修订号比较更新；冲突返回 409，不覆盖他人修改。管理 API 继续只允许 Admin Token。读取或保存策略不触发采集。

只想暂停账号资料时，应使用这里的业务开关。上游供应商页面的“获取资料 ID”等操作开关属于共享底层控制，仍会同时影响依赖它的业务。

## 执行边界

- 新 `/api/v1/data/social/crawl`、`/api/v1/data/social/user-info` 在每次新派发前读取对应业务状态。
- 原 `/api/v1/search/{crawl,user-info}` 与 `/api/v1/night-all/search/{crawl,user-info}` 也检查对应状态，避免从兼容入口继续采购。
- 完成响应按原请求重放；有效的已购缓冲可以继续交付。缓冲不足需要新采购时停止，已有采购结果按现有 partial/nextCursor 合同返回。
- 未开始采购即暂停时返回 503 `facebook_account_paused`。配置缺失或无法读取时返回 `strategy_search_route_unavailable`，不会继续派发。
- 账号内容的前置资料解析仅检查 crawl 开关，独立 user-info 暂停不会阻断它。
- 已派发请求不取消，不改写历史证据或退款；跨节点更新通过数据库读取生效。
- 此开关不修改直接调用供应商原生接口的授权和状态；如需全平台禁用，应另行处理原生接口权限/操作状态。

其他平台、现有内容搜索策略、钱包和采购预算、LCY-delta 配额豁免规则、MX-H2I 登录及联网行为均未修改。

## 发布

随 Hub 正常发布流程先执行 migration `170_facebook_account_business_pause.sql`，再启动新版 Hub。迁移保留既有搜索策略和上游操作配置，只为两个 Facebook 账号业务补入默认启用策略及审计记录。重复执行不覆盖已保存状态。

上线后在管理页分别选择需要暂停的业务、填写原因并保存。不要以暂停共享供应商操作代替业务开关。此前正常启用的业务不会因迁移自动暂停。

## 验证

覆盖独立启停、修订冲突、管理权限、数据库约束及重复迁移、旧入口拦截、响应重放、跨步骤暂停、已购余量、其他平台账号查询。六个相关测试文件运行 104 项通过、1 项现有数据库条件跳过；已单独发现并排除一条既有 Telegram capabilities 断言（现有响应新增 semanticSearch，旧断言未更新）。未修改该无关断言。

`npm run typecheck`、`npm run build` 通过。浏览器使用本地静态构建与内存策略 API，验证账号资料暂停保存并刷新至修订 2，账号内容仍启用、内容搜索策略不变；无浏览器错误、无真实供应商请求。
