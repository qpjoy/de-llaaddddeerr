# 试验场 · 星港物资台（Proving Ground）

一个埋好已知缺陷的小型网页应用，给 Rig 演示、评测和上手用。每个缺陷都能单独开关：同一组检查步骤先在“有缺陷”的版本上跑，再在“已修复”的版本上跑。检测手段的价值就看这两件事：第一个版本里能找到，第二个版本里不报。

**这是夹具。** 它的结果只说明 Rig 的检测能力，永远不作为任何真实产品的通过证据。

## 启动

```bash
npm run proving-ground                     # 全部缺陷打开，http://127.0.0.1:4610
npm run proving-ground -- --bugs none      # 修复版
npm run proving-ground -- --bugs PG-001,PG-008 --port 4620
```

零依赖：Node 自带的 http 服务、一个 HTML 外壳、一个脚本、一个样式表。登录只要填用户名。每次启动都是独立的数据和会话。

在 Rig 里使用时，把 `http://127.0.0.1:4610` 加进站点范围，或者第一次打开时确认即可。

## 缺陷目录（`defects.json`）

| 编号 | 缺陷 | 谁能发现 |
| --- | --- | --- |
| PG-001 | 「已归档」加关键字筛选，接口返回 500，页面却显示 0 条 | 传感器 `http_error` |
| PG-002 | 搜索没有结果时前端崩溃，整页白屏 | 传感器 `blank_page`、`page_error` |
| PG-003 | 详情页显示「负责人：undefined」 | 传感器 `content_leak` |
| PG-004 | 英文界面的保存按钮显示 `settings.save.button` | 传感器 `content_leak` |
| PG-005 | 英文界面「Notification preferences」被截断，且看不到全文 | 传感器 `text_truncated` |
| PG-006 | 报表页加载时控制台报错 | 传感器 `console_error` |
| PG-007 | 导出接口不返回，加载提示永远不结束 | 传感器 `stuck_loading` |
| PG-008 | 「收藏」按钮点了没有任何反应 | 传感器 `dead_click` |
| PG-009 | KPI 接口要 2.5 秒 | 传感器 `slow_request` |
| PG-010 | 登录后跳转地址里带着令牌 | 传感器 `secret_in_url` |
| PG-011 | 连点两次「提交」创建两条记录 | 断言 |
| PG-012 | 未登录访问列表不跳登录页 | 断言 |

`detect` 字段写明每个缺陷应该由什么发现。后续的风洞（故障演练）、侦察（自动探索）等能力会在这里加新的缺陷，并标明各自的检测手段。

## 检查步骤（`procedures.json`）

8 条规程，覆盖登录、筛选、空结果、详情与收藏、新建、报表与导出、英文界面、未登录访问。`baseUrl` 是默认端口，运行时替换成实际地址；可以通过 Rig 的规程 API 导入后在桌面端试车。

大多数断言即使有缺陷也会通过。这是有意的：它们演示的正是“测试绿了，但传感器发现了问题”。

## 评测

```bash
npm run eval:sensors              # 无模型重放：有缺陷版本 vs 修复版
npm run eval:sensors -- --headed  # 看着浏览器跑
```

输出检出率、误报、无法对应到已知缺陷的线索，以及“断言通过、但传感器报警”的规程。报告写到 `.runtime/evals/sensors-*.json`。传感器检出率低于 80%，或者修复版上有误报，退出码为 1。
