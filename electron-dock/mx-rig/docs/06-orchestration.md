# 编排中心

状态：MX Rig 0.4 已实现的边界；2026-09-16。

编排（orchestration）是一条被保存下来的固定流程：先做什么、按什么条件分岔、在哪里停下来等人。它由管理员在界面上拼装，存成配置，由 [编排运行时](05-agent-center.md) 编译成一张真实执行的图。

## 为什么是"节点调色板"，不是脚本

作者能决定的是：**下一步走哪个已知步骤、带什么参数、结果存进哪个变量**。作者不能决定步骤本身怎么实现。

这条线划在这里，是因为编排要能在浏览器里编辑、由管理员保存、对所有人生效。如果保存的配置可以变成任意执行逻辑，那么"改一条编排"和"往服务端塞一段代码"就是同一件事，Internal 的工具允许列表也随之失去意义。节点类型固定，工具仍受允许列表约束，写动作仍然逐次确认——编排只是把这些既有边界串起来，一个都没有放宽。

## 七种节点

| 类型 | 作用 | 关键字段 |
| --- | --- | --- |
| `tool` | 调用一个被允许的工具 | `tool`、`args`、`capture`、`next` |
| `branch` | 按变量的值分岔；只判断，不做事 | `test`、`then`、`otherwise` |
| `fanout` | 几条互不依赖的分支都要跑，全部到齐后再继续 | `branches`、`join` |
| `approval` | 停下来等人看过再放行 | `message`、`next` |
| `analyze` | 把已收集的证据交给一个 Agent，产出文字结论 | `agentKey`、`instruction`、`next` |
| `subflow` | 把另一条已保存的编排整条嵌进来 | `orchestrationKey`、`inputs`、`next` |
| `finish` | 写下结论并结束 | `message` |

`next` / `then` / `otherwise` 为 `null` 表示走到结束。

### 变量

变量是一个扁平的字符串袋子。来源有两个：运行编排时填写的 `inputs`，以及 `tool` 节点的 `capture`。

```jsonc
"args":    { "taskId": "{{taskId}}" },          // {{name}} 取变量，其余是字面量
"capture": {
  "runId":        { "from": "run.id" },                                  // 点路径取值
  "onlineRunners": { "from": "runners", "select": "count", "where": "online" }  // 数数组，可按字段筛
}
```

取值路径只允许点号分隔的字段名，且只读自有属性——`__proto__.x`、`constructor.name` 一律读不到。

### 判断

`{ var, op, value | values }`，`op` 为 `exists / missing / eq / ne / gt / lt / in`。数值比较遇到非数字返回"不成立"，不会在半路抛错。

### 分叉汇合

`fanout` 声明两到四条分支和一个汇合节点。分支**按顺序依次执行**，不是并发——一个任务同一时刻只有一个执行器、一次确认，真并发只会让两条分支抢同一个待确认的工具调用。它买到的是结构：分支之间互不依赖，汇合节点只跑一次，在最后一条分支到达时。

汇合的计数在编译期就定好了，运行时只是数到达次数，并且和暂停点一起 checkpoint：一条分支停在确认上，另一条还在队列里，恢复之后两条都不会丢。

两个会让编排半路停住的形状在保存时就被拒绝：某条分支走不到汇合节点（永远等不齐），以及分叉之外的节点指向汇合节点（提前用掉一个名额）。

### 子编排

`subflow` 在**编译期整条内联**，不是嵌套执行。内联之后仍然是一张平图，所以确认、checkpoint、轨迹、步数预算全都照旧工作；嵌套运行时得把这些各自重新实现一遍。

子编排的节点和变量都带上调用它的那个节点 id 作前缀，因此同一条子编排在一个父编排里可以用两次而互不干扰：

```jsonc
{ "id": "web", "type": "subflow", "orchestrationKey": "dispatch-one",
  "inputs": { "taskId": "{{webTask}}" }, "next": "el" }
// 父编排读子编排的结果：{{web__runId}}
```

环、找不到的子编排、超过三层嵌套、展开后超过 80 个节点，都在保存时拒绝。子编排里的 `finish` 结束的是**整条编排**，不是"子编排返回"——那是它字面的意思。

### 手工摆位置

拖动节点会把它钉在那个位置（按 8px 网格吸附），位置存在 `layout` 里，键是编译后的节点名。没有位置的节点仍然自动分层排布，所以只挪一个节点不需要为其它节点都记一份坐标。「自动排布」清空 `layout`。

## 定时执行

只有**能自己跑完**的编排可以排期。保存时会拒绝带人工检查点、写工具、子编排或必填输入的编排——定时执行时没有人在场，这些会让任务停在 `awaiting_approval` 直到有人碰巧看见，每天积一条。

```jsonc
"schedule": { "cronExpr": "0 9 * * 1-5", "timezone": "Asia/Shanghai", "enabled": true }
```

五段式 cron，时区用 IANA 名字，复用测试平台已有的 cron 实现。服务每 30 秒检查一次（`MX_RIG_ORCHESTRATION_TICK_MS` 可调），到点的编排以服务账号身份在一个独立 Runtime 上启动，一次只跑一条。触发时间记在 `.runtime/control/schedule.json`，**不写进配置文件**：写进去会让每一次定时触发都产生新的策略版本号，把别人正在看的确认全部作废。

定时产生的任务归服务账号所有——用管理员 token 登录的会话能在工作台看到它们，用 Launcher 身份登录的管理员目前看不到。

## 保存前一定会做的检查

存进 Internal 之前，每一条编排都要通过：

1. **schema 校验**（zod，strict）——多余字段是拒绝，不是忽略。
2. **展开子编排**——内联之后才做后面的检查，所以子编排里的悬空边也是父编排作者的问题。
3. **结构校验**——入口存在、节点 ID 不重复、每条边都指向真实节点、工具在注册表里、引用的变量有来源、引用的 Agent 存在、分叉的汇合算得齐。
4. **编译**——用一组空操作 handler 真正编译一次。
5. **定时规则**（如果填了）——这条编排能不能无人值守跑完。

倒数第二步是关键：**能存下来的编排一定能编译**。作者在编辑时就会看到"节点 has_runner 判断了未定义的变量 ghostVariable"，而不是让操作者在跑的时候撞上。

从入口不可达的节点只报警告不拒绝——半拼好的分支是编辑过程中的正常状态，为此丢掉作者的工作不值得。

界面上的「校验并预览」走同一条路径，但**不写入**：服务端编译草稿、把真实的图形状还回来，上方的图随即换成草稿版本。作者核对的那张图，就是保存后会执行的那张。

## 执行

编排任务和 Agent 任务共用同一套运行时，因此自动继承：写动作逐次确认、确认只对当前参数生效、策略版本变化即作废、取消、步数预算、checkpoint 与重启后不重放。

一条编排里有两种暂停点：

- `tool` 节点调用写工具（如 `tests_run`）→ 展示工具名与渲染后的完整参数。
- `approval` 节点 → 展示作者写给确认人的那句话。

两者都记成同一种待确认记录，拒绝都意味着编排停止，不会替你走另一条分支。

`analyze` 节点只做一次模型调用，**不提供任何工具**：它负责总结编排已经收集到的证据，不负责自己去找更多。它消耗与 Agent 对话同一份步数预算。

任务启动时用的是当时那一版编排；保存新版本不会改变正在跑的任务。

## 内置两条

- **有人接才派发**：先读执行机，没有在线的就直接说清楚并停止，绝不制造一条永远排队的 Run；有在线的才进入派发确认。
- **失败定级链**：拉齐执行结论、用例级结果与产物，交给「失败定级员」给出四选一的判断和下一步，报告前停下来让人复核。

两条都可以改写、可以停用，但不能删除——停用后它不出现在工作台，也不能被任务引用。

## 还没有的

- **节点类型仍然由运行时提供。** 作者组合已知步骤，不能定义新的步骤实现——这不是没做完，是这条产品线的边界：能在浏览器里改、由管理员保存、对所有人生效的配置，一旦可以变成任意执行逻辑，工具允许列表就没有意义了。需要新步骤时，加一个节点类型到 `packages/graph/orchestration.mjs` 的调色板，走代码评审。
- 分叉是顺序执行的，不是并发；想要真正同时跑，靠的是测试平台那一侧的多台执行机。
- 没有子图级别的循环控制（只有全局步数上限），没有跨任务共享 checkpoint。
- 定时执行不支持需要人参与的编排，也没有失败重试与告警——失败的定时任务会留在任务列表里等人看。
