# 对话工作台：固定项目上下文，再把验证过的流程变成任务

创建：2026-10-18。范围：`mx-rig`。本文基于当前仓库代码和用户提供的两张截图整理。

**状态：设计与分阶段实施方案。** 文中“现有”指已在源码中确认的能力，不代表本轮重新完成了线上验收；“本轮预览”指独立导航与交互演示；“规划”指尚未接入实际后端的行为。不能把演示结果当作真实测试证据。

本轮预览入口为 `/rig/conversation-preview.html`，使用示例项目、配置草稿、模拟冒烟证据和模拟复跑门禁，提供返回现有工作台的真实链接。预览不调用模型、不执行测试、不写服务端业务数据，不改变现有默认入口。它用于比较新旧功能组织，验证操作顺序，再决定后续真实接入范围。

## 1. 要解决的问题

MX Rig 已经部署，也能在本机打开。此次调整的目标是让日常使用更直接：按项目组织聊天，在开始前通过固定表单明确本机目录、分支、环境和执行位置，在对话中完成测试分析与探索，然后把验证过的流程保存成可重复执行的任务。

这不是重新建设测试平台。继续复用当前的 Mission、用例簿、实现提案、规程试车、执行计划、Runner、Run、测试版本和证据存储。新工作集中在两个地方：

1. 把分散入口收进一条可理解的工作流程。
2. 将项目上下文与“是否可以启用自动任务”的关键条件，从提示词和界面约定提升为可检查的契约。

用户提出“自己先冒烟通过，再做成系统流程自动测试”，方向成立，但需要区分三件事：

- **草稿可以随时保存。** 未通过的探索、用例、测试实现也有价值，不应强迫用户丢弃。
- **冒烟通过是进入系统化回归的前置条件。** 它说明当前环境可用、关键路径跑通，不说明权限、异常输入、边界条件、所有平台都已覆盖。
- **正式启用和定时需要更完整的证明。** 自动流程必须在固定版本和环境中确定性重放，并完成该任务声明范围的首次执行；不能用 Agent 的“看起来正常”替代执行证据。

约束：本轮只改 Rig 自身的设计与独立预览。不得改变 MX-H2I 的用户登录和联网，不改 Launcher 的 SSO、网络、VPN、路由、DNS、更新或会话逻辑，不因新工作台改动 Hub、Pay、Dataport、Embedding、Night-All 等系统。Rig 的身份接入继续使用现有方式；本设计不增加另一套登录系统。

连接信息仍然需要可见，但建议在常驻连接状态与详情中呈现；只有真实阻断条件才占据主任务区域。模型配置、权限、Runner 离线等问题应对应具体操作给出原因，避免让使用者在多个管理页寻找同一个阻塞。

## 4. 页面与产品对象

### 4.1 日常界面

左侧以项目为第一层，下面是该项目的聊天。置顶、最近更新、归档等可以逐步增加，但首版只需项目分组、创建聊天、选择已有聊天。新建聊天前必须完成上下文，不允许 Agent 从聊天文本猜项目。

主区保持三部分：

1. 顶部上下文条：项目、机器、本机目录、被测分支及提交、dev/prod、目标地址、被测端。
2. 中间对话：消息与真实动作卡片。动作卡片包含用例草稿、执行预览、运行中状态、证据和“保存为任务”。
3. 侧边详情：当前阶段、验收点、证据清单；需要时展开执行细节和高级配置。

项目设置承载本机绑定、环境、团队访问和测试资产。全局设置承载模型、工具策略和执行机管理，沿用现有权限。首版不再创建新的 Agent 管理中心或新的总览大屏。

### 4.2 名称与现有数据的映射

| 用户看到的对象 | 含义 | 复用对象 |
| --- | --- | --- |
| 项目 | 被测应用与团队共享资产 | app |
| 聊天 | 围绕一个固定上下文的测试讨论与探索 | Mission，保留 workbench 关联 |
| 验收点 | 本次要验证的可观察结果 | 用例簿及其 revision |
| 流程草稿 | 可以修改、尚未启用的步骤或代码 | Procedure draft / implementation proposal |
| 冒烟结果 | 关键路径在指定上下文中的实际结果 | Run / procedure replay，附范围 |
| 自动任务 | 已定义怎么跑、跑什么、在哪跑的可复用任务 | 执行计划 task，绑定规程或测试版本 |
| 执行记录 | 一次确定的运行与证据 | Run |

聊天与自动任务应在界面上分名，避免再次把 Mission 和 `mxt_tasks` 都叫“测试任务”。聊天可以产生多个流程草稿和自动任务；自动任务的多次执行可以回到原聊天分析，但不能修改历史证据。

## 5. 固定配置流程：让程序核实，让人选择

建议顺序：**项目 → 执行机器 → 本机目录 → 分支/提交 → 环境 → 核对并开始**。相同项目下一次聊天可以带入已保存值，但必须展示并验证，不能把上一次选择当作永远正确。

| 字段 | 从哪里来 | 校验与行为 |
| --- | --- | --- |
| projectId | 当前成员可访问的项目列表 | 服务端验证项目存在、启用、具备所需权限 |
| hostId | 当前桌面运行时或显式选择的在线工位 | 本机路径只在所属机器解析；网页不能假装访问用户电脑 |
| localBindingId | 本机为该项目保存的绑定 | 与服务地址、账号/工作区、项目、机器关联，避免切账号误用 |
| localPath | 用户通过目录选择器指定 | realpath、目录存在、可读、与 Rig 数据目录不重叠；不从自由文本自动寻找 |
| requestedRef | 本机读取到的分支/显式提交 | 用户选择；解析为完整 commit，显示当前检出与所选分支的差别 |
| resolvedCommit | Git 实际解析结果 | 不允许模型填；执行前核验快照仍对应这个提交 |
| dirtyState | 当前源码观察 | 明确展示未提交修改；首版选择干净提交或显式快照，不自动 stash/reset/checkout |
| environmentId | 项目环境列表，预设 dev/prod 名称 | 环境名称存在不代表 URL 已配置或执行已获准 |
| environmentRevision | 环境保存时的版本 | URL、动作范围、凭据引用等变化后，旧证明不能直接用于新配置 |
| targetUrl | 当前环境配置 | 规范化 origin；不由模型根据项目名猜地址 |
| platform / dataMode | 用户选择或已保存配置 | 与 suite、Runner 能力及环境对应；mock 结果明确标记 |

### 5.1 本机绑定与代码快照

复用 `sourceGit()` 和现有只读源码/项目快照实现。`sourceGit()` 已禁用 hooks、fsmonitor 和交互提示，见 `packages/runtime/source-repository.mjs:8`。选择其他分支时读取隔离快照，不改变开发者当前检出。

持久化的绑定只保存恢复所需信息；每次启动或续接前仍检查目录、仓库身份、提交和权限。目录不存在时显示“此机器需要重新绑定”。不能看到历史 `sourceBaseline` 就认为现在仍能读取源码。

优先把绝对路径留在本机。服务端保存项目、机器、绑定标识、版本摘要与执行所需元数据；团队成员在另一台电脑打开聊天时看到“来源于另一台机器”，而不是尝试使用同一个绝对路径。现有记录可能含目录，本方案不要求立即迁移或删除历史字段。

对没有 Git 的目录，现有项目快照能力可以保留，但不能虚构分支。首版新工作流可要求选择 Git 项目；后续若开放无 Git 模式，应显式标记“目录快照”，以内容指纹代替 commit，并提供对应验收。

### 5.2 环境预设

新增项目时预置 `dev`、`prod` 两个环境名称，URL 为空、待配置，不能推导线上域名。最小环境记录包含：名称、targetUrl、允许的 origin、被测端、默认数据模式、凭据引用和 revision。

dev 也不是无限授权；测试写操作仍受项目权限和执行策略限制。prod 首阶段用于明确目标、查看历史和分析证据，实际浏览器行为继续服从现有 productionHosts 禁区。若以后需要生产只读探测，需单独定义允许的检查项和执行接口；“页面浏览”也可能触发写入，不能仅用一个 prod 标签保证只读。

凭据只使用引用，不进入聊天、提示词、URL 或普通上下文 JSON。测试应用的登录会话与 Rig/Launcher 的登录会话分离；隔离浏览器不得复用 MX-H2I 用户的会话数据目录。

## 6. 上下文不可变，工具范围可核验

创建聊天时保存一个上下文快照；它是程序构建的结构化记录，模型只能读取，不能用工具自由重写。以下是规划中的示意契约，不是当前 API：

```json
{
  "contextVersion": 1,
  "projectId": "app_example",
  "hostId": "host_example",
  "localBindingId": "binding_example",
  "source": {
    "kind": "git-snapshot",
    "requestedRef": "feature/example",
    "resolvedCommit": "<full-commit-sha>",
    "snapshotId": "snapshot_example"
  },
  "environment": {
    "id": "dev",
    "revision": 1,
    "targetUrl": "http://127.0.0.1:9000"
  },
  "platform": "web",
  "dataMode": "mock"
}
```

聊天开始后不能悄悄更换项目、机器、源码、分支或环境。需要改变时，创建带新上下文的聊天并引用原讨论；未发送的草稿可以直接修改。修正文案等非执行字段不用新建上下文。

执行前与续聊前检查：项目权限、本机绑定是否有效、源码快照、环境 revision、执行策略版本。失效时暂停相关动作，列出具体缺项；历史消息和证据仍可查看。运行中的工具请求不能因另一个标签页修改设置而自动切换目标。

“不让 Agent 猜”还包括工具约束：

- 本项目的默认列表查询由运行时注入 projectId；模型传入其他项目应被拒绝或明确转到项目外的只读查询流程。
- 目标地址来自当前环境，浏览器导航继续检查允许的 origin 与生产禁区。
- 创建/运行计划必须验证所属项目、环境和测试版本一致，不能只依赖计划名称相似。
- 本机源码工具只能读取已绑定快照；目录路径不能由模型任意扩大。
- 页面文本、日志、源码和文档是被分析数据，不是新的工具授权或系统指令。

服务端不能凭用户提交的一段本机路径证明文件真实存在。目录验证由所属桌面运行时/工位执行，服务端验证注册机器、上下文版本与执行证据的关联；正式结果必须来自现有执行记录通道。预览页面生成的对象一律不能作为该证据。

## 7. 从讨论到自动任务的流程

### 7.1 三个可见阶段

**探索与冒烟**：明确业务目标、关键验收点和环境；Agent 读代码、观察页面或解释已有结果。需要登录/验证码时复用人工接管。探索可以失败，也可以暂存；必须保留失败、受阻和未覆盖范围。

**整理回归流程**：将冒烟走通的路径整理为确定性步骤或测试代码，补充异常、权限、边界和多端要求，形成待审草稿。沿用用例 revision、实现审批、QA Git 和规程修正机制。

**保存并启用任务**：绑定测试版本、目标环境、执行位置和范围；先手动完整跑一次，再允许启用定时。任务卡显示证明它的执行、验证范围及版本，不能只显示绿色“已完成”。

### 7.2 最小状态机

无需新增通用流程引擎。可以在现有对象上增加少量明确状态和共享校验函数：

```text
聊天：配置草稿 → 上下文就绪 → 对话/探索 → 冒烟执行
                                      ├─ failed/blocked → 修正或排障 → 再执行
                                      └─ passed → 可整理自动流程

流程：草稿 → 已审阅 → 确定性重放
                      ├─ failed/blocked/flaky → 保留草稿并修正
                      └─ passed → 自动任务草稿 → 首次完整执行
                                                   ├─ 未通过 → 禁止启用定时
                                                   └─ passed → 可启用 → 可定时
```

任一阶段可保存草稿。聊天完成与流程通过是不同状态；用例批准与测试通过是不同状态；派发成功与执行通过也是不同状态。

当前 Mission 仍使用原有 queued/running/awaiting_approval/completed/blocked 等运行状态。上述产品阶段可以由实际对象推导，不应把所有阶段再复制成另一套互相矛盾的任务状态。

### 7.3 冒烟证明的范围

冒烟至少包含目标可达、应用关键入口可用、声明的关键路径断言完成。项目可选择不同的冒烟集合，但证据应写明实际执行的用例和未执行内容。

有效的冒烟结果必须同时满足：

- Run 属于当前项目和所选环境/数据模式/平台。
- 测试代码或规程 revision 与当前候选一致。
- 实际执行的断言数量大于零，预期的关键验收点没有 missing/skipped/blocked。
- 原始结论为 passed，并有可查看的执行和证据引用。
- 源码快照只证明分析和测试资产的来源；若环境没有提供部署版本，明确写“线上部署提交未知”，不能把本机 commit 当作线上部署证明。

冒烟通过后仍需针对任务范围补充系统化回归。Web 通过不等于 Electron 通过；mock 通过不等于真实接口通过；dev 通过不等于 prod 通过。首版不要求每个项目都建设完整覆盖率体系，只要求清楚声明范围和缺口。

## 8. 证据、审批与定时门禁

### 8.1 证据记录

复用 Run、规程 replay 和产物引用，不另造结果存储。建议在执行快照中补齐：contextHash、environmentId/revision、sutRevision、testRevision、caseRevision、runnerId、执行配置指纹和范围摘要。

`sutRevision` 表示实际被测版本，可能来自源码快照、安装包或部署元信息；未知时保持 null。`testRevision` 表示 QA commit 或 procedure revision。两者都应在证据卡中可见，不能继续用一个模糊的“版本”字段替代。

截图、录像和日志是证据材料；红绿结论来自确定性断言与执行结果。模型负责提出、解释和归类，不修改判据来凑通过。失败修正沿用现有规程提案、重放验证和人工审批。

### 8.2 最少且具体的审批点

不把每个页面点击都升级为新的流程审批。现有策略允许的操作继续执行。需要用户决定的是：确认验收标准、批准测试资产变更、启用具有外部影响的自动任务，以及既有策略要求的敏感动作。

审批界面必须给出具体对象、版本、环境和影响；不能只问“是否继续”。批准测试代码不代表已经证明测试通过；批准任务也不能绕过确定性失败。草稿保存不需要先跑通。

### 8.3 服务端统一校验

规划中的共享校验函数可命名为 `validateTaskReadiness()`；名字和文件归属可在实施时确定。它应复用现有计划哈希、用例 revision、规程试车和测试版本证明，不建设新调度器。

调用点包括：规程激活、自动任务启用、cron/once/webhook 开启、计划关键配置更新，以及调度器准备执行时。服务端必须与界面共用规则，不能只禁用按钮。

最小规则：

1. 项目、环境、suite、Runner 能力及权限有效。
2. 存在符合当前任务范围的真实 passed 记录，且测试版本、用例/规程版本、环境版本与执行配置指纹一致。
3. 不能仅凭同一个 taskId 的历史通过，也不能仅凭任意一次同 QA commit 的通过。
4. flaky、blocked、cancelled、expired、missing 和 skipped 均不自动满足启用条件；将来如支持豁免，必须明确范围、理由、负责人和有效期，不改写原始结果。
5. URL、环境策略、测试代码、断言、关键运行参数变化时，标记“需要重新验证”，保留原证据与旧配置。定时不能继续使用失效的证明。
6. 团队定时绑定明确的已发布测试版本。若将来提供跟随 latest，必须定义新版本验证与切换规则，不自动继承旧版本证明。
7. 前端先预览；提交带 expectedRevision、contextHash/planHash、验证 Run ID 和 requestId。服务端重新计算并拒绝过期或重复冲突请求。

新规则会影响现有可直接设 cron 的接口，所以应分阶段兼容：先用于新工作流创建的计划，并显示旧计划“尚未按新规则验证”；不能在本轮预览中批量停用现有计划。扩大到全部计划前，需要迁移报告和明确执行策略。

## 9. API 与桌面契约建议

本节全部是后续规划。优先扩展已有资源，不要求将下表逐项变成新接口。

| 需要的能力 | 复用入口 | 最小扩展建议 |
| --- | --- | --- |
| 项目列表及权限 | `/api/v1/apps`、`/api/v1/apps/:app/access` | 使用已有项目权限；不要新增身份系统 |
| 目录选择与本机核验 | 桌面 `workspace-pick`、`source-status/connect` | 将机器绑定持久化；增加只读分支枚举、上下文校验；不得自动切换原检出 |
| 项目环境 | 项目设置/现有文档存储 | 新增项目级环境列表与 revision，可使用已有 FileDocument/PgDocument 模式 |
| 创建聊天 | `POST /api/rig/v1/test-tasks` | 新版本请求要求结构化 context；先验证再建就绪聊天，旧请求保留原入口行为 |
| 续聊 | `POST /api/rig/v1/missions/:id/followup` | 服务端读取已冻结 context，客户端只提交消息与预期版本 |
| 用例草稿与确认 | `.../missions/:id/cases`、`:confirm` | 在聊天卡片就地调用，保留 CAS revision |
| 实现草稿与批准 | `.../missions/:id/implementation`、`:approve` | 延用 sourceBaseline、实现 hash 和用例版本 |
| 冒烟预览/执行 | `.../missions/:id/executions:plan|dispatch` | 明确执行范围；冻结环境与两类版本；保留幂等 requestId |
| 对话轨迹固化 | `ProcedureBench.capture()`、`/procedures:capture` | 只生成草稿；不把捕获成功视为试车通过 |
| 无模型重放 | `ProcedureBench.fire()` / 现有 Runner | 真实返回 passed/failed/blocked，不由对话文本生成 |
| 测试版本发布 | `/projects/:app/test-versions` | 保留 bundle/CAS/Run 对账；新流程要求更严格的范围与 passed 校验 |
| 自动任务及调度 | `/api/v1/tasks` 与现有 scheduler | 增加验证证据和上下文关联，执行服务端 readiness 检查 |

创建聊天请求示意：

```json
{
  "app": "example-project",
  "goal": "验证核心登录后页面与查询流程",
  "context": {
    "contextVersion": 1,
    "projectId": "app_example",
    "hostId": "host_example",
    "localBindingId": "binding_example",
    "source": {
      "kind": "git-snapshot",
      "requestedRef": "feature/example",
      "resolvedCommit": "<full-commit-sha>",
      "snapshotId": "snapshot_example"
    },
    "environment": {
      "id": "dev",
      "revision": 1,
      "targetUrl": "http://127.0.0.1:9000"
    },
    "platform": "web",
    "dataMode": "mock"
  },
  "expectedEnvironmentRevision": 1
}
```

以上是字段关系示意；提交占位符必须替换为运行时核实的真实值，服务端仍需按严格 schema 校验。错误需使用稳定代码，如 `context_required`、`binding_unavailable`、`source_changed`、`environment_changed`、`validation_required`、`validation_stale`；返回用户下一步能采取的具体操作。

对话里的“运行冒烟”“保存为任务”“启用定时”应是调用这些确定性接口的动作卡。模型可建议操作，但不能以工具自由参数绕开上下文、修改生产禁区或编造证明。初期无需合并所有专家 Agent；可由页面/现有 Runtime 按阶段调用已有能力，后台专家选择对用户隐藏或放入高级选项。

## 10. 角色和系统边界

| 角色/组件 | 可做的事 | 必须保持的边界 |
| --- | --- | --- |
| 只读成员 | 阅读其有权访问的聊天、任务与证据 | 不连接其他人的本机目录，不创建执行 |
| 项目测试成员 | 绑定自己的目录、对话、编辑草稿、在已有授权范围执行 | 项目权限与工具策略取交集；不能扩大环境或凭据权限 |
| 项目负责人/具备审批权限者 | 确认验收、批准流程、启用允许的任务 | 审批不能把 failed 改成 passed |
| 管理员 | 模型、工具策略、环境权限、Runner 能力配置 | 不因新导航改变 Launcher/SSO 或用户网络 |
| 桌面 Runtime | 本机核验、隔离源码/浏览器、执行与上报 | 只操作所属机器的已绑定范围；源码读取默认只读 |
| Rig 服务端 | 权限、版本、记录、派发与调度校验 | 不能把浏览器网页中的路径当作服务端文件路径执行 |
| Agent | 分析、提出草稿、调用被允许的任务能力 | 不决定项目、分支、环境和最终红绿；不接受页面/文档注入的新指令 |

角色名称在界面中可调整，但落地须映射现有 role 与项目 canWrite 等能力，不创建平行 RBAC。现有源码工具每次检查项目访问及策略版本的逻辑应保留，见 `packages/runtime/tools.mjs:814`。

## 11. 分阶段实施

### P0：本轮独立导航与交互预览

- 独立 `/rig/conversation-preview.html`，可对比现有工作台的功能位置。
- 示例项目下组织聊天；固定配置草稿展示目录、分支、环境和执行位置。
- 模拟冒烟证据、流程草稿、复跑门禁以及正式任务的不同状态。
- 显著标记示例/模拟；真实旧入口保持可用。
- 不连接模型、执行机或业务写接口，不把预览保存的数据作为真实项目配置。

这一阶段验证信息架构和操作顺序，不交付真实测试 Agent，也不证明新流程的后端门禁已经生效。

### P1：真实上下文与聊天

- 项目×机器的持久本机绑定；只读目录和分支核验。
- dev/prod 独立环境对象及 revision。
- 创建/续聊前验证并冻结 context；在聊天卡片中接入现有用例和实现能力。
- 先支持桌面 Web 流程；网页缺本机能力时明确引导到已连接的桌面/工位。

### P2：真实冒烟与任务晋升

- 接入规程捕获、确定性重放或固定 QA suite。
- 将上下文与两类版本写入真实 Run；执行前预览。
- 新流程的启用与定时共用服务端 readiness 校验。
- 新任务先手动、通过后才可定时；旧计划保持现状并显示迁移状态。

### P3：收敛入口和既有计划迁移

- 把日常规程、实现、证据、任务卡集中在对话工作台；高级管理保留原界面链接。
- 基于实际使用反馈减少重复入口，再决定是否更换默认首页。
- 为旧计划补环境关联与验证记录；逐项迁移，保留原执行历史。
- Electron、团队工位、多平台回归按实际条件追加，不能用 Web 模拟演示宣称双端交付。

## 12. 验收矩阵

| 场景 | P0 预览应表现 | 真实接入后的验收 |
| --- | --- | --- |
| 未选择项目/路径/分支/环境 | 开始按钮阻止并定位缺项 | API/Runtime 同样拒绝，不能绕过前端 |
| 项目切换 | 聊天按项目分组，不混用草稿 | 所有执行、用例、源码读取均受当前项目权限与上下文约束 |
| 本机路径 | 明确标注草稿或示例，不显示“已核实” | realpath 核验、目录不存在、跨机器、Rig 数据目录重叠分别给出正确结果 |
| 分支选择 | 显示选择值，不声称已读取 Git | 枚举真实分支，完整 commit 固定，原工作区分支和文件不变化 |
| 重启/换电脑 | 说明本机绑定需要实际接入 | 重启可恢复并重新核验；另一台机器要求重新绑定 |
| 源码/环境变化 | 演示证明失效与重新验证 | 已有证据保留，续聊/执行拒绝使用过期 context |
| dev/prod 与 mock/real | 表单演示 dev/prod，功能对比解释与 mock/real 的区别 | 数据模型、Run、报告分别记录，不能互相替代 |
| prod | 提示示例不产生执行 | 原生产禁区继续生效，无自动授权或访问 |
| 冒烟失败/受阻 | 失败阻断固化，保留当前对话；尚未演示 blocked | 使用真实 Run 状态，failed 与 blocked 明确分开 |
| 模拟冒烟通过 | 仅解锁演示步骤，标注模拟 | 模拟 ID 或本地页面伪造证据不能被服务端接受 |
| 冒烟通过后的回归 | 显示需补充范围并复跑 | 关键路径通过不替代完整任务范围结果 |
| 修改测试或环境后复跑 | 旧模拟证据失效 | revision/hash 不一致时启用和调度都被拒绝 |
| flaky/skipped/missing | 不当作普通通过 | 新流程门禁不自动接受；报告保留原始语义 |
| 直接调用定时 API | P0 不调用任何业务写接口 | 无证据、证据不匹配、过期证明均被服务端拒绝 |
| 重复派发 | 预览不产生真实运行 | 同 requestId 幂等，参数变化冲突，沿用现有机制 |
| 权限撤销 | P0 仅说明真实权限边界 | 下一次读/写/执行重新校验，不能使用缓存角色绕过 |
| 旧入口与现有计划 | 原入口可访问，默认页面不变 | 旧计划按迁移策略继续运行，记录不丢失 |
| MX-H2I 登录/联网 | 预览代码无相关调用或写入 | 改动范围与回归检查证明未改变 Launcher/H2I 的登录、网络和会话 |

P0 的页面交互检查不能代替 P1/P2 的 API 与执行验收。后续只在对应能力接入时增加有意义的测试：固定上下文拒绝、证据过期、幂等、权限、真实确定性重放和调度门禁。不要为了模拟界面的每个文案复制实现逻辑写测试。
