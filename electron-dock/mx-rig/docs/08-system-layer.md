# 系统：随版本更新的操作教程，与对话式下任务

状态：MX Rig 0.7 已实现；2026-09-16。

这一层解决两个具体问题：新人不知道下一步点哪里，以及老用户不知道这个版本多了什么。它不是第三份新手文档——0.5 已经有总览上的五步横幅和「新手引导」页，两者都撑不住一个还在长的产品：横幅只认识五件事，页面是一次性读物，发版后没人会重读。

## 三种事实，分开标注

系统里每一项任务都要回答"这件事到底做了没有"。答案只有三个来源，界面上分别标注：

| 来源 | 判定依据 | 例子 | 能不能被伪造 |
| --- | --- | --- | --- |
| 平台状态 | 测试内核与已存配置：应用、计划、执行机、执行结果、Provider、编排、通道 | 「接入一个被测应用」读 `listApps()` | 不能，请求里说什么都不看 |
| 个人任务历史 | 这个成员自己的 Mission 记录与事件 | 「亲手批准一次写动作」读 `events.kind === 'approved'` | 不能，按 owner 过滤 |
| 界面上报 | 工作台主动上报的一个名字 | 「打开一次执行的完整报告」 | 能，所以界面明写"界面上报" |

第三类存在的理由很简单：服务端看不到有人点开了报告、按了打印、或者读完了一条口径。与其假装能验证，不如把来源写在卡片上——这一层的说服力全靠这句实话。上报的内容是封闭枚举（`SIGNALS`），只记名称和时间，不带路径、工具名或任务 ID。

平台状态是整个部署共享的：第一个人接入应用，对所有人都算接入了。任务历史、上报与领取记录按人保存。这条区别写在页面底部。

## 任务目录与版本

目录在 `apps/server/system.mjs`，是纯数据加纯函数：`systemFacts()` 归一化事实，`evaluateSystem()` 输出每项任务的状态、章节进度、等级与更新提示。没有 IO，所以整份目录可以在没有服务的情况下测试。

- 每项任务带 `since`，即它随哪个版本发布；目录带 `SYSTEM_VERSION`（当前 0.7）。0.7 新增两项：「看一次模型边写边出」（界面上报）与「拿到一次结构化结论」（平台状态：有任务带 `finding`）。
- 成员看过哪个版本记在 `seenVersion`。`isNewer()` 逐段比数字，`0.10` 比 `0.6` 新。
- 界面上，`since` 比 `seenVersion` 新的任务标「新 · 0.6」，页面顶部出现一次"系统更新到 0.6"，按「知道了」才清除。
- `CHANGELOG` 记录每个版本新增了哪些任务，直接列在页面底部——升级是可见的，这是这一层与静态文档的根本差别。

主线五章跟着产品主线走：点火（第一条真实执行）→ 回收（读证据）→ 副驾（Agent、流式输出、结构化结论与边界）→ 编排 → 控制面。支线是手感与自救：换视角、开面板、停掉跑飞的任务、跑一次浏览器工具、在桌面端登录一次。

## 奖励只是进度

领取一项任务加经验，经验到阈值升等级，等级有称号。三条限制写在代码与页面上：

- **等级不解锁任何权限。** 角色仍然只有 viewer / operator / admin，由 Internal 判定。一个会发能力的教程就是第二套更差的策略引擎。
- **经验只来自"领取"。** 验证是真的，但奖励要点一下：默默把别人做出来的状态算成你的进度，什么也没教会。
- **领过不回收。** 执行机下线、应用归档，平台状态会退回去；那项任务的卡片会同时显示「已领取」和"未完成"的当前事实，而不是把奖励收走。

进度存在 `.runtime/control/system-progress.json`：每个成员只有 `claimed`、`signals`、`seenVersion` 三个字段，全部受封闭列表约束，文件不随流量增长。写入是临时文件加 rename，和 `settings.json` 同一套做法。

## 常驻面板

右上角「⬢ 系统」开关一个悬浮面板，它在 `#view` 之外，所以跨页面存活、每次重绘都不受影响。面板一次只讲一件事：当前该做哪一项、步骤、跳哪里、能不能领。想看全部就进「系统」页。开关记在 localStorage，私密窗口里读不到也不影响功能。

## 接口

| 方法与路径 | 角色 | 说明 |
| --- | --- | --- |
| `GET /api/rig/v1/system` | 任何已登录成员 | 任务状态、章节、等级、更新日志与口径 |
| `POST /api/rig/v1/system/signal` | 任何已登录成员 | 记一次界面上报，名称必须在封闭列表里 |
| `POST /api/rig/v1/system/claim` | 任何已登录成员 | 领取奖励；**服务端重新验证**，请求只说领哪一项 |
| `POST /api/rig/v1/system/seen` | 任何已登录成员 | 记住已看过的目录版本 |

读教程不需要 operator——它只是教程。派发、编排、切换通道仍然各按原有角色判定。

## 对话式下任务

任务工作台的输入框旁多了「解析成任务 ⌕」。它把一句话解析成**候选派发**，每个候选写清：匹配到什么、还缺什么、会不会被阻断，以及**将要发出的请求体本身**。确认之前什么都不会发生。

解析在 `apps/server/dispatch-intent.mjs`，不调用模型。三条理由：

- 派发是写动作。会替你挑测试计划的模型，也会挑错一个；确认页上的计划 ID 必须来自可核对的地方。
- 它必须在没有 Provider 的时候就能用——「跑一下登录验收」正是第一天会打的字。
- 理由要能列出来。"计划名匹配「compass、web、冒烟」"是人能核对的；一个软判断不是。

中文没有空格，所以匹配用的是二字切片：候选名字切成 `compass`、`electron`、`登录`、`录验`、`验收`，与句子的切片取交集算覆盖率。单个偶然重合的汉字不构成匹配。句子里出现 `tsk_*` 或 `trun_*` 时，ID 直接压过名字相似度。

三类候选：

| 候选 | 触发 | 缺什么时怎么办 |
| --- | --- | --- |
| 测试工作流 | 派发类动词，或匹配到某个计划 | 缺计划就给下拉，选了才允许确认 |
| 编排 | 匹配到编排名，或提到"编排 / 流程 / 巡检" | 必填输入逐个给输入框；已匹配到的计划自动填入 |
| Agent 对话 | 分析类动词，或匹配到某个 Agent | 没有模型时明确标注受阻，而不是假装能跑 |

没有在线执行机是候选上的一条**提示**，不是拒绝——派发出去会等执行机，这和测试失败是两件事。一条都对不上时，界面直接说该怎么改口，不硬凑一个候选。

## 当前边界

- 界面上报无法独立验证，只能证明"工作台这么说"。页面与本文都写明了这一点。
- 目录是服务端内置数据，不能在界面里增删任务。教程内容跟着版本走，不是给每个部署自定义的。
- 进度按 `principal.id` 存单机文件，和 Mission 一样不支持多副本共享同一状态目录。
- 解析器不做多步计划、不改写参数、不学习历史；它只做一次匹配。
- 支线任务「在桌面端登录一次」依赖桌面上报；Web 端看不到桌面的任务历史（两个执行面本来就不同步）。
