# 流程走查：罗盘双端冒烟与新项目上手（2026-10-06）

依据：M5 对真实 `feat/yjj/hdo_v2@a4cc5de` 的端到端运行、M6 的冒烟脚本，以及逐页走查工作台。

## 1. 罗盘 hdo_v2 全量冒烟：方不方便

### 1.1 Web 端：基本顺了，但“全量”名不副实

**现在怎么跑**（桌面端）：

1. 「项目与任务 → 从验收包创建」，选 `po-frontend` 目录，点建立（约 2 秒，原仓库只读）；
2. 「执行计划」页「启动本机执行机」；
3. 「罗盘 Web · 全部用例」立即执行。

约 1 分钟出结果，每条用例有录像、步骤和截图。实测：10 条通过，1 条失败。失败的是真实产品问题：策略页在平台列表接口失败时不加载列表。

| # | 问题 | 影响 |
| --- | --- | --- |
| W1 | 11 条用例只覆盖 hdo_v2 25 个路由里的 4 条主路径：登录、首页、AI 对话、策略。社媒线索、内容线索、账户与评论线索、人物画像、敌情发现、文件分析、Agent 超市、政情报告、设置、隧道都还没有用例 | “全量冒烟”目前只是主路径冒烟 |
| W2 | rig-specs 只有假数据模式，不支持对测试环境运行 | 回答不了“接真实后端是否正常” |
| W3 | 执行绑定在持有快照的那台电脑上；桌面端要一直开着，本机执行机要启动 | 适合个人日常，不适合团队每晚回归：电脑一关，定时计划就一直等到过期。测试仓库项目已由 M7b 解决（团队计划跑已发布版本，任何执行机都能领）；验收包的快照项目仍是这样 |
| W4 | 持有快照的电脑要有 Node.js 22 和 pnpm | 测试同学的电脑上不一定有 |
| W5 | 原分支前进后，更新基准要手动做；没有“新提交自动跑一遍” | 容易一直测旧提交。M7c 加了「上线检查」：一键更新到最新提交并跑全部用例；自动触发仍没有 |
| W6 | 假后端按页手写；hdo_v2 接口一改，用例要跟着改 | 维护成本随页面数增长；还没有“录制真实接口生成假数据”的工具 |

### 1.2 桌面端（Electron）：目前跑不起来

| # | 缺什么 | 说明 |
| --- | --- | --- |
| E1 | 可测的安装包 | 桌面端执行测的是安装包。M6 已有登记入口（项目设置 → 安装包），但 hdo_v2 还没有登记过。从快照构建安装包要下载 Electron、原生编译 better-sqlite3，Windows 安装包要在 Windows 上构建，这些都还没接进来 |
| E2 | 专用测试机 | 罗盘启动会初始化 Launcher、代理和隧道，不能在装有 MX-H2I 的办公电脑上跑；执行方式要求 Windows。目前没有接入这样一台执行机 |
| E3 | 正式登录的前提 | 需要评审过的非生产验证码钩子和专用测试账号；没有就保持受阻（这是对的，不能绕过） |
| E4 | 桌面端执行计划 | 因为 E1–E3，验收包没有给桌面端建计划 |
| E5 | 一次触发两端、合并报告 | Web 和桌面是两个计划，各出各的结果，没有“双端冒烟”这一个入口 |

**结论**：现在说“罗盘双端冒烟”，实际只有 Web 主路径能跑。桌面端卡在机器、安装包和账号三件需要人准备的事上，代码侧能做的是 E4 和 E5。

## 2. 测试一个新项目：复不复杂

### 2.1 顺序：你描述的是对的

登记项目 → 执行方式 → （用例）→ 执行计划 → 立即执行并确认通过 → 再开启定时。M6 把这条顺序落实到界面上：

- **上手清单**：项目页顶部，按真实状态判断每一步（执行方式、用例、执行计划、执行机、试跑通过、定时），并带你去下一步；全部完成后自动收起。
- **定时前先验证**：
  - 新计划只能手动；最近一次执行通过后，“定时重复”才能选；
  - 计划卡片显示“已验证 / 未验证 / 最近一次失败 / 最近一次受阻”；
  - 定时的改动进审计，可以查到谁、什么时候、从什么改成什么。

### 2.2 仍然复杂的地方

| # | 问题 | 建议 |
| --- | --- | --- |
| N1 | **最大的断点：测试代码从哪里来。** 执行方式需要“装着测试代码的仓库 + 一条命令”，新项目通常没有。Rig 的测试任务能让 Agent 起草测试实现，审批后导出成 QA 版本，但这个导出没有接到执行方式和计划上，计划跑不了它 | 测试实现审批通过后，提交到项目 QA 仓库，并自动建好（或更新）工作区执行方式。新项目的路径就变成：写用例 → Agent 起草测试 → 审批 → 立即执行 → 定时，不用手配执行方式 |
| N2 | 执行方式只有管理员能建，要懂引擎、仓库、工作目录、目标模式、命令、执行机类型。非测试专业的人到这一步只能等 | 向导式执行方式：先问“网页还是桌面”“测试代码在 Rig 里还是在我们的仓库里”“被测地址是什么”，命令和工作目录按选择自动填 |
| N3 | 计划表单里的术语：数据模式 mock/real、轨道 functional/demo、在哪跑 server/any/pinned | 默认值已经合理；把它们折进“高级”，只留名称、执行方式、被测地址 |
| N4 | 第一次立即执行常常卡在“等待执行机” | 上手清单已提供“在本机托管并启动执行机”（桌面端一键）；网页端仍要找一台电脑接入。服务器执行要部署了服务端容器才有 |
| N5 | “测试任务”（Agent 主导）和“执行计划”（手动配置）两条路并存，新手不知道从哪开始 | 新手引导和上手清单已经写明顺序；中期按 N1 合成一条主线 |
| N6 | 登记项目时填的“目录 / Git / 分支”和执行方式里的“代码来源”是两份，容易不一致 | 执行方式默认继承项目的代码来源，只在不同时才单独填 |
| N7 | “定时前先验证”只在工作台里约束；通过接口（CI、Jenkins）仍可直接建定时计划 | 有意保留给自动化，改动都进审计。需要的话可以改成服务端强制，给 CI 一个显式的豁免参数 |
