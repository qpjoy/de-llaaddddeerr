# 测试仓库：本机版本、验证、发布与同步（M7，2026-10-06）

起因：docs/22 N1——测试任务里 Agent 起草、人批准的测试实现，只能导出成本机的一个文件夹，执行计划跑不了它。另外，用户提出了测试仓库的设想（见 §1）。

## 1. 用户的设想

- 服务器或用户本机不一定能访问 Git 仓库，代码也可能是复制到本机的。
- 执行机用本地 Git：一个测试项目一个 `.git`，按版本或任务名建分支。
- 流程验证后同步到服务器，让其他客户端也能看到，或者基于某个计划修改调优。
- 用户在本机管理自己的测试版本（增删查改 Git 历史），把优化好的用例、流程、报告选出来同步到服务器。
- 最终可以直接对接要上线的分支，由 Rig 分析出流程和报告。

## 2. 评估：方向对，五处建议调整

| 设想 | 建议 | 理由 |
| --- | --- | --- |
| 本机一个测试项目一个 `.git` | **采纳**。M5 的罗盘已经是这样，M7 推广到所有项目 | 离线可用，不依赖任何 Git 服务器和凭据 |
| 按版本或任务名建分支 | **按任务建分支，版本用提交和标签** | 每个版本一个分支会越来越多。任务分支 `task/<任务>` 放这个任务每次批准的实现；本机主线 `main` 收已验证的；服务器版本对应 `published` 分支和 `rig/v<N>` 标签 |
| 同步到服务器的 Git 仓库 | **服务器不需要 Git 服务器：发布时上传 Git bundle** | `git bundle` 把一段 Git 历史打成一个文件。服务器只当文件存（与现有状态存储同一处），不跑 Git，也不需要仓库地址和凭据。其他客户端下载后 `git fetch` 进自己的仓库，历史和校验都由 Git 负责。以后有公司 Git 仓库，再加一个可选的镜像推送 |
| 用户随意管理 Git 历史 | **本机分支随意改；已发布的版本只追加、不改写** | 别人已经基于 v3 调优了，v3 就不能被改掉或删掉。撤回 = 发布一个新版本，或把旧版本标为不再使用 |
| 报告也选出来同步 | **报告不进 Git；进 Git 的是“怎么测”** | 报告、录像、截图是执行的产物，已经在服务器的执行记录里。每次执行都记了被测提交和测试版本，能双向追溯。“选好的报告”以后做成“把某次执行设为基线证据”，不往仓库里塞二进制 |

另外三条补充：

1. **发布要有证据**：只有“这一个提交被执行机跑过且通过”才能发布，服务器核对执行记录里的测试提交。这和 M6 的“定时前先验证”是同一条原则。
2. **团队的定时计划只跑已发布的版本**：草稿只在作者本机跑，所以每晚的结果在任何一台执行机上都可复现。远程执行机下载已发布版本的 bundle 来跑，见 §5 的 M7b。
3. **并发**：发布时带上“我基于的服务器版本”。服务器已有更新的版本就拒绝，提示先同步。合并在本机用 Git 做，冲突显示为文件列表。

关于“复制到本机的代码”：被测源码的快照现在支持没有 Git 的目录。Rig 把目录复制进自己的快照仓库并提交，基准记为这个提交加内容哈希；“原目录是否变了”用内容哈希比较。

关于“对接要上线的分支”：把源码快照固定到上线分支的最新提交，用已发布的测试版本跑一遍，再由 Rig 的 Agent 读执行详情出上线检查报告。M7 做好了地基（本机仓库、发布版本、证据链），这条放在 M7c。

## 3. 一次完整的流程（M7 做到的）

```text
测试任务：用例确认 → Agent 起草实现 → 人批准
   │  「写入本机测试仓库」
   ▼
本机测试仓库  project-workspaces/<项目>/qa
   task/<任务>   ← 每次批准的实现一个提交（用例映射在 .rig/cases/<编号>.json）
   │  执行与结果：用「本机测试仓库」计划派发（指定本机执行机，跑这个提交）
   ▼
执行通过（这个提交 = 已验证）
   ├─ 「合入本机主线」 → main
   └─ 「发布到服务器」 → 服务器版本 v<N>（bundle + 执行证据）
                          │  其他客户端「同步服务器版本」
                          ▼
                       published 分支、rig/v<N> 标签
```

## 4. 落地细节

- **仓库模板**（`packages/runtime/qa-template/web`）：
  - `@playwright/test`（与桌面端同版），带锁文件；
  - `playwright.config.mjs`：被测地址取自执行计划，录像开启，只跑筛选到的用例文件；
  - `rig/reporter.mjs`：把 Playwright 结果按 `.rig/cases/<编号>.json` 换算成平台的用例结果（schema 2），步骤带录像偏移；
  - 用例映射一个用例一个文件：两个任务覆盖不同用例时，合并不会冲突（最初是一个共享的 mappings.json，测试一跑就冲突，已改）。
- **写入**：用 Git 底层命令和临时索引生成提交，不切换工作区分支，不打扰用户自己在这个目录里的操作。同一个实现版本重复写入，不产生新提交。
- **执行方式**：内核新增 `POST /api/v1/apps/:app/workspace-suite`（测试工程师可用）。它按固定定义建立“本机测试仓库 · Web”，不接收命令，与规程回放的执行方式同理。计划指定本机执行机。
- **派发**：测试任务的“执行与结果”可以带上 `qaRef`（分支和提交）。执行机检出这个提交，用例与测试文件的对应关系取自实现的映射。
- **发布**（Rig 服务）：
  - `GET/POST /api/rig/v1/projects/:app/test-versions`，以及 `GET .../test-versions/:n/bundle`；
  - 存储与用例簿、实现历史同一处：单机是 JSON 文件，多副本是 PostgreSQL；
  - 发布时核对：执行属于这个项目、状态为通过、测的正是这个提交、基于的版本是服务器当前最新。
- **Git 依赖**：持有测试仓库的电脑要有 git。测试同学的 Windows 机器上不一定有，后续在桌面安装包里内置便携 git。

## 6. M7b / M7c 交付记录（2026-10-06）

### M7b：团队执行机跑已发布版本

- 内核新增固定定义的「已发布测试版本 · Web」执行方式（`POST /api/v1/apps/:app/published-suite`），仓库地址是 `rig-published://<项目>`，默认版本 `latest`。
- 任何执行机都能跑它，只有服务端执行器不行：版本要在执行机上检出，服务端拒绝时给出原因（`placement_impossible`）。
- 执行机凭这次执行的执行令牌下载版本（`/runner/v1/runs/:runId/test-versions[/:n/bundle]`）。服务端核对：
  - 令牌属于这次执行；
  - 执行正在进行；
  - 执行方式确实是已发布版本。
  
  执行机把 bundle 导入自己的缓存仓库，已合并进完整版本的旧增量自动跳过。
- 执行记录写的是 `rig/v<N>`、提交号和 `QA <提交>`，所以团队的执行结果也能证明这个版本。
- 工作台的项目「测试仓库」区块里，「团队计划」一步建好：已发布版本的执行方式，加上任意执行机都能跑的计划。
- 端到端：一台没有任何测试仓库的“团队工位”执行机跑 `rig/v1`，两条用例都通过。

### M7c：上线检查与 Agent 分析

- **上线检查**（「执行计划」页「测试项目工作区」，原分支或原目录有变化时出现）：
  1. 把基准更新到原分支的最新提交（复制来的代码就重新复制）；
  2. 跑覆盖全部用例的计划；
  3. 打开这次执行。
  
  旧快照保留，上一次的结果还能对照和复跑。
- **让 Agent 分析这次执行**（执行详情，执行结束后出现）：
  - 带着执行编号、计划和测试版本，跳到「测试任务」；
  - 有失败或受阻时用「失败定级员」，全部通过时用「结果分析师」；
  - 要求它把失败归成产品缺陷、环境受阻、用例问题或不稳定并附上证据，再单独给出能不能上线的建议；
  - 草稿要人确认后才开始，Agent 只读，不派发、不取消执行。
- 只有测试仓库、没有源码快照的项目（只填被测地址）怎么做上线检查：把团队计划的被测地址指向预发布环境，立即执行，再让 Agent 分析。

## 7. 存储：服务器会不会被撑满

**结论**：

- 测试代码是文本，按下面的设计，10 个项目各发布上千个版本也只占几十 MB；
- 真正占空间的是录像和截图，它们是执行产物，不进测试仓库，有保留期和总量上限；
- 被 `.gitignore` 忽略的文件不会进入提交；
- 图片要分两种看：小的测试素材允许，大的被发布检查拦下。

### 7.1 实测

用真实的测试仓库代码模拟一个持续增长的项目：200 个版本，每个版本改 3 个测试文件，每 4 个版本加一个，最后 50 个文件、300 条用例。测试文件里掺了随机内容，压缩效果比真实代码差，算是偏保守。

| 版本 | 测试文件 | 类型 | 这个版本的 bundle | 服务器上这个项目占用 |
| --- | --- | --- | --- | --- |
| v1 | 1 | 完整 | 6.3 KB | 6.3 KB |
| v2 | 1 | 增量 | 1.1 KB | 7.3 KB |
| v10 | 3 | 完整 | 15.8 KB | 15.8 KB |
| v100 | 25 | 完整 | 146 KB | 146 KB |
| v200 | 50 | 完整 | 298 KB | 298 KB |

如果什么都不清理，200 个版本合计 3.3 MB；按下面的方式清理后是 298 KB。外推：

- 一个项目 1000 个版本约 1.5 MB；
- 100 个项目约 150 MB；
- 测试文件再大 10 倍，也只有约 1.5 GB。

复现：`node scripts/measure-test-versions.mjs [版本数]`（200 个版本约 1 分钟）。

### 7.2 设计

- **bundle 是文件**：存在产物目录下的 `test-versions/<项目>/v<N>.bundle`，不在 JSON 或数据库里，没有 base64 膨胀。产物目录的总量统计包含它们；执行产物的定期清理只清 `runs/`，不会误删版本。
- **增量加完整版本**：
  - 平时每个版本只上传上一个版本以后的部分；
  - 第 1 个和每第 10 个版本上传完整 bundle；
  - 服务器上的历史是线性的（新版本必须包含上一个版本），完整版本已经包含之前的全部内容，所以它到达后，之前的增量文件删除，列表里标记「已合并进 vN」。
  - 一个项目常驻的大约是一份压缩后的完整历史，加不超过 9 个增量。
  - 完整历史大到一次传不上去（超过 8 MB）时，这一版改为增量。增量之间互不重叠，所以服务器上仍然大约是一份历史，只是同步时要按顺序取多个文件。
  - 另一台电脑同步时，跳过已合并的版本，直接从完整版本拿，再给跳过的版本补上标签。
- **每个项目的上限**：默认 1 GiB（`MX_RIG_TEST_VERSION_QUOTA_BYTES`）。增量会超出时拒绝，提示发布一个完整版本，或者检查仓库里的大文件。工作台显示「服务器上占用 x MB / 上限」。
- **不挤占磁盘保留区**：发布前检查磁盘剩余空间，不低于产物存储的保留值（默认 5 GB，`MXT_ARTIFACT_MIN_FREE_BYTES`），否则返回 507。录像上传和版本发布共用这条底线。
- **单次上传**：不超过 8 MB。发布检查把一个版本新带上的内容限制在 6 MB 以内，图片这类压缩不了的内容也能放下，超过就提示分成几个版本发布。

### 7.3 `.gitignore`、图片和视频

| 内容 | 会不会进服务器 | 机制 |
| --- | --- | --- |
| `node_modules`、`test-results`、`playwright-report`、`artifacts` 等被忽略的目录 | 不会 | 批准的实现由 Rig 直接写成提交，只包含实现里的文件，不扫描工作目录。有人在本机用 `git add -f` 强行提交，发布检查也会按路径拦下，跟 `.gitignore` 怎么写无关 |
| 执行录像、失败截图、Trace | 不会 | 它们是执行产物，跟执行记录走：默认保留 30 天，总量上限 20 GB，磁盘保留 5 GB。测试仓库模板已把输出目录设在被忽略的 `test-results/` |
| 视频文件（webm、mp4、mov 等） | 不会 | 发布检查直接拒绝，提示录像属于执行产物 |
| 压缩包、安装包、`.env*` | 不会 | 发布检查拒绝。安装包请登记在「项目设置 → 安装包」；`.env` 可能含密钥 |
| 小图片：上传用的测试素材、视觉比对的基准图 | 会 | 允许，因为测试需要。单个文件不超过 2 MB，一个版本新带上的内容合计不超过 6 MB |
| 中途提交、随后又删掉的大文件 | 会被拦下 | bundle 带着整段历史，所以发布检查逐个看两次发布之间的每个提交，不只看最终结果 |

**要留意的是视觉比对的基准图**。每更新一次截图基准，历史里就多一整份图片，Git 对图片几乎不能做差量压缩。估算：

- 100 张、每张 100 KB 的基准图，每次界面改版更新 20%，一次约 2 MB；
- 改版 100 次约 200 MB，仍在单个项目的 1 GiB 上限内。

建议：

- 只给关键页面放基准图；
- 基准图的更新单独作为一个版本发布，在任务里写明原因；
- 如果某个项目的占用接近上限，主要原因多半就是基准图。这时用下面 §8 的「压缩历史」。

### 7.4 本机

- 桌面端的测试仓库和执行机的已发布版本缓存，大小与服务器上的完整历史相当（上面的量级）。
- 本机录像在 `test-results/`，执行结束后上传，下次执行前由 Playwright 清空，不会一直累积。
