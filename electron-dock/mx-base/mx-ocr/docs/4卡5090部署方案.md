# 4× RTX 5090 + 128 核 部署方案（最终形态）

> 定稿于 2026-09-09，取代 [128核CPU服务器专项方案.md](128%E6%A0%B8CPU%E6%9C%8D%E5%8A%A1%E5%99%A8%E4%B8%93%E9%A1%B9%E6%96%B9%E6%A1%88.md)
> 该文档已作废（其前提「无 GPU」不成立），保留仅供纯 CPU 场景参考

## 实际硬件

```
GPU     : 4× NVIDIA GeForce RTX 5090 (32,607 MiB each, 总计 ~128 GB VRAM)
          GPU 3 挂载显示输出（Xorg / gnome-shell / firefox，占用 ~607 MiB）
CPU     : 128 核
内存    : 大容量
驱动    : 570.124.04
CUDA    : 12.8
架构    : Blackwell GB202, Compute Capability 12.0 (sm_120)
```

## 业务特征

- **图片 OCR 为主，并发要求高** ← 主要优化目标
- PDF OCR 量少，单个处理、慢一点可接受

---

## 一、结论

**回归双引擎，规格上调：**

| GPU | 角色 | 技术栈 |
|---|---|---|
| **0 / 1 / 2** | **图片 OCR 主力（高并发）** | PP-OCRv6_medium → ONNX → **TensorRT FP16** + Triton dynamic batching |
| **3** | **PDF 精修 + 备用** | PaddleOCR-VL-1.6 + **vLLM** |
| 128 核 CPU | GPU 饲养员 | 解码 / 预处理 / 后处理 / 网关 / 队列 |
| 大内存 | 缓存层 | `sha256(图片字节)` 内容寻址缓存 |

**OCR 是纯数据并行任务，不需要 NVLink / tensor parallel，4 张卡各跑各的即可。** RTX 5090 无 NVLink 这一点对本场景毫无影响。

---

## 二、⚠️ 最关键决策：不要用 PaddlePaddle 原生 GPU 后端

### 问题

**PaddlePaddle 官方 GPU wheel 不包含 sm_120 kernel**，在 RTX 5090 上直接报：

```
CUDA error: no kernel image is available for execution on the device
```

### 三条出路

| 方案 | 代价 | 推荐度 |
|---|---|---|
| 1. 社区 wheel（`horhe-dvlp/paddlepaddle-sm120-wheels`，CUDA 13.0 构建） | 非官方；**CUDA 13.0 需驱动 ≥580，当前 570.124.04 必须先升级** | ⚠️ |
| 2. 源码编译 `-DCUDA_ARCH_NAME=Manual -DCUDA_ARCH_BIN=120` | 编译数小时，每次升级重来 | ⚠️ |
| 3. **PP-OCRv6 → ONNX → TensorRT FP16** | 无 | ✅ **推荐** |

**方案 3 不是妥协。** 追求极限吞吐时 TensorRT 本就快于 Paddle Inference，选它等于顺手把性能拿满，同时完全绕开 sm_120 wheel 问题。

### 版本要求

- **TensorRT ≥ 10.9** 起支持 SM 120（10.9 为 `bertQKVToContextPlugin` 加入 SM 100/120 支持）
- **TensorRT 10.8 会明确报错**：`Target GPU SM 120 is not supported by this TensorRT release`
- TensorRT 10.15.1 / 11.x 均支持 SM 120，注意限制：**SM 120 上 FP8 卷积不支持 kernel size > 32**
- TensorRT 11.2.1 修复了 Blackwell 上的 GPU 时间回退问题

### 🕳️ 最阴的坑：onnxruntime-gpu 静默回落 CPU

`onnxruntime-gpu` 官方 PyPI 包同样**不含 sm_120 kernel**。它**不报错**，而是让 `CUDAExecutionProvider` 不可用、所有算子静默回落到 CPU —— 表现为「GPU 好慢」而非报错。

若必须走 ORT 路线：
- 用预编译 Blackwell wheel（如 `Natfii/onnxruntime-gpu-blackwell`）
- **务必显式断言** `session.get_providers()` 中 `CUDAExecutionProvider` 真的生效

这也是推荐直接上 TensorRT 而非 ORT 的核心理由。

## 三、Blackwell 环境检查清单（开箱第一天执行）

```
✅ 驱动 570.124.04  → 支持 CUDA ≤ 12.8（CUDA 12.8 最低驱动 570.26），够用
⚠️ 上 CUDA 12.9 / 13.0 需升驱动（约 575.x / 580.x，请核对 NVIDIA 官方兼容表）
✅ PyTorch 必须 cu128 及以上（sm_120 已进入稳定版）
✅ TensorRT ≥ 10.9（10.8 明确不支持 SM 120）
✅ vLLM ≥ 0.17.0（含 SM120 专用 FP8 GEMM 优化）
⚠️ vLLM 设 VLLM_FLASH_ATTN_VERSION=2 —— FlashAttention 3 在 Blackwell 上尚不工作
❌ paddlepaddle-gpu 官方 wheel 无 sm_120  → 走 ONNX→TensorRT 绕开
❌ onnxruntime-gpu 官方 wheel 无 sm_120  → 静默回落 CPU，必须验证 EP
❌ RTX 5090 为消费卡，不支持 MIG        → 多进程共享 GPU 用 MPS
```

### 硬件层面

- 4×575W GPU + 128 核 CPU，**满载功耗约 2.5kW+，确认电源与风道**
- 压测时用 `nvidia-smi -q -d PERFORMANCE` 确认没有因温度/功耗掉频
- `nvidia-smi -pm 1` 开启持久化模式，避免首次调用的初始化延迟

## 四、吞吐预期

### 基准起点

PP-OCRv6_medium 官方数据：**A100 上 0.29s/图**。

⚠️ 这是**单流未批处理**数字，仅 3.4 QPS，远未喂饱 GPU，不能直接当容量规划依据。

### 估算

小 CNN 模型在 TensorRT FP16 + batch 32 下通常有 10~30× 吞吐提升：

| | 保守 | 乐观 |
|---|---|---|
| 单卡 RTX 5090 | ~30 QPS | ~100 QPS |
| **3 卡主力** | **~100 QPS** | **~300 QPS** |
| 日处理量（50% 占空比） | ~430 万图/天 | ~1300 万图/天 |

**先按 100 QPS 做容量规划，实测收敛。** 这个量级下云 API 兜底基本可以取消（保留 <1% 走 `qwen-vl-ocr` 处理极端难例即可）。

---

## 五、瓶颈会从 GPU 转移到 CPU

这是本配置最需要提前设计的部分。跑到 100+ QPS 时，卡住系统的不是 GPU：

| 瓶颈 | 量级 | 对策 |
|---|---|---|
| **JPEG 解码** | 100 QPS × ~15ms ≈ 持续占用数个核 | **nvJPEG / NVIDIA DALI 把解码搬到 GPU**，顺便省掉原图 H2D 拷贝带宽 |
| **DB 检测后处理** | 轮廓查找 + unclip，纯 CPU，**PaddleOCR 已知瓶颈** | 多进程并行，128 核正是为此存在 |
| **crop 与 resize** | 每图 10~30 个文本行 crop | GPU 侧批量完成，避免逐 crop 往返 |

**128 核的定位是「GPU 的饲养员」，不要再让它做推理。**

### 核心分配建议

| 用途 | 核数 | 说明 |
|---|---|---|
| 网关 + Redis + 爬虫 + OS | 16 | cgroup 隔离 |
| 解码 / 预处理 / 后处理 | 96 | NUMA 均分，**对齐到各 GPU 所在 socket** |
| vLLM 侧 + 机动 | 16 | |

用 `nvidia-smi topo -m` 查 GPU 与 NUMA node 的亲和性，把喂某张卡的 worker 绑到同 socket，避免跨 NUMA 搬运图像数据。

## 六、架构

```
   爬虫集群
      │  只投递对象引用（MinIO/S3 路径）
      ▼
 ┌──────────────┐   先查 sha256 缓存，命中直接返回（爬虫场景命中率 30~60%）
 │ Redis Stream │
 └──────┬───────┘
        │
        ├──► 图片通道（高并发）
        │    ┌────────────────────────────────────────┐
        │    │ CPU 预处理池（96 核，NUMA 对齐）          │
        │    │   └ nvJPEG/DALI GPU 解码                │
        │    ▼                                        │
        │    Triton Inference Server                  │
        │    ├ GPU0  PP-OCRv6_medium TensorRT FP16    │
        │    ├ GPU1  PP-OCRv6_medium TensorRT FP16    │
        │    └ GPU2  PP-OCRv6_medium TensorRT FP16    │
        │      （dynamic batching，det + rec ensemble）│
        │
        ├──► PDF 通道（低并发，可慢）
        │    GPU3  PaddleOCR-VL-1.6 + vLLM
        │          gpu-memory-utilization=0.7（给桌面留余量）
        │          VLLM_FLASH_ATTN_VERSION=2
        │          --enable-chunked-prefill
        │
        └──► API 兜底（<1%，可选）  qwen-vl-ocr
                    │
                    ▼
        PostgreSQL（结构化）+ Elasticsearch（全文检索）
```

### 为什么用 Triton

自建 worker 池要自己实现 dynamic batching、多 GPU 调度、模型实例管理。Triton 原生提供：
- **dynamic batching** —— 这是把 3.4 QPS 拉到几十 QPS 的关键
- 多 GPU 多实例并发执行
- det + rec 的 ensemble / BLS 编排
- 内建指标，直接对接 Prometheus

**建议**：P0 先用自建 worker 池快速跑通验证，P2 迁移到 Triton 拿满吞吐。

## 七、验证顺序

| 天 | 任务 | 产出 |
|---|---|---|
| D1 | 直接 `pip install paddlepaddle-gpu` 试跑 | 确认是否真报 sm_120 错误（万一官方已补，省大量工作） |
| D2 | PP-OCRv6 导出 ONNX → `trtexec` 转 TensorRT FP16 → batch 扫描（1/8/16/32/64） | **真实吞吐曲线** |
| D3 | vLLM 在 GPU3 跑通 PaddleOCR-VL | PDF 通道可用性 |
| D4 | 接 Triton，三卡并行压测 | 全系统 QPS 上限 + CPU 瓶颈定位 |

**D2 的吞吐曲线是整个架构的地基** —— worker 数量、batch size、CPU 核分配全部依赖它。优先做。
