# 128 核 CPU 服务器专项方案

> 补充于 2026-09-08，是 [OCR选型调研报告.md](OCR选型调研报告.md) 的落地细化章节
> 前提：128 核 x86 服务器、大内存、**假设无 GPU**

---

## 一、结论：单引擎，不再是双引擎

**PP-OCRv6_medium + OpenVINO 高性能推理（HPI）+ 多进程 + NUMA 绑定。**

原报告推荐的「PP-OCRv6 + PaddleOCR-VL」双引擎方案，在**纯 CPU 机器上必须砍掉 VL 通道**。

### 为什么 PaddleOCR-VL 在纯 CPU 上不可行

| 证据 | 内容 |
|---|---|
| 官方最低配置 | **RTX 3060 12GB**，要求 Compute Capability ≥ 7.0（即 V100 及以上） |
| 社区实测 | RTX 4060 Ti 上未优化路径 **20~32 秒/页** |
| 模型性质 | 0.9B 自回归 VLM，每页需 decode 上千 token |

自回归解码是串行的，核数再多也无法缩短单页延迟；而 CPU 单核算力远低于 GPU SM。**128 核救不了 VLM。**

### 为什么 PP-OCRv6 反而是 CPU 的最优解

PP-OCRv6 论文标题即为《PP-OCRv6: From 1.5M to 34.5M Parameters, **Surpassing Billion-Scale VLMs** on OCR Tasks》—— 在纯文字识别任务上，34.5M 的 CNN 打得过十亿参数级 VLM。

CNN 流水线的特点正好匹配多核 CPU：
- 无自回归解码，单图延迟固定
- 无状态，进程级横向扩展近线性
- 模型极小（34.5M），128 个 worker 各加载一份也只占几 GB 内存

## 二、官方 CPU 基准数据

**Intel Xeon 8350C + OpenVINO，端到端单图延迟：**

| 档位 | 参数量 | CPU 延迟 | 检测 Hmean | 识别准确率 | 对比 A100 |
|---|---|---|---|---|---|
| Tiny | 1.5M | **0.20s** | 80.6% | 73.5% | A100: 0.13s |
| Small | 7.7M | **0.59s** | 84.1% | 81.3% | A100: 0.25s |
| **Medium** | 34.5M | **1.40s** | **86.2%** | **83.2%** | A100: 0.29s |

**关键观察**：Medium 档 CPU 仅比 A100 慢 4.8 倍。对比之下 VLM 路线 CPU/GPU 差距是几十倍以上。这就是选型的分水岭。

其他平台参考：V100 + ONNX Runtime Medium 0.67s；Apple M4 + ONNX Runtime Medium 5.55s。

## 三、吞吐容量估算

按「core·秒/图」折算。资源分配：112 核跑 OCR，16 核留给网关 / Redis / 爬虫 / OS。

| 档位 | core·s/图（按 8 线程反推） | 保守吞吐 | 日处理量（50% 占空比） |
|---|---|---|---|
| Medium | ~11.2 | **≈ 10 QPS** | **~43 万页/天** |
| Small | ~4.7 | ≈ 23 QPS | ~100 万页/天 |
| Tiny | ~1.6 | ≈ 70 QPS | ~300 万页/天 |

> ⚠️ 这是**保守下界**。官方 1.40s 是多线程单实例延迟，多线程存在并行损耗；拆成多个低线程数进程后，单位图片的 core·秒成本通常低于此估算，实测吞吐一般更高。**必须用自己的业务图跑 benchmark 确认。**

### 经济性对照

| 方案 | 43 万页/天成本 |
|---|---|
| 本机自建（电费+折旧） | 可忽略 |
| qwen-vl-ocr API | **约 5000 元/天** |
| 百度 OCR 高精度版 | 约 8200 元/天 |

单这一项，这台机器一周内即可收回成本。

## 四、关键工程配置

### 4.1 启用高性能推理（HPI / OpenVINO）

Xeon 上 5.2 倍速提升完全来自 OpenVINO 后端，**不开等于浪费一大半算力**。

```bash
paddleocr install_hpi_deps cpu
paddleocr ocr -i img.png --lang ch --enable_hpi True
```

Python API 侧在初始化 pipeline / module 时传 `enable_hpi=True`。

> ⚠️ **必须实测验证**：社区存在 issue 报告 PaddleOCR v3 + OpenVINO 在部分机型上反而慢于 v2。开启与关闭各跑一次 benchmark 再定，不要盲信文档数字。

### 4.2 Worker 环境变量

```bash
export FLAGS_allocator_strategy=auto_growth   # 显存/内存按需增长
export FLAGS_mkldnn_cache_capacity=10         # OCR 是动态 shape，不设会导致 MKLDNN 内存暴涨
export OMP_NUM_THREADS=4                      # 每 worker 固定线程数，禁止互抢
```

**`OMP_NUM_THREADS` 必须显式设置。** PaddlePaddle CPU 数学库默认 10 线程，128 核上起 30 个 worker 会开出 300 个线程互相抢核，吞吐不升反降。容器环境下尤其要注意（社区有专门的容器线程失控 issue）。

### 4.3 多进程而非多线程

Python GIL 决定了多线程方案吃不满 CPU：

| 方式 | 实测效果 |
|---|---|
| 多线程 | 只能利用 30~50% CPU |
| 多进程 4 个 | 约 3 倍加速 |
| 多进程 6 个 | 约 5 倍加速 |

结论：**每个 worker 独立进程，进程内低线程数，靠进程数堆并发。**

### 4.4 NUMA 绑定

128 核基本是双路架构（2 NUMA node）。跨 NUMA 访存会吃掉可观性能，OCR 这种访存密集负载尤其敏感。

```bash
# node0 承载一半 worker
numactl --cpunodebind=0 --membind=0 python worker.py
# node1 承载另一半
numactl --cpunodebind=1 --membind=1 python worker.py
```

K8s 场景则开启 CPU Manager static policy + Topology Manager，保证 Pod 独占整核且不跨 NUMA。

### 4.5 线程数调优

`OMP_NUM_THREADS` 的最优值只能实测。扫描 1 / 2 / 4 / 8，找吞吐拐点：

```
总吞吐 = (112 / OMP_NUM_THREADS) 个 worker × (1 / 单图延迟)
```

线程数越低 worker 越多、并行损耗越小，但单图延迟上升。通常拐点在 2~4。

## 五、大内存的用法

大内存是这台机器的第二个优势，别浪费：

1. **内容寻址缓存全量化**：`sha256(图片字节)` 作 key 存 Redis。爬虫场景重复图命中率 30~60%，缓存开到几百 GB 等于直接把有效负载砍半 —— **这是投入产出比最高的一项**。
2. **模型常驻**：Medium 档仅 34.5M，几十个 worker 各加载一份也只占几 GB，无需考虑共享。
3. **图片走 tmpfs 暂存**：避免磁盘 IO 成为 128 核的瓶颈。
4. **队列内存化**：Redis Stream 全内存运行，关闭不必要的持久化。
5. **页缓存**：大内存让 OS page cache 吃下热数据，进一步削减 IO。

## 六、表格 / PDF / 版面的替代方案

VL 通道砍掉后，用 **PP-StructureV3** 补位。

它是**小 CNN 模型流水线**而非 VLM：
- PP-DocLayout —— 版面分析
- SLANet / SLANeXt —— 表格结构识别
- PP-FormulaNet —— 公式识别

全部是可在 CPU 上运行的小模型，输出 Markdown + JSON 并保留原始版面层级。精度低于 PaddleOCR-VL 一档，但在纯 CPU 机器上这是唯一可行解。

真正的疑难件（复杂合并单元格、古籍、手写、印章）→ 走 `qwen-vl-ocr` API 兜底。占比控制在 1~3% 时成本几乎可忽略。

## 七、最终架构

```
   爬虫集群
      │  只投递对象引用（MinIO/S3 路径）
      ▼
 ┌──────────────┐
 │ Redis Stream │ ── 先查 sha256 缓存，命中直接返回
 └──────┬───────┘
        ├────────────► Fast Pool    PP-OCRv6_medium × ~24 workers   ← 90% 流量
        ├────────────► Struct Pool  PP-StructureV3  × ~4  workers   ← 表格 / PDF
        └────────────► API 兜底     qwen-vl-ocr                     ← 1~3% 疑难
                            │
                            ▼
              PostgreSQL（结构化）+ Elasticsearch（全文检索）
```

### 核心分配建议

| 用途 | 核数 | 说明 |
|---|---|---|
| 网关 + Redis + 爬虫 + OS | 16 | cgroup 隔离，防止爬虫抢占 OCR 资源 |
| Fast Pool | 96 | 24 worker × 4 线程，NUMA 均分 |
| Struct Pool | 16 | 4 worker × 4 线程 |

### 路由策略

```
先查 sha256 缓存                        → 命中直接返回
图片短边 < 1000 且无表格版面            → Fast Pool
PDF / 检出表格、公式、多栏              → Struct Pool
置信度 < 0.75 且业务标记高价值          → qwen-vl-ocr API
队列深度超阈值                          → 网关 429 + Retry-After
```

## 八、如果能加一张 GPU

**强烈建议加一张 24G 显存的卡（RTX 4090 / L4 / A10，甚至 RTX 3060 12G 也能起步）。**

| 收益 | 说明 |
|---|---|
| 解锁 VL 通道 | PaddleOCR-VL-1.6 + vLLM，模型本体仅 ~2GB 显存，约 45 页/分钟 |
| 文档解析质量跃升 | 从 PP-StructureV3 跳到 **OmniDocBench v1.6 96.3%，全球第一** |
| Fast 通道也受益 | PP-OCRv6_medium 从 1.40s 降到 A100 上的 0.29s 级别 |

以硬件采购价衡量，128 核 CPU 服务器的成本远高于一张 4090。**若 PDF / 合同 / 发票 / 表格类文档占业务 30% 以上，这张卡不是可选项而是必选项。**

届时架构回归原报告的双引擎形态：CPU 128 核跑 Fast Pool 吃海量图片，GPU 跑 VL Pool 吃文档解析，二者互不争抢，是相当理想的组合。

## 九、待确认事项

1. **该服务器是否确实无 GPU？** 有 GPU 则方案改回双引擎。
2. **业务中 PDF / 表格类占比？** 超过 30% 则纯 CPU 方案短板明显，应优先加卡。
3. **CPU 型号与 NUMA 拓扑？** `lscpu` 输出决定 worker 绑核策略（Intel 走 OpenVINO，AMD 需实测 OpenVINO 收益）。
