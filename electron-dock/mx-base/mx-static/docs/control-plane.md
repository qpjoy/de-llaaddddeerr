# 控制面：SQLite 的作用、上限，以及要不要换 PostgreSQL

0.4.0，2026-09-12。配套 [容量与吞吐](capacity.md)。

## 1. SQLite 在这里负责什么

两个库，都在 `/state`，都必须留在本机盘（[mounts.mjs](../src/mounts.mjs) 在启动时拒绝 NFS/CIFS/virtiofs/9p）。**它们不存媒体字节，只存控制面。**

| 库 | 内容 | 丢了会怎样 |
| --- | --- | --- |
| `jobs.sqlite` | 持久下载队列、租约与 owner 围栏、按 `project+source_hash` 的去重索引、完成记录 | "已接收"的承诺作废：已返回 202 的任务凭空消失，调用方无从得知 |
| `archive.sqlite` | NAS 镜像状态机（`local`/`mirrored`/`action`/`state`）、卷身份、后端健康心跳 | 不知道哪些对象已上 NAS、哪些本机副本已释放；可重扫重建，但期间不能 evict |

三个设计约束决定了它必须是本机嵌入式库，而不是远端数据库：

1. **`synchronous=FULL` 是 202 的语义基础。** `enqueue` 提交落盘后才回 ACK，所以进程被 `kill -9`、主机断电，任务都还在。这条承诺不能建立在一个可能连不上的网络服务上。
2. **NAS 挂死时控制面必须还活着。** 整个架构的核心隔离就是"主服务只碰本机盘"。控制面一旦跨网络，NFS 故障就又有了一条传染路径。
3. **去重查询在请求路径上。** 每次 ingest 都要问"这个 URL 我是不是已经存过了"。`[实测]` 本机 7.2 µs，走网络最快也要几百 µs。

代价也很明确：`node:sqlite` 的 `DatabaseSync` 是**同步 API**，每一次查询、每一次提交都**直接阻塞事件循环**。这是控制面所有性能问题的共同根源。

## 2. 能撑多大

`[实测]` 开发机，200 万行 `objects` 表，只说明数量级和拐点位置：

| 指标 | 实测 / 上限 | 说明 |
| --- | --- | --- |
| 库文件大小 | 每百万行约 0.48 GiB | 1000 万对象 ≈ 5 GB；48 TB 装满（按 300 KB/对象约 1.6 亿）≈ 80 GB。SQLite 理论上限 281 TB，**不是约束** |
| 主键点查 | 7.2 µs（复用 prepared）/ 14.7 µs（每次重新编译） | 见 §3 第 2 条 |
| `GET /storage` 汇总（改造前） | 20 万行 416 ms → 100 万行 2.3 s → **200 万行 6.0 s** | 全表扫 + 每行一次 `json_extract`，**同步阻塞**：查一次 storage，整个 writer 停 6 秒 |
| `GET /storage` 汇总（改造后） | **200 万行 178 ms** | 覆盖索引 `objects(project,action,state,size)`，`size` 提成真实列。33× |
| 写事务 | 每次提交 1 次 fsync，同步阻塞 | 预算按"提交数 × fsync 延迟 < 20% 事件循环"倒推：1 ms/fsync 时约 **200 提交/s** |
| 并发写进程 | **1** | WAL 单写者。这也是 writer 只能有一个实例的根本原因 |
| 并发读进程 | 多个 | reader 用只读句柄；WAL 读不阻塞写 |

**拐点结论**：库大小和行数都不是墙，**按项目聚合的查询才是**。200 万对象（约 600 GB 媒体）时 `GET /storage` 已经是 6 秒的事件循环停顿——这个量级会很快到。覆盖索引把它推到千万级；再往上（单项目 5000 万行以上，覆盖索引也要约 4 秒）需要维护一张计数表增量更新，而不是每次实时聚合。

## 3. 0.4.0 已经改掉的三件事

1. **覆盖索引 + `size` 实列**（[archive-catalog.mjs](../src/archive-catalog.mjs)）：`status()` 从全表扫加 JSON 解析变成纯索引扫描，200 万行 6.0 s → 178 ms。旧库启动时自动 `ALTER TABLE` 补列并回填。
2. **缓存 prepared statement**（[jobs.mjs](../src/jobs.mjs)、[archive-catalog.mjs](../src/archive-catalog.mjs)，29 处调用点）：原先每次查询都重新编译 SQL。`[实测]` 点查 14.7 µs → 7.2 µs。对同步阻塞的调用来说，省下的全是事件循环时间。
3. **批量入队**（`POST .../ingest/batch`）：上游一页 60 个媒体 URL 从 60 次事务、60 次 fsync 变成 **1 次**。这是把控制面写入压力降一个数量级最直接的一条，也正好对上"上游一次返回 10 条、每条带图带视频"的形状。

另外补了 `jobs(project,state)` 索引，`GET /jobs` 的分状态计数不再扫全项目。

## 4. 要不要换 PostgreSQL

**结论：现在不要。** 当前所有看起来像"SQLite 撑不住"的现象，实际来源是别的：

| 现象 | 真实原因 | 是否需要 PG |
| --- | --- | --- |
| ingest 一多事件循环就卡 | 每个 URL 3 次 `synchronous=FULL` 提交 | 否，批量入队把 60 次压成 1 次 |
| `GET /storage` 卡死几秒 | `project` 无索引 + 每行 `json_extract` | 否，覆盖索引解决 |
| 每次查询都偏贵 | 每次重新编译 SQL | 否，缓存 prepared statement 解决 |
| 表无限增长 | 没有任何保留策略 | 否，这是策略问题，换库一样会涨 |
| 同步 API 阻塞事件循环 | `DatabaseSync` 的本质 | **这条是真的结构性问题**，但不必靠 PG 解决，见下 |

换 PG 会拿到什么、失去什么：

**拿到**
- 异步驱动，不阻塞事件循环。
- 多 writer 实例，写入可水平扩展（现在 WAL 单写者，writer 只能单例）。
- `SKIP LOCKED` 领任务；分区表按月滚动淘汰历史。
- 大表聚合有更好的计划器和并行扫描。

**失去**
- **多一个跨进程故障域。** 现在整个服务是"一个容器 + 本机盘"；引入 PG 后它自己会挂、会 OOM、要备份、要升级，而"控制面必须在 NAS 挂死时还活着"是这套架构的核心不变量。
- **fsync 成本一分不少。** PG 的 `synchronous_commit=on` 同样是每次提交一次 fsync，同一块盘、同样的延迟。PG 的优势是 group commit，而那需要**多个并发会话**才有效；现在是单个 Node writer 串行 await，拿不到这个收益。
- **单次查询更贵。** 进程内 SQLite 7.2 µs，PG 走 unix socket 最快也要几百 µs。去重查询在请求路径上，这是净损失。
- 备份流程从"detach → stop → 拷 data/state/secrets"变成还要加 `pg_dump`/PITR。

**同步阻塞怎么办（不换 PG 的解法）**：把两个库放进 `node:worker_threads` 的工作线程，主线程用异步消息接口访问。SQLite 不变，`synchronous=FULL` 不变，故障域不变，但事件循环不再被 fsync 和聚合查询卡住。这是比换 PG 小得多、收益重叠度很高的一步。

**什么时候该换**，三条里满足任意一条：

1. 需要**多个 writer 实例**同时写入（单机纵向扩展已经到头）。
2. 单项目对象数**超过 5000 万**，且需要实时的复杂聚合/报表——此时维护计数表也开始变得笨重。
3. 控制面需要**跨主机高可用**，即主服务器本身不能是单点。

三条目前都不成立，而且用户已经说明实际负载达不到 100 QPS。先把 §3 这三项的收益吃完，再用 [容量与吞吐 §7](capacity.md#7-上线前必须先量的数) 的 `fio` 量出本机盘真实的 fsync 延迟——那个数才决定控制面的真实写入预算。
