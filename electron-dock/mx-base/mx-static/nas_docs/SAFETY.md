## Delta 正式切换边界

最新回执已通过部署审核，正式执行器使用独立 `/var/lib/mx-static/nas-delta-cutover/delta-…` 报告，保留原复制/准备报告和 NAS marker。新安装声明要求 delta 使用 NAS：缺完成登记时拦截发布/开机补启动，不主动停止当前服务；实际切换必须显式维护命令。先持久记录 `/etc/mx-static/nas/delta-media.json` 维护所有权，再只停止/重建十个媒体角色。数据库、队列和 websearch 保持原运行身份；媒体 HTTP、应用默认身份 I/O、停写并集复核通过后才完成独立登记。不对 infra 常量做全局替换，不复用 infra 历史执行状态。

中断后不自动回滚 SSD、不自动续跑迁移。已可能产生 NAS 业务写入后禁止重新补写 SSD 内容；部分创建且缺完整新 ID 时须只读核对，不能猜测并删除/重建混合容器。普通恢复仅按依赖启动已有容器，缺数据库/NFS 卷或登记时拒绝创建替代品。delta 仅新增只读 cleanup check，报告使用独立 `delta-retained-review-v1`，不自动选作删除清单，不改历史记录；删除入口未启用，`reclaim_ready=false` 不能解释为可删除。

## 操作分级

delta 的迁移准备区分媒体消费者、PostgreSQL/Redis 依赖和已核对的辅助服务。`websearch` 无持久卷挂载，现有 `/tmp:size=64m,noexec,nosuid` 临时目录原样保留；不因存在或不可用阻止媒体准备，不加入 NAS override、不随媒体重建。私有 tmpfs 须核对 Compose 与 HostConfig.Tmpfs 路径/选项一致、路径规范且不与 raw-media 重叠，不能把它误作持久媒体卷；实际/声明的持久挂载和额外主机访问权限仍须审核。全局媒体源/目标别名检查、必需媒体角色和数据库卷核对保持有效。新增未知服务、重复角色、一次性任务仍须识别，不自动删除或启动它们来满足固定数量。

- **只读**：项目/主机状态、挂载表、进程、网络路由、发布脚本静态审查、目录身份/权限检查。仍须注意 hard NFS 的目录访问可能等待；宿主机概览故意只读本机 `/proc` 和 systemd。
- **小范围写探测**：显式 `permissions probe --write-test`，用现有应用容器默认身份各创建独立私有 4 KiB 探测，改名、读回并仅清理自身 inode。无递归权限修复。
- **维护操作**：恢复、同版本重建、安装/启用开机服务。明确对象和能力，保持数据库/队列独立；同版本重建要求 `--maintenance`。
- **数据回收**：明确任务 + 原始清单 + `--business-accepted`；核对 NAS 对应文件、当前消费者与源文件身份，先落盘意图日志再删除。任务完成、执行中断或失败不能混淆。

本工具不提供全局 `rm -rf`、`docker volume prune`、NAS 强卸载、自动批量 kill、全局 Docker 重启、按 tmp 年龄清理等快捷动作。root 仍能绕过工具，因此运维约定也必须落实。

用户最新明确边界：迁移可以在明确授权、清单和校验范围内删除；正式重启、部署、容错恢复不得删除 NAS 文件，也不得删除/清空依赖应用的数据库或队列。独立归档 worker 的远端 purge 已禁用，旧队列保留不执行。迁移的清理能力不进入普通项目恢复路径。

应用正常发布可以新增项目自己的普通本地持久化卷。发布检查区分这类 Compose 管理卷与必须已有的 NAS、media、static、PostgreSQL、Redis 卷；不把新增卷自动迁到 NAS，也不将缺失基础卷当作新卷。新卷不得冒用现有卷名、使用远程/绑定驱动选项或遮住受保护/现有挂载；已存在的应用卷核对 Compose 归属。只有应用明确发起的 Compose 发布命令可创建新应用卷，只读检查、开机恢复及存储维护不会创建。原始 Docker 命令不受本入口拦截，应用新增卷也不因此变成具有历史备份/恢复登记的媒体卷。

## 审计与恢复

新 `media-v1` 采用独立、显式登记的存储身份，日常恢复不依赖应用目录、`.env`、API 或历史镜像/容器 ID；缺登记不回退旧恢复适配。用户已授权按当前容器依赖顺序补启动已有 PostgreSQL/Redis 和媒体服务；已运行的跳过，停止的数据库先核对本地数据卷，按依赖条件等待健康检查，不查表、不清队列。显式维护重建才读取当前 Compose/构建，限定媒体角色、不创建缺失数据卷，不执行数据库迁移/账号初始化；未完成维护标记阻止开机启动部分重建的容器。详细边界见 [媒体恢复与按需重建](operations/media-runtime.md)。原迁移/清理证据与逐文件保护未放宽，恢复通过不是删除授权。

重部署后的新回收清单使用 `retained-union-media-v1`：原切换报告和停写文件证据保持不变，重新证明 SSD 未变化、NAS 对应数据有效，并核对当前登记、全部媒体内核 NFS、依赖健康及额外 SSD 访问路径。每份清单绑定核验时的当前容器状态；后来再部署、重启或改变登记则拒绝该清单，不能自动采用新状态继续删除。旧清单仍使用旧保护，不原地升级。新适配不执行 Compose、账号初始化、数据库/队列操作或 NAS 删除。

运行指纹只规范化 Docker 实际 `Mounts` 集合顺序，保留全部挂载属性，拒绝重复目标；命令、Entrypoint、Env 和 HostConfig 列表继续保持顺序。新私有 `runtime.json` 使用 schema 2，旧 schema 1 计划必须重新核验。实际运行差异输出 `nas_reclaim_runtime_changed` 的服务/字段名，不能凭“可能是顺序问题”跳过失败或改写旧指纹。

统一恢复可以按明确启用的 `migrated` 策略检查所有已登记成功迁移；必须验证报告、实际配置和已审核适配，保留全局/项目暂停，不能只凭目录存在或声明字段自动接管。`recovery check` 只检查；安装/启用、复制、删除仍是独立操作。默认易读显示不改变 JSON 审计和失败退出码。

统一入口的写操作在 `/var/log/mx-static-nas/actions.jsonl` 留下 root 私有记录：时间、操作、任务、UID/PID、请求和结果，不记录完整参数、环境变量或密钥。`command_completed` 对后台任务只表示已提交任务，真正结果仍看该 unit 日志和迁移/清理收据。旧底层脚本保留用于兼容，直接调用时不会经过这份入口审计，但其原有报告/清理意图日志仍有效。

迁移与清理报告在 `/var/lib/mx-static/`，自动恢复选择在 `/etc/mx-static/nas/auto.json`，安装代码快照在 `/usr/local/lib/mx-static-nas/`；这些由统一入口定位和管理，不手工删改。Git 保存无密钥声明、单元模板、工具和操作文档，不保存私有报告。

独立备份与 NAS 管理端健康目前未确认，用户暂缓 OSS；不凭“NAS 一直稳定”宣称已有备份，也不额外把云备份变成本轮迁移硬门槛。删除 SSD 后保留副本减少，这是已知事实。

## 权限原则

运维 root、容器 UID/GID、NAS 端身份映射是三个不同层面。NFS `sec=sys` 依据 UID/GID 访问，服务端 squash/ACL 会影响结果；root 命令成功不代表任意业务身份均可写。[NFS exports 用户映射说明](https://man7.org/linux/man-pages/man5/exports.5.html)

现有 infra 先保持已经验证的身份和 mode；新项目采用独立目录与明确的 UID/GID/组或 ACL，再测试应用写入和读服务读取。需要修改存量文件权限时，先准备限定范围/原属性清单及回退方案；不执行递归 chmod/chown 或在迁移工具里悄悄放宽安全目录检查。
