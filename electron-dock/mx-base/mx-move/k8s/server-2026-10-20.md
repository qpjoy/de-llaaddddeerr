服务器实际上有两块约 2 TB 的 NVMe 物理盘。这里所称的“1T 盘”是 `nvme1n1` 上的 **1 TiB `cl-root` 逻辑卷**，该物理盘还承载接近满载的 `/home`；`/data` 位于另一块 `nvme0n1` 上。此次目标是把选中的 Kubernetes 存储迁入根逻辑卷，不涉及重分区或扩容。

## 数据与身份保护

- etcd 已在根文件系统，保留现有绑定挂载、启动保护及数据，不重复迁移。
- 报告中的 Launcher、mx-common、Pay PostgreSQL 标识与各自现存身份记录匹配。迁移后必须保持数据库标识、用户、凭据和联网配置，仅按实际新挂载调整存储身份字段。
- Pay 同时持有主机身份文件与 Kubernetes ConfigMap；两处需协调更新，保留安装标识、集群标识、数据库标识以及 PV/PVC 身份。
- 本次检查的 5 个 PostgreSQL 数据目录均未发现外部 WAL/表空间链接。这不替代迁移前的停写检查和数据库备份验证。
- `/var/lib/mx-auto` 已在根文件系统；虽然 Auto 已整合到 Rig，本次仍保留该旧目录，不据此删除数据。已有根文件系统上的 Kubernetes 配置、CNI 数据及其他目录也不重复搬迁。
- `/shared_dir` 是符号链接，首份报告未解析其目标；下文 02:08 补充报告已确认其直接指向 NAS 路径。不因链接位于根文件系统就认定数据已在目标盘，也不自动复制 NAS 内容。

## 维护窗口的实际影响

报告发现 **97 个 Docker 容器，其中 82 个正在运行**。Docker 的 `--containerd` 指向 `/run/containerd/containerd.sock`，与 Kubernetes 共用运行时。

`docker_overlap: []` 仅表示未检测到 Docker 卷路径与待迁数据路径直接重叠，**不表示 Docker 不受运行时调整影响**。还需确认 Docker live-restore、容器重启策略、运行时命名空间与存活任务，并保存原有运行集合，避免把原本停止的容器重新启动。不能仅停止 kubelet/containerd 就认定所有写入者已停止。

用户已允许在同一个维护窗口内短暂停止受影响的 Docker 服务，同时明确 **Docker 数据不搬迁，只迁移 Kubernetes 数据**。原 Docker containerd 服务、数据根及 `/data/docker` 保持原位；不能以已允许停机为由搬迁共享 containerd 整树。全部用户、凭据和联网配置必须保留。本次报告没有执行任何停机、挂载切换或迁移。

## 完整切换边界（尚未执行）

1. **业务持久数据要求**：准备 mx-common、Launcher、Pay、Rig 的停写、备份、复制、挂载与身份更新方案。维持现有 PV/PVC 路径及数据库身份，按应用依赖停启，并验收 MX-H2I 现有用户登录、联网和跨应用 SSO。此阶段完成仍不能称为全部 Kubernetes 数据迁移完成。
2. **Kubernetes 运行时要求**：已选择独立 containerd 方案，使用根文件系统上的独立数据根、独立 state 与 socket；原 Docker containerd 及其数据根保持原位。下文记录配置与镜像预备成功证据，候选安装是当前下一步；正式切换仍须核验 kubelet 子挂载与容量、全部写入者、恢复顺序及维护访问通道。禁止整树复制共享 containerd，也不能把其中的命名空间目录当作可独立搬运的完整数据集。
3. **两阶段共同要求**：保留原始数据和身份记录，明确备份目的地及空间预算；业务恢复写入后的回滚必须携带最新数据，不能简单切回已经落后的旧目录。切换前重新核对现场状态，切换后验证存储身份与服务健康，再做用户功能验收。

初始报告不能单独支持全量停机切换。后续共享运行时证据和镜像预备结果见下文；它们支持候选安装，尚不能替代完整停写、复制、身份更新与恢复事务。
