# mx-pay implementation boundary

- 2026-10-04 deployment intent: user confirms there are currently no historical orders and permits a fresh production launch. Do not require a historical-order migration project for this installation. Retain runtime empty-history and legacy-collection-disabled activation checks; an unexpected existing order still needs investigation. Internal API startup does not require a pay subdomain; human SSO requires a dedicated HTTPS origin, and automatic provider callbacks need a provider-reachable public endpoint. This authorization does not establish target cluster, TLS or channel configuration readiness.

- 2026-10-04 SSO/operations: see docs/sso-and-application-onboarding.md. Optional human query console uses shared mx-common SSO, payment-owned encrypted sessions and exact issuer/subject/client + app/environment viewer grants. Keep its process, listener, Kubernetes workload and Secret separate from machine payments; Auth outages cannot gate API/notifications/readiness. No inherited Auth admin/Hub tenant roles or browser machine secrets, no human money writes. Hub consumes ./integration guards while retaining its local intent/inbox/wallet transactions and legacy cutover gates. Internal Pay operations call only this product's manage.sh. Preserve MX-H2I login/networking. Production deployment and formal handover remain unperformed.

- 2026-10-03 Hub delivery adapter: Hub (see ../../mx-insight-hub/docs/operations/payment-delivery.md) now supports reviewed test/fresh-live activation, durable intent/inbox, atomic existing-wallet credit and post-commit ACK. Default legacy path and all historical live orders stay in place pending dedicated handover. GET /v1/identity exposes source/app/environment/features/scopes under orders.read; optional immutable initiatorRef is application-attested audit data, never a human login or authorization claim. SSO remains deferred.

- Financial changes must follow docs/transactions-and-failure-model.md: keep payment truth, unknown call outcomes and business delivery separate. A cancelled static-QR order does not prove that funds cannot arrive. Excess/short/late/unmatched receipt resolution, refunds and standalone Hub wallet delivery still have explicit gaps; never claim rejection or generic retries close them. Preserve stable identities and durable evidence; new money paths require failure-boundary tests and a defined manual resolution path.
- Official Alipay page checkout, verified notifications and explicit query recovery are implemented; see docs/alipay-channels.md. Never settle from browser redirects, local timeout, unsigned query data or manual confirmation of an automatic order. Preserve channel bindings, stable seller identities, app/environment allowlists, channel observations and atomic paid/audit/outbox/reporting. Disabled channels must retain receipt verification. Review records are not resolved cases; recurring reconciliation, automatic close/refund and raw signed evidence archival remain absent.
- Alipay channel order IDs are immutable snapshots distinct from internal UUIDs. Legacy orders retain their original remote identity for query/notifications; never backfill or accept alternate aliases. Follow docs/alipay-java-reference-review.md and preserve deploy's checkout pause/compatibility rollout barrier before issuing new-format trades. Updating a Deployment template is not proof all old replicas exited.

- Preserve the package's original `.` rule exports: Hub's existing embedded recharge path still imports them. The independent runtime/SDK is additive; deploying it does not switch Hub or migrate historical money.
- `scripts/manage.sh deploy` is the per-product unattended contract: automatically discover then pin the target, deploy lock, immutable image/config, dedicated database bootstrap, migration-before-rollout, readiness, nonzero on failure. Existing config wins. Never restart Launcher/Hub, use their database, provision all mx-common services, enable real collection, or delete persistent data as a side effect.
- Dedicated PostgreSQL owns payment facts. Confirm + outbox commit atomically; consumers commit their own inbox + business ledger before acknowledging. Keep request keys, application/environment isolation, provider receipt uniqueness, unknown outcomes and immutable audit evidence.
- Reporting is an independent read-only contract, never a money decision or the business ACK queue. Preserve source/app/environment cursor identity, commit ordering, revision-guarded baseline replay and consumer-local transactional checkpoints. No PII/checkout leakage or cross-application wildcard reporting credentials. See docs/cross-center-reporting.md for current delivery versus planned Hub/finance projections.
- The optional `./reporting` consumer belongs to the consumer's PostgreSQL (`pay_reporting`), never the payment source database. Keep batch projection/checkpoint atomic, version fencing, source bindings, unknown fee counts and truthful catch-up/failure status. Hub now exposes optional admin-only reporting APIs; no browser report console, tenant mapping, wallet delivery or payment cutover is implied. Consumer migration/deployment belongs to Hub, not mx-pay deploy.
- Machine credentials are distinct from Launcher human sessions and Hub API/Admin tokens. The optional SSO console is read-only and separate from the independent API; no refunds or invoice authority. Never infer money-write capabilities from the planning docs. Alipay keys are confined to the private channel file/versioned API Secret, not a browser, query console, business application or migration Pod.
- Kubernetes is the production deployment target; Compose is a development/transition option. Tests with command substitutes do not establish actual rollout availability. Preserve existing credentials and fail on database identity drift.
- Runtime discovery may generate first-install config; it is never permission to select backup data. Retain cluster UID, PV/PVC UIDs, filesystem UUID/local path and PostgreSQL system identifier. Normal database startup cannot run initdb. Backup/restore are separate from restart/deploy; archive readability is not a completed recovery drill or proof of ledger freshness. Registryless deployment must verify the image on every selected worker and restrict scheduling to those nodes.
- Read README.md for current delivery, first-run setup and remaining Hub single-writer cutover. Test financial changes against a disposable PostgreSQL database, never a live business database.
