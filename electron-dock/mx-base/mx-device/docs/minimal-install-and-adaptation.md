# 最小安装、能力适配与集群验收边界

更新：2026-10-10，补充用户提供的 `8787/devices` 设备池与直接访问 8788 的截图。本文是产品/安装边界与适配评估，**没有新增部署脚本或已完成集群 HA 的含义**。当前源码证据见 [Mobile-Agent 审阅](mobile-agent-source-review.md)，分阶段实施见 [产品路线](product-roadmap.md)。

## 1. 定位收敛

**MX Device 的核心产品是稳定、高可用、高性能的手机机架/集群基础设施；小红书采集是第一条端到端示范业务，不是把中心做成又一个小红书工具或侵权业务中台。** 当前版本仍是独立单机实验实现，目标与完成状态必须分开。

8787 中的设备池、设备元信息、连接/观察、任务编排等产品能力适合纳入 mx-device；不需要让用户长期在两套设备管理界面之间切换。迁入的是功能及清晰的能力契约，不是原封不动复制其全局配置、SQLite 调度器、进程管理和全部业务页面。

业务可以在同一个产品界面中提供“示范应用 / 小红书采集”入口，但其参数、流程、结果解析和依赖属于插件边界。禁用插件、旧 PoC 失效或某台手机下线，不能阻断中心登录、设备管理、任务历史和其他插件运行。

## 2. 四个端口对应的最小依赖

| 现有入口                             | 当前最小接入需要吗                               | 在长期产品中的位置                                                                   |
| ------------------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 8765 侵权处置子服务                  | 不需要；保持既有服务不动                         | 专门业务系统，按需作为外部调用方，不属于手机集群底座                                 |
| 8787 设备/业务管理 HTTP              | 需要其中的最小观察接口；当前截图/设备报告已适配  | 兼容供应端之一；设备 UI 和调度归 mx-device，最终可由独立 Host Agent 替代所需底层能力 |
| 8788 H.264 WebSocket                 | 当前不需要，PNG 已能显示真实画面                 | 可选媒体通道；集成前解决解码、鉴权、共享采集和清理作用域                             |
| 宿主机 18081 → 容器 18082 → 手机 PoC | 仅旧搜索/翻页/详情 JSON 流程需要，通用观察不需要 | `legacy-poc` 可选采集能力；不成为所有设备任务的必经路径                              |

同名路径也不能混用：8787 `/api/state` 含旧项目配置，而手机 PoC `/api/state` 是业务状态。不能做“任意端口 + 任意路径”的透明代理。

## 3. 三种安装档位

### A. 当前最小增量：原环境不变（已具备）

只部署本项目 API + Worker + 独立 PostgreSQL，一次性 migrate 在 deploy 中执行。使用现有 Docker/Compose；手机、旧 mobile-agent、ADB、VPN 和端口映射均不改。

- **中心新增**：现有 `scripts/manage.sh deploy` 管理的 Compose 服务及独立数据卷，管理端口 18891；不是整套旧侵权业务的重装。
- **手机新增**：无。读取既有 8787 截图和报告，无需安装 scrcpy server、UIAutomator、输入法、PoC 或模型。
- **UI 配置**：原设备 observer 入口 `http://127.0.0.1:8787` + serial `8ad5ef10` + 正确 Worker；保存后仍暂停。
- **可运行**：中心管理、模拟调度、真实截图/报告；旧 PoC 取数另需明确空闲/独占条件。纯 Mobile-Agent 观察设备不能提交采集。
- **不可宣称**：真机任意操作、全局所有权、自动恢复、机架 HA。

示范接口 busy 不妨碍继续建设设备平台；不能反过来为了展示任务成功把 busy 当作 false。

### B. 新设备的最小独立控制安装（待实现）

此档位针对未来新接入/明确交接的设备，不是在当前手机旁启动另一个竞争控制器。

| 安装位置        | 最小组成                                                                                       | 按需才增加                                            |
| --------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 中心            | 管理 API/UI、持久任务/资源状态、调度消费、鉴权审计                                             | 外部媒体/证据存储、工作流引擎等，按实际瓶颈引入       |
| 每台 USB 宿主机 | 一个受管 Host Agent；一个明确归属的 ADB server；身份/心跳、白名单命令、租约/代次校验、持久回执 | scrcpy 视频/输入后端、UI 层级自动化、OCR/视觉等能力   |
| 每台手机        | 经授权的调试连接；开展小红书示范时安装并人工准备好对应 App/账号                                | 特定输入/层级驱动需要的设备端组件，逐项批准并记录版本 |
| 浏览器          | mx-device 管理页面；最小方案仍可 PNG 观看                                                      | 使用视频解码时再验证 HTTPS、浏览器与 codec 支持       |

不把 PoC/VPN、侵权案件库、Claude/豆包或其他模型服务作为必装底座。已有旧业务可能依赖它们，因此“不作为新平台必要依赖”不等于可以卸载当前环境中的组件。

基础 ADB 可按设备 serial 选择目标并抓取屏幕，平台不必要求额外常驻手机 App 才能开始观察；但不同机型的输入权限与驱动能力需实机验证。[Android 官方 ADB 文档](https://developer.android.com/tools/adb)

scrcpy 是后续媒体/控制组件候选，不是第一步必须安装；其设备端代码会被推送并启动，“不用安装常驻 App”不等于零改动。UI 自动化组件也可能需要设备端进程或辅助包，不能在文档里统一写成“完全免安装”。[scrcpy 开发说明](https://github.com/Genymobile/scrcpy/blob/master/doc/develop.md)

先提供一个版本受控的 Host Agent 安装包/镜像和配对流程，而不是要求每台宿主机部署旧 mobile-agent 的完整业务套件。代理运行语言和媒体后端在独立原型评估后确定，不为兼容旧项目强制打包所有 Python/Node/模型依赖。

### C. 高可用生产部署（目标，不是当前一个命令已经具备）

最小单机安装不能同时承诺消除该主机的单点故障。HA 需要按故障域增加冗余，而不仅仅增加进程数：

- 中心入口与管理 API 的多实例、健康摘除、稳定的服务地址；鉴权/配置/状态跨实例一致。
- 调度器/消费者可恢复且领取互斥，重复投递不导致重复手机动作；代理验证 owner/代次，不能只依赖中心进程存活。
- 数据库有经过验证的备份、恢复及符合目标的故障切换方案；复制也不代替备份。当前独立 PG 单实例仍是单点。
- USB 宿主机或整机架失效时，物理连接在其上的手机不可凭空迁到另一个进程。可继续服务需要其他故障域中有可用且账号/能力兼容的手机容量。
- 屏幕/证据传输故障与任务调度隔离；媒体不能拖垮管理数据库或排挤命令回执。
- RTO/RPO、允许的任务未知比例和吞吐目标需与团队确定并演练；当前没有生产 SLA，也不将租约超时当作安全重试证据。

“中心还在线”“任务最终没丢”“某一台手机始终可用”“任意步骤自动跨机接管”是不同等级的可用性，不能用其中一项替代全部。

## 4. 适配度矩阵：不使用未经测试的百分比

这里分别评价**现有能力能否调用**与**可靠集群还缺什么**。功能像，不代表可靠性也相同。

| 能力                               | 现有 mobile-agent 证据 / 接入程度                             | mx-device 归属与补齐项                                                     |
| ---------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 设备池、机型、系统、电量、前台 App | 高：旧服务有缓存接口；本中心已有定向过滤读取                  | 中心设备模型/展示；显示来源及缓存时间，不等价实时硬件状态                  |
| 发现设备                           | 有实现，但旧 `refresh=1` 查询 ADB 并更新旧库；当前未调用      | 未来受管代理上报候选、批准绑定；不把打开页面当发现动作                     |
| 连接、重命名、移除                 | 旧 UI 有入口；已审阅的旧移除是隐藏数据库记录，不是物理断线    | 中心本地名称/退役记录可独立实现；连接/断开语义要逐项核实，不直接透传旧按钮 |
| 原比例截图                         | 高：指定 serial 的 PNG 已接入                                 | 中心认证、去重、限流、过期标记已有；大规模改为独立观察通路                 |
| 连续视频                           | 有 8788 H.264 能力，当前未接                                  | 媒体适配器；解决解码、单源多观看者、流资源作用域和授权                     |
| 点击/滑动/返回/应用导航            | 原端点具备部分动作，但当前不接真机写入                        | 归统一命令执行层；先解决排他、前置条件、审计及未知结果，再复用能力         |
| 中文输入 / UI 层级 / 复杂自动化    | 已导出通用动作 API 不完整；旧 README 另有 Portal/输入法等依赖 | 单独可选驱动，不臆造旧 HTTP 能力；版本、安装副作用与适配成本需补证         |
| 任务池/定时/多 serial runner       | 有旧 SQLite 调度系统                                          | 中心已有持久任务池，吸收产品概念但不引入第二个调度权威                     |
| XHS 搜索/翻页/详情 JSON            | 旧 PoC 适配已实现，实际 busy 仍未解决                         | 示范插件之一；校验来源/字段，失败不能自动降级 UI 后伪装相同完整结果        |
| 所有权、取消确认、物理 fencing     | 旧接口缺足够协议证据，可靠性适配缺口最大                      | 目标 Host Agent 核心职责，不能用 wrapper 凭空补出上游未执行的锁            |
| 多主机 HA、吞吐与长期稳定性        | 无当前部署实测证据                                            | mx-device 的核心工程目标，按故障/容量验收建设，不复制页面后即宣布完成      |

迁移可分为：产品交互吸收 → 最小接口适配 → 中心协议统一 → 底层后端替换。直接复制旧源文件不是必经步骤；若移植实现仍须确认来源许可、依赖和机型兼容性。

## 5. 新截图说明了什么

### 8787 设备池

用户截图显示一条在线、一条离线设备记录，页面报告 Android 11、1080×2400 等字段。这支持“旧服务有设备池与状态展示”，**不能证明当前已插两台可并发手机**。名称不是身份；离线条目可能是另一台设备或旧记录，必须按 serial/宿主机核对后才能纳入可用容量。

右侧显示“未选择设备”，因此空白画面本身也不是截图/视频能力失效证据。旧页面的“发现设备”“连接”“停止投屏”可能有各自副作用；本次没有点击或调用。

### 直接打开 8788 报错

地址栏访问 `http://10.88.88.88:8788` 是普通 HTTP 导航，不是 WebSocket 客户端的 Upgrade 握手。报错中的 `invalid Connection header: keep-alive` 与这种访问方式一致；说明该地址返回了协议错误，既不是普通 HTML 页面，也不能据此认定视频链路健康或故障。[WebSocket 握手说明](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers)

导出源码实际处理的是 `ws://<host>:8788/ws/video?device=<serial>`，不是根路径 `/`。正确消费者还需理解状态消息和 H.264 数据并解码，不能直接把地址填进 `<img>` 或认为握手成功就能播放。旧 8787 页面设计上承担这部分客户端职责；本次未重新打开流或验证旧前端。

旧 README 描述 WebCodecs；`VideoDecoder` 受安全上下文及浏览器兼容性限制。因此 `http://10.88.88.88:8787` 下即使管理页面正常，也不能保证视频解码可用；这只是待排查条件，**不是凭截图确认的另一根因**。未来采用 HTTPS + 经鉴权的同源媒体入口，并保留 PNG 降级；不要要求用户关闭浏览器安全限制。[VideoDecoder 官方参考](https://developer.mozilla.org/en-US/docs/Web/API/VideoDecoder)

已审源码的流清理会运行广泛的 `pkill screenrecord`，所以不要把“打开再关闭旧视频试试”当作绝对无副作用的健康检查。保持本中心已实现的 PNG 观察，连续视频另行设计和验收。

## 6. 高性能的重点：让更多手机有效工作，不是一部手机多线程点击

单手机只有一个共享 UI 上下文，普通业务任务仍串行；多台设备可以并行。提高 API 请求并发或线程数不会自动提高物理操作吞吐。账号策略、App 响应、USB 稳定性、网络和页面等待都可能比中心 CPU 更早成为瓶颈。

优先顺序：

1. **正确调度**：按能力、账号与故障域分配；有界步骤/会话、幂等提交、未知结果隔离，避免重复执行和设备争用。
2. **画面分流**：列表仅取元信息/低频缩略图，只有正在观看的手机开较高频流；单手机单源共享，慢客户端丢旧帧，不堆积无限内存。
3. **减少全量轮询**：当前实验版快照/DB 最新 PNG 可以保留，规模化后按测量结果引入增量事件与独立媒体/证据存储，不让每帧穿过全量调度状态事务。
4. **缩小竞争范围**：现有模式级短锁是实验保护；后续按设备/账号等资源领取、索引化队列和分区处理。若采用 `SKIP LOCKED`，它只帮助多个队列消费者减少等待，并不能代替物理设备锁或自动保证优先级公平。[PostgreSQL 文档](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)
5. **分级限流/背压**：中心、Host、设备、账号与媒体各有预算；超载有可见排队/拒绝原因，不把所有任务都抢成 running。

验收至少分别测：API 响应和任务入池延迟、排队时长、设备利用率、任务成功率/未知率、重复物理执行事件、图片帧龄、单主机资源、USB/网络错误和恢复耗时。按 1 台真机 → 2 台真机 → 一个机架递进；模拟负载可测中心，但不能替代真实设备的编码、USB 和业务耗时测试。当前 64 台登记上限、4 个 Worker 在途上限都不是容量承诺。

## 7. 小红书作为第一条“参考业务”

建议业务流程：提交关键词 → 排队/设备与账号匹配 → 有界搜索 → 校验列表 → 创建详情依赖 → 保存结果与证据 → 释放执行槽。平台提供通用任务/步骤/证据；插件提供 XHS 参数、页面/JSON 解析和成功标准。

两种后端分开验收：

- **legacy-poc**：沿用既有结构化 JSON 协议，忙或未知时阻止执行；全局分页上下文仍独占设备，不自动改派。
- **UI 工作流（规划）**：走统一控制代理，使用定位/截图/OCR 等获取获准访问的内容；结果标明 `source`、采样时间、字段覆盖及证据。不能因标题可见就宣称取得完整详情/全部分页，也不能遇到风控/登录挑战就自动绕过。

核心成功指标不是“页面上像小红书”，而是：同一手机无交叉动作、任务不丢、结果可追溯、故障不扩散、未知可解释、增加第二台能按策略并行。首个参考业务通过后，其他应用只增加驱动/业务流程，不重做一套机架平台。

示范默认是经授权的搜索/读取，不纳入点赞、发布、举报、支付等写入业务。采集 token、账号资料、截图和完整结果按敏感数据处理。业务结果可以将来供 Hub 消费，但 Hub 停机不阻止中心自身观察/管理，设备故障也不应阻断 Hub 原有业务。

## 8. 下一轮交付建议

1. 以当前代码完成单机观察/状态/可选 PoC 的逐项验收，保持现役环境不变。
2. 在 mx-device 中定义最小设备能力与命令回执契约，先做 mock Agent 的双 owner、代次、取消未确认、重启/迟到回执测试。
3. 将设备池交互和 XHS 示范入口逐步统一到 mx-device；不自动同步修改旧设备名称、旧任务、旧连接状态。
4. 真机输入/新 Agent 安装需明确交接方案后另行授权；再做一台手机串行、两台并行、主机故障与剩余容量验证。

本次补充仅更新文档、核对导出代码与公开协议资料；未部署任何新控制端，未访问 8787/8788 真机接口，未改变 mobile-agent、手机、VPN、ADB 或业务系统。
