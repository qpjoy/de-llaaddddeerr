# V2-4：工作台 2.0——实时推送、泳道时间轴、流转图、解释面板、回放与分屏对照

日期：2026-10-18。依据 [2.0 方案](device-center-v2-plan-2026-10-15.md) §11 实施，只改 mx-device。**没有部署 18891，没有迁移线上库，没有连接手机、PoC、ADB 或 VPN**，不影响 MX-H2I 登录与联网。前置内容见 [V2-3 宿主机 Agent](v2-3-host-agent-2026-10-18.md)。

## 1. 结论

- **实时推送（SSE）**：
  - 页面改为订阅 `GET /api/stream`：先收一份完整状态，之后按秒收增量补丁，在本地维护模型；SSE 不可用时自动退回每 1.5 秒轮询。页头显示"实时 / 轮询"。
  - 每个 API 进程、每个模式只有一个状态生产者：观察者再多，也不会增加快照和规划次数；`/api/state` 轮询读的是同一份缓存。
  - 本进程内的写操作会让缓存立即失效，并在约 50 ms 内推送；"先写后读"立即可见。
- **四种视图**：工具栏的"屏幕 / 列表"扩展为"屏幕 / 列表 / 泳道 / 流转"。
  - **泳道时间轴**：每台设备一条泳道，范围是过去 2 分钟到未来 3 分钟。
  - **流转图**：从接收到完成六个阶段的计数，加上吞吐与等待分位数。
  - **解释面板**：任务"为什么在这里、为什么还在等、计划怎么变过"。
  - **回放与分屏对照**：策略对照结果可以按 1× / 5× / 20× 回放，也可以拖动进度，左右并排比较两种策略的泳道。回放使用与实时工作台同一个泳道组件。
- **目标规模达成**：100 台设备、约 1900 个活动任务（模拟上限提高到 2000）时，在桌面和手机浏览器上都流畅。
  - 屏幕墙只渲染视口内的迷你屏，10 秒内长任务合计 0.26 秒；
  - 泳道自动按机架分组成紧凑模式，10 秒内长任务合计 0.16 秒；
  - 每个观察者的推送流量压缩后约 30 KB/s，首屏约 170 KB；
  - 测试证实 5 个观察者加 20 次轮询只触发约每 100 ms 一次构建，不随观察者数量增加。
- **规划性能**：顺带修掉了规划的热点。100 台 / 2000 任务时，调度快照从 617 ms 降到 117 ms，`planPool` 从 347 ms 降到 47 ms。中心的领取轮次同样受益：100 台引擎压测从 4.2–4.4 s 变为 4.0 s。
- **测试**：`npm run test:pg` **257 项全部通过**（V2-3 后为 250 项）；新增补丁往返、SSE 分发、写后读、泳道/流转模型、计划解释、回放轨道等测试。浏览器验收见 §7。

## 2. 实时推送

| 部分 | 做法 |
| --- | --- |
| 接口 | `GET /api/stream?mode=`（登录会话或令牌）：先发 `snapshot` 事件，之后每有变化发 `patch` 事件，事件带版本号；每 15 秒发一次心跳注释；断线后浏览器自动重连并重新拿完整状态 |
| 生产者 | `server/state-hub.mjs`：有观察者时每秒构建一次（快照 + 汇总 + 调度视图），与上一份比较后广播补丁。构建较慢时自动拉长间隔（不低于构建耗时的 3 倍，最多占约 1/3 核） |
| 补丁格式 | `server/state-patch.mjs`，服务端与浏览器共用：按 id 比较各集合，只发变化或新增的行和删除的 id；行顺序与服务端不同时才发 `order`；其余字段 JSON 有变化时整体替换 |
| 规划节奏 | 计划与等待原因每 3 秒重算一次，本进程有写操作时立即重算；设备、任务、会话等行数据每秒更新 |
| 压缩 | 请求带 `Accept-Encoding: gzip` 时，事件流逐条压缩并立即发出；大于 64 KB 的 JSON 响应也会压缩 |
| 实时数据瘦身 | 实时视图中的任务不带每一步的冻结指令定义、回执、策略快照、计划指针与计划历史；指令只保留名称与动作；队列只带调度顺序中的前 300 项和总数；软计划只带每台设备未来 3 分钟内的前 5 项。完整内容按需取（`/api/explain`、`/api/jobs/:id`） |
| 写后读 | 本进程处理写请求时，缓存立即失效；写完成后再失效一次并推送 |

### 100 台 / 约 1900 个活动任务时实测（本机预览）

| 项 | 数值 |
| --- | --- |
| 首屏完整状态 | 原始 2.9 MB；压缩后 168 KB |
| 增量补丁 | 平均每次原始约 340 KB，压缩后约 32 KB；每个观察者约 30 KB/s（大量重新规划时） |
| 一次状态构建（内存快照） | 调度视图 117 ms（之前 617 ms），比较补丁约 30 ms |

### 规划热点修复（同时让中心的领取更快）

- 规范化后的策略按对象缓存。状态中的策略只会整体替换，不会原地修改。
- 设备 App 行改为按"设备 → App"两级索引查找。
- 账号按 id 建索引，并缓存每个 App 行对应的账号 id。

## 3. 泳道时间轴

- **编码**：
  - 实色条表示已执行或执行中；
  - 半透明条表示预计剩余；
  - 虚线框表示软计划（可变）；
  - 细带表示 App 冷却（按 App 颜色）或整机休息（灰色）；
  - 红色带"!"表示结果待核验或隔离；
  - 竖线表示现在。
- **配色**：4 个 App 用数据可视化参考调色板的分类色 1–4，按固定顺序分配。已用 `validate_palette.js` 校验：亮度、彩度、色盲分辨与正常视觉下限全部通过。对比度提示要求配合可见标签，因此有图例，宽度足够时条内直接写任务名，条内文字颜色按底色深浅选黑或白。
- **交互**：
  - 悬停显示进度、实际 / 预计耗时、计划原因、App 切换耗时与改派次数，键盘聚焦也能显示；
  - 点色块打开解释面板，点设备名打开手机工作台；
  - 把虚线计划块拖到另一条泳道即"指派"（只限未领取的任务，走原有版本校验）。
- **大规模**：超过 24 台时自动按机架分组，组内每台 8 px，点组名展开。
- **数据**：快照中的已结束会话从"最近 100 条"扩为"最近 100 条，加上 3 分钟内开始的全部（最多 4000 条）"，走已有索引。每个会话记录显示名、步数与排队用时，因此不需要查任务。

## 4. 流转图

- **阶段**：已接收（近 3 分钟）→ 排队 → 已计划 → 已签租约（设备已绑定但尚未发出指令，此时撤回无副作用）→ 执行中 → 完成（近 3 分钟）。
- **其他内容**：
  - 异常终态单独汇总：结果待核验、业务失败、已取消、依赖阻塞、已跳过、租约退回；
  - 指标：近 3 分钟吞吐、排队等待 P50 / P95；
  - 阶段卡片用一组按顺序加深的蓝色区分，点击可跳到相应视图。
- **总数来源**：不按机架筛选时，排队总数和已计划总数由服务端提供，不受实时队列只带前 300 项的影响。
- **统计卡片**：顶部的统计卡片可以点击，按状态筛选设备，或跳到中央队列。

## 5. 解释面板

点队列卡片的"解释"或泳道上的色块打开，回答三件事：

1. **为什么在这里**：计划设备、预计开始 / 完成、耗时与 App 切换、是否复用前台 App、候选设备数、前三个备选设备的开始时间和完成相差多少，以及计划稳定性（改派可以提前多少、门槛多少、是否保留原计划）。
2. **为什么还在等**：节奏账本与调度给出的阻塞原因（含截止时间）、已等待时长、最早可开始时间。
3. **计划历史**：最近 6 次改派的时间、从哪台到哪台、原因和提前量。规划器在计划设备变化时记录。

面板每 3 秒从 `/api/explain` 取一次该任务最新的完整计划（实时数据里没有备选设备和计划历史）。

单机工作台新增"执行与租约"：执行方（中心进程 / 宿主机 Agent 及其在线状态、心跳、时钟偏差、缓冲条数）、设备令牌，以及当前租约的 token、seq、是否已确认和剩余时间。

## 6. 回放与分屏对照

- 虚拟时钟对照的报告新增 `lanes`（所选策略）和 `baselineLanes`（空闲分散基线），记录每台设备的会话起止。
- 在"场景与策略 → 策略对照结果"中点"回放与对照"：
  - 可以播放、暂停、跳到结束，选择 1× / 5× / 20×，或拖动进度条；
  - 勾选"分屏对照基线"后，两种策略左右并排（窄屏改为上下）；
  - 每侧显示当前已完成和执行中的数量。
- 同一刻已开始的会话，画到当前时刻为止；尚未开始的不显示。
