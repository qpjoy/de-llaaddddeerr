# 一机多 App、独立冷却与两层任务循环

日期：2026-10-10。范围仅为 `electron-dock/mx-base/mx-device`。这是本地代码增量；前一机架版本用户反馈已部署，不代表本次增量已上线。本次未连接或修改服务器 Mobile-Agent、手机、ADB、VPN 或其他项目。

## 为什么继续实现中心调度

复核本机既有导出中的 `TaskScheduler.try_start_next_queued`、`_claim_device` 与 runner：旧 Mobile-Agent 能按 serial 串行运行不同平台脚本，但领取路径按设备取 queued、按 ID 倒序挑选，未按 App/账号冷却过滤；写入 `last_run_at` 不等于用它限制下次执行。脚本内 sleep 会占着 runner，不能实现“这个 App 休息时先执行另一个 App”。已有 adapter 转发不会增加这些调度语义，需要更改旧调度核心。

因此按用户“不能实现就直接实施”的授权，在 mx-device 补齐该能力，保留原 Mobile-Agent 运行边界。此判断针对审阅到的不完整本地导出，不代表旧系统在技术上无法开发，也不是当前服务器镜像的逐文件复验。来源和局限见 [源码核实](mobile-agent-source-review.md)。

## 已实现的调度标准

| 层次 | 规则 |
| --- | --- |
| 物理设备 | 一个 running Attempt；不同 App 不能在同一手机同时执行 |
| App/账号 | 固定 `deviceId + appId + accountKey` 绑定，分别记录策略、冷却截止、上次领取/派发/完成/成功 |
| 整机节奏 | 整机任务间隔与 App 冷却都通过才可领取；跨 App 也不绕过整机间隔 |
| 排队选择 | 按有效优先级；同级且都未等满 30 秒时预计短任务优先；任一已等待 30 秒后按入池顺序；再按 ID 稳定决胜 |
| 防长任务饥饿 | 原有每 30 秒提升一级继续生效；达到同一有效优先级的老任务按 FIFO，不被不断新来的短任务插队 |
| 设备选择 | 满足 App/账号、机架/主机、设备绑定和冷却后，优先最久未分配任务的设备，再按名称/ID |
| 任务占用 | `exclusive-session.v1`：当前搜索的 1–3 页连续占用同一设备；等待页间间隔时仍持有槽，不切 App |
| 结果未知 | 保留已派发时间与冷却，隔离整台手机；不能靠换 App 继续；迟到回执仅留证，不改变新占用/冷却 |

用户的“大小 event loop”在本版表示两层职责，**不是为同一手机启动两个竞争的 Worker，也不是 JavaScript 微任务队列**：

```text
外层循环：读取持久队列 → 优先级/等待提升/预计耗时 → 匹配资源与 App 冷却
                                  ↓ 短事务领取一个物理槽
内层循环：执行本次步骤 → 保存检查点 → 继续下一页/详情 → 校验已有完成条件
                                  ↓ 完成或隔离
外层循环：更新独立冷却 → 为此手机选择下一任务（可以换 App）
```

预计耗时：搜索 1/2/3 页默认 15/25/35 秒，详情默认 20 秒；提交可用 `estimatedDurationMs` 覆盖，范围 1000–180000 毫秒。15 秒及以内标记为短任务，其余为长任务，标签不是另一套执行槽。默认值是初始调度估计，不是实测性能，也不会改变模拟器实际等待时间。预计耗时不含排队/冷却，不是 SLA、强制超时、租约延长或可抢占凭证；当前租约仍是原有 180 秒。调用方不能用低估耗时获得手机并行权。

内层尚未新增任意脚本编排、按条数/完整正文的业务验收、复合 Job 或真实复位。搜索＋详情仍为两个 Job。以后需要细分可让出的步骤时，必须先证明 adapter 能保存/恢复上下文、确认停止，再由中心制定切换边界；不能只因高优先级任务到来就打断搜索游标。

## 冷却持久性与一致性

新增 `004_device_apps.sql`。PostgreSQL 为唯一持久依据，领取、Attempt 占用、App 历史及截止时间写入同一个模式级短事务，使用数据库时间。手机调用仍在事务外。原有单设备/单任务 running 唯一约束继续兜底；新增 `(device_id, app_id)` 和 `(mode, app_id, account_key)` 唯一约束，账号绑定不能换别名来重置节奏。

派发前先记账，成功回执再按完成时间延长截止；结果未知时停止整台手机的新任务。人工核验旧执行确已停止后恢复，会从核验时间保守延长涉及 App 与整机的冷却，且保持暂停，不伪造业务成功。

重启、暂停、重新启用、切换 App、演示重置均不清空已有截止。策略提高可延长截止；策略降低只影响将来的记账，不能提前释放当前已记录的等待。读取快照不写截止、不领取、不发手机请求。Redis 未引入；即使未来增加 Redis 提醒，也只能提示重查，不能把 key 消失当作执行许可。

升级兼容：保留原设备与账号、整机截止；模拟设备补小红书/微博两条绑定，真实 legacy-poc 补小红书一条，Mobile-Agent 观察设备不凭空获得执行能力。App 额外冷却默认 0，整机默认仍为模拟 300 毫秒、真机至少 2000 毫秒。需要在界面配置业务间隔；这些数值不保证账号免受平台风控。本版不支持账号切换/跨机迁移、多账号轮换、按操作类别/每日/出口预算。

无 `appId` 的历史任务按小红书解释；无预计耗时的历史任务按上述默认值解释。默认 App/默认预计值省略或显式填写视为同一规范化请求，保留旧幂等键；改变 App 或自定义耗时会产生参数冲突。

## 界面与复现

1. 模拟模式 →「任务池与调度」→「一机双 App 冷却」。没有活动任务/控制预留，首台演示设备已过冷却且所属资源未排空时可启动。
2. 首台手机接三条任务：小红书搜索 A、小红书搜索 B（同为优先级 2）、微博搜索（优先级 5）。演示保存小红书 12 秒、微博 6 秒、整机 0.3 秒策略；不会在结束时隐式还原。
3. 执行顺序应为小红书 A → 微博 → 小红书 B。第二条小红书因自身冷却等待，微博虽优先级较低仍能利用执行槽；始终不重叠。
4. 机架卡片与工作台显示各 App 的冷却、上次完成/派发和最早通过冷却时间。时间只表示冷却下界，不能保证届时设备/Worker/机架可用。
5. 工作台暂停设备，等当前执行/预留结束，打开「冷却策略」配置整机与 App 间隔，再显式启用。修改不会连接手机。
6. 「提交任务」可选择小红书/微博（模拟）、填预计耗时；任务表展示预计秒数与长/短标签，证据保留 Attempt 的 App、账号及估计值。新任务同优先级时可观察短任务先领取。

真实模式仍只有既有 PoC 小红书有限执行；真实微博提交被服务端拒绝，Mobile-Agent adapter 仍是截图/状态观察。模拟微博搜索/详情使用合成结果，不连接平台。未来真实跨 App 启动、账号确认、收尾/复位和可恢复步骤依赖完整 adapter。

## 部署与验证边界

仍用本项目既有 `bash scripts/manage.sh deploy`：先收尾本中心旧 Worker，再迁移 004 并更新 API/Worker。不能只更新前端或让不知道 App 冷却的旧 Worker 混跑；不用重新登记手机。不支持跳过迁移账本随意降级。

验证项目见 [verification.md](verification.md)：单元、HTTP、PG 升级/多连接池竞争/重连、模拟端到端及浏览器交互。它们不等于真实多 App 操作、设备侧 fencing、数据库故障切换或生产高并发/HA 验收。下一步仍是 D0/S2：一个 Job 内搜索＋详情、可配置完成标准、执行停止与收尾证据；再扩展真实 adapter。
