# V2-1：执行内核——快照引用、调度索引、行级事务、单活调度器与计划稳定

日期：2026-10-15。依据 [2.0 方案](device-center-v2-plan-2026-10-15.md) §15 与 [V2-0 基线](v2-0-baseline-2026-10-15.md) 测得的常数成本实施，只改 mx-device。测量都在本机一次性 PostgreSQL 18.4 上完成（同一台机器同时跑 PG 与 Node，负载 3–7）。**没有部署 18891，没有迁移线上库，没有连接手机、PoC、ADB 或 VPN**，不影响 MX-H2I 登录与联网。

## 1. 结论

| 指标（100 台满载在线状态） | V2-0 后 | V2-1 后 |
| --- | ---: | ---: |
| 全局事务（领取、管理员写入）P50 | 24 ms | 10.5 ms |
| **每台设备的执行事务**（指令开始/完成/收尾）P50 | 24 ms，且全域串行 | **1.7 ms，各设备并行** |
| `/api/state` P50 | 276 ms | 28 ms（历史 6 万时 50 ms） |
| 100 台 / 200 任务 / 720 条指令全部完成 | 26.2 s（27.5 条/s） | **3.8 s（187 条/s）** |
| 同上，启用池策略 | 28.0 s（25.7 条/s） | 8.4 s（85 条/s）→ 一轮只规划一次后 **3.7 s（195 条/s）** |
| 软计划改派（10 台 4 类场景、5 个 seed 平均） | 143–509 次 | **67–105 次**（−53% 至 −79%） |
| 调度器进程崩溃后由备用接管 | 无备用 | **约 0.1–0.5 s** |

"V2-0 后"一栏的吞吐，是用同一份新代码强制所有事务走域锁得到的（相当于 V2-1 之前的路径），两组数据出自同一次压测。

## 2. 改了什么

### 2.1 指令快照按引用存储

组合任务的每个计划步骤、每条执行指令，都冻结一份指令定义快照。指令目录的版本行不可变，所以 `PgStore` 写库时，把与目录行完全相同的快照替换为 `definitionRef`；读出时（事务、快照、任务详情）再还原成共享的、冻结的目录对象。模型代码与 API 看到的仍是完整定义。

- 与目录行不同的快照、目录里不存在的 ID，仍按原样内嵌。引用指向缺失的版本时，事务直接报错，不静默回退。
- 旧数据（内嵌形式）照常读取；只有被修改时才改存为引用，没有修改的行不会被重写。
- 效果：200 个活动任务的 JSON 从 1021 KiB 降到 305 KiB。测试见 `tests/snapshot-storage.test.mjs`。

### 2.2 调度只读索引

`schedulingIndex(state, now)` 一次性建立以下查找，替代原来反复的线性扫描：

- 每台设备的阻塞原因（缓存）。
- 机架/宿主机的运行计数。
- App 记录与资源策略按键查找。
- 池计划按任务分组。

`schedulingSnapshot`（`/api/state`）和 `claim`（含检查点插入）都通过可选参数使用它，不传则行为与原来完全一致。`tests/scheduling-index.test.mjs` 让实验室插入、池策略加资源限额、排空加真实设备三类状态逐步推进；每一步都断言带索引与不带索引的快照深度相等，且领取到的任务和设备一致。

### 2.3 行级版本号与乐观写入（迁移 010）

- 设备、任务、尝试、App、指令、资源策略、循环策略都新增 `version` 列。写回改为 `UPDATE … WHERE id=? AND version=?`，新行改为 `INSERT … ON CONFLICT DO NOTHING`。
- 任何一行冲突、死锁、锁等待超时或并发插入，都会整体回滚，在新数据上重跑纯函数 fn，最多 4 次。fn 不做 I/O，重跑是安全的。`PgStore.conflicts` 记录重试次数。
- 目录表仍只追加：新版本插入；已有版本若在内存中被修改，直接报错。
- `tests/scheduler-pg.test.mjs` 构造了这样的场景：全局事务读到旧版本后，另一个写入先提交。结果是全局事务重跑一次，两边的修改都保留。

### 2.4 每台设备的执行不再排在域锁后面

`atomic(fn, { scope: "attempt" | "device", deviceId, attemptId, jobId })` 不取域锁，只按固定顺序 `FOR UPDATE` 锁定这台设备的数据：设备 → 在途/让出的尝试（含大任务父尝试）→ 这些尝试的任务 → 指令（含回执）→ App。另外读取循环策略、资源策略和指令目录。

- **未加载的集合**（任务定义、规则、策略目录等）一旦被访问就直接报错，避免在部分状态上静默做出全局判断。
- **走按行事务的操作**：指令开始/完成、旧式搜索的派发/检查点/收尾、执行异常收尾，以及真实设备的探测、截图、状态读取完成。
- **仍走全局事务的操作**：领取、清扫，以及所有 HTTP 写入。全局事务之间仍由域锁串行，与执行事务之间靠版本号 CAS 保证不丢更新。
- **一致性依据**：
  - 全局操作只会把空闲设备变忙，而空闲设备上没有执行事务。
  - 执行事务修改的行都已被它锁住，全局写入会因为版本变化而重跑。
  - 唯一索引（每台设备一个运行中尝试、一条运行中指令）仍是最后一道防线。

### 2.5 单活调度器（迁移 010 的 `scheduler_leader`）

- 每个 Worker 用一条专用连接争抢会话级咨询锁。拿到锁的实例把 `epoch` 加一，成为领导者；连接断开时锁由 PostgreSQL 自动释放，备用实例在下一次检查（500 ms 周期）时接管。
- **模拟任务的清扫与领取只由领导者执行**，事务里用 `SELECT epoch … FOR SHARE` 校验 epoch：
  - 已被取代的旧领导者，其调度事务会以 `LeadershipLost` 失败，不会重试。
  - 新领导者递增 epoch 时，会等待旧领导者仍在进行的调度事务结束。
- **真实设备仍由所在宿主机的 Worker 领取**，不受领导权限制。跨主机的统一派发留到 V2-3 的 Agent 协议。
- 已经绑定到设备的执行不受领导权影响：失去领导权的实例会把在途工作做完，靠尝试的租约和代次、行版本保证安全。
- 测试覆盖：只有一个领导者；旧 epoch 无法提交；epoch 递增会等待旧事务；两个 Engine 中只有领导者领取模拟任务；领导者停止后，备用接管并跑完剩余任务。

### 2.6 派发方式

- **批量领取**：每轮在一个全局事务里先清扫，再领取到空闲槽位用满为止，不再每领一个任务开一次事务。
- **即时唤醒**：只在"可调度性"变化时发 `pg_notify('mx_device_work')`，即任务新增、任务/尝试状态变化、设备状态/启用/连接/会话变化，单纯的指令进度不通知。Worker 收到通知后，或本进程有执行结束时，都会在 50 ms 内只针对对应 realm 派发。完整扫描（领导权检查、心跳、事件清理、真实设备观测请求）仍是 500 ms 一次。
- **大任务在执行端续跑**：大任务在每个检查点让出设备。如果此时不可能插入小任务（池策略机架、定义不可恢复、插入次数已用完、设备已暂停），执行端就在按行事务里直接续跑自己的会话；只有一个冷却挡着时，等到冷却结束再续跑。可能插入时，交还全局领取决定。这修复了方案中的 P1-6（每步都要回到全局重新领取）。测试见 `tests/self-resume.test.mjs`。
- **每实例一行心跳**：使用领导权时，心跳行 ID 为 `workerId/instanceId`，文档中带上 `workerId`、`scheduler`（leader/standby）和 `epoch`。Docker 健康检查（`server/worker-health.mjs`）同时接受新旧两种行；超过 24 小时的心跳行会自动清除。设备页的执行器表新增"调度"列。
- **可配置项**（worker 配置文件，非法值会阻止启动）：`maxSimulationInflight`（默认 10，1–200）、`maxRealInflight`（默认 4，1–64）、`poolSize`（默认 10，2–64）。

### 3.3 故障演练（`npm run drill:failover`）

一次性 PG、API 进程，以及两个同 `workerId` 的 Worker 进程，在 20 台、40 个任务的模拟工作台演示上运行：

1. 上线后恰好一个领导者、一个备用，两者的容器健康检查都通过。
2. 完成约 1/4 任务后，`SIGKILL` 领导者进程。
3. 备用在 **137–535 ms** 内接管（epoch 1→2），剩余排队任务全部完成。
4. 被杀进程在途的会话（演练中为 10 个）保持占用，等 180 秒租约到期后转为未知并隔离设备，不自动重派——这是既有的保守语义。

## 4. 有意改变的行为

- 同一 `workerId` 可以运行多个 Worker 实例，只有领导者领取模拟任务；备用在心跳里报告模拟槽位已满，避免页面把它当作可用产能。
- 大任务的会话在执行端连续执行，一个 Worker 的在途计数会在整个大任务期间都占着这个槽位（以前每一步都会短暂释放）。
- 心跳行 ID 格式变化，见 §2.6。旧格式的行会在 24 小时后被清除。
- 全局事务冲突时会重跑 fn。fn 必须保持纯函数、无 I/O（这本来就是既有要求，`atomic` 会拒绝异步 fn）。

## 8. V2-1 剩余项（同日完成）：切换成本、执行容量、计划稳定、每轮一次规划

### 8.1 新增策略参数

全部是池策略的可选字段，缺省时取默认值。已有规则版本、迁移 008 的种子和机架上已保存的策略都不用改。前端规则编辑器已加入这些字段，编辑旧规则时自动补齐默认值。

| 字段 | 所属规则 | 默认 | 范围 | 含义 |
| --- | --- | ---: | --- | --- |
| `switchCostMs` | 设备分配 | 3000 | 0–600000 | 设备的热 App（正在运行的 → 最近打开的 → 最近领取的）与任务不同时，计划额外计入的设备时间；不计入 App 服务预算 |
| `stickyGainMs` / `stickyGainPct` | 队列预算 | 2000 / 20 | 0–600000 / 0–100 | 已计划的任务换设备，至少要提前 max(两者) 完成；比例按原设备的剩余预计时间计算 |
| `maxPlanMoves` | 队列预算 | 3 | 0–100 | 每个任务最多主动改派次数 |
| `planFreezeMs` | 队列预算 | 1000 | 0–60000 | 原计划设备在此时间内就要开始时，不再改派 |

### 8.2 规划规则

1. **切换成本**：预计完成时间 = 开始 + 切换 + 估时。分散模式下，只要有 1 秒内就能开始的候选设备，就只在这些设备里选最早完成者，不为热设备等待；非分散模式仍是"最早完成（含切换）+ 有界亲和"。
2. **执行容量**：领导者领取时，把自己的 `maxSimulationInflight` 作为全局并发许可传给规划器；页面的 `/api/state` 从新鲜的领导者心跳推出同一个值。其他机架正在运行的会话也计入占用；槽位数不少于设备数时不做这项检查。
3. **计划稳定**：每轮先按上述规则选出设备，再与任务的 `poolPlan`（上一轮记录的计划设备）比较：
   - 原设备已不可用，或者新设备现在就能开始、原设备不能：直接改派，不计次数。软计划没有物理代价，所以永远不会为了稳定而让任务错过立刻开工。
   - 两边都要在未来才开始：只有不在冻结窗口内、未达次数上限、并且提前量够门槛时才改派，否则保留原设备，并注明原因（`sticky-gain` / `sticky-frozen` / `sticky-limit`）。
4. **记录计划**：领取时只要有排队任务，就规划并记录 `poolPlan = {deviceId, moves, since}`，与是否有空闲设备无关；只在设备变化时写入。
5. **每轮一次规划**：Engine 的批量领取在同一事务里共享一个 `round`，规划只算一次；后续领取复用这份计划，硬约束仍逐次重新核对。
6. **模拟执行计入切换**：实时模拟和虚拟时钟实验在会话第一条打开指令上计入 `switchCostMs`，打开后记录设备的 `foregroundAppId`。耗时校准会扣掉切换部分，避免规划时重复计算。

### 8.3 对照实验（10 台，4 类场景，5 个 seed 平均）

为了公平，模拟出的切换耗时统一固定为 3 秒（内部实验参数 `modeledSwitchMs`，不对外开放），只改变规划器的假设。"归零"一行表示把切换成本和粘性参数都设为 0。

| 场景 | 规划器 | 总时长 | 等待 P95 | 切换次数 | 软改派 |
| --- | --- | ---: | ---: | ---: | ---: |
| mixed | 切换与粘性参数归零 | 52.3 s | 21.8 s | 15.4 | 509 |
| mixed | 仅计切换 | 50.6 s | 20.2 s | 13.2 | 725 |
| mixed | **切换 + 粘性（默认）** | 52.6 s | 20.6 s | 13.6 | **105** |
| affinity | 归零 | 26.9 s | 5.6 s | 2.6 | 143 |
| affinity | **默认** | 26.0 s | 5.3 s | 2.2 | **67** |
| cooldown | 归零 | 25.6 s | 14.1 s | 5.0 | 434 |
| cooldown | **默认** | 23.9 s | 13.3 s | 4.6 | **104** |
| burst | 归零 | 43.6 s | 18.3 s | 13.4 | 353 |
| burst | **默认** | 43.0 s | 18.7 s | 14.2 | **79** |

- 计入切换成本后，四类场景的总时长都缩短或持平，切换次数减少。
- 粘性把软改派降低 53–79%，代价是 mixed 总时长比"仅计切换"多约 2 秒、burst 的 P95 略差。这是有意的取舍：页面上的计划不再频繁跳动。
- 第一版粘性规则会阻止"立即开工"，总时长最多恶化约 30%。改为"新设备能立刻开始就直接改派"之后才得到上表的结果，这条修正已写成测试。
- 单 seed（mixed / 10 / 42）：adaptive 52.6 s、P95 18.6 s、切换 12 次；spread 50.3 s、P95 20.6 s、切换 23 次。各有所长，仍然不存在全面最优的策略。
