# V2-0：基线测量与快速修正

日期：2026-10-15。依据 [2.0 方案](device-center-v2-plan-2026-10-15.md) §15 的 V2-0 阶段实施，只改 mx-device。全部测量都在本机的一次性 PostgreSQL 18.4 上完成：fsync 关闭，用完即删。**没有部署 18891，没有迁移线上数据库，没有连接手机、PoC、ADB 或 VPN**，也不影响 MX-H2I 登录与联网。

## 1. 结论

1. **方案中 P0-1 的推断已被测量证实，并已修复与历史相关的部分。** 修正前，存储事务和页面快照的耗时随历史线性增长：历史 6 万个任务时，单次事务 P50 为 113 ms，快照 805 ms，`/api/state` 1.1 秒。100 台满载约 2 小时就能积累到这个规模。修正后，同样规模下事务 P50 为 26 ms，快照 37 ms，从 5 千到 6 万基本持平，执行计划中没有任何全表扫描。
2. **剩下的是与历史无关的常数开销，属于 V2-1 内核重构的范围。** 100 台满载时，每次事务约 26 ms：其中约 11 ms 是加载 200 个活动任务约 1 MB 的 JSON（每个组合任务都内嵌了指令定义快照），约 12 ms 是进程内的克隆、序列化、对比和事务本身。按每条指令需要 2–3 次串行事务计算，**当前架构约支撑 20–30 台设备同时持续执行**。`/api/state` 每次请求约 280–300 ms CPU（`schedulingSnapshot`），按页面每 1.5 秒轮询一次计算，约 5 个观察者就能占满一个 Node 核。
3. 优先级老化不再塌缩；事件时间线有了保留策略；PG 测试和压测可以在本机一条命令复现。

## 2. 改了什么

| 项 | 改动 | 证据 |
| --- | --- | --- |
| 历史查询 | `server/store.mjs` 中会随历史增长的 6 条查询提为导出常量 `SQL`，并把 OR 条件改写为分支各自走索引的 UNION；外层用 `id = ANY(ARRAY(...))` 强制主键查找；"最近 N 条"先从索引取 ID，再读文档 | `tests/history-queries.test.mjs`：同一份数据上新旧 SQL 跑 8 组任务参数、4 组指令参数、3 类快照 × 2 个 realm，结果逐行一致 |
| 迁移 009 | `jobs(mode, created_at DESC, id DESC)`、`attempts(mode, created_at DESC) INCLUDE (status)`、`events(mode, at)`；迁移内把语句超时放宽到 600 秒，避免大表建索引时触发迁移器默认的 4 秒上限 | PG 集成测试覆盖 001→009 迁移；`postgres.test.mjs` 的迁移计数更新为 9 |
| 事件保留 | 新增 `server/retention.mjs`；两种 store 都实现 `pruneEvents`；Worker 每 10 分钟在扫描循环之外分批清理（每批 5000 行，每轮最多 20 批），结果写入心跳的 `eventPrune`；默认模拟 7 天、真实 90 天，始终保留每个 realm 最新 1000 条；配置项为 worker 配置的 `eventRetention`，非法值阻止启动 | `tests/event-retention.test.mjs`：配置校验、按 realm 保留最新、批次上限、幂等、Engine 周期调度、清理失败不影响调度，以及 PG 上的分批删除和快照 |
| 优先级老化 | 仍是每 30 秒提升一级，但**最多提升 3 级**；等待满 **5 分钟**的任务视为最高级，同级 FIFO，领取原因中注明"按防饿死规则提前" | `tests/model.test.mjs` 新增老化上限与比较器一致性的穷举测试（5 个优先级 × 9 个等待时长 × 2 种估时，验证反对称和传递性） |
| PG 测试 | `scripts/pg-temp.mjs` 启动一次性集群（只监听 127.0.0.1 的随机端口，不开 unix socket）；`npm run test:pg` 跑全量测试 | 全量 **203 项通过、0 失败、0 跳过**（改动前基线 197 项） |
| 压测 | `npm run bench:pg`：先构造在线状态（100 台模拟设备、100 个执行中、100 个排队，并启用池策略），再按阶梯批量复制由真实模型产生的历史文档；输出 EXPLAIN、事务、快照和 `/api/state` 的耗时，以及事务成本分解 | 原始结果：[修正前](benchmarks/pg-baseline-2026-10-15-before.json)、[修正后](benchmarks/pg-baseline-2026-10-15-after.json) |

**有意改变的行为**：旧测试断言"优先级 8 的任务等待 3.5 分钟后会排在新到的优先级 1 前面"，那正是塌缩问题。现在这种情况下新到的优先级 1 先执行；等待满 5 分钟后，旧任务才会被提前。

## 3. 测量方法

- **在线状态**：100 台模拟设备，每台支持 4 个 App，按 5 种内置任务（含大任务）排入 200 个任务，领取其中 100 个并让每台各有一条运行中的指令。
- **历史**：用真实模型完整跑一个 `pdd.search_detail_ocr` 大任务，把得到的 Job / Attempt / 5 条指令 / 9 条事件作为模板，按阶梯批量复制。每个历史任务约 25 KB 文档。
- **指标**：每级先 `ANALYZE`，然后：
  - 对 6 条查询各做一次 `EXPLAIN (ANALYZE, BUFFERS)`，记录耗时、缓冲块数和全表扫描的表。
  - 事务空操作和写一行：模拟指令完成路径的参数，各 20 次。
  - 只读快照，以及快照加 `schedulingSnapshot`（等同 `/api/state`）。
  - `planPool` 的纯 CPU 时间。
- **复现**：

```bash
npm run bench:pg -- --jobs 0,5000,20000,60000 --iterations 20 --out report.json --plans
```

受本机磁盘余量限制（约 14–18 GiB），最大只跑到 6 万个历史任务（约 1.3 GB 数据库）。趋势已经足够明确。线上镜像是 PostgreSQL 17，规划器的细节可能与 18.4 略有不同，但"每个分支走索引"的改写不依赖具体版本。部署前可以用 PG 17 的二进制设置 `MX_DEVICE_PG_BIN` 后重跑一遍。

### 4.3 剩余的常数成本（V2-1 的输入）

100 台满载时，单次事务空操作的分解（历史 6 万时）：

| 部分 | 行数 | 数据量 | P50 |
| --- | ---: | ---: | ---: |
| jobs（活动 200 + 最近 100 + 依赖来源） | 200 | **1,021 KiB** | **10.7 ms** |
| execution_commands | 100 | 115 KiB | 1.0 ms |
| device_apps | 400 | 167 KiB | 0.7 ms |
| devices | 100 | 60 KiB | 0.6 ms |
| 其余 7 张表 | — | 67 KiB | 1.3 ms |
| **查询合计** | | | **14.3 ms** |
| 进程内克隆/序列化/对比 + BEGIN/锁/COMMIT | | | **11.6 ms** |
| **事务合计** | | | **25.9 ms** |

- **任务文档过大**：每个组合任务的 `workflow.plan` 都内嵌了每一步的完整指令定义（输入/输出 Schema、绑定），活动任务平均约 5 KB。快照不可变，可以改为按"定义版本 ID"引用，或单独存一张表，只在执行时读取。
- **整域读写**：每次事务都要克隆、序列化并逐行对比整个运行域，这是 V2-1 改为行级表和内存索引的直接理由。
- **容量估算**：38 次事务/秒 ÷ 每条指令 2–3 次事务 ≈ 13–19 条指令/秒。按每条指令 1.5 秒计，约能支撑 20–30 台设备持续执行，还没算领取和管理员写操作。在线 Worker 目前把模拟并发限制在 10，所以这个上限暂时还没被触及。
- **`/api/state` 的 CPU**：约 280–300 ms，与历史无关。Profiler 显示热点在 `schedulingSnapshot`：
  - 对每个排队任务和每台跑大任务的设备都调用 `insertionBlockers`，而它内部又遍历全部设备、重算 `deviceBlockers`，复杂度约为 O(任务 × 设备²)。
  - `appBlockers` 每次线性查找 400 条 App 记录。

  `planPool` 本身只占约 6 ms。建议作为 V2-1 的第一项：预先计算设备可用性和 App 索引，并由 leader 发布计划，页面只读计划。

## 6. 部署注意（本轮未部署）

- 迁移 009 在迁移事务里普通建索引（不是 `CONCURRENTLY`），期间会阻塞对应表的写入。当前线上实验库数据量很小，预计瞬间完成；如果以后历史已经很大，应选择空闲窗口部署。
- 事件清理由 Worker 执行，不需要新增容器或端口。首次部署时如果有大量旧事件，会按每 10 分钟最多 10 万行的节奏逐步清理。
- 本地临时 PostgreSQL 来自 10-13 一轮留在 `/tmp` 的 embedded-postgres 18.4 二进制，可能被系统清理。长期建议 `brew install postgresql@17`（与线上镜像同一大版本），`npm run test:pg` 会自动找到。
