# V2-2：统一节奏账本、账号池与策略 2.0

日期：2026-10-15。依据 [2.0 方案](device-center-v2-plan-2026-10-15.md) §8、§9 实施，只改 mx-device。**没有部署 18891，没有迁移线上库，没有连接手机、PoC、ADB 或 VPN**，不影响 MX-H2I 登录与联网。前置内容见 [V2-1 内核](v2-1-kernel-2026-10-15.md)。

## 1. 结论

- **三套冷却合并到一个账本。** 整机间隔与 App 固定冷却、机架循环策略的随机休息、池策略的窗口预算，现在都由 `server/ledger.mjs` 统一判定和记账。每条阻塞原因都带着作用域（device / session / account）、原语（最小间隔、随机休息、预算休息、核验保护、连续服务休息、风控退避、24 小时上限……）和截止时间。页面上"为什么还在等"全部来自账本。
- **旧数据等价迁移。** 截止时间仍保存在原来的设备和设备 App 字段里，已经产生的冷却原样保留。重构前的 205 项单元测试没有任何修改就全部通过。
- **新增账号作用域与账号池。** 账号成为独立的一等对象（迁移 011），跟随账号而不是设备。账号状态（受限 / 待复核 / 停用）对模拟和真实两种模式都是硬约束；平台信号会自动转人工复核，并指数退避；恢复账号需要明确确认，而且不会缩短已有的退避截止时间。系统**不会自动换号绕过限制**。
- **策略 2.0。**
  - 新增规则类型"节奏账本"（`pacing`）：机架应用了带节奏规则的策略后，策略就是该机架节奏配置的唯一来源；没有节奏规则时，沿用旧的机架循环设置。
  - 按流量自动切换平静/繁忙两套策略：有迟滞、最短驻留和每小时次数上限，只由单活调度器执行。
  - 影子评估：用当前队列分别按现行策略和候选策略规划一次，只读对比。
- **测试与性能**：`npm run test:pg` **233 项全部通过**（V2-1 后为 222 项）。账号记账让每个执行会话多一次加锁读取和两次写入，在负载约 6.8 的机器上，100 台池策略压测从 3.7 s 变为 4.2–4.4 s，开销约 10–15%。

## 2. 节奏账本

### 2.1 作用域与原语

| 作用域 | 原语 | 配置来源 | 记录位置 |
| --- | --- | --- | --- |
| device | `minGap` 整机间隔 | 设备设置（`taskIntervalMs`；默认模拟 0.3 s、真实 2 s） | 设备 `cooldownUntil` + `restReason` |
| device | `continuousRest` 连续服务上限后休息 | 策略节奏规则 `continuous` | 设备 `serviceStreak` |
| device | `verifiedStop` 核验停止后的保护间隔 | 固定（≥ 2 s） | 设备 |
| session（设备 × App） | `minGap` 任务后间隔 | 设备 App 设置（`cooldownMs`） | App `cooldownUntil` |
| session | `burstRest` 连续执行后随机休息 | 策略节奏规则 `burst` > 机架循环设置 | App `rest` / `restHistory` |
| session | `windowRest` 窗口预算用完后休息 | 策略 App 预算（含单 App 覆盖） | App `poolRuns` / `poolRestUntil` |
| account | `status` 受限 / 复核 / 停用 | 运营操作或平台信号 | 账号 `status` |
| account | `minGap` / `windowRest` / `dailyCap` | 策略节奏规则 `account` | 账号 `runs`、`hourly`、`cooldownUntil` |
| account | `signalBackoff` 风控退避 | 平台信号（10 分钟起，翻倍，最长 24 小时） | 账号 `signals` |

### 2.2 统一规则

- **判定**：`devicePacingBlockers` 和 `pacingBlockers`（会话 + 账号）是唯一的准入判定。领取、规划器（`windowAdmission` 加账号状态与预算）、大任务续跑和页面解释都走这两个函数。
- **记账**：`pacingDispatch` 在发出指令时预留，丢失回执也算已消耗；`pacingSettle` 在确认结束时按实测时长结算；`pacingVerifiedStop` 在人工核验停止后施加保护。未知结果保持已消耗。
- **截止时间只会延长**：改策略、停用规则、刷新页面都不会缩短已经产生的截止时间。
- **配置来源合一**：每台设备的节奏由 `pacingFor` 解析，并标明每条规则的来源。设备间隔属于物理设备的设置，在单机工作台修改；随机休息、窗口预算、整机连续服务和账号预算属于机架策略，在规则编辑器里修改。旧的循环策略表单仍可用于没有节奏规则的机架；机架应用了节奏规则后，表单会提示其中的休息设置不再生效。

### 2.3 账号池

- **迁移 011**：新增 `accounts` 表，从每条设备 App 记录生成一个正常状态、用量为空的账号。账号 ID 为 `mode/appId/accountKey`。数据库约束保证一个账号只绑定一台设备，与"一机一 App 一账号"的决定一致。
- **生命周期**：新登记的设备在创建 App 记录时同时加入账号池；只读路径（`/api/state`、诊断）从不创建账号。
- **文档体积有界**：
  - 运行记录只保留当前预算窗口内的部分；
  - 24 小时上限用 24 个按小时滚动的计数桶；
  - 累计只保存总次数和总时长。
  - 400 个账号约 120 KB，可以随领取事务一起加载。
- **并发**：按行执行事务会对本设备各 App 的账号加 `FOR UPDATE` 锁，并按版本号写回；并发的平台信号和状态修改都不会丢失。
- **接口**：
  - `GET /api/accounts?mode=`：账号列表，含绑定设备、24 小时次数、在途、退避和最近信号。
  - `POST /api/account-status`：参数 `{id, status, reason, revision, confirmed?}`。恢复为正常需要 `confirmed:true`；已停用的账号不能恢复。
  - `POST /api/account-signal`：参数 `{id, kind: captcha|rate-limited|logged-out|risk-warning, detail?}`。
  - 测试令牌只能操作模拟模式；真实模式只接受管理员。真实账号被标记受限或进入复核后，会阻止该账号的真实领取，这是有意的保守行为。
- **页面**：左侧导航新增"账号池"，可按状态筛选，并执行标记受限、报告信号、恢复（需勾选确认）、停用。

## 3. 策略 2.0

### 3.1 节奏规则（第 5 阶段，可选，每个策略最多一条）

字段是平铺的，便于在编辑器里修改，编译后成为 `scheduler.pacing`；上限为 0 表示关闭对应部分：

| 字段 | 含义 |
| --- | --- |
| `burstWindowMs`、`smallLimit`、`largeLimit`、`burstRestMinMs`、`burstRestMaxMs` | 同 App 连续执行后的随机休息；`smallLimit` 或 `largeLimit` 为 0 时关闭 |
| `continuousCapMs`、`continuousRestMs` | 整机连续服务上限与休息时长 |
| `accountMinGapMs`、`accountWindowMs`、`accountMaxRuns`、`accountMaxServiceMs`、`accountRestMs`、`accountDailyCap` | 跨设备的账号间隔、窗口预算与 24 小时上限 |

迁移 012 新增两个种子，由代码生成，与内存目录逐字节一致：

- 规则 `pacing.default`：随机休息取值与旧的循环默认值相同，整机连续服务和账号预算关闭。
- 策略 `pool.paced`（均衡 + 节奏账本）。

原有的推荐策略 `pool.balanced` 保持不变，避免悄悄改变现有机架的行为；迁移 008 的种子也保持逐字节不变（测试同时比对 008 与 012）。

### 3.2 按流量自动切换

`POST /api/strategy-auto`，参数为 `{rack, revision, enabled, calmStrategyId, busyStrategyId, enterPressure, exitPressure, minDwellMs, maxSwitchesPerHour}`：

- **压力**：可领取的排队任务数 ÷ 可用设备数。
- **切换条件**：压力 ≥ `enterPressure` 时切到繁忙策略，≤ `exitPressure` 时回到平静策略。两个阈值必须不同（迟滞），每次切换后至少驻留 `minDwellMs`，每小时最多切换 `maxSwitchesPerHour` 次。
- **启用时**：按当前压力立即应用对应的策略。
- **执行者**：只有单活调度器在带 epoch 防护的派发事务里检查并切换。切换就是一次普通的策略应用：未领取的任务重新规划，在途会话和已产生的冷却保持不变。每次切换都写一条事件，记录压力、任务数和设备数。
- **目标策略被归档时**：自动切换停用，并记录原因。
- **范围**：与其他策略管理写接口一致，当前仅限模拟域（真实域返回 403）。

### 3.3 影子评估

`POST /api/strategy-shadow`，参数为 `{rack, strategyId}`。用当前排队任务和设备状态（含执行器槽位），分别按机架现行策略和候选策略各规划一次，返回以下指标：

- 可规划任务数
- 立即开始数
- 平均 / P95 预计等待
- 队列预计清空时间
- App 切换次数与耗时
- 留在中央队列的原因分布

两列都按各自策略重新规划，不沿用当前策略已记录的粘性计划，否则候选策略会被旧计划拖住、看起来和当前完全一样（浏览器验收时发现，见 §7）。评估只读，不应用策略、不修改任务，当前仅限模拟域。设备工作台的策略条上新增了"影子评估"和"自动切换"两个入口。

方案中提到的"基于最近 1 小时真实轨迹回放"需要先记录真实流量，本轮没有做（见 §5）。

## 7. 浏览器验收（2026-10-16）

用户同意在仓库根目录 `.claude/launch.json` 增加预览配置 `mx-device-sim`。它运行新增的 `npm run dev:sim`（`scripts/dev-sim.mjs`）：

- 启动一次性本机 PostgreSQL，在同一进程里运行 API 和一个模拟执行引擎，再启动 Vite；
- 预置一个 10 台、使用 `pool.paced` 的演示机架；
- 管理员令牌写入 `.runtime/dev-sim.json`（权限 0600，不进 git，不打印）；
- 退出时删除临时数据；如果上次被强制结束，下次启动时清理残留；
- 只用模拟设备，不连接手机、PoC、ADB、Docker 或项目数据库。

本机需要 `MX_DEVICE_PG_BIN` 指向 PostgreSQL 程序目录（launch.json 里已写上本机路径）。

在桌面宽度（1440）和手机宽度（390）下逐项操作：

| 页面 | 结果 |
| --- | --- |
| 账号池 | 44 个模拟账号正常列出；标记受限、报告验证码信号（转待复核、退避 10 分钟）、恢复（不勾确认无法提交；恢复后退避仍在）、停用（停用后排到最后、不再显示操作）全部生效，计数随之更新 |
| 节奏账本（手机工作台） | 显示整机间隔与来源，每个 App 的随机休息、窗口预算和来源；运行中能看到"连续执行后随机休息 1 秒"；自动切到没有节奏规则的策略后，来源正确变为"机架循环" |
| 影子评估 | 当前与候选两列指标正常显示 |
| 自动切换 | 在 39 个排队任务 / 10 台时启用，立即切到繁忙策略；队列降到 5 个（压力 0.5）后切回平静策略，并写入切换事件 |
| 规则库 | `pacing.default` 的说明、摘要和 13 个字段的编辑表单（单位为秒）正常 |

验收中发现并已修复：

1. **影子评估各列结果完全相同。** 规划器会保留当前策略已记录的粘性计划，候选策略因此无法体现差异。修复：
   - 影子评估两列都重新规划；
   - 机架调度策略变化时（手工应用或自动切换），清掉该机架排队任务的粘性计划；
   - 新增回归测试。
2. **自动切换的默认平静策略不对。** 默认值是推荐策略，而不是机架当前策略，直接启用会悄悄把机架从"均衡 + 节奏账本"换掉。已改为默认使用机架当前策略。
3. **界面细节：**
   - 影子评估弹窗正文缺少内边距，两列标题改为"当前：…/候选：…"并带版本号；候选与当前策略相同时给出提示；
   - 标记受限说明会立即停止领取、在途任务照常完成；停用提示不可撤销；
   - 节奏账本里账号非正常状态时显示原因；
   - 账号池操作按钮不再在窄屏上竖排，表格改为横向滚动。
4. **预览代理被拒绝。** Vite 字符串形式的代理会改写 Host，触发 API 的跨站写入保护；`dev:sim` 改为保留原 Host。现有的 `npm run dev` 配置没有改。

已知问题：在 Claude 预览窗格里，Vite 热更新的 WebSocket 连不上，前端修改后需要手动刷新页面，不影响功能。
