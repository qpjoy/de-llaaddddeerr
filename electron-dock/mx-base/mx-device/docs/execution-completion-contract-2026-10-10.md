# 实施前决策：调度归属、执行完成与设备收尾

日期：2026-10-10。响应用户“再继续实施之前”提出的问题。本次仅核对本地导出和项目代码、补充设计，不改运行代码、不访问服务器、不更改现役 Mobile-Agent。以下接口/字段除明确列为源码已见外，均为目标契约。本文补充并约束 [调度中心优先方案](scheduler-first-plan-2026-10-10.md)。

## 1. 推荐保留中心，但不再增加第三套调度系统

如果只有一个宿主机、少量设备、固定业务、人工处理失败，继续扩展旧 Mobile-Agent 可以是成本更低的方案；“外部调度”不是所有规模的必要条件。旧系统支持指定设备和不同任务类型，不能笼统说它无法定制业务。

本项目已有的目标包括外部并发调用、多机架、账号/设备节奏、不同完成标准、独立模拟及更换执行端，因此推荐继续让 **mx-device 成为唯一业务调度中心**，复用已有 PostgreSQL 和 Worker。增加的价值是统一业务和资源契约，不是多包一层 HTTP，也不因外置就自动获得 HA。

Mobile-Agent/adapter 可保留本地执行槽、动作序列和回执记录；它们属于执行机制。受中心管理的同一设备不能同时接受旧业务队列独立派发，否则中心的冷却、账号预算和优先级均可能被绕过。当前旧服务保持原状，尚未交接的设备只观察；上述单一调度权是以后真实接入的验收条件，不是现在停旧任务的授权。

## 2. 两层职责需要补上“观测事实”边界

| 内容 | MX Device | Mobile-Agent / adapter |
| --- | --- | --- |
| 接收、排队、优先级、选择机器 | 唯一决策点 | 接受明确设备与执行身份，不能自行改派业务任务 |
| 冷却、账号预算、任务间间隔 | 持久策略和账本，决定何时允许再次派发 | 执行已获准的节奏约束，及时上报实际动作；不能在长任务内部无限操作 |
| 设备状态 | 汇总带来源/时效的报告，推导是否可调度 | 报告连接、占用、App/页面、限制信号和是否结束；保留本地拒绝忙碌设备的保护 |
| 业务任务 | 固定版本的流程、输入、目标与完成标准，验证结果 | 运行已支持的步骤/流程，输出结构化结果和证据 |
| 设备控制 | 申请受限能力，不直接假定手机状态 | 负责截图、输入、导航、取数等能力与底层传输；缺失能力明确拒绝 |
| 收尾/恢复 | 决定策略、预算和是否可释放资源 | 执行获准收尾并报告最终状态；未知时不能伪造“已复位” |

因此“设备状态由 mx-device 控制”应精确为“中心拥有可调度状态的决定权”。真实在线/执行停止等事实必须来自执行端或核验证据，管理员把状态改成 idle 不能让手机上仍在运行的操作停止。当前适配能力也不等于已具备完整手机控制。

## 3. 原 Mobile-Agent 的并发、可用性与定制证据

来源是本机选定导出，路径和包哈希见 [源码核实](mobile-agent-source-review.md)，不是运行镜像的完整审计，也没有进行线上压力/故障测试。

| 问题 | 本次源码能支持的结论 |
| --- | --- |
| 能否同时接请求、执行多台手机？ | `ThreadingHTTPServer`；`RUNNERS` 按 serial 区分，逐设备锁/子进程；SQLite 开启 WAL 和 10 秒 busy timeout。存在并发机制，不能说完全不支持并发。 |
| 能否称高并发服务？ | 无本次可用的容量/延迟压测证据；物理吞吐受单设备串行、动作时长、冷却与账号预算限制。HTTP 并发与设备执行并发是两项指标。 |
| 是否已是 HA？ | 已见进程内 runner/锁、SQLite、本机子进程、启动清占用/处理遗留任务。未见经过验证的多实例 owner/代次隔离、持久事件投递、主机/数据库故障切换。因此没有依据称已满足目标 HA；也不能靠多启动同一服务直接获得 HA。 |
| 能否不同手机做不同任务？ | `tasks.device_serial`、`type/platform/config_json` 已存在，`api_run_task` 优先用任务绑定的 serial，`build_video_scan_command` 按类型调用不同 Agent。支持绑定设备和已有类型的定制。 |
| 是否支持不同完成条件？ | 已导出的 `scripts/nurture/agent.py` 按最大检查数或特定配额结束，写 `completed/reason/history` 报告，再将完成布尔值映射退出码。说明业务脚本可以定义完成条件。 |
| 是否已经支持任意新标准？ | 未取得 product_scan 等完整脚本和平台 collectors，不能确认“搜索看 N 条不进详情”“所有正文完整提取”已有现成实现。保存 config 不表示脚本必然执行新字段。 |
| 能否保障账号不触发限制？ | 没有这样的保证。中心可统一频率、并发、预算、失败退避与限制信号暂停，但服务 HA 不等于账号可用。所有控制方遵守同一入口才有完整账本。 |

对前次结论作精确补充：runner 的确把退出码 0 标为 succeeded，但部分脚本在退出之前有业务检查；不能把它理解成“完全没有完成标准”。缺少的是跨流程、可关联某次运行、可由外部检验的统一完成契约。

## 4. 完成事件存在，但还不是可靠的外部完成协议

已核对的路径：

1. `task_runner.py::_read_output` 等子进程退出，推导 succeeded/failed/canceled。
2. `_finish_active_run` 写 `task_runs` 和 `tasks`，清中心旧设备占用，之后调用进程清理 hook；hook 异常会记录日志。
3. 调用 `on_finished(active, status)`；`web_server.py::get_runner` 将其连接到 `advance_next_task`，继续旧设备队列。回调异常记录日志，没有在所读路径看到持久重投递。

这个 callback 是可借鉴的完成通知挂点，但它在 Python 进程内，当前未见对外 webhook/SSE 订阅或持久完成事件流。数据库任务标完成、清理 hook 成功、回调送达是不同步骤，不能把收到一个状态等同于设备已安全释放。

外部也不是完全无法观察，已导出 HTTP 路由包含：

| 已有入口 | 提供什么 | 观察限制 |
| --- | --- | --- |
| `GET /api/tasks/{taskId}` | 任务记录/状态 | 同 task 可被每日重跑，任务状态不是永久绑定到某个 run 的终态 |
| `GET /api/tasks/{taskId}/collected` | 此 task 的采集明细、total，部分记录含 `task_run_id` | 按 taskId 查全部运行的数据；总数不能用作本次运行完成证明，缺 run 关联的数据不能冒认 |
| `GET /api/run` | 各 runner 的运行/日志/元数据摘要 | 进程内快照，meta 会清空，重启会丢；不作为唯一持久回执 |
| `api_run_task` 的返回 | `run_id`、task、device 等 | 已有执行调用的结果，但旧接口没有已核验的提交幂等/超时查询契约；响应丢失不能盲目再启动 |

在已审阅路由中未找到按 runId 查询完整持久终态的通用 API。现有 mx-device 的 `mobile-status.mjs` 只读设备记录与过滤后的 runner 摘要，尚未接入上述 task/collected 的业务证据读取。

可分层接入：先以带退避的只读轮询观察明确关联的 task/run，限定字段、频率与数据大小；以后在可修改的执行端增加持久回执查询与事件推送。仅通过旧任务记录无法明确归属的结果应显示“无法核验”，不能靠时间接近或 runner 空闲凑成成功。当前不会为了补事件而修改旧服务器。

可靠目标是“持久回执为准，事件减少等待”：执行端写终态时同时记录待发送事件，带 executionId/commandId/eventId/递增序号；中心幂等消费，重复不重复结算，丢失可查询补齐，迟到不能覆盖新代次。仅在内存 callback 里 POST 一次不足以保证送达。旧服务不改时，adapter 不能凭空补出它没有的执行幂等、停止证明或正文完整性。

## 5. 业务定制应该同时定义执行和验收

流程模板至少固定：版本、允许设备/账号与所需能力、输入/目标、最大动作数/时长、完成规则、证据要求、收尾策略。模板和验证器可分别实现，但版本必须匹配；通用调度器不解析平台正文或依据任意自然语言猜成功。

| 任务示例 | 完成条件（待落地示例） | 必需证据及不足处理 |
| --- | --- | --- |
| 只取搜索列表 20 条 | 匹配关键词/筛选，取得 20 个去重条目，详情进入数为 0 | 列表来源/目标 ID、数量、步骤记录；返回列表不等于“用户实际浏览过” |
| 搜索并浏览 20 条，不进详情 | 20 个不同结果卡实际进入可见区域并满足模板约定的观察条件 | 执行轨迹与对应 UI/结构化观察；仅得到 20 条 API JSON 不满足该任务 |
| 搜索后提取 3 条详情正文 | 固定 3 个目标 ID，各自打开匹配详情，提取定义范围内完整正文并验证 | 每目标内容、来源、完整性状态、展开/终止依据及必要截图；只有标题/摘要/首屏则不能成功 |

“所有正文”需限定对象与范围，例如只含笔记文字，还是包含图片内文字、评论、折叠区域。UI 提取可要求展开正文并确认文本末尾、保存覆盖证据；结构化来源则须核验该字段的完整性语义。图片 OCR、视频语音和评论属于独立能力，不能默认为正文接口已经包括。

目标不足也必须显式规定：`exactly N` 未达到就不能成功；`up to N` 可在可靠的结果耗尽证据下完成，并返回不足原因。网络失败/页面加载失败不能被当成“结果耗尽”。没有目标时是否成功同样取决于模板，不能全局一律 `no_targets → succeeded`。

不同设备按版本化能力和可配置资源标签匹配：列表任务可用列表能力；全文任务只发给能满足正文完整性/证据要求的设备。无法满足时留池或拒绝 unsupported，不把标准偷偷降级。完整业务流程可在执行端作为有界包运行，也可由中心逐步骤驱动；两者都必须遵循同一预算、身份和完成契约，避免中心下发一次后执行端内部无限操作。

中心验证可见证据和契约一致性，不能从信息不足的截图/JSON 推导一个外界不可观测的“绝对完整”。可靠度来源于明确能力、可重复测试和真实验收；重要字段缺失就失败或待核验。

## 6. 业务完成、执行停止、设备可用必须分开

建议分别记录业务判定、执行状态、收尾状态和调度资格。不要只用一个 busy 布尔值承载全部含义。

| 情形 | 业务证据 | 设备处理 |
| --- | --- | --- |
| 正文已保存，仍在执行获准的返回操作 | 业务条件可已满足；收尾尚未结束 | 仍持有执行槽，禁止下一任务插入 |
| 结果成功，返回目标页面失败但确认动作已结束 | 保留成功数据与收尾错误，最终 Job 按模板是否要求收尾成功来聚合 | 暂停/待维护，不自动丢弃数据或再采一次 |
| 超时/回执丢失，不知道动作是否仍在执行 | 可能有部分结果；完成/停止证据不足 | unknown/隔离，不能先复位再探测是否停止 |
| 执行与必需收尾均确认结束 | 按模板判定业务终态 | 更新操作历史和冷却，全部条件满足后才可再次领取 |

数据获取型模板可规定“业务成功＋收尾失败”仍保留业务成功，但设备不可调度；若返回已知页面本身就是任务必需条件，则整体不能成功。选择在提交时固定，并分别返回两项结果；允许调用方忽略收尾错误也不能解除设备隔离。

**不要求每个任务结束都复位。** 默认无额外操作；下一任务先检查自己的前置状态，必要时执行受限准备步骤。上下文敏感流程可以要求“回到已知页面”，须有动作上限、超时、页面验证和 owner 校验。不能使用无上限反复 back，也不能默认清后台、force-stop、重启手机、清数据或更改 VPN。

收尾是设备动作，也要计入次数/间隔/预算，受同一执行权保护；冷却下界必须覆盖最后一次收尾动作，不能在采集结束后开始倒计时、同时还操作手机。未知执行未确认停止之前，禁止释放给新任务或发送所谓“复位”。

## 7. 实现前先固定的小契约

在 S1/S2 之前增加 D0：用模拟输入/回执明确三件事，不接真实设备，也不引入新的调度框架。

1. 两类参考模板：列表/浏览与详情正文，明确“查看”的含义、数量严格程度、正文范围和收尾要求。
2. 执行报告：可靠的 execution/run 关联、已发起/已停止、逐目标结果、完整性与限制信号、收尾结果；缺失字段会造成什么状态。
3. 验收矩阵：达到数量、数量不足、结果耗尽、旧结果混入、只拿到摘要、重复/丢失完成事件、回执迟到、收尾失败、停止状态未知。

随后按原计划做 S1 节奏/分配、S2 有界流程，模拟与真实共用上述契约；S4 再验证真实执行端能提供哪些证据。当前首要问题是“如何可验证地宣布完成并释放设备”，不是先把完成按钮或定时器补出来。
