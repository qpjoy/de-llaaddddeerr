## 0. 一页结论

1. **分工不变**：中心负责接单、排序、放置、节奏、完成判定；adapter 负责单机顺序执行和可信回执。
2. **三处结构性调整**（详见 §2 问题清单）：
   - **内核**：从"每次事务加载整个运行域 + 全局咨询锁 + JSON 对比回写"改为"行级表 + 单活调度器的内存索引 + 租约行"。这是 100 台只能在虚拟时钟里成立、在线 worker 被限在 10 并发的根因。
   - **执行面**：worker 演进为"每台宿主机一个 Host Agent"，模拟机架也是一个 SimAgent。中心按"任务级租约 + 逐指令回执"派发，Agent 侧校验 fencing token。只有这样才能从机理上解决"同一手机两个任务串起来"，而不只是事后发现。
   - **节奏**：现有三套冷却合并为一个 **Pacing Ledger**（多作用域、硬约束、可组合）。策略/规则成为唯一的配置入口，账号池直接复用。
3. **调度算法**：采用 Kubernetes 式分阶段框架、EEVDF 式按实际服务时间的调用方加权公平、显式计入 App 切换成本的"预计完成时间"放置、带迟滞的自适应分散/亲和，以及粘性计划和冻结窗口。没有对任意流量都最优的单一算法；默认参数用多 seed 对照和 Pareto 指标选出。
4. **可视化**：设备工作台新增"泳道时间轴"（运行块 / 计划块 / 冷却带 / 休息带 / 当前时刻线），与场景演练共用同一组件。实时和回放只是数据源不同。
5. **最大的外部依赖**：同事的 PoC 能否配合（请求标识、抓取序号、只接受 Agent 调用）。已确认先不改 PoC、按 L0 接入，后续再争取 L1；在此之前，真实设备的并发安全只能做到"协作式独占 + 事后检测隔离"（§7.5）。Host Agent 已获准先部署在测试宿主机；Hub 两种调用方式都支持，并能在 Hub 管理界面内嵌实时工作台（§10.1）；账号模型为一机一 App 一账号（§17.1）。

## 3. 目标架构

```text
              ┌───────────── 调用方 ─────────────┐
              │ Hub / 外部客户 / MX Rig / 管理台  │
              └──────┬──────────────────▲────────┘
          Job API v1 │ 提交/查询/等待    │ 回调（outbox）
┌────────────────────▼──────────────────┴─────────────────────────┐
│ 控制面：无状态 API × N  +  单活 Scheduler × 1（另有热备 × 1）    │
│  准入 → 排序 → 规划(过滤/评分/预留) → 许可(节奏账本) → 绑定(租约) │
│  Pacing Ledger · 目录(指令/任务/规则/策略) · 结果/Outbox          │
│  可视化事件流(SSE) · 审计                                         │
└──────────┬───────────────────────────────▲─────────────────────┘
   租约 + 任务计划（携带 fencing token）    │ 逐指令回执 / 心跳 / 观测
┌──────────▼───────────────────────────────┴─────────────────────┐
│ 执行面：每台宿主机一个 Host Agent（模拟机架 = SimAgent）          │
│  Device Gate（单写槽 + token 校验）→ Driver：PoC / ADB /          │
│  Mobile-Agent(只读) / Sim / custom                                │
└──────────┬──────────────────────────────────────────────────────┘
           ▼
         手机（USB / 网络）；PoC、VPN 保持原样
```

PostgreSQL 仍是唯一的事实来源（独立库，不并入 mx-common）。Redis、Temporal、Kubernetes 调度器都不需要。

| 决策 | 内容 | 理由 | 放弃的方案 |
| --- | --- | --- | --- |
| D1 | 放置决策集中在单活 Scheduler，执行分布在 Agent | 放置需要全局视图；多个 worker 各自规划必然冲突 | 每个 worker 各自规划 + 全局锁（即现状） |
| D2 | 行级表 + 版本号 CAS + 唯一索引；调度器把热数据放在内存索引里 | 事务成本与历史规模无关；没有全局锁 | 整域文档读写 |
| D3 | 晚绑定（late binding）：只给"马上要开始"的任务签租约，其余都是可改的软计划 | 保留动态调度空间；与"已派发不改派"一致 | 提前把任务硬绑定到设备队列 |
| D4 | 任务级派发 + 逐指令回执：Agent 拿到整段计划后本地顺序执行 | 消除每步往返（P1-6）；中心短暂不可用时当前任务仍能完成 | 中心逐条指令下发 |
| D5 | Device Gate 在 Agent 内：每条指令都校验 `(leaseId, token, seq)` | 只有执行侧校验才能形成真正的 fencing | 只在中心加锁 |
| D6 | 统一的 Pacing Ledger | 一个地方回答"能不能跑、何时能跑、为什么" | 三套冷却叠加 |
| D7 | 模拟也走 Agent 协议（SimAgent），虚拟时钟实验复用同一调度内核 | 演练验证的就是生产代码路径 | 模拟单独一套执行逻辑 |

## 4. 内核：存储、并发与单活调度

### 4.1 表结构演进（迁移 010 起，只增不改历史迁移；009 已用于 V2-0 的历史索引）

| 表 | 关键列 | 说明 |
| --- | --- | --- |
| `devices` | 状态、启用、健康、`agent_id`、`revision` | 把常查字段从 jsonb 提到列，jsonb 只放扩展信息 |
| `device_capabilities` | `device_id, app_id, app_version, command_code, verified_at` | 能力来自 Agent 上报或人工声明，并标明来源 |
| `accounts` / `account_bindings` | 账号状态；在哪台设备、哪个 App 登录 | 见 §8.6 |
| `jobs` | `client_id, priority_class, deadline_at, not_before, plan_device_id, plan_rev, estimate_ms, status` | 队列查询走部分索引 `WHERE status IN ('queued','planned')` |
| `device_leases` | `device_id` 主键, `lease_id, token, attempt_id, agent_id, expires_at, leader_epoch` | 一台设备一行；token 单调递增，用作 fencing |
| `attempts` / `command_runs` | 后者以 `(attempt_id, seq)` 唯一，按月分区 | 回执幂等写入 |
| `pacing_state` / `pacing_entries` | 作用域键、预留/消耗/结算 | §8 |
| `clients` / `client_usage` | 配额、权重、虚拟运行时间 | §6.3、§9 |
| `outbox` | 投递 ID、目标、重试状态 | §9 |
| `events` | 按天分区，热数据保留 14 天，投影明细只存引用 | 解决 P2 的增长问题 |
| `scheduler_leader` | `epoch` | §4.2 |

热路径事务（全部是行锁，没有全局锁）：

- **绑定**：`UPDATE device_leases SET token=token+1, attempt_id=…, expires_at=… WHERE device_id=$1 AND attempt_id IS NULL AND $epoch=(SELECT epoch FROM scheduler_leader)`，然后 `UPDATE jobs … WHERE id=$2 AND status='planned' AND plan_rev=$3`，再插入 attempt 和节奏预留。任意一步影响行数为 0 即回滚。
- **回执**：`INSERT command_runs … ON CONFLICT (attempt_id, seq) DO NOTHING`，更新 attempt 进度，消耗节奏账本。
- **管理员指派/回池/取消**：对单个 job 做 CAS（`plan_rev`），与绑定只竞争那一行。

### 4.2 单活调度器与故障接管

- 调度器实例启动后，用专用连接执行 `pg_try_advisory_lock` 竞选；成功者把 `scheduler_leader.epoch` 加一并持有。连接断开时锁自动释放，热备在 10–15 秒内接管。
- 每次绑定都在 SQL 里核对 `epoch`。即使旧 leader 假死后恢复，也无法再绑定（数据库层 fencing）。
- 新 leader 从数据库重建内存索引（100 台 / 2000 个排队任务，预计不到 1 秒），已签发的租约由 Agent 继续执行。
- API 副本无状态，写入 PG 后用 `NOTIFY` 唤醒 leader。
- 调度轮由事件触发（新任务、回执、租约释放、节奏到期、策略变更），每 100 ms 至多合并一次，另有 1 秒一次的保底轮。页面查询读取 leader 发布的最新计划，不再自己跑 `planPool`。

### 4.3 容量估算

| 项 | 100 台满载 |
| --- | --- |
| 回执写入 | 约 67 条/秒 × 2–3 行 ≈ 200 次写/秒，对 PG 来说很轻 |
| 调度轮 | J ≤ 2000、D ≤ 100：最坏约 20 万次候选评估，预计 10–30 ms（需在阶段 0 测量） |
| 事件 | 只写状态迁移和摘要，约 100 行/秒，按天分区后可以直接删除过期分区 |

### 4.4 迁移方式

按 realm 切换：先 `sim`，验证通过后再 `real`。现有纯函数（`matchesJob`、`appBlockers`、`planPool` 的约束部分）抽成 `scheduler-core`，同时供 leader 和虚拟时钟使用。`MemoryStore` 继续服务单测和虚拟时钟。旧 API 在过渡期保留，由新内核实现。

## 5. 任务模型与生命周期

### 5.1 对象

| 对象 | 不可变部分 | 可变部分 |
| --- | --- | --- |
| CommandDefinition | 代码、版本、输入/输出 Schema、副作用类别（read / navigate / write）、是否幂等、是否安全点、超时、各 driver 的绑定 | 新版本取代旧版本 |
| TaskTemplate | 步骤、有界循环、结果引用、完成条件、收尾步骤、能力需求 | 新版本的默认参数 |
| Job | 调用方、幂等键、模板版本、输入、截止时间、新鲜度、优先级等级 | 状态、计划设备、`plan_rev`、结果引用 |
| Lease | 设备、token、attempt、agent、leader epoch | 到期时间（Agent 心跳续期） |
| Attempt / CommandRun / Receipt | 执行身份、序号 | 进度、证据、终态 |

### 5.2 任务模板的表达能力

在现有"步骤 × 重复次数"之上增加三项能力，全部是有界声明，不允许上传代码：

```jsonc
{
  "code": "xhs.search_topN",
  "appId": "xhs",
  "inputs": { "keyword": "string", "n": "1..200" },
  "steps": [
    { "use": "xhs.open" },
    { "use": "xhs.search", "with": { "keyword": "$in.keyword" }, "as": "page" },
    { "loop": { "until": "count($collected) >= $in.n || $page.hasMore == false",
                "maxIterations": 20 },
      "steps": [ { "use": "xhs.next", "as": "page" } ] }
  ],
  "collect": "$page.items[*]", "dedupeBy": "id",
  "complete": { "atLeast": "$in.n", "orExhausted": true },
  "finally": [ { "use": "xhs.home" } ]
}
```

- **完成条件**：明确区分 `atLeast` / `exactly` / `orExhausted`。凑够 N 条（`succeeded`）、结果已耗尽（`succeeded` 并标注 `exhausted`）、只拿到部分（`partial`）是不同的终态。
- **收尾**：`finally` 步骤总会执行，并单独记录"设备已复位"的证据。数据已经够了，但收尾没完成时，设备仍不释放。
- **固定任务**就是经过验收的模板，例如"小红书搜索关键词取前 N 条"。自定义任务走同一套执行与验收机制。

### 5.3 大小任务

分为两个独立维度：

- **成本等级**：按校准后的 P50 划为 micro（<5 秒）、small（<15 秒）、large（≥15 秒），阈值可配置。
- **恢复能力**：`yieldable` / `resumable` 由模板声明并逐 driver 验收。large 不等于可插入。

### 5.4 生命周期

```text
accepted ─► queued ─► planned ⇄ queued              （重排 / 回池，无物理副作用）
                        │ 绑定：签租约，token+1
                        ▼
                      leased ──（Agent 确认"尚未开始"）──► queued   （可安全撤销）
                        │ 第一条指令已发出
                        ▼
                      running ─► verifying ─► succeeded / partial / failed
                        │
                        ├─ 超时 / 回执不符 / Agent 失联 ─► suspect ─（宽限期内无新证据）─► unknown + 隔离
                        └─ 取消请求 ─► stopping ─（停止证据）─► cancelled
queued / planned ─（超过 deadline）─► expired；─（调用方取消）─► cancelled
```

规则：

- 绑定之前都可以重排。
- `leased` 状态只有在 Agent 确认"尚未开始"后才能撤销。
- 第一条指令发出后，任务就绑定在这台设备上。
- `suspect` 是新增的中间态：给网络抖动留出宽限期，不立刻隔离。

## 6. 调度算法

### 6.1 流水线与可配置点

| 阶段 | 做什么 | 规则能影响什么 | 不能被规则改变的 |
| --- | --- | --- | --- |
| 准入 Admission | 鉴权、幂等、配额、可行性 | 配额、拒绝阈值 | 鉴权、幂等 |
| 排序 Order | 决定谁先参与放置 | 等级、权重、老化 | — |
| 过滤 Filter | 硬条件 | 追加更多硬条件 | 单写槽、隔离、能力、已生成的冷却 |
| 评分 Score | 软偏好 | 权重、模式 | — |
| 预留 Reserve | 写软计划 | 粘性、队列上限 | 计划不占真实设备 |
| 许可 Permit | 绑定前核对节奏账本 | 节奏策略 | 账本硬约束 |
| 绑定 Bind | 签租约 | — | 全部 |

整体借鉴 [Kubernetes Scheduling Framework](https://kubernetes.io/docs/concepts/scheduling-eviction/scheduling-framework/) 的分阶段思路。上层拒绝不能被下层高分抵消。

### 6.2 准入

- 每个调用方有 `maxQueued`、`maxInflight`、提交速率（令牌桶）。全局任务池上限从 200 提到可配置（例如 2000），并为每个调用方预留份额。
- 带 `deadline` 的任务先做可行性检查：如果预计完成时间晚于截止时间，直接返回 `422` 和 `predictedFinishAt`，由调用方决定是否改为 best-effort 再提交。
- 任务超过 `deadline` 仍未绑定时，转为 `expired`，不再执行。

### 6.3 排序：调用方加权公平 + 等级 + 截止时间

借鉴 [Linux EEVDF](https://docs.kernel.org/scheduler/sched-eevdf.html) 的"按实际服务记账 + 虚拟截止时间"：

```text
每个调用方 c：权重 w_c（配置），虚拟运行时间 V_c
  绑定 job 时：V_c += est(job) / w_c；完成后按实测设备耗时修正差值
  系统虚拟时间 V = 有排队任务的调用方 V_c 的加权平均
  调用方重新活跃时：V_c = max(V_c, V)        // 防止空闲期攒额度后突然涌入
  资格：V_c ≤ V + lagLimit
  排序键：V_c + est(job) / w_c                // 虚拟截止时间，越小越先
调用方内部：截止时间先到者优先（EDF）→ 短任务优先 → FIFO
```

- **等级**：interactive / standard / batch 三级，取代自报的 1–9。调用方允许使用哪些等级由配置决定。等级之间按严格优先，但 batch 至少保底 10% 的设备时间，避免饿死。
- **老化**：等待超过本等级的 `maxWait` 时最多提升一级，并且只提升一次，解决 P1-1 的塌缩。
- **排序与放置的关系**：排序只决定"谁先参与放置"。放不下的任务不会阻塞后面的任务（现有行为保留）。

### 6.4 放置：显式计入切换成本的预计完成时间

对每台通过硬过滤的设备 d：

```text
startAt(j,d) = max(now, freeAt(d), j.notBefore, ledger.nextEligible(j,d), permitAt(机架/宿主机/Agent 槽))
switch(j,d)  = 0（d 当前前台或上一任务就是 j 的 App），否则 switchCost(app)   // 由 open 指令实测校准，默认 3 秒
finish(j,d)  = startAt + switch + est(j,d)
cost(j,d)    = finish
             − affinityBonus     // 仅非分散模式；d 的热 App = j.app 且 est ≤ shortTaskMs；上限 maxAffinityDelayMs（默认 3 秒）
             + boundaryPenalty   // 放入 j 后 d 上该 App 会进入休息，且另有不会触边界的候选：+ restMs × 0.5
             + riskSpread        // 同账号 / 同出口近期使用率高：+ w × 使用率
取 cost 最小者；同分按最近使用时间（LRU），再按 ID。
```

**用你的 B 机器例子推一遍**（5 台都支持小红书；新任务 T 是小红书小任务，预计 6 秒，切换成本 3 秒）：

| 设备 | 当前状态 | startAt | switch | finish | cost |
| --- | --- | --- | --- | --- | --- |
| A | 小红书大任务，还剩 40 秒 | 40 | 0 | 46 | 46 |
| B | 小红书小任务还剩 2 秒，另有 1 个小红书小任务已在计划中（6 秒） | 8 | 0 | 14 | 14 − 3 = **11** |
| C | 闲鱼刷新，还剩 3 秒 | 3 | 3 | 12 | 12 |
| D | 空闲，上一个 App 是微博 | 0 | 3 | **9** | **9** |
| E | 空闲，但小红书窗口已用满，休息到 20 秒 | 20 | 0 | 26 | 26 |

- 兼容设备中现在就能开始的只有 D，空闲比例 1/5 = 20%，低于 50%，所以不是分散模式。B 的亲和加分是 3 秒，但它排队太长，最终 **D 胜出**。
- **变体 1**：B 还剩 0.5 秒、没有排队任务。B 的 finish = 6.5、cost = 3.5，**B 胜出**，亲和成立。
- **变体 2（"B 快进入冷却期"）**：在变体 1 基础上，B 在窗口内已经跑了 2/3 次，T 是第 3 次，跑完要休息。若休息 5 秒，惩罚 2.5，B 的 cost = 6，仍然胜出；若休息 30 秒，惩罚 15，B 的 cost = 18.5，**改选 D**。
- **变体 3（超过一半空闲）**：进入分散模式，候选集合收窄为"1 秒内就能开始的设备"，亲和加分取消，优先最近使用少的设备和账号。B 如果还要 8 秒才空闲，就不在候选里。
- **服务时间上限**：若 B 已连续服务 14 分 58 秒，而整机连续服务上限是 15 分钟，那么 6 秒的 T 会让它超限，B 在过滤阶段就被排除。

### 6.5 模式切换要有迟滞

- 自适应模式按"机架 × App 组"计算兼容设备的空闲比例 r。
- r ≥ 50% 时进入分散模式；r ≤ 30% 时退出；每次切换后至少保持 15 秒。三个阈值都可以配置。
- 每次切换都写一条事件，工作台顶部会显示当前模式和原因。

### 6.6 粘性计划与冻结窗口（解决 P1-2）

- 已有计划设备的任务，只有新方案的 cost 至少降低 `max(2 秒, 20%)` 才会改派；每个任务最多改派 3 次。
- 距离计划开始不到 1 秒的任务冻结，不再改动。
- 报告新增指标：改派次数和改派带来的收益（节省了多少秒）。

### 6.7 执行容量感知（解决 P1-3）

Agent 的并发槽、机架/宿主机的 `maxConcurrent`、截图通道都作为"许可资源"参与 `permitAt` 计算。预计开始时间因此与真实执行能力一致。

### 6.8 同 App 聚集与请求合并要分开

- **聚集**（§6.4）只改变放置，每个任务仍有独立的输入、结果、幂等身份和完成回执。
- **合并（single-flight，可选规则）**：同一模板、同样的输入、在新鲜度窗口内，并且双方都声明 `shareable` 时，后到的请求挂到正在执行的任务上，共享结果。会额外记录每个调用方的份额。默认只在同一调用方内开启；跨调用方开启前要先确认权限和计费口径（待确认问题 Q4）。

### 6.9 大事件环与小事件环

| 你的概念 | 2.0 中的含义 | 落点 |
| --- | --- | --- |
| 小事件环 | 任务内部的指令节奏：两条指令之间的最小间隔 + 抖动（像人一样操作） | 节奏账本"设备×App"作用域的 `commandGap`；由 Agent 在本地执行 |
| 大事件环 | 会话周期：一段连续工作（N 个任务或 T 分钟）之后休息 R（随机区间，生成时持久化） | 节奏账本"设备×App"作用域的 `burstRest`；设备级的 `continuousServiceCap` |
| 大任务 / 小任务 | 预计成本等级（§5.3） | 影响亲和资格和插入资格 |
| 大任务中插入小任务 | 只允许在声明 `resumable` 的安全点插入，次数和绕行预算都有上限 | 保留现有机制，规则化为策略的一部分 |

### 6.10 CPU 调度能借鉴什么、不能借鉴什么

| CPU / 集群概念 | 设备中心中的对应 | 差异 |
| --- | --- | --- |
| 时间片抢占 | 不存在 | 手机会话不可随意抢占，只能在声明的安全点让出 |
| EEVDF 欠账 / 虚拟截止时间 | 调用方加权公平（§6.3） | 记账单位是设备秒，不是 CPU 时间 |
| cache 亲和 / NUMA | 同 App 亲和、切换成本 | 有上限，并受节奏账本约束 |
| 负载均衡迁移 | 只迁移软计划 | 已绑定的任务不迁移 |
| K8s Filter / Score / Reserve / Permit / Bind | 流水线（§6.1） | Permit 阶段核对节奏账本 |
| Sparrow 晚绑定 | 只给即将开始的任务签租约（D3） | — |

## 7. Adapter 与 Host Agent

> **V2-3 更新（2026-10-18）**：协议 v1 已实现（HTTP 长轮询加批量回报，WebSocket 待做）、Device Gate、SimDriver、HostAgent、一致性测试套件 `tests/agent-contract.mjs`。中心把指令逐条写在回报的答复里，因此失联的 Agent 自然停在安全点。真实驱动在 V2-6 接入。详见 [V2-3 宿主机 Agent](v2-3-host-agent-2026-10-18.md)。

### 7.1 Agent 的职责

每台宿主机一个 Agent 容器，与 PoC 的 docker 并列部署，**不进入、不修改** PoC 或 mobile-agent 容器。职责如下：

- 设备发现与身份：`adb devices` 序列号、型号、系统版本、已装 App 及版本。
- 健康上报：电量、亮屏/解锁、前台包名、网络、PoC 可达性。
- Device Gate：每台设备一个单写槽，并校验 token。
- 按任务计划顺序执行指令，执行小事件环节奏、收尾步骤。
- 回执：逐指令带序号和证据；与中心失联时在本地有界缓冲。
- 观测：截图限流（同设备合并请求），可选低帧率画面流。

### 7.2 中心与 Agent 的协议

由 Agent 主动连出（WebSocket，或 HTTP 长轮询作降级），宿主机不需要开放入站端口。连接使用 Agent 专属令牌，后续可升级为 mTLS。

| 方向 | 消息 | 要点 |
| --- | --- | --- |
| Agent → 中心 | `hello{agentId, version, devices[], capabilities[]}` | 中心核对已登记设备，不认识的设备只进入"待登记" |
| Agent → 中心 | `heartbeat{devices:[{id, health, foreground, leaseId, token, seq}], clockOffset}` | 每 5 秒一次，同时续期租约 |
| 中心 → Agent | `lease.grant{deviceId, leaseId, token, attemptId, plan[], pacing, deadline}` | 整段任务计划 |
| Agent → 中心 | `lease.accept` / `lease.reject{reason}` | 拒绝时说明 busy、能力缺失或设备异常 |
| Agent → 中心 | `command.started{seq}` / `command.finished{seq, receipt, evidence}` | 以 `(attemptId, seq)` 幂等 |
| 中心 → Agent | `lease.revoke{leaseId, token}` | 仅对尚未开始的租约有效；已开始的返回 `already-started` |
| 中心 → Agent | `attempt.stop{leaseId, token, reason}` | 在下一个安全点停止并执行收尾，然后回报 `stopped` 证据 |
| Agent → 中心 | `signal{deviceId, kind: captcha / rate-limited / logged-out / app-crash}` | 平台风控和异常信号 |

### 7.3 Device Gate 规则

1. 每台设备同一时刻只有一个有效 `(leaseId, token)`。收到更小的 token 一律拒绝；更大的 token 会让旧租约立刻失效。
2. 每条指令都必须携带当前的 token 和连续的 `seq`。乱序、重复或使用旧 token 的指令一律拒绝，并上报。
3. Agent 用单调时钟判断租约到期。与中心失联后，Agent 完成当前指令，然后在下一个安全点暂停。到期后不再开始新指令。
4. 所有真实手机写操作只能经过 Agent。其他控制端是否也遵守这一点，取决于 §7.5 的 PoC 配合程度。

### 7.4 Driver SPI

```ts
interface Driver {
  kind: "poc" | "adb" | "mobile-agent" | "sim" | "custom";
  capabilities(device): Promise<{ apps: AppCap[]; commands: string[]; canCancel: boolean; canFence: boolean }>;
  probe(device): Promise<Health>;                          // 只读
  execute(cmd: CommandRun, ctx: GateContext): Promise<Receipt>; // 必须回显 commandId / seq / token
  stop?(ctx): Promise<StopEvidence>;                       // 不支持就声明 canCancel=false
  reset?(device, app): Promise<ResetEvidence>;             // 回到首页 / 关闭 App
}
```

每条指令声明 `effect`（read / navigate / write）、`idempotent`、`safePoint`、`timeoutMs`、`estimateMs`。driver 不支持的能力必须显式声明，由中心选择保守路径。

### 7.5 PoC driver：按同事配合程度分三级

| 等级 | 前提 | 能达到的安全性 |
| --- | --- | --- |
| **L0 不改 PoC** | Agent 是本中心唯一的调用方，但无法阻止外部调用 | 执行前检查 idle、执行后校验 keyword/page/ID；发现不符就 unknown 并隔离。需要在管理上停用其他调用方（Hub 旧路径、Night-All）。抓取数据只能按时间窗口归属 |
| **L1 PoC 小改** | 回显请求 ID；抓取数据带单调序号或请求 ID；busy 状态可靠 | 抓取数据可以精确归属到指令；能识别并发插入；可以拒绝第二个请求 |
| **L2 PoC 只听 Agent** | PoC 只监听 Agent 所在网络，或要求 Agent 签发的令牌 | 真正的设备侧独占，串任务从机理上消除 |

抓取数据的归属算法（L1 起完整可用）：

```text
执行指令前：读取 PoC 抓取游标 cursor0（L0 退化为记录时间戳 t0）
执行指令：请求携带 requestId = attemptId:seq
执行指令后：读取 seq > cursor0 的抓取记录，校验 requestId、keyword、page、ID 集合
          出现不属于本请求的记录 → 判定外部插入 → unknown + 隔离 + 告警
```

多手机场景下，每台手机需要一个可以独立验证的 PoC 入口（独立端口或者带设备参数）。只填一个新序列号不能复用全局分页接口，这一点维持现有结论。

### 7.6 ADB driver 与 OCR

- 支持的指令：`am start`、`input tap/swipe/keyevent`、`uiautomator dump` 定位、截图。定位规则按"App 版本 × 机型类别"版本化，失效时返回 `locator-miss`，不盲点。
- OCR 作为后处理指令调用 mx-ocr，不在 Agent 的热路径里。是否接入 mx-ocr 单独决定，不因本方案自动产生依赖。

### 7.7 Adapter 一致性测试套件

任何 driver（包括 SimAgent）上线前都必须通过同一套契约测试：

- busy 时拒绝；旧 token、乱序 seq 被拒。
- 回执身份必须回显 commandId / seq / token。
- 超时后语义为 unknown，不得报成功。
- 声明支持停止的 driver 要能给出停止证据；不支持的必须如实声明。
- 收尾证据完整；风控信号能上报。

测试先在 SimAgent 上跑通，再在测试机架的单台真机上跑。

## 8. Pacing Ledger：统一冷却与节奏

> **V2-2 更新（2026-10-15）**：已实现设备、会话、账号三个作用域，以及最小间隔、随机休息、窗口预算、核验保护、连续服务休息、风控退避和 24 小时上限等原语，新增账号池（迁移 011）。出口 IP 作用域、静默时段和按日历计数的每日上限尚未实现。详见 [V2-2 节奏账本](v2-2-pacing-ledger-2026-10-15.md)。

### 8.1 作用域

| 作用域 | 稳定键 | 典型策略 |
| --- | --- | --- |
| 设备 | `device` | 任务间隔、连续服务上限、每日上限 |
| 设备 × App（会话） | `device/app` | 指令间隔（小环）、burst 休息（大环）、窗口预算 |
| 账号 | `platform/account` | 跨设备累计预算、每日上限、受限退避 |
| 账号 × 操作类别 | `account/op`（search / detail / refresh / like …） | 按操作计费的令牌桶 |
| 出口 IP | `egress` | 同出口的总频率（多台手机共用一个 VPN 出口时尤其重要） |
| 调用方 | `client` | 准入速率（与 §6.2 共用） |
| 机架 / 宿主机 / Agent | `rack`、`host`、`agent` | 并发许可 |

### 8.2 原语（全部是硬约束，可以组合）

| 原语 | 参数 | 含义 |
| --- | --- | --- |
| `minGap` | 间隔 + 抖动区间 | 两次操作之间的最小间隔；抖动值在决策时生成并持久化，刷新页面不会重抽 |
| `tokenBucket` | 容量、补充速率、按次数或成本单位计 | 窗口预算 |
| `burstRest` | N 次或 T 时长之后休息 R（区间） | 大事件环 |
| `continuousCap` | 最长连续服务时长 | 防止单机或单账号长时间不间断工作 |
| `dailyCap` / `quietHours` | 每日上限、静默时段 | 时间窗口限制 |
| `signalBackoff` | 指数退避 + 人工复核门 | 收到验证码、限流或登录失效信号时生效 |

统一接口：`ledger.check(scopes[], cost, at) → { allowed, nextEligibleAt, blockers[] }`。工作台的"为什么等待"就直接展示这里的 `blockers`。

### 8.3 账本生命周期

1. **绑定时预留**：按最坏合理成本预留。
2. **指令发出时消耗**：重复回执不会重复扣账。
3. **完成时结算**：只有确认未执行的部分可以退还；unknown 按已消耗处理。
4. 已经产生的冷却和休息不会因为策略放宽、关闭或窗口过期而被清除。这条沿用现有行为。

### 8.4 旧配置的迁移映射

| 现有机制 | 迁移为 |
| --- | --- |
| 设备 `taskIntervalMs` | `device.minGap` |
| `device_apps.cooldownMs` | `device/app.minGap` |
| 循环策略 `smallLimit / largeLimit / cooldownMin–Max` | `device/app.burstRest` |
| 池策略 `appDefaults / appPolicies` | `device/app.tokenBucket` + `burstRest` |
| 已产生的 `cooldownUntil / poolRestUntil / rest` | 原样导入，作为 `pacing_state` 的下界 |

迁移后，规则编辑器是唯一的配置入口。旧的"节奏设置"页面改为只读展示，并跳转到规则编辑。

### 8.5 账号池复用

- **账号实体**：平台、标识（加密存储，不进浏览器）、状态（active / limited / review / retired）、健康分、绑定关系（在哪台设备的哪个 App 登录）。
- **默认 1:1**：一台设备的一个 App 只绑定一个账号（与现有唯一约束一致）。账号预算跨设备累计，账号换设备不会重置历史。
- **多账号切换**（如需要）作为额外的放置维度：放置时同时选择设备和账号，账号切换的成本计入 `switch`。
- **合规边界**：收到风控信号后，暂停该账号并进入复核。**不自动换账号来绕过限制**。节奏配置只能降低风险，不能保证不触发平台限制。

## 9. 策略与规则 2.0

> **V2-2 更新（2026-10-15）**：已新增节奏规则（第 5 阶段，可选）和种子 `pacing.default`、`pool.paced`（迁移 012），以及按队列压力自动切换平静/繁忙策略、只读影子评估。基于真实轨迹回放的影子评估尚未实现。详见 [V2-2 节奏账本](v2-2-pacing-ledger-2026-10-15.md) §3。

### 9.1 阶段与组合语义（"追加"还是"替换"）

| 阶段 | 规则类型 | 组合方式 |
| --- | --- | --- |
| admission | 配额、可行性阈值 | 同一调用方唯一，替换 |
| order | 等级、权重、老化 | 唯一，替换 |
| filter | 额外硬条件（例如只用电量 >30% 的设备） | 取交集（AND），追加 |
| score | 各项权重（切换成本、亲和、边界惩罚、风险分散） | 加权求和，追加 |
| mode | adaptive / spread / affinity + 迟滞参数 | 唯一，替换 |
| queue | 粘性、冻结窗口、队列上限、等待预算 | 唯一，替换 |
| pacing | 各作用域的节奏原语，可按 App 覆盖 | 同作用域取最严格值；按 App 覆盖替换通用值 |
| failure | 模拟自动重试次数；真实只允许"有未执行证据"时重试 | 唯一，替换 |
| coalesce | single-flight 开关、新鲜度窗口 | 可选，替换 |

规则是有界 JSON，带 Schema 校验和版本，不允许上传任意代码。

### 9.2 按流量自动切换策略

- **Profile Switcher**：条件来自观测指标（队列长度、空闲比例、等待 P95、截止时间违约率），每个条件都有进入/退出阈值、最短驻留时间和每小时最多切换次数。
- **影子评估**：新策略或新参数应用前，先在最近 1 小时的真实轨迹上回放，对比关键指标，再由管理员确认。
- **审计**：每次切换都记录操作者或触发条件、旧/新版本、影响范围。已绑定的任务和已产生的冷却不受影响。

### 9.3 默认策略 `balanced.v2`（初值，需对照实验校准）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 进入/退出分散模式的空闲比例 | 50% / 30%，驻留 15 秒 | §6.5 |
| 亲和加分上限 | 3 秒 | 与现有 `maxAffinityDelayMs` 一致 |
| 切换成本 | 实测 `open` 耗时；无样本时 3 秒 | §6.4 |
| 边界惩罚系数 | 0.5 × 休息时长 | §6.4 |
| 粘性门槛 | max(2 秒, 20%)，最多改派 3 次，冻结 1 秒 | §6.6 |
| 短任务阈值 | 15 秒 | 沿用现有 |
| batch 保底份额 | 10% | §6.3 |
| 设备 × App 节奏 | 窗口 60 秒最多 3 次，然后休息 5–8 秒；指令间隔 1.0–2.0 秒 | 仅为模拟初值，不是平台安全阈值 |

## 10. Hub 与外部调用契约 v1

| 接口 | 说明 |
| --- | --- |
| 鉴权 | 每个调用方一个 API key（只存哈希），带作用域：允许的 realm、App、模板、优先级等级 |
| `POST /v1/jobs` | `{clientRequestId, template, version?, params, class, deadlineAt? / ttlMs?, freshnessMs?, shareable?, callback?}` → `202 {jobId, status, predicted:{startAt, finishAt, confidence}}`；超出配额 `429 + Retry-After`；不可行 `422 + predictedFinishAt` |
| `GET /v1/jobs/:id` | 状态、原因（可读的 blockers）、结果引用；重复查询不会再次操作手机 |
| `GET /v1/jobs/:id/wait?timeout=25` | 长轮询，供 Hub 的同步接口包装使用 |
| `POST /v1/jobs/:id/cancel` | 排队中的任务立即取消；运行中的任务进入 stopping |
| 回调 | 通过 outbox 持久化后投递，带 HMAC 签名、`deliveryId` 和指数退避，接收方按 `deliveryId` 去重 |
| 结果 | `{realm, jobId, attemptId, template@version, collectedAt, completion: succeeded / partial / exhausted, counts, items 或 resultRef, evidenceSummary}` |

### 10.1 Hub 管理界面中的设备工作台与实时状态

用户答复（Q3）：调用方式还没定；如果 Hub 管理界面里也要一个设备工作台，两种方式都可以，最好能实时看状态、看画面。据此设计为**同一套数据接口服务两种调用方式和两种界面**：

- **调用方式**：同时支持异步（提交 + 回调/查询）和同步（`/wait` 长轮询包装）。Hub 的每个业务接口可以自己选择，不必全局统一。
- **实时状态**：新增按作用域过滤的只读接口和 SSE 事件流 `GET /v1/stream?scope=…`，内容包括设备状态、队列、计划、节奏阻塞原因、任务进度。mx-device 自己的工作台也改用同一个流（§11.8），两边看到的数据完全一致。
- **实时画面**：模拟设备使用合成投影；真实设备使用 Agent 截图（V2-6 前沿用现有 Mobile-Agent 8787 只读截图）。按视口限流：屏幕墙缩略图约 0.2–0.5 帧/秒，聚焦的单台设备约 1–2 帧/秒，同一设备的多个观看者合并为一个请求。查看画面永远不会触发手机写操作。
- **嵌入方式（推荐）**：Hub 后端把 `/device-center/*` 反向代理到 mx-device 的嵌入路由，由服务端携带调用方 API key 和签名的用户身份头。浏览器只持有 Hub 自己的会话，同源加载，不受第三方 Cookie 限制，**也不会把凭证放进 URL 或浏览器存储**（遵守 AGENTS.md）。备选做法是 Hub 用同样的接口自己渲染界面。
- **两种作用域**：`ops`（Hub 管理员，可查看全部机架；是否允许指派/取消由单独的权限控制）；`client`（外部客户，只能看到自己的任务和设备池汇总，见 §11.7）。
- **分期**：V2-4 先做 SSE 和 mx-device 自己的工作台；V2-5 增加作用域过滤、嵌入路由和代理接入说明。Hub 侧的代理和页面改动不在本仓库范围内。

> **V2-5 更新（2026-10-18）**：本节与 §6.2、§6.3 已实现：调用方（密钥只存摘要、作用域、配额、权重、回调来源、嵌入范围）、EEVDF 式公平与等级、`/v1/jobs` 提交 / 查询 / `wait` 长轮询 / 取消、`/v1/templates` 的结果 Schema、outbox 签名回调、`/v1/stream?scope=client|ops` 与只读的 `/embed/*`。按待确认问题的默认值实现：Q6 客户只看自己的任务和设备池汇总；Q8 嵌入工作台只读；Q4 结果共享暂不启用（请求带 `freshnessMs` / `shareable` 返回 400）。详见 [V2-5 调用方契约](v2-5-caller-contract-2026-10-18.md)。

**从 Night-All 迁移**：逐个接口进行。第一步，Hub 调用模拟模板，核对结果 Schema；第二步，对一个真实流程做单机验收；第三步，按比例灰度切换路由。同一个真实副作用不同时提交给新旧两套系统。回退只影响新进入的流量，在途任务仍归原调度方。这一流程沿用 10-13 文档的原则。

### 11.3 泳道时间轴（一眼看懂调度）

### 11.4 解释面板

对任意任务回答三件事：

1. **为什么在这里**：评分分解，包括 finish、切换、亲和、边界惩罚、风险分散。
2. **为什么还在等**：节奏账本的 `blockers` 加上 `nextEligibleAt`。
3. **计划历史**：每次改派的时间、原因和收益。

对任意设备展示：租约与 token、Agent 健康、每个 App 的预算条（已用 / 预留 / 剩余）、休息倒计时。

### 11.5 单机工作台（弹窗）

保留现有的手机投影、指令流水和 Adapter 调试，并新增三项：节奏账本状态、当前租约（含 token/seq）、Agent 上报的前台包名和健康信息。真实设备展示真实截图；模拟设备展示合成投影，并明确标注"合成"。

### 11.6 场景与工作台合并

场景 = 负载 + 机架形态 + 初始条件；策略 = 规则组合。"运行对照"之后，可以在**同一个工作台组件**里回放（1×/5×/20×、拖动时间轴），左右分屏对照两种策略的泳道。"加入现场"则创建独立的模拟机架，由 SimAgent 实时执行。

### 11.7 外部客户视图

只读、按调用方隔离：只能看到自己的任务、预计时间和结果，以及设备池的汇总状态（总数、忙闲比例）。看不到其他调用方的任务、手机画面或账号信息（待确认问题 Q6）。

### 11.8 推送与性能

- 改为 SSE 推送增量事件，前端维护本地模型，取代每 1.5 秒拉一次全量快照（解决 P1-7）。
- 计划只由 leader 计算并发布，页面不再触发规划。
- 迷你屏只渲染视口内的设备；截图按需请求，同一设备合并请求。

## 12. 模拟器与验证体系

- **统一路径**：实时模拟使用 SimAgent，走与真实设备相同的租约、Gate 和回执协议；虚拟时钟实验直接驱动 `scheduler-core`，与 leader 共用同一份代码。
- **负载模型**：泊松到达、突发（MMPP）、日内周期；耗时用对数正态分布（参数来自校准数据或配置）；加入 App 切换成本、PoC busy 尖峰、掉线、慢机、回执丢失、风控信号、Agent 崩溃、leader 切换、PG 暂停。
- **轨迹回放**：记录真实流量（到达时间、模板、实际耗时），之后可以原样回放，用来比较策略。
- **统计**：每个对照默认跑 20 个 seed，报告均值和 95% 置信区间。展示 Pareto 前沿（等待 P95、吞吐、切换次数、截止时间违约率），不只展示获胜样本。
- **不变量检查（属性测试）**：单机指令不重叠；已绑定任务不迁移；冷却与预算不被突破；重复回执不重复结算；旧 token 回执不生效；unknown 不自动重试（真实）；同一幂等键只接收一次。
- **确定性故障模拟**：在虚拟时钟里注入崩溃点（绑定后、首条指令前、回执丢失、leader 切换），逐一断言语义。
- **耗时校准改进**：分层收缩估计（设备 → 机型/App 版本 → 全局 → 静态估计）；对数正态拟合，任务级 P90 由方差合成，不再简单相加；超时样本按删失数据处理；估计带版本号，attempt 冻结估计快照。

## 13. 高可用与故障语义

| 故障 | 行为 |
| --- | --- |
| 调用方重复提交 | 幂等返回原任务 |
| API 副本宕机 | 其他副本继续服务（无状态） |
| Scheduler leader 宕机 | 热备 10–15 秒内接管；已绑定任务由 Agent 继续执行；接管前暂停新绑定 |
| 旧 leader 假死后恢复 | 数据库层 epoch 校验拒绝它的绑定 |
| PostgreSQL 不可用 | 停止绑定和提交（返回 503）；Agent 完成当前任务，在本地缓冲回执；恢复后，token 仍有效的回执照常结算 |
| Agent 宕机 | 租约不再续期，进入 suspect；宽限期内没有新证据则转 unknown 并隔离 |
| Agent 与中心网络分区 | Agent 不开始新任务；当前指令完成后在安全点暂停；恢复后补报回执 |
| 手机掉线 / ADB 断开 | 能证明"未发出"则回到队列；否则 unknown |
| PoC busy 或被外部占用 | 派发前拒绝，任务回队；设备进入 suspect |
| 回执身份不符（串任务） | unknown + 隔离 + "疑似外部调用"告警 |
| 平台风控信号 | 账号转为 limited，节奏账本退避，相关设备 App 暂停，等待人工复核 |
| 时钟偏差 | 租约以 PG 时间为准；时长以 Agent 单调时钟为准；心跳上报时钟偏移 |

PostgreSQL 先用单实例 + WAL 归档 / 时间点恢复，并定期演练恢复；规模上来后再加流复制备库。HA 声明必须以故障演练记录为证据，不能以"启动了两个进程"为证据。

## 16. 做不到或需要接受的限制

- **没有全局最优**：任意到达流量下，最低平均等待、最低尾延迟、最大吞吐、公平和零冷却违规不可能同时达到。只能按目标权衡，并持续测量。
- **物理 exactly-once 做不到**：已发出但没有确认的指令可能已经执行。只能做到"可检测、不自动重试、可人工核验"。
- **平台风控不可预知**：节奏只能降低风险，不能保证账号不受限。
- **PoC 在 L0 级别下**，外部调用方插入只能事后发现。
- **估计永远有误差**：长尾任务会让计划失准，只能靠粘性、冻结窗口和"超时只影响下一次估计"来控制影响。
- **待优化项**：亲和导致的局部热点；能力或登录状态随设备变化而过期；跨 cell 的账号账本；长期公平与配额的计费口径；证据与截图的存储成本；从轨迹回放到自动调参的闭环。
