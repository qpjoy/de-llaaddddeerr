最新本地增量：已实现 [App 独立冷却、整机间隔与预计耗时排序](app-pacing-2026-10-10.md)。本页后续 S1 表保留原路线拆分，剩余期限/预算和 S2 复合任务继续推进；本次增量尚未部署。

## 1. 产品定位与最小操作面

MX Device 是“设备资源 + 任务执行 + 证据”的独立控制中心。Hub 是业务/数据调用方，Launcher 可承载入口，Rig 是测试客户；三者不持有另一套手机调度锁。8765 的侵权处置业务不是设备底座，旧 PoC 的补丁取数是可选能力，不是中心启动条件。

用户进一步明确：核心目标是稳定、高可用、高性能的手机机架/集群；8787 设备池和通用任务管理可以统一到 mx-device，小红书采集作为首个参考业务/插件。不能让中心退化为旧业务 UI 的复制品。安装档位、能力适配矩阵与验收边界见 [最小安装与适配度](minimal-install-and-adaptation.md)。

最小可用操作面分三层：

| 层                              | 负责                                                        | 不负责                                               |
| ------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------- |
| 中心控制面                      | 设备/主机登记、任务身份、能力匹配、优先级、权限、证据、展示 | 不直接暴露 ADB/shell，不依赖某业务 App 才能启动      |
| 宿主机执行面（目标 Host Agent） | 物理设备身份、单机写槽、租约/代次校验、命令回执、观察通道   | 不复制旧侵权业务数据库，不另建与中心争夺设备的任务池 |
| 可替换能力/流程                 | 画面、输入、UI 层级、平台搜索/详情、OCR/视觉规划            | 不绕开写槽；规划器不能持有不受控的任意 ADB 权限      |

当前 Worker 是中心的有限执行器，不等于已实现完整 Host Agent。它访问旧 HTTP 服务而不接 USB/ADB。先保持这个兼容层，再在隔离测试/新设备上验证统一代理，最后由用户批准既有手机的交接。

## 2. 不必在“永远依赖旧服务”和“立即替换”之间二选一

### 路线 A：现状兼容（已有主干，继续验收）

只读接入 8787 的屏幕/报告；旧 PoC 数据能力可选。MX Device 自己管理队列、结果、会话与 UI。可完成安全观察、调度模拟和旧接口的有条件执行，但不能保证真实全局抢占。

### 路线 B：有明确独占窗口的有限旧接口控制（待授权，不默认启用）

只有在其他控制端已停止写入、无在途任务、批准该窗口后，才评估复用旧 action 做有限导航。旧接口仍不识别中心 token，检查占用到发送动作之间有竞争窗口；此路线最多是“人工约束下的实验”，不能标成技术上强排他或自动故障接管。不能为此自动关闭旧定时任务、杀进程或改防火墙。

### 路线 C：统一 Host Agent（推荐长期目标）

通过一个经过认证的入口管理手机动作、状态和画面；底层评估 ADB + scrcpy，UI 层级/输入再选择自动化组件，来源见 [开源调查](mobile-agent-source-review.md)。先独立 mock/闲置测试设备验证；接入当前手机前必须决定现有 ADB 归属、旧业务如何提交任务、旧直连入口如何获准隔离以及回退。

“一个控制端”指**一个逻辑写入仲裁点**，不是所有代码挤进一个进程。多实例中心可以共用持久队列；每个手机只有一个当前有效 owner。若旧程序继续有直接 USB/ADB/输入权限，新增代理无法仅凭本地锁实现全局独占。

沿用当前 MX 冷灰蓝/青绿视觉和 React/Vite，不为了机架概念另做无关风格。日常设置在鉴权 UI，bootstrap 密钥/TLS/构建代理属于运维层。

| 页面        | 已有基础                                     | 后续交付                                                                             |

| 总览 / 机架 | 独立机架总览、资源汇总/筛选、并发限额/排空、Worker 心跳          | 稳定资源身份、可信故障域/物理槽位、容量测量；不把 Worker 在线显示成手机开机       |
| 手机工作台  | 原比例真实 PNG、历史接口投影、放大、过期标记 | 观察/控制两个明确模式；帧时间与数据时间分开；点击坐标经缩放/旋转换算、绑定所见帧代次 |

| 连接设置    | 手工登记、本地入口批准、状态读回、PoC 开关   | 主机安全配对、发现候选→人工批准、能力探测与版本；不能添加后即自动操作                |

| 演示中心    | 五任务、优先级、双模拟设备接管               | 逐步播放、排队原因/时间线、断线/迟到回执/优先级老化开关，始终标识模拟与真实          |

真实手机优先显示原图，不按旧 JSON 猜一个“当前小红书屏幕”。JSON 投影是独立可回放视图；模拟也可以使用手机外框，但必须显著标记合成数据，不能用真机历史图冒充另一台在线手机。

未来画面服务宜“一台手机一个受管采集源，多观看者分发”；只读观看不授予输入权。慢观看者丢旧帧，不阻塞动作队列。断流只显示最后帧及过期状态，不自动发回退、重启或清后台动作。现有 8788 的宽泛 screenrecord 清理风险未解除前继续使用 PNG。

## 4. 资源、能力与健康模型（目标）

层级：Rack → Host → Device → Session；Job → Step → Attempt → Evidence。设备识别优先稳定 serial + 可信 Host 身份，中心另有不可变 deviceId；名称、IP、端口和 USB transport_id 不是身份。

能力应按版本和安全语义分别声明，例如：

- `screen.snapshot`、`screen.stream`、`device.inspect`：观察能力。
- `input.tap/swipe/key/text`、`app.navigate`、`ui.hierarchy`：写入或 UI 读取能力，不能默认为旧服务全有。
- `xhs.search/note`：业务插件能力；来源注明 legacy-poc、UI 流程等，不混淆字段完整性。
- `execution.query`、`execution.cancel-confirmed`、`execution.fence`、`checkpoint.resume`：恢复能力。没有就不能启用相应自动迁移策略。

健康至少拆为：主机心跳、控制服务可达、ADB transport、屏幕证据时效、App/登录状态、账号/平台限制、所有权状态、任务状态。无法确认就是 unknown；网络断开不能推断手机关机，电量/前台缓存不能冒充实时值。显示“采样时间 / 接收时间 / 来源 / 是否缓存”。

同一宿主机增加手机通常是相同 8787 + 不同 serial；不同宿主机是不同 Host/Worker 身份和当地入口。旧 PoC 每台需要隔离会话的入口/路由。不能用两个端口把同一物理手机登记成两个可并发执行槽。

发现方式先沿用人工登记。目标代理经授权枚举后只上报候选设备，批准绑定、核对能力和所有权后仍暂停；不自动升级为可调度，不扫描任意网段。远程 Agent 应主动通过私网/TLS 与中心通讯，不向外开放本中心 PostgreSQL、ADB 或手机端口；当前 Compose 并没有这一套远程配对部署。

## 5. 调度：借鉴 CPU / event loop，但保留物理设备语义

- **CPU ready queue**：任务可并发到达，单手机写入串行，多台手机并行。优先级决定下一个可运行任务，不把一个全局分页会话拆坏。
- **event loop**：状态转换短小，异步等待 I/O；事件与任务必须持久化，不能只放一个 Node 内存队列。
- **数据库事务锁**：解决中心“谁领任务”和结果归属；不撤销已经发到手机上的操作。
- **持久工作流**：适合未来多步骤依赖、补偿/人工审批；并不能自动令不幂等的手机动作安全重试。当前不用为一台机引入重型工作流集群。

已有规则继续：1–9 优先级、等待提升、防饥饿、同有效优先级新任务按预计耗时，等待满 30 秒后按 FIFO；选择时同时过滤设备能力、明确设备绑定、账号及冷却。未来按租户/项目公平配额、账号/出口速率、机架容量进一步限制，但先用可解释规则，不黑盒猜时长。

典型顺序：A 是执行中的两页搜索；B 随后来一个低优先级长任务；C 在 A 快结束时来一个高优先级短任务。**A 完整结束 → C → B**。C 若与 B 同有效优先级且均未等满 30 秒则较短者先，任一等满 30 秒后 FIFO；若依赖尚未满足则继续等；不能仅因“短”抢掉 A 的第二页。一个任务多个 CPU/网络处理步骤可与手机等待并行，但不能让两条 UI 命令流共享同一屏幕。

目标 UI 流程只有在定义了“可恢复检查点”之后才可协作式让出：保存业务上下文、当前页/目标、账号/设备约束和验证证据；新的任务完成后重新建立并核对上下文。旧 `/api/next` 没有独立 cursor，当前不支持这种切换。

## 6. 统一执行协议：先用 mock 落地

这是待设计的契约要点，不是现有 API。建议最小闭环为 observe → acquire → execute → query receipt → release，而非任意命令转发。

| 数据   | 要求                                                                                      |
| ------ | ----------------------------------------------------------------------------------------- |
| 身份   | hostId、deviceId、serial、agentInstanceId；重连不得悄悄换成另一台设备                     |
| 所有权 | leaseId、owner、单调 fencingEpoch、有效期；设备代理是最终校验点                           |
| 执行   | jobId、attemptId、stepId、commandId、deadline、能力版本、白名单参数、前置状态             |
| 回执   | accepted/running/succeeded/failed/cancelled/unknown，明确是否开始物理执行、证据与来源时间 |
| 查询   | commandId 可查询持久回执，重复请求返回原结果/运行状态，不重新点一次                       |
| 取消   | 请求取消与已停止是两个状态；在安全点确认停止前，不给新 owner 发冲突操作                   |
| 审计   | 谁申请/批准/释放/抢占、拒绝原因、代次、超时和人工核验，秘密与完整画面不进入常规日志       |

实现约束：

1. 中心短事务分配 Attempt/代次，提交后发命令；网络请求不持数据库锁。
2. 代理在真正派发每条命令前校验当前 owner、代次和有效期；过期/旧代次拒绝。代理重启/失联时先 reconcile，不能默认旧命令已停止。
3. 持久记录 commandId 与回执可以减少重放，但“手机已点下、回执落盘前崩溃”仍可能未知，不能承诺所有 UI 动作物理 exactly-once。
4. 新 token 阻止的是旧 owner 的**后续命令**；已开始且不可取消的动作必须收尾/核验，不能靠 epoch 擦掉物理后果。
5. 控制租约使用中心/代理可验证的有效期和本地单调超时，不依赖浏览器时钟。网络分区时停止接收新写入并保留证据，不双主继续执行。
6. 命令白名单、坐标边界、设备/帧代次和 App 前置条件严格校验；默认不提供 reboot、force-stop、清数据、安装、任意 shell、支付/发布/点赞等业务副作用动作。
7. 仅旧服务适配无法提供上述完整保证，应报告 `fencing=false`，而不是发明一个中心 token 假装上游会检查。

### 操作命名必须精确

| 操作        | 当前或目标语义                                                                         |
| ----------- | -------------------------------------------------------------------------------------- |
| 暂停 / 排空 | 不领新任务，在途尽量自然结束，不等于手机停止                                           |
| 预留        | 当前仅锁中心槽；目标才是经代理确认的设备控制会话                                       |
| 解除        | 释放自己的会话，默认保持暂停，不删除任务，也不把锁直接交给旧未知控制端                 |
| 复位        | 初期只能重置模拟上下文或中心会话；未来导航回已知页面需单独定义，不等于重启/清 App 数据 |
| 抢占        | 先撤销旧写授权、确认旧执行停止/安全点，再交新 owner；超时不能直接强行双写              |

## 7. 故障与迁移边界

| 事件                          | 当前安全行为                            | 将来允许恢复的必要条件                                              |
| ----------------------------- | --------------------------------------- | ------------------------------------------------------------------- |
| 未领取设备离线                | Job 留池；明确绑定任务等待              | 若任务允许改派，能力/账号策略匹配另一设备                           |
| 派发后 HTTP 超时、Worker 消失 | 真机 unknown + quarantine               | 原 commandId 回执核验，或明确确认未执行/已安全停止且步骤可重试      |
| 第一台执行到半途断线          | 不凭租约超时自动重放真实 UI             | 持久检查点、旧 owner fencing、业务去重/结果核验、账号和目标设备兼容 |
| 迟到回执                      | 保存证据，不覆盖新代次结果              | 同样保留审计；冲突结果人工核验                                      |
| 中心暂时离线                  | 历史在独立 DB；上游不受中心健康探针牵连 | 代理按有效租约完成有界动作/停止新动作并暂存回执，恢复后 reconcile   |
| 手机 API 失效但 ADB 可见      | 不重启旧服务，不自动修复                | 按故障类别、明确授权、维护窗口及回退逐项处理                        |

关键限制：账号登录和平台 token 可能不能跨手机迁移；分页游标也可能属于 App 内存。跨机恢复应是业务级重新建立上下文并去重，不是“把第 2 页指针搬过去”。UI 查询本身也可能改变 App 状态，不能因为是取数就认为任意重试无副作用。

## 8. 用一台真机做可信演示

目标是说服团队建设设备中心，不用失真的“假双机真并发”换效果。

### 已可演示：真机观察 + 模拟调度，分屏分证据

1. 真机保持暂停，开始短时真实 PNG 观看，显式读取 Mobile-Agent 报告。展示同一手机真实首页与旧 PoC busy/page=1 并存，说明层次区别。
2. 在允许的前置条件下停用**本中心** PoC 通道，仍能看截图/报告/旧历史；证明观察不硬依赖 PoC，不停止手机 VPN。若设备处于未知隔离，不为演示绕过开关前置条件。
3. 切模拟，一次到达 5 个任务：同一设备的 Attempt 不重叠，界面能解释队列和顺序；任务数量与可执行槽数量分开。
4. 优先级场景展示 A 在途、B 等候、C 后到优先；A 不被破坏，C 在下一个安全调度点执行；观察等待提升避免饥饿。
5. 双模拟机 A/B：A 中断后 Job 不丢，6 秒等待后 B 领取，新 Attempt 成功，旧回执不覆盖。明确这是合成故障，不关机、不拔 USB。
6. 在不同管理窗口展示本中心预留冲突、续期/解除与到期暂停；真实画面旁标“未取得外部独占”，不误导观众。

现有三场景自动验收入口和通过标准见 [demo.md](demo.md)。一台真实手机换名成 B，只能做顺序角色演示，不能验证两台同时运行；当前不要提供把一个 serial 冒充两个执行槽的功能。

### S4 mock 控制协议验收（未实现，排在中心任务闭环之后）

至少覆盖：两个 owner 同时申请只成功一个；旧代次命令拒绝；重复 commandId 不重复执行；动作已开始但回执丢失为 unknown；取消请求未确认时不接管；代理重启/网络分区不双写；失效画面坐标点击拒绝；模拟与真实适配器绝不串路。

### 经授权后的单真机动作验收（未开放）

先明确唯一写入口，只做批准的应用导航/查询流程；给出每步前后截图、动作回执和任务归属。出现 unknown 即暂停隔离，不自动执行“复位套餐”。真正的 5 任务串行演示必须所有任务走统一入口，不能只是并发调用一个不受控的旧 API。

真实双机阶段再验证不同 serial 同时有在途 Attempt、账号约束、错误不串机、原设备结果不覆盖另一台。真机断线迁移最后验收，不是第一场演示。

| S2 | 单 Job 的搜索/搜索＋详情、有界步骤、统一完成判定 | 同设备连续占用；部分失败不冒充成功；重复/迟到回执不重复结算 |
| S3 | 调用方身份/配额/公平性、账号预算、完整并发演练 | 权限隔离、幂等命名空间、预算原子记账；可选缓存/定时按需追加 |
| S4 | 持久命令/回执 mock、能力声明、完整设备 adapter | 双 owner、旧代次、重复命令、未知与取消确认边界通过；真实交接另行核验 |
| S5 | 获准单机→双机→多机架、配对、备份恢复与 HA | 真实独占/并行证据、未知无盲重试、容量与 RTO/RPO 实测 |
| 后续按需集成 | Hub/Launcher 入口、Rig 套件、能力插件与可选 AI 规划器 | 外设不可用不阻断业务系统启动；调用有预算/超时/审计，保持各项目独立 |

用户最新要求先完成 D0：固定 [完成证据与设备收尾契约](execution-completion-contract-2026-10-10.md)，再按 S1 实施，S2 让业务完成语义闭环。完整拆分、默认规则与测试矩阵见 [调度中心优先方案](scheduler-first-plan-2026-10-10.md)。不要把 PoC busy 或完整 Host Agent 作为模拟调度产品的前置，也不降低真实控制的独占与核验门槛。

## 10. 可靠服务的运维清单（逐步补齐）

- 限制每设备、每主机观察/动作并发，动作与大图传输分开限流；队列积压要有背压和可见拒绝原因。
- 指标至少包括任务等待/执行时长、未知率、帧龄、代理心跳龄、命令拒绝、租约冲突、数据库/截图体积；阈值按试验测量，不预先承诺 SLA。
- 操作审计、机架权限、业务凭证分级、敏感画面保留期、脱敏导出、会话撤销、TLS/Agent 身份轮换。
- 独立数据库备份并做还原演练；历史 Job 与证据不能靠删除旧任务“复位”。部署保留数据不等于自动备份。
- 长期大队列再按索引/行级领取、固定资源锁顺序与故障域分区优化；先证实瓶颈，不提前引入多套队列和调度器。
- 即使未来使用 K8s，也不把 Pod 重启当手机动作取消；USB/ADB 归属、物理副作用和账号会话仍需专门协议。
