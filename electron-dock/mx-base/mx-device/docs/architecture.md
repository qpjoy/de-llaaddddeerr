# 设备调度设计

本文保留首版调度模型；新增 Mobile-Agent 观察适配、服务器证据与长期统一控制面请结合 [交接入口](README.md)、[适配说明](mobile-agent-adapter.md) 和 [产品路线](product-roadmap.md) 阅读。下面的 Legacy PoC 执行图不表示整个中心必须依赖 PoC 才能启动。

## 部署与所有权

```text
管理员 / 未来 Hub、Launcher 入口       mx-rig（仅测试客户端）
                │                         │
                └────── MX Device API ────┘
                            │
                     独立 PostgreSQL
                            │ 短事务领取 / 回执
                    MX Device Worker
                     │               │
              Simulator Adapter   Legacy PoC Adapter
                无外部 HTTP          本机 127.0.0.1:18081
                                           │
                               现有 mobile-agent → 手机
```

不把 Hub 请求、计费、登录、数据库或健康检查接到这个实验链路。未来嵌入只是入口或独立前端模块；任务与设备所有权仍属于设备中心，不把 mx-rig 变成第二个真实调度器。旧 Hub 外设历史保留；本轮未移除、停用或更改旧模块，启用真机前需单独完成独占交接。

当前 Rack / Host 仍是中心登记分组，Worker 是真正有心跳的执行主体。2026-10-10 已增加独立总览、持久分组并发上限/排空和归属编辑；这不把标签变成可信物理身份，细节见 [本轮实施分析](rack-scheduling-2026-10-10.md)。旧 API 无设备身份接口，所以设备发现是「管理员登记已知入口 → 指定主机执行器显式只读检查 → 人工核验 → 显式启用」，不是伪装成 ADB 自动发现。接口离线不等于关机。

## CPU、event loop 与事务锁各能借鉴什么

- CPU 的 ready queue / 执行槽：一个手机只有一个 UI 上下文。优先级只选择下一件工作，不在当前搜索中途切到详情。
- event loop：事件驱动、短事务处理状态、慢 I/O 在事务外；不能仅靠单个 Node 进程内的队列保存真实任务。
- 数据库：持久任务、原子领取、唯一占用约束、执行尝试、租约与回执校验。数据库锁保护调度记录，**不是手机上的取消令牌或物理锁**。

首版每个模式使用 PostgreSQL 事务级 advisory lock，短暂串行化调度决策；HTTP 不在事务内。数据库另有每设备、每任务最多一个 running Attempt 的部分唯一索引。多个手机的耗时执行可以并行，不是整个系统串行。锁语义依据 [PostgreSQL 官方文档](https://www.postgresql.org/docs/17/explicit-locking.html)。

这是有界实验调度器，不声称实现了 `SKIP LOCKED` 高吞吐队列，也没有引入 Redis、Temporal 或 Kubernetes Operator。每个模式 64 台、200 个活动任务的上限是保护措施；历史结果较大时仍需监控数据库体积。管理列表返回活动任务、最近 100 个终态及活动依赖、最近 100 个事件，以及所有 running Attempt 和最近 100 个结束尝试；使用只读一致快照，完整任务证据按 ID 查询。

## 调度规则

1. 校验模式、能力、明确设备绑定、账号约束与依赖；同一账号资源不能重复登记。
2. 优先级数字 1 最高、9 最低；等待每 30 秒提升一级，最高到 1；同有效优先级按入池时间、ID 排序。
3. 有空闲且启用的兼容设备才创建 Attempt，数据库提交后才调用手机。
4. 搜索的 1–3 页构成一个不可抢占的有界会话，避免 `/api/next` 全局上下文被打断。页间至少等 2 秒；不同真机任务间也有 2 秒冷却。
5. 详情可依赖成功搜索的首条可用详情链接；依赖未完成则等待，失败则阻塞，空结果则跳过。真实详情沿用来源设备，不能默默换账号。
6. 每进程最多 4 个在途工作，设备槽全局由数据库互斥；该数字不是跨 Worker 的全局额度。机架与主机现已有跨 Worker 的并发限额，领取和策略变更共用模式事务锁；每设备单槽不变。租户、账号与网络出口预算仍待实现。

优先级示例：A 是正在进行的两页搜索；B 是后来入池的后台三页搜索；C 是 A 快完成时来的高优先级单条详情。执行顺序为 **A 完整完成 → C → B**。如果 C 与 B 同优先级则按 FIFO，不仅因为 C 短就插队；否则估计时长不准会导致长任务饥饿。

## 状态与故障

| 情形 | Job / Attempt / Device |
| --- | --- |
| 普通提交 | queued，尚无 Attempt；任务不依附于某个进程内队列 |
| 领取成功 | running / running / running |
| 全部步骤有可信回执 | succeeded / succeeded / idle + cooldown |
| 真机预检查报告忙碌 | queued / blocked / paused，不发搜索命令 |
| 真机 HTTP 失败、超时、响应不匹配 | unknown / unknown / quarantined，未派发任务仍在池中 |
| 执行器消失、租约到期 | unknown + quarantine；不把超时当成手机停止的证明 |
| 管理员暂停 | 停止新领取，当前操作继续完成；不杀进程、不关机 |
| 模拟断线 | 旧 Attempt interrupted，Job 保留并延迟 6 秒；其他模拟设备可领取 |
| 模拟迟到回执 | 留存 lateEvidence，旧 epoch 无权覆盖新结果 |

单次状态超时 5 秒，任务 HTTP 超时 35 秒（原文档称 PoC 最长等待 25 秒），Attempt 租约 180 秒。响应上限 1 MiB，超过上限或结果无法核验按未知处理。搜索核对关键词、页码、数量，详情核对笔记 ID；保存 JSON 回执及检查点，不声称保存了网络逐字节原始报文。

Legacy PoC 缺少 taskId、幂等执行键、取消确认、执行令牌校验和逐任务查询。控制端 epoch 只能拒绝陈旧数据库回执，**不能阻止旧 Worker 已经发送的手机操作**。所以实际手机不能像模拟器一样自动重放或迁移，不能保证物理 exactly-once；租约结束后的人工恢复还必须确认旧执行器和手机操作已停止。

当前每个真实任务在执行前另做一次只读状态检查，但这不是手机侧原子加锁。必须让本中心成为该手机唯一入口；绕过本中心的旧脚本仍可能与其冲突。重复手机可用不同转发端口伪装，未知序列号时无法从软件完全证明唯一身份。

## 一台真机如何做可信演示

把两类证据分开：一台真实手机验证适配与互斥；两台模拟设备验证分发、断线、任务保留和迟到回执。模拟设备没有 HTTP 能力，测试凭证也无 real 权限。一台手机改名成“第二台”只能做顺序角色切换实验，不能证明真实双机并发或安全接管。本版没有提供这种容易误导的真机改名接管按钮。

## 演进路线

1. **当前实验版**：本地和单主机演示；独立生命周期；保守兼容旧接口。
2. **单机真机验收**：独占交接、已知 busy 人工核验、一页搜索 / 详情 / 两页搜索、断联不影响 Hub 的服务侧验收。保持原容器不变。
3. **机架 Host Agent v2**：稳定物理 ID、经过批准的发现、mTLS、每台手机单一命令入口、持久执行令牌与拒绝旧 token、逐任务回执与查询、明确的取消/停止确认。只有具备这些能力，才讨论真实自动接管。
4. **多机中心**：能力匹配、账号会话 / 网络出口 / 平台额度、可信主机配对、心跳监控、租户公平性。大队列改为索引化 `SKIP LOCKED` 短事务领取、资源锁固定次序与队列分区；加审计保留策略、指标、告警、备份恢复与容量测试。
5. **工作流与集成**：跨设备协作 DAG、检查点和结果归一化；mx-rig 消费测试 API，Hub/Launcher 用独立入口或受保护 API，不共享手机锁实现。

市场参考：AWS Device Farm 将设备槽与并发能力关联，可借鉴资源池抽象，但不是此旧 PoC 的即插即用替代品。[官方说明](https://docs.aws.amazon.com/devicefarm/latest/developerguide/how-to-purchase-device-slots.html) Temporal 的 Activity 重试仍需要业务幂等与正确的失败语义；引入它不会替旧手机接口实现幂等或取消。[Activity 官方定义](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/activities/activity-definition.mdx)

初期优先验证手机协议边界，不为一台试验机增加新的大型工作流基础设施依赖。
