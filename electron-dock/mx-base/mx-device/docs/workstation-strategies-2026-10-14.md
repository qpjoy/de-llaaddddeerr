# 设备工作台、场景与版本化调度策略

日期：2026-10-14。本文描述本地增量，区分运行中的模拟机架、独立虚拟时钟实验与真实手机。前置设计见[任务调度中心](task-scheduling-center-2026-10-13.md)和[平台指令与任务库](platform-command-catalog-2026-10-13.md)。本次不修改 Launcher、MX-H2I 登录与联网，不操作现役 PoC、ADB、手机或 VPN。

## 产品分工

设备工作台作为首要操作入口，统一看机架容量、每台手机状态、在途任务、预计候选队列、App 冷却、指令进度和回执投影；点击设备进入单机工作台，再查看 Adapter 调试、指令流水和任务结果。机架管理保留为资源管理入口，不再要求管理员在多个页面拼凑同一机架的执行状态。

“场景”描述负载和初始条件，例如设备数、任务类型、到达批次、初始冷却。“策略”描述怎样选设备、怎样限制排队、怎样核算 App 预算。“规则”是策略内部的分阶段配置。设备数属于场景或机架容量，不属于单条调度规则。选中场景不会静默改动现有机架；显式启动才创建新的独立模拟机架并入池。

模拟手机画面是最近可信回执的合成投影，包含正在执行指令、列表、详情、OCR 等变化。它不是实时真机视频；无回执时不能假装平台页面已经变化。连接、物理执行槽和 App 可用性需要分别显示：连接在线不等于手机已解锁或已登录，App 冷却不等于整机暂停，任务排队也不等于已发送手机指令。

## 中央队列怎样进入设备

```text
API 请求 → 幂等校验 / 固定任务与指令版本 → 中央 queued 队列
       → 硬条件过滤 → 策略预算 / 预计耗时 / 同 App 亲和 → 可重算候选队列
       → 短事务内重新核验并 claim → 创建 Attempt、独占设备执行槽
       → 逐条指令执行 → 验证身份、Schema、停止与业务回执
       → 下一条指令或任务完成 → 写入结果、释放执行槽、累计 App / 整机冷却
```

候选队列是当前快照的计划，不是另一份拥有执行权的队列。页面刷新、设备恢复、任务到达或策略切换后，它可以改变；`queued` 任务仍在中央任务表中。页面应将“候选设备 / 预计等待”与“已领取 / 正在执行”分开显示，解释未计划任务的原因，例如能力不匹配、等待预算超限或尚未到达 `notBefore`。

真正领取在 PostgreSQL 每个运行域的短事务内串行化，领取与人工指派、取消竞争同一把域锁。一次竞争只能有一个顺序：管理员先指派则领取按新约束执行；执行器先领取则指派得到 409。事务外才做指令 I/O，多台设备可同时执行，同一台设备保持一条指令流。当前实验控制面有界：模拟池总量最多 100 台、活动任务最多 200 个；在线 Worker 的模拟并发仍受现有工作槽限制，设备数不等于瞬时执行并发。

大任务从领取到最终回执保持设备与 App 上下文。已有检查点式旧循环可以保留插槽并按预算插入小任务；启用新的整段任务池策略时不进行这种插入。两种机制都不允许在某条指令执行中抢占，`yielded` 是保留中的会话，不是可以随意迁移的待执行任务。

失败、超时和不匹配回执需要按现有机制标记未知并隔离；已发送但没有确认不代表没有执行。任务 ID、Attempt、指令及晚到证据保留，不承诺物理 exactly-once，不把未知任务直接重新塞到另一台手机。

## Strategy 与 Rule

新增持久化规则目录与策略目录，迁移种子和内存种子一致。它们使用不可变版本及 `expectedVersion` 并发保护，支持新建、查看、修改为新版本、归档、查看历史、以新版本恢复。归档保留历史快照；已应用机架保持其版本，规则编辑不会悄悄改变运行行为。

策略采用固定阶段组合，当前每个基本阶段恰好一条规则，单 App 覆盖按 App 唯一。禁止重复阶段和互相覆盖的模糊组合，不允许上传任意可执行脚本。

| 阶段 | 规则类型                   | 作用与默认值                                                                                |
| ---- | -------------------------- | ------------------------------------------------------------------------------------------- |
| 1    | 设备分配 `placement`       | 自适应 / 空闲分散 / 同 App 亲和；兼容设备空闲比例超过 50% 时优先分散，亲和额外等待最多 3 秒 |
| 2    | 队列预算 `queue`           | 候选设备队列最多 100 个、预计等待最多 30 秒、短任务阈值 15 秒                               |
| 3    | App 通用预算 `app-budget`  | 60 秒窗口，最多 3 次任务或 60 秒服务量，达到预算后冷却 5 秒                                 |
| 4    | 单 App 覆盖 `app-override` | 按 App 替换预算参数；拼多多示例为最多 2 次、冷却 8 秒                                       |

不可关闭的硬条件位于规则之前：模式隔离、设备单写槽、机架/主机范围、设备暂停/隔离/离线、App 和指令能力、资源排空/并发限制、控制会话预留、已生成冷却。规则不能绕过这些条件。这里的“亲和聚合”是同 App 任务优先复用设备和上下文，**不会把两个客户任务的指令、结果或完成回执混成一个任务**。

内置三种策略为“均衡自适应”“空闲分散”“亲和聚合”。默认推荐 `pool.balanced`，它是缺少真实负载测量时的均衡起点，不是全局最优证明。新增工作台演示自动应用推荐策略；手动登记新机架首台模拟设备可以显式传入默认策略，已有机架不会因加一台设备而被覆盖。

一次固定负载对照（`mixed`、10 台、seed 42、40 个任务、相同预算）中，均衡策略与分散基线都完成 40/40，约束违规均为 0。均衡吞吐为 56.9 个/分钟、等待 P95 为 12.7 秒、App 切换 13 次；分散基线为 60.1 个/分钟、10.5 秒、21 次切换。这个例子体现的是延迟与上下文复用的取舍，不能将推荐默认值写成所有指标都最优；应该按目标负载及切换成本选择。

应用策略时机架保存 `strategySnapshot`：策略 ID、版本、规则快照、编译后的参数和应用时间；下一次规划使用新参数，运行中 Attempt 和已经发生的冷却不撤销。若管理者通过旧循环配置单独修改调度参数，快照仍保留，界面标为“已修改”而不能继续声称它严格等同原策略。恢复原策略需要显式再次应用。

## 冷却的含义

1. 整机任务间隔限制所有 App，设备只能在整机截止时间之后领取。
2. 单设备的 App/账号有独立截止时间；小红书冷却时，兼容的微博或拼多多仍可使用这台手机。
3. 窗口任务次数与服务时长预算在派发时先记预留，完成后用实测服务时长替换；未知执行保留预算，不能靠超时逃账。
4. 旧循环冷却和新的 App 预算产生的截止时间取更严格约束，刷新页面不会重抽已经生成的冷却。改变策略不能追溯删除已经发生的冷却。

人工指派允许将任务排到正在忙碌或尚有冷却的兼容设备之后，表示“指定等待这台”，不是强制立即执行。真实平台安全限额需要平台证据与实际观察，这些默认数字仅是模拟参数，不保证规避账号限制。

## 人工管理与资源编辑

| 操作                  | 允许条件                                                                                   | 结果                                       |
| --------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------ |
| 指派任务到设备        | 模拟、`queued`、revision 一致；同范围、能力匹配，目标未暂停/隔离/离线/排空或被控制会话预留 | 更新任务硬绑定；继续等待当前任务和全部冷却 |
| 回收中央队列          | 模拟、尚未领取、revision 一致                                                              | `deviceId:null`；默认保留机架/宿主机范围   |
| 清除范围后回池        | 上述条件，且显式 `clearPlacement:true`                                                     | 同时移除旧范围，等待全池兼容设备           |
| 取消排队任务          | 模拟、尚未领取、revision 一致                                                              | 标记 `cancelled`，保留任务、幂等键和审计   |
| 修改模拟 App/指令能力 | 先暂停、设备空闲、无 running/yielded/预留会话                                              | 增加或移除声明能力，保持暂停               |
| 修改机架/宿主机归属   | 遵守既有暂停与空闲要求；演示插槽固定归属                                                   | 只改变中心元数据，不声称变更物理接线       |
| 机架排空与并发限制    | 既有资源 revision 校验                                                                     | 停止新领取；在途任务继续收尾               |

移除设备能力前检查绑定的排队任务：如果会让这些任务失去可执行能力，必须先把任务回收中央队列。移除 App 不删除该 App 的历史冷却与审计；以后重新启用同一 App 时仍读取原账本。`simCommandCodes:null` 表示恢复全部已登记模拟指令能力，并非执行任意未知指令。

## 场景边界

实时演示在实际模拟任务池内创建独立新机架，不修改其他机架；任务有明确机架范围，演示设备只接收本次演示或明确指定到该机架/设备的任务。普通无范围旧任务不会意外消耗演示资源。所有请求先校验容量，失败整体回滚，不留下半个机架。相同幂等键重放返回原演示，即使任务已完成、不在最近任务查询窗口中，也不会重复创建设备。

| 实时场景              | 设备与任务                                                               |
| --------------------- | ------------------------------------------------------------------------ |
| 长短任务混合          | 2 倍设备数的有界混合模板，涵盖小红书长搜索、微博、闲鱼、拼多多详情/OCR   |
| 同 App 亲和与空闲分流 | 小红书小任务分两批，第二批延后 1.5 秒允许进入领取；由所选策略决定去向    |
| 冷却与跨 App 使用     | 首台小红书初始冷却 5 秒；新机架各 App 任务间隔 3 秒；其他 App 可继续使用 |
| API 洪峰与积压        | 一次创建 6 倍设备数的混合任务，最多 200 个                               |

规模支持 2、10、20、50、100 台，总设备和活动任务上限仍全局生效。已有 10 台时不能再创建 100 台而自动清掉旧机架。当前不做破坏性删除来满足演示规模。

既有 8 类虚拟时钟场景继续保留，用于相同 seed 的策略对照，包含故障隔离、异构能力、逐步扩容和流量变化。它们独立计算，不会把故障注入、100 台负载或策略切换偷偷施加到工作台的现有机架。页面需要明确区分“启动实时演示”和“运行独立策略对照”，对没有实现实时版本的场景不能用同一按钮伪装支持。

## 问题与后续优化

- **估计误差**：候选等待依赖历史耗时；卡住的指令不能靠预计结束时间当作已停止。现有实测校准可减少误差，后续需区分设备型号、App 版本、操作参数与网络状态，并为尾部耗时保留余量。
- **规划抖动**：页面候选归属可随流量变化重算，尚无跨规划周期持久 sticky reservation 和切换成本反馈。接下来可加短期稳定窗口，但必须保留队列重新平衡能力，不能提前锁死设备。
- **公平性与优先级**：现有优先级、等待提升、短任务倾向覆盖基本排队；尚未实现客户级加权公平、租户配额、预约容量或计费级 SLA。外部客户接入前需定义这些预算归属。
- **有限规则语言**：当前按固定阶段编译规则，能预见冲突。任意布尔规则树、按流量自动替换策略和自动调参需要额外的验证、灰度、回滚和可解释性，当前不支持用户上传任意执行代码。
- **扩容与 HA**：100 台是有界模拟容量，不能视为线上吞吐或高可用验收。短事务域锁简化一致性；生产规模需测量锁等待、分片、设备侧租约、fencing 和故障恢复，再决定是否拆队列或升级协调系统。
- **手机与 Adapter 证据**：缩略图属于模拟投影；PoC/ADB/custom 的真实驱动仍需完成能力、完成回执、取消和独占语义验收。无可信停止证据时继续隔离，不因前端按钮存在就声称真机可安全重派。
- **资源生命周期**：当前修改元数据、暂停、排空和能力开关保留历史。设备停用、长期历史归档、删除引用关系及批量导入需要独立生命周期设计；这次演示不会自动删除旧数据。

## 验证记录

模型回归覆盖任务指派与领取的两种事务顺序、CAS、在途/保留会话禁止迁移、冷却等待与跨 App 运行、能力移除保护、取消保留记录、demo 幂等与失败回滚、2–100 台有界创建，以及 10 台混合任务的逐指令完成和单机不重叠。

HTTP 回归覆盖策略/规则 CRUD、版本冻结、机架应用 CAS、默认策略不覆盖已有机架、归档恢复、模拟域限制、鉴权、同源 JSON 检查，以及 GET 不派发。PostgreSQL 测试使用临时数据库核验并发领取/指派和重启后演示幂等。

- 完整后端回归 **188 项通过、0 失败、0 跳过**；使用独立临时 PostgreSQL 18.4，实际覆盖 001–008 迁移、升级保留旧配置、规则/策略 CAS、领取/人工指派竞争、重启与历史持久化。临时数据库已停止。
- 新增视图模型回归 **9 项通过**：计划/领取分离、暂停在途显示、检查点保留、App 与整机冷却区分、移除能力后的历史账本不误入视图、机架过滤、控制会话预留与虚拟零时刻。合计 197 项测试通过。
- `npm run build`、`npm run check`、`git diff --check` 通过。
- 独立浏览器对真实本地 HTTP/内存服务验证：默认首屏、8 场景、规则与策略 CRUD/版本/归档恢复、40 任务策略对照、10 台/20 任务加入现场、指派/回池/取消、任务证据、应用机架策略、拼多多模板入池、屏幕墙/列表切换、回执驱动缩略图、手机弹窗/Adapter 页、暂停后能力编辑及新机架默认策略。
