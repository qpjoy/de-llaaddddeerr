# 调度中心优先：独立模拟、资源节奏与任务完成契约

日期：2026-10-10。

后续实施更新：用户授权后，S1 中的 App/账号独立冷却、整机间隔、历史轮换与预计耗时排序已落地，并加入一机双 App 模拟。准确实现范围见 [增量说明](app-pacing-2026-10-10.md)；操作预算、复合 Job、完成模板和完整 adapter 仍待实现。下面的“当前已有/缺口”保留规划时点，不能覆盖这条实施更新。

规划时点：用户已反馈前阶段机架/调度版本部署完成；本轮仅审阅本地代码、已导出的 Mobile-Agent 源码并更新规划，没有连接服务器或修改运行代码。**本文除“当前已有”外均是待实现方案，接口名称/字段是设计草案，不是现有 API。** 现有接口仍以 [api.md](api.md) 为准。

实施前补充：用户要求先明确调度/执行分工、旧系统完成事件、业务标准和复位。以 [执行完成与设备收尾契约](execution-completion-contract-2026-10-10.md) 约束下文；S1 前先固定 D0 最小契约，业务成功、执行停止和设备可用分开判定。

## 1. 本轮确定的方向

MX Device 的核心产品是任务调度中心：外界并发提交任务，中心可靠接收、排队、挑选设备、约束操作频率、跟踪执行证据、判定完成并返回结果。没有 Mobile-Agent、PoC、真手机也应能跑完整闭环。模拟器替换的是设备执行端；API、数据库、调度规则、完成判定和界面要复用实际中心。

Mobile-Agent/后续 Host Agent 负责设备侧执行、状态和证据，中心负责业务任务生命周期。中心不能只凭截图、HTTP 200、进程退出或一段“完成”日志宣布成功；执行端也不能私自再排一套业务任务、换设备或重跑未知动作。

近期顺序调整为：**资源节奏与并发入池 → 搜索/搜索＋详情的统一任务闭环 → 调用方治理与可重复演练 → 持久命令回执/真实 adapter → 真机与 HA 验收。** 旧规划中“先做完整 Host Agent，再补业务流程”的顺序不再作为下一步。旧 PoC busy 不是中心建设的前置条件。

## 3. Mobile-Agent 能否直接承担完整调度

结论：**导出源码表明它已有实用的单宿主机、多设备业务执行机制，但没有足够依据认定它已覆盖目标设备中心。应借鉴设计，继续建设现有 mx-device 调度器。** 导出不是完整项目，未与当前运行镜像逐文件核验；未读到的能力不能断言绝对不存在。

| 本地导出中的证据 | 能说明什么 | 在 MX Device 中如何取舍 |
| --- | --- | --- |
| `TaskScheduler.enqueue_run`、`tasks/task_runs` | 任务定义与每次运行记录分离 | 保留已有 Job/Attempt；每次重试增加 Attempt，不覆盖历史 |
| `get_runner(serial)`、`_device_start_lock`、`current_task_id` | 逐设备 runner、进程内串行启动与 SQLite 占用记录，多设备可并行 | 借鉴单设备执行槽；中心仍以 PostgreSQL 原子领取为准，不复制 Python 调度器 |
| `try_start_next_queued` | 按绑定 serial 取 queued，`ORDER BY id DESC`，较新的任务先运行 | 不照搬；中心使用公平队列与等待提升，按能力/资源选机 |
| `activate_batch`、`on_finished`、`drain_queued` | 批次激活、完成接力、上线/启动后继续领取 | 借鉴批次/事件驱动；定时触发只生产 Job，不另设派发通路 |
| `ScheduleRunner` | once/daily、约 30 秒轮询、避免 queued/running 重复触发 | 日后可做 Schedule→Job；每次触发建立独立 Job，保留每次结果 |
| `_claim_device` 写 `last_run_at` | 有上次开始运行的时间记录 | 在审阅的队列/runner/定时器中未见用该字段实施冷却；中心补完整节奏账本 |
| `_read_output`、`progress_from_logs` | 框架以退出码 0 标 succeeded，以日志模式解析进度 | 可作为执行证据，不能独自判定“搜索及详情满足请求”；完整业务子脚本未导出 |
| `recover_stale_tasks`、清理钩子 | 重启时清占用、运行项标失败，并清理部分遗留进程链 | 不迁入中心，不用重启旧服务作恢复；手机动作未知仍须隔离/核验 |

补充：已导出的 `scripts/nurture/agent.py` 有最大检查数/配额的完成判断和报告，故退出码可承载某脚本自身的业务结论，但不代表满足中心新增的验收条件。内部 `on_finished` 用于队列接力，现有 task/collected HTTP 可供观察；尚未见可靠的外部完成事件或按 runId 查询完整持久终态的通用路由，详见上述契约。

这套旧机制与手机 18081 PoC 又是两层：8787 有 task/run，并不让 `/api/search/next/note` 自动获得 commandId、取消确认或跨机游标。完整证据目录及缺失材料见 [源码核实](mobile-agent-source-review.md)。本轮仅参考语义，没有导入第三方源码。

## 4. 职责与最小模型

```text
外部调用方 / 本中心演示客户端
              ↓ 提交、查询、取消尚未执行的任务
MX Device：鉴权 → 幂等接收 → 持久任务池 → 调度/节奏/设备占用
              ↓ 已确定的设备、流程、步骤、命令身份
执行端：Simulator 或经核验的设备 adapter
              ↓ 结构化回执、结果、错误分类、采样/接收时间
MX Device：校验完成条件 → 保存结果/历史 → 冷却 → 下一任务
```

| 对象 | 最小职责 |
| --- | --- |
| Client | 由凭证确定的调用方，拥有任务/结果可见范围、入池与运行额度；不能信任请求体自报身份 |
| Job | 一次外部业务请求，固定输入、流程版本、完成规则、资源约束、幂等键和截止时间 |
| Workflow/Step | 首期仅 `search.v1`、`search-detail.v1` 两个有界模板；步骤身份/次序、输入结果与校验规则可追踪 |
| Attempt | Job 的一次执行，绑定设备、账号、Worker、epoch、执行租约；失败历史永不覆盖 |
| Command/Receipt | 每条动作的稳定 ID、是否已发起、执行结果、证据；重复/迟到回执可识别 |
| Resource/Policy | 设备/机架/主机并发、账号限制、冷却与操作预算；策略有版本与变更审计 |

平台字段解析、搜索/详情完成验证放在版本化流程模块，通用调度器只处理资源、步骤、状态与预算。无需首期就引入任意 DAG、脚本编辑器或另一套消息中间件；沿用 PostgreSQL 单一持久事实来源。历史 Job 不因流程模板升级而改变完成规则。

## 5. “任务是事务”应落为三种保证

1. **接收原子性**：一次请求只产生一个完整 Job 与初始流程定义，提交成功后才返回 202；搜索＋详情不能先创建搜索、再由浏览器补建详情。
2. **分配原子性**：在短数据库事务中同时确认 Job 可领取、设备/账号兼容、各层限额和预算，创建 Attempt 并预留资源；提交之后执行 I/O。
3. **执行连续性和完成一致性**：搜索及后续详情属于同一有界 Attempt，默认持有同一设备/账号，其他任务不能在步骤之间插入。中心收到所有必需证据后原子结算业务结果；资源释放还需执行停止和收尾条件满足，不能只凭业务结果到齐释放设备。

这不是把几分钟操作放进数据库长事务；已发生的手机操作也无法像 SQL 一样回滚。详情失败不撤销已经完成的搜索，需保留部分结果并按明确规则终结。真实派发后断联仍可能 unknown，不能宣称物理 exactly-once。

首期流程契约：

- `search.v1`：页数模式完成请求上限或取得经校验的“结果已耗尽”证据；若扩展为严格 N 条/实际浏览 N 条，须另固定数量和可见性条件，不能把返回列表等同实际浏览。
- `search-detail.v1`：搜索完成后，从结果按固定规则选择最多 N 个有效、去重目标（首期 N=1）；目标列表先持久化，再逐个查询。不能在恢复时重新搜索出另一组目标。
- 默认所有选中详情都必须完成；允许“最多 N 条”的模板无目标时可 `succeeded/no_targets`，严格要求 N 条则不能成功。明确详情失败则 `failed` 并保留搜索证据；结果无法确认则 `unknown`；正文任务另需完整性证据，不能用摘要代替。
- 首期不开放任意“部分成功”开关。未来若支持，必须在接收时固定 `completionPolicy` 并返回成功/失败/跳过计数，不能执行到一半放宽标准。
- adapter 报告执行事实与能力限制，中心流程验证器决定业务终态。HTTP 200、退出码、日志、截图都只是证据的一部分。

任务状态保持有限集合：`queued → running → succeeded/failed/unknown`，未执行可 `canceled/expired`；退避仍是 queued＋`notBefore`，核验/收尾可作为 running 的 phase。业务与收尾结果分别保存，最终 Job 按模板是否要求收尾成功来聚合。旧 `blocked/skipped` 保留兼容展示，不借升级重写旧证据。任务成功后设备仍可能冷却或因收尾失败暂停，两种状态不能混用；收尾动作也计入频率与预算。

## 6. 冷却与上次处理时间

设备卡不能只显示“空闲”。至少展示：上次领取、上次发起操作、最近确认结束、当前任务/步骤、冷却原因、最早可再次使用时间；状态与时间来自持久记录，刷新页面或重启 Worker 不得归零。

| 字段/规则（目标） | 语义 |
| --- | --- |
| `lastClaimedAt` | 中心分配执行槽的时间，不表示手机已开始动作 |
| `lastDispatchedAt` | 中心最近一次准备发起外部动作的时间，保守计入频率，不能只在成功后记账 |
| `lastExecutionFinishedAt` | 取得执行结束确认的中心接收时间；另存上游发生时间，避免迟到/时钟差缩短冷却 |
| `lastSucceededAt` | 最近业务成功时间，与失败/取消/未知操作历史分开 |
| `cooldownUntil` | 设备任务间冷却下界，按任务类型/结果分类/策略生成 |
| `nextEligibleAt(job, device)` | 综合设备、账号/平台窗口、步骤间隔、退避、Job.notBefore 得到的最早候选时间 |

计算规则是取相关时间下界的最大值，**再同时检查**在线/健康、能力、排空、单设备占用、账号占用及机架/主机/调用方并发。unknown/隔离没有可靠恢复时间，显示“待核验”，不能只用冷却倒计时使其自动可用。`nextEligibleAt` 是时间条件下界，不是保证开始/完成时间。

分两步落地：

1. 先做可配置的设备任务间冷却、同类动作最小间隔、成功/已确认失败后的退避和历史摘要。以 deviceId 记账，改设备名称或分组不能清账。
2. 再做稳定账号资源＋平台的滚动窗口预算；后续需要时才加出口网络预算。当前 real 的 `UNIQUE(mode,account_key)` 仍保留，不能为共享账号预算擅自开放同账号多设备。

预算检查/预留必须和领取同一事务；仅前端倒计时或先 SELECT 再异步扣额会在并发下超发。复合流程按有界最大成本预留，步骤派发时将预留转为消耗，不重复扣款；只有确认未发生的剩余额度可释放，含糊执行不能退款后再发一次。业务请求可接受较少页/详情时需写入完成规则，不能自动缩减任务。

步骤间仍要节奏限制，不能只在整个 Job 后冷却。若预算不足以开始完整有界流程，留在池中等待，避免占住设备数小时。步骤间短等待保持同一槽；执行租约需受总截止时间约束地续期。租约到期或运行截止并不证明物理停止，必须禁止新动作并查询/核验，在确认旧执行结束前不释放冲突资源。

策略收紧立即限制后续派发；策略放宽不回溯缩短已确定的冷却期限或解除隔离。真机频率参数需按授权场景和平台允许范围设定；不存在可承诺“不会风控”的通用秒数。收到限流、验证或账号受限证据应延后/暂停并待处理，不能通过自动换账号继续绕过。

### 6.1 同一手机跨 App 使用与分层冷却

用户补充的目标：一台手机完成小红书任务后可以处理微博等其他 App，分别计算相关冷却。**前台/UI 执行槽始终属于物理设备；冷却则按适用范围记录。** 小红书的任务间冷却不应自动占住整部手机，但整机操作间隔、故障隔离和未结束的执行仍会阻止所有 App。

| 约束范围 | 标识示意 | 对其他 App 的影响 |
| --- | --- | --- |
| 物理设备执行槽/整机间隔 | `mode + deviceId` | 全部前台操作互斥；整机冷却未到不能切 App 接新任务 |
| 设备上的 App 会话 | `mode + deviceId + app/profile` | 只限制该设备的对应 App；切到别的 App 不清除它的历史 |
| 平台账号 | `mode + platform + accountId` | 约束这个账号；未来获准迁移设备时历史仍跟随账号，不能因换机归零 |
| 账号的操作类别 | 上述账号标识＋`search/detail/...` | 精细限制某类动作，同时仍受该平台账号的总预算约束 |

平台与 Android 包名/用户空间分开建模，避免分身或别名造成同账号重复额度。首期账号资源仍保守限制单一有效设备绑定，不能通过扩展多 App 模型顺带开放同账号多机并行。

示意时间线（只用于解释，不是真机频率建议）：09:00 小红书任务及收尾确认结束；小红书账号下次允许 09:10，整机下次允许 09:00:05；微博自己的条件通过时，09:00:05 可以领取微博任务。09:10 小红书只是不再受该冷却阻塞，若微博仍执行则继续等待，不能抢占。

`nextEligibleAt(job, device)` 取**该任务适用**的整机/App/账号/操作时间下界最大值，不把这台手机上所有 App 的冷却一起取最大值。调度器应跳过因小红书冷却等待的任务，继续寻找可执行的微博任务；界面显示“小红书冷却中、微博候选”，不只有一个全局“冷却中”。

跨 App 领取前必须确认上一执行与必需收尾已停止、无残留控制者；下一流程检查目标 App、账号与页面前置条件。上一任务为 unknown 或设备被隔离时，不能通过切 App 解除隔离。普通 App 冷却与整机故障隔离必须区别显示。搜索多页/搜索＋详情仍在一个占用期内，不为利用冷却而在步骤之间切换其他 App。

当前代码只有 Device 的 `accountKey/cooldownUntil`，未实现上述模型。需将物理 Device 与其 App/账号绑定分开，一台设备关联多个 App 会话；不能为每个 App 重复登记同一 serial，制造多个手机执行槽。已有设备冷却保留为整机保守下界，历史记录不凭空改成某个平台的冷却；新增绑定、能力和预算通过增量迁移落地。微博执行能力须另行实现/验收。

### 6.2 冷却存储决定：先用 PostgreSQL，Redis 仅按需加速

对当前项目的选择是：**PostgreSQL 保存任务、占用、账号预算、冷却截止时间及来源；不为倒计时增加 Redis 依赖。** 冷却是一个绝对时间条件，不必每秒更新数据库，也不必在时间到时删除记录。

目标冷却记录包含 realm、scope、资源标识、`nextAllowedAt`、最近动作/结束时间、策略版本、原因和来源 Attempt；唯一键包含模式及完整资源维度。初始记录的创建、检查、预算预留与 Attempt 创建须在同一事务中完成，避免两个 Worker 同时读到“尚无冷却”都派发。现有 `PgStore.atomic` 已在获取模式锁后取数据库 `clock_timestamp()`，可以延续此时间源；浏览器倒计时仅用于展示。

领取时在短事务中核验设备槽、该任务适用的冷却/预算、账号与机架限制，随后创建 Attempt 并占用资源；事务提交后执行 I/O。回执结算时原子更新结果、各作用域冷却和符合条件的资源释放。已有模式级事务锁可先覆盖这些写路径；将来测出瓶颈再拆行锁，须固定多资源锁顺序并保留唯一约束。PostgreSQL 支持事务级 advisory lock 和行级锁，但应用必须正确使用，不能只靠一次普通 SELECT 获得互斥。[官方锁说明](https://www.postgresql.org/docs/current/explicit-locking.html)

调度器可周期检查到期条件，并在新任务/回执到达时唤醒；定时器丢失只会延后一次检查，不得永久丢任务或提前领取。数据库保存截止时间，页面按服务端时间计算剩余秒数；不需要“每秒扣一”的存储结构。数据库不可用或事务提交结果含糊时不派发新动作，先恢复查询核验。

Redis 可以存 TTL，但 TTL 不是可靠的准点任务事件：过期通知可能晚于截止时间，Pub/Sub 订阅断开期间的通知会丢失。[官方过期通知说明](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/) Redis 也有持久化方案，不能笼统称“重启必丢”；不过 Sentinel/Cluster 的故障切换保证需单独设计，`WAIT` 也不使其成为强一致存储。[官方持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)、[WAIT 一致性边界](https://redis.io/docs/latest/commands/wait/)

这里更直接的风险是拆开存储：如果 PG 已提交任务结束，而 Redis 的冷却写入未成功，就出现两份状态不一致；Redis 原子脚本也不能同时提交 PostgreSQL 事务。一个 Redis key 不存在，还可能是从未初始化、被删除或缓存丢失，不能作为允许操作的唯一证据。

未来若测得必要，可用 Redis 缓存展示、辅助入口限流，或以 Sorted Set 的时间分值维护可重建的唤醒索引；它只提示“值得检查”，最终领取仍回 PG 事务重新核验。缓存缺失/故障回查 PG，索引可从 PG 重建，并保留周期补查，避免过期缓存永久阻塞；关键冷却与设备锁不在两处分别裁决。[Sorted Set 官方说明](https://redis.io/docs/latest/develop/data-types/sorted-sets/)

PG 的优势在于沿用现有事务边界，减少跨存储协调，并非天然保证 HA 或账号安全。持久提交、备份、复制和故障切换仍需配置/验收；异步提交/异步复制的损失窗口不能忽略。[PostgreSQL 提交与 WAL 配置](https://www.postgresql.org/docs/current/runtime-config-wal.html)

新增验收：同机小红书冷却不阻止符合条件的微博；微博不能突破整机间隔；两个 Worker 竞争不同 App 仍只能占一个手机槽；切 App/改名不清账；步骤间不切 App；未知执行阻止所有 App；重启恢复冷却且不重发；延迟/重复唤醒只触发核验；同账号的新绑定不能绕过已有冷却。以上均待实现，当前不更改服务器或引入 Redis。

## 7. 并发接入：队列、幂等和结果缓存分开

| 机制 | 解决什么 | 首期策略 |
| --- | --- | --- |
| 持久队列 | 请求来了，设备忙/冷却也不丢 | PostgreSQL 落盘，异步 202＋jobId；轮询本中心结果，不等待手机结束才返回 |
| 幂等接收 | 同一个调用方重试提交不能新建多份任务 | `(mode, clientId, idempotencyKey)` 唯一；同 key 同指纹返回原 Job，参数不同 409 |
| 入池背压 | 外界并发超过可承受范围 | 保留每模式活动任务 200 保护；加调用方队列/运行限额、速率与明确 429 原因，可提供合理 Retry-After |
| 等待有效期 | 排队过久后结果失去意义 | 支持 `notBefore`、入池等待截止；未派发超期转 expired，运行后的超期走执行核验，不假装已取消 |
| 结果缓存 | 允许旧结果时减少重复操作 | 默认关闭，后续显式 `maxAge`；不能把请求重试的幂等返回当成新鲜查询 |

幂等检查在容量拒绝之前：即使池满，已接收任务的合法重试仍能取回 jobId。指纹包括规范化业务输入、流程版本、资源/账号约束、完成与新鲜度要求；客户端重复提交不能暗改原任务。新增客户端身份时，旧凭证/历史 key 映射为保留的 legacy 调用方；新增迁移调整唯一约束，不能改写已应用的 001 迁移。

排队规则分两层：调用方达到运行限额则暂时跳过，其余任务保留有效优先级/等待提升与 FIFO；第二步才增加有明确权重和优先级上限的调用方轮转。先约束某个调用方持续以最高优先级占池，避免所有人自行声明 priority=1。

入池额度也需明确是否预留：演示先为两个调用方划分各自容量，额度总和不超过模式上限，避免 A 填满全池导致 B 无法提交；后续才评估共享剩余额度。运行限额与排队容量分别配置，不能把“已入池任务能公平领取”误称为“所有请求都能无限接收”。

设备分配先过滤兼容与可用条件，再选最长时间未被分配的设备，最后按稳定 ID 打破平局；在分配事务内写入最近领取时间。仅在适合该任务的集合内轮换，不能为“均衡”跨账号、换能力或打断既有流程。未来需要时再按负载/故障域/任务成本优化，不把名称排序当策略。

后续结果缓存只保存通过完成校验且权限允许复用的结果；按 realm、调用方可见范围、账号、业务输入、流程版本/来源和新鲜度区分。命中应返回独立请求记录及源 Job、采集时间、年龄、`source=cache`，不修改源任务历史，不计为新的设备操作。缓存 TTL、幂等保留期、Job 审计保留期是三项独立策略；暂不做跨调用方合并或拿缓存 cursor 继续手机分页。

## 8. 不依赖真机的演示应是什么样

使用当前 API＋PostgreSQL＋Worker，提供明确的 sim-only 启动模式和模拟专用凭证；模拟 Worker 不领取 real 探测/截图/状态/任务。测试注入的所有真实 transport 一旦被调用立即失败并计数，验收要求计数为零，不只靠页面提示“模拟”。

建议默认演示配置：2 个逻辑机架、每架 1 个主机、每主机 2 台虚拟设备，2 个调用方并发提交 20 个请求，包含不同优先级、同 key 重试、搜索/搜索＋详情。示例时长与冷却是演示参数，不是真机推荐值。

| 页面区域 | 应能直接解释的问题 |
| --- | --- |
| 任务池 | 谁提交、排了多久、为何等待、是否过期、幂等是否命中、允许哪些设备 |
| 机架/设备 | 当前谁在执行、在哪一步、上次操作/结束时间、为何冷却、何时最早满足时间条件 |
| 任务详情 | Job→Attempt→Step→证据时间线；选择这台设备的依据；哪些完成、失败或仍未知 |
| 演示控制 | 设定模拟耗时、空结果、明确失败、未收到执行确认、回执丢失/重复/迟到、Worker 重启 |
| 统计 | 接收/拒绝/重复数、等待时长、完成率、未知数、设备占用和冷却时间；完整来源可追溯 |

演示故障由明确配置与固定种子驱动，能够重复验收。正常 Web 演示先用真实时间跑缩短后的模拟参数；可推进虚拟时钟优先放在独立测试环境，同时驱动领取、步骤完成、租约和冷却，避免只把 UI 倒计时加速。虚拟时钟和故障注入不得作用于 real。

模拟器至少有两种失败语义：可证明未执行的失败，及已开始但结果丢失的 unknown。不能让所有模拟断线都自动换机成功，否则会教出与真机相反的恢复规则。现有“模拟可接管”场景可保留，但明确其额外停止确认/可重试假设。

## 9. 分阶段交付与验收

### D0：实施前固定完成与收尾契约

明确列表获取/实际浏览、严格数量/最多数量、正文范围/完整性、执行停止证明及收尾策略。补充模拟验收样本：旧 run 数据混入、摘要冒充全文、数量不足、丢失/重复完成事件和收尾失败。具体边界见 [契约决策](execution-completion-contract-2026-10-10.md)，本阶段不修改现役 Mobile-Agent。

### S1：可配置节奏与设备分配（下一项实现）

- 增加设备历史、版本化节奏策略与共享 `eligibility` 计算；最久未分配设备优先，领取和只读解释同源。
- 支持异步 API 并发压入模拟任务、冷却等待与未派发任务的时间限制；保留当前优先级、排空、机架/主机限额及幂等。
- 在机架卡/任务详情展示上次操作、下次时间条件、阻塞来源，提供 sim-only 隔离运行与并发演示脚本。
- 验收：20 并发请求无丢失；相同 key 重试只建一个 Job；多 Worker 不超并发/冷却；重启保留任务与时间账本；改名不重置历史；真实 transport 调用为零。并发样本是验收工作负载，不是容量承诺。

### S2：统一复合 Job 与完成契约

- `search.v1`、`search-detail.v1`，N=1；单次接收事务、同 Attempt/设备/账号、持久步骤及组合结果，替代前端两次创建的实现。
- 引入最小 command/receipt 身份、明确失败与未知分类；完成验证/冷却更新原子提交。加入动作间隔及有界流程预算，等待/租约/总期限分清。
- 验收：搜索成功＋详情失败不能显示整体成功；空结果符合契约；中途不能插入其他任务；回执重复不重复结算、旧代次不能覆盖；Worker 在各派发边界退出后恢复规则可解释。暂不扩大真实任务能力。

### S3：外部调用方治理、账号预算与重复演练

- 调用方鉴权/任务归属、幂等命名空间、入池与运行配额、优先级上限/公平性；账号＋平台窗口预算持久化；完成可查询的并发演示。
- 验收：A 不能读取/取消 B 的任务；A 洪峰不能耗尽 B 的预留额度；重复接收不重复扣额；账号预算不能被不同 Worker 同时透支；限流/验证信号暂停且可解释。
- 按真实需求再做结果缓存、定时 Schedule→Job、批量接收；不作为 S1/S2 完成的前置。批量 API 若实现须先规定全有或全无/逐项结果语义。

### S4：持久执行协议与完整设备 adapter

- 在隔离 mock 执行端验证持久命令查询、重复提交去重、单 owner/epoch、重启核验和取消确认，再按能力声明接真实 adapter。
- 复用 S1–S3 的 Job/Steps/完成校验，只替换执行实现；真实能力逐项登记，缺少 query/cancel/fence 时继续报告缺失并隔离未知结果。
- 旧 Mobile-Agent 只读接入继续使用；不把中心任务塞入旧自动接力队列形成两套调度权。现役写入口交接必须另有明确范围/授权，当前不改旧容器、不关闭旧任务、不抢手机。

### S5：真实单机→双机→多机架可靠性

先完成稳定 Host/设备身份与单一写入口，在获准的设备上验证同样契约；再做双机并行、故障域、持续观测、容量、备份恢复及 HA。模拟通过是中心语义证据，不替代手机侧独占或跨控制者故障接管证据。

## 10. 实现边界与升级注意事项

- 所有后续改动限制在 `electron-dock/mx-base/mx-device`；模拟演示客户端/测试也放在该项目，不要求改 Hub、Launcher、mx-rig 或服务器 Mobile-Agent。
- 先扩展已有 `model/scheduling/engine/store`，必要时拆出 pacing、流程验证和模拟执行模块；不同时重写整个架构。
- 每个阶段补递增迁移、旧记录默认值和兼容测试。旧记录缺少可信结束时间时显示未知/采用明确保守策略，不凭空补成最近成功；策略变化不影响历史结果。
- 数据库唯一约束、领取、预算预留、回执结算和恢复使用一致事务边界；所有手机/网络 I/O 保持在事务外。先沿用有界模式锁，测到瓶颈再做行级领取与索引优化。
- API/Worker 协议和数据库迁移需协同升级，先让旧 Worker 收尾；新流程不能交给不识别版本的旧 Worker。迁移后的回退单独验证，不删除任务历史来“兼容”。
- 本轮交付是分析与执行顺序，不声称上述 S1–S5 已完成；本次未运行或更改线上服务。
