# MX Device：任务调度中心与可重复机架模拟

日期：2026-10-13。本文是本轮调度演进的设计与交接入口，更新并细化 2026-10-10 的方案。代码能力、模拟验证、真实接入、生产验收分别记录；本文不授权连接、重启或接管现役手机、PoC、ADB、VPN 或其他服务。

## 1. 目标与系统边界

推荐名称为 **Task Scheduling Center / 任务调度中心**。它接收 Hub 等调用方的业务请求，选择具备能力的设备与账号，按照预算和节奏执行完整任务，并返回可以关联本次执行的结果与证据。手机操作与抓取机制放在 adapter；调度器不依赖某一种 PoC。

两层分工如下：

| 层 | 负责 | 关键边界 |
| --- | --- | --- |
| 中心 | 入池、幂等、排序、放置、预算、策略、完成判定、审计 | 唯一业务调度权；计划不能直接发手机指令 |
| 执行端 / adapter | 设备独占、按顺序执行指令、状态/结果/停止证据 | 不能暗中创建第二套业务队列；未支持能力明确拒绝 |
| Hub | 业务接口、业务数据、结果消费 | 通过异步任务接口调用中心，不成为第二个物理调度器 |
| MX Rig | 自动化测试、契约测试、故障演练 | 作为调用方使用中心，不要求中心依赖 Rig |

MX-H2I 的操作面继续在 Internal；本轮只改 mx-device，既有 Launcher 登录、MX-H2I 联网、独立 k8s/数据库及其他应用部署不变。Hub 到 Night-All 的迁移按单个业务接口逐步接入；mx-pay、mx-embedding、mx-ocr、mx-static 不因本方案自动获得新的依赖或调用关系。

当前先强化模拟机架，是为了让设备互斥、选择原因、排队、冷却和故障语义可复现；它不能替代真实 adapter 的单控制权、停止证明和结果验收。

## 3. 数据模型：任务独立于机器，命令独立于回执

建议保持以下对象，而不是把 API 请求直接转换成某台手机上的一串 HTTP：

| 对象 | 不变内容 | 可变内容 |
| --- | --- | --- |
| CommandDefinition | 指令代码、版本、输入/输出 schema、副作用类别 | 新版本取代旧版本，不重写历史 |
| TaskDefinition | 固定/组合流程、完成条件、能力需求、恢复条件 | 新版本的默认参数 |
| Job | 调用方、幂等键、输入、定义版本、完成/新鲜度要求 | 排队状态、计划位置、最终结果引用 |
| PlacementPlan | 决策版本、候选、评分、预测与原因 | 仅未派发任务可重新规划 |
| Attempt | 执行身份、设备/账号、执行代次、策略快照 | 执行阶段、租约、证据、终态 |
| Command / Receipt | 稳定指令 ID 与执行身份 | 派发、接收、结果、停止/收尾证据 |
| Resource / Budget | realm 与资源作用域、稳定标识 | 预留、消耗、冷却下界、隔离状态 |

同一 App 下多条指令组成一个有界任务，例如 `open → search(keyword) → next × K → collect → home`。固定任务只是经过验证的 TaskDefinition；自定义任务使用同一执行与验收机制，不能绕过互斥和预算。

“搜索前 N 条”必须指定 `at_most` 或 `exactly`、最多页数、去重规则、结果耗尽的证据、结果新鲜度。返回列表不等于实际浏览；摘要不等于完整正文。数据已够但执行尚未停止时，也不能立即把设备给下一个任务。当前模拟回执不代表上述业务语义都已实现。

## 4. 大事件环、小任务环与不可抢占

建议将两个概念拆开：**大小分类是预计成本；能否让出设备是恢复能力**。短任务可能不可恢复，长任务也只有经过验证的检查点才可让出。不能因为任务标为 large 就允许任意指令之间插入。

默认一个 Attempt 保持设备和账号不变，任务内的指令严格串行。同一手机可以先执行小红书、再执行闲鱼，但不能同时有两个前台控制流。设备 App 冷却不占用整机；执行未停止、整机间隔和故障隔离仍阻止所有 App。

当前模拟的大任务允许在确认的安全检查点插入小任务，并限制次数、累计绕行时间、恢复成本。真实 legacy PoC 没有已验证的全局分页恢复能力，所以真实多页搜索仍持有整个设备会话；不能把模拟 `session.restore` 当作真实可用功能。

本轮池策略的 `shortTaskMs` 按候选设备上的校准完整耗时决定能否享受小任务亲和；既有 `workflow.loop` 继续用于旧实验室的插入/恢复语义，不被估时阈值暗中改写。后续统一分类展示，同时保留 `yieldable/resumable` 独立标记。耗时超过预估只影响下一次预测，不能自动打断当前手机操作。

## 5. 借鉴成熟算法，但不承诺万能最优

CPU 调度、集群调度和工作流系统分别解决不同部分，没有一种算法能同时保证任意到达流量下的最低平均等待、最低尾延迟、最大吞吐、所有租户公平和零冷却违规。手机还有切 App 成本、不可恢复页面与不确定执行时间，因此应定义多目标并通过相同工作负载对照，而不是宣称“默认最优”。

- Linux EEVDF 先依据服务欠账判断是否有资格，再按虚拟截止时间选任务，可借鉴其公平记账与延迟照顾。CPU 抢占能力不能照搬到手机会话。[Linux EEVDF 文档](https://docs.kernel.org/scheduler/sched-eevdf.html)
- Kubernetes 将 Filter、Score、Reserve/Unreserve、Permit、Bind 分离，适合借鉴为中心的可扩展决策阶段；预留用于防止绑定前资源竞争。[Scheduling Framework](https://kubernetes.io/docs/concepts/scheduling-eviction/scheduling-framework/)
- Temporal 区分持久流程与可能重复执行的 Activity，要求副作用幂等。引入工作流引擎也不能让旧 PoC 的点击天然获得 exactly-once。[Activity Definition](https://docs.temporal.io/activity-definition)

当前建议采用“资格过滤＋优先级老化＋有限短任务优先＋预计完成时间＋有上限的 App 亲和＋空闲分散”。待调用方模型齐备，再增加按实际服务时间记账的加权公平/deficit 轮转；首期不需要新增 Kubernetes 调度器、Redis 或 Temporal 集群。

## 6. 调度流水线与可解释放置

1. **接收**：验证调用方、幂等键、定义版本与容量；持久成功后返回 jobId。
2. **资格过滤**：realm、设备/App/命令能力、指定设备/机架、账号、在线/隔离、排空、执行占用与预算。
3. **任务排序**：受控优先级、等待提升、同级成本；不能让调用方无限自报最高优先级。
4. **预测排队**：把未执行任务放入虚拟队列，预测开始/完成与窗口消耗；计划不占真实手机槽。
5. **评分选择**：预计完成时间、切 App 成本、亲和收益、空闲资源、服务时间余量、估计不确定性。
6. **原子领取**：在短 PG 事务内再次验证硬约束，创建 Attempt、占槽/预留；事务提交后才做 I/O。
7. **执行与结算**：逐条保留证据、消耗账本、确认业务完成和执行停止，再更新冷却与释放资源。

目标预测公式：

```text
earliestStart(job, device) = max(now, deviceAvailableAt, job.notBefore,
                                applicableCooldownUntil, budgetAvailableAt)
predictedFinish = earliestStart + queuedService + setupCost + estimatedService
eligible = capabilityMatch AND exclusiveSlot AND health AND allHardBudgets
```

这里的最大值只包括该任务适用的资源；小红书任务不应被闲鱼专属冷却直接挡住。`predictedFinish` 是估计，不是开始或完成承诺；unknown 设备的可用时间应为“待核验”，不能伪造有限 ETA。

亲和只有有界收益。例如 B 已处理小红书且排着两个小任务：新任务在 B 的预计等待、运行、收尾仍满足服务窗口，且兼容空闲设备比例较低时，可以留在 B 的计划队列。若 B 即将进入冷却、预计延迟超预算，或兼容空闲设备很多，则选其他机器。不是无条件把同 App 任务串在一起。

同 App 聚集与跨请求合并必须分开。前者改变放置；后者让多个请求共享一次采集结果，涉及权限、账号、输入、流程版本与新鲜度。当前不以“任务合并”暗中复用结果或取消请求。

### 6.1 本轮实际策略字段

权威定义见 `server/pool-policy.mjs`。策略保存于模拟机架的 `loopPolicies.scheduler`，只有显式 `enabled: true` 的机架使用新放置；真实模式和未配置机架保持原有领取规则。新池策略将完整会话作为放置单位，不启用旧实验室的父任务插入机制；旧十槽演示仍可单独验证检查点插入。

| 字段 | 默认 | 含义 / 范围 |
| --- | --- | --- |
| `version` / `enabled` | `1` / `true` | 规范化策略的默认；旧机架未配置不等于自动启用 |
| `strategy` | `adaptive` | `adaptive`、`spread`、`affinity`；后两者固定选择分散/有界亲和 |
| `idleSpreadThresholdPct` | `50` | 当前 Job 兼容可规划设备的空闲比例阈值，0–100；超过阈值才分散 |
| `maxAffinityDelayMs` | `3000` | 亲和候选比最早完成候选最多增加多少预计开始等待，0–3600000 |
| `maxQueueWaitMs` | `30000` | 从当前决策时刻算的预测排队上限，0–86400000；不是 Job 到期时间 |
| `maxQueuePerDevice` | `100` | 每设备本次软计划的队列上限，1–10000；不是无限接单许可 |
| `shortTaskMs` | `15000` | 校准完整耗时不超过此值可享受小任务亲和，1000–180000；不改变恢复能力 |
| `appDefaults.windowMs` | `60000` | App 服务历史窗口，1000–86400000 |
| `appDefaults.maxRuns` | `3` | 同一 burst 的窗口内次数预算，1–10000 |
| `appDefaults.maxServiceMs` | `60000` | 窗口服务成本预算，200–86400000；完整任务估时大于它则不准入 |
| `appDefaults.cooldownMs` | `5000` | 满预算后的休息下界，0–86400000；完整空闲休息也重置 burst |
| `appPolicies` | `{}` | 按 App 覆盖默认预算，最多 32 个；输入缺省字段在规范化时继承默认 |

这些秒数是模拟初值，不是真实账号安全建议。服务成本按估计准入、完成后使用实测值，实际运行可能超过估计；它不是可证明的硬实时上界。未结束的派发预留不会仅因滑动窗口到期而自动消失。既有 App cooldown、整机间隔和机架/宿主机并发约束仍需同时满足。

计划输出每 Job 的设备、预计开始/结束、队列位置、成本、原因及 `mutable: true`，不写入 Job 的强制 deviceId；每次规划重算。每个 assignment 的 `idlePercent` 是该任务实际决策比例，顶层同名字段只概括整个机架。原因包括 `idle-spread`、`bounded-affinity`、`earliest-finish`；阻塞包括能力、队列、服务预算、未结束预算、资源并发和等待预算。首次无合适设备时保留 queued，不能将预测阻塞误报为业务失败。

## 7. 计划可以重排，已发指令不能凭无 ACK 改派

目标执行阶段为 `queued → planned → reserved → dispatching → accepted/running → verifying → terminal`。现有存储仍以 queued/running 等状态为主；完整阶段模型是后续演进，不能把下述目标字段当作已有 API。

- queued/planned 没有物理副作用，可以在新任务、完成、设备变化、冷却到期或策略版本变化时重算。
- reserved 只有在确认未发送，或执行端确认撤销且旧代次无法再执行时，才可安全释放和改派。
- **已发送但未收到 ACK 可能已经执行。** “尚未确认开始”不是重新分配的充分条件；缺少 fencing/取消确认时应进入 unknown，保留占用并隔离。
- accepted/running 默认保持设备、账号和上下文；仅显式恢复契约允许安全检查点的有限插入，不能任意跨机迁移。
- 取消排队任务可立即终结；运行取消先请求停止并核验，不能把页面状态改为 cancelled 就假定手机已停止。

既有 epoch 和 executionGeneration 保护的是中心状态与旧回执；若执行端不验证代次，它们本身不构成物理 fencing。任务成功、执行停止、设备收尾、资源可再次领取是四项独立事实。

## 8. 冷却、服务窗口与可复用资源策略

冷却不是“每个任务后随机睡一会儿”。需要同时描述时间下界、窗口预算、连续服务上限、失败退避和限制信号。

| 作用域 | 稳定键 | 作用 |
| --- | --- | --- |
| 设备 | realm/deviceId | 前台单槽、整机间隔、连续服务、隔离 |
| App 会话 | realm/deviceId/app/profile | 当前设备此 App 的切换、会话和冷却 |
| 平台账号 | realm/platform/accountId | 账号总预算；换设备不重置历史 |
| 操作类别 | 账号键＋search/detail/refresh 等 | 按操作成本的窗口额度与最小间隔 |
| 调用方 | realm/clientId | 入池配额、并发、公平权重 |
| 机架/主机 | realm/rack/host | 故障域、并发上限和排空 |

通用策略模块输出 `allowed / nextEligibleAt / cost / blockers`，手机资源额外叠加命令顺序和会话恢复规则；账号池可以复用记账和准入，不需要复制整套 UI 执行模型。现有数据库限制一个账号有效绑定，不应在引入账号池时顺带开放同账号多机并发。

有界流程应在领取时预留最坏合理成本；每个已派发动作转为消耗，重复回执不能再次扣账。未知执行保守计入消耗；只有确认未执行的剩余额度可释放。超长冷却不应让任务先占着设备等待数小时。

当前 App/整机截止时间及模拟 App 的 `poolRuns` 已持久化；模拟派发按 Attempt 去重记一次预留并保存 App 策略快照，成功完成用实际服务时长结算。达到次数/服务预算时将本次产生的休息写为 `poolRestUntil` 并延长 App 截止时间，因此执行期间窗口过期、关闭池策略或后续放宽参数都不能清除已产生的冷却。操作加权、独立账号多维预留和限制信号仍需落地。收到验证、限流或账号受限证据应暂停/退避并等待处理，不通过自动换账号继续规避该限制；可配置节奏无法保证不会触发平台限制。

## 9. 策略组合、热更新与防抖

采用固定层级：`系统互斥/真实性边界 > 已生效冷却与隔离 > 资源硬限制 > 队列公平 > 软评分`。上层拒绝不能被下层高分抵消。不同作用域硬限制取交集，时间下界取最大值。

“追加策略”适合增加新的过滤器或独立评分项；同一阶段的互斥算法用有版本的 profile 替换，不同时启用互相冲突的排序器。流量变化调整亲和/分散等软权重，不能替换单设备互斥、账号预算或任务完成标准。

本轮实际更新是既有 `configureLoops` 的版本校验与 `scheduler` 字段合并：未提交 scheduler 时保留旧配置；未提交 `appPolicies` 保留原清单，显式提交它则以这次键集合为准，保留的 App 内部字段可合并旧值，`{}` 清除所有 App 覆盖。通用插件安装/卸载和自动 profile 切换尚未实现。

未派发计划可按新 profile 重算；已领取任务固定定义和必要策略快照。安全收紧作用于下一次尚未发送动作；放宽不缩短已记录冷却、不解除隔离。每次变更应记录操作者、旧/新 revision、影响范围和原因。

进一步的自动 profile 切换需迟滞：分散进入阈值与退出阈值不同、满足最短驻留时间、收益超过最低阈值才重排，且每轮限制迁移量。当前显式策略配置与每次决策重算不能称为已实现持续流量学习或完整防抖控制器。

## 10. 指令耗时校准

初始化使用版本化指令预估，任务预估为各步骤、必要等待、切换与收尾之和。后续统计键应至少包含 App/指令版本、设备类别、adapter 版本与必要输入桶，避免把不同手机和不同页数混为一谈。

保留 `queuedAt / dispatchIntentAt / acceptedAt / executionStartedAt / finishedAt / receivedAt`，区分排队、网络与真正执行时间。机器单调时钟适合测持续时间；跨机器绝对时间不得直接相减而忽略时钟偏差。

用 EWMA 或稳健分位数进行有样本量门槛的校准：平均服务时间辅助吞吐排序，P90/P95 与安全余量辅助窗口准入。未收到结果的耗时是删失样本，不能当成零或简单丢弃。既有 Job/Attempt 的预计耗时快照不随统计更新而改写；新增任务或新计划使用新的估计版本。

本轮 `command-timing.mjs` 只从校验通过的模拟回执学习，以设备＋`definitionId/commandCode` 为键，保留最近 32 个样本、EWMA（新样本权重 0.2）与 P90；同键至少 3 个样本后规划使用 P90，否则使用静态指令估时。每设备最多保留 128 个时间模型，恢复指令不参与训练。历史 Job 的原始预估不重写，当前新计划可以使用新校准值。

模拟 seed 与命令耗时用于公平比较策略，不是生产设备校准器；真实分布学习、置信度、不可变估计版本账本及对原始静态成本之外的等待/切换校准仍属后续阶段。

## 11. 可重复场景与验收指标

模拟实验应使用同一任务模型的领取、指令开始和回执完成函数；只替换时间推进与 adapter 证据。所有真实 transport 禁止调用，模拟器自报的计数还应由独立测试桩断言。实验结果不落入真实设备/任务 realm。

| 场景 | 要观察的行为 |
| --- | --- |
| mixed | 大小任务、多个 App 混合，单设备指令从不重叠 |
| affinity | 同 App 聚集有等待上限；兼容空闲比例高时分散 |
| cooldown | App 冷却不阻止另一 App；临近服务预算不继续追加 |
| burst | 突发入流、排队与公平；超容量有明确拒绝而非静默丢失 |
| capabilities | 不同设备声明不同 App/命令，缺能力者不领取 |
| failure | 回执缺失/失败产生可解释终态，隔离设备不再接任务 |
| scale | 2、10、20、50、100 台相同条件下的行为对比 |
| policy-change | 排队任务应用新策略，既有执行与冷却不被回溯清除 |

上述场景名称对应本轮模拟实验入口；细分故障类型以返回的事件/报告为准，不能把一个 failure 场景理解成已经覆盖数据库故障、网络分区与全部崩溃点。

实际入口为已认证的 `GET /api/pool-scenarios?mode=sim` 和 `POST /api/pool-simulate?mode=sim`；real 返回 403。POST 输入 `scenario`、`deviceCount`（2/10/20/50/100）、`seed`（0–2147483647）及上述 `policy`。默认 mixed、10 台、seed 42。实验使用独立工作线程与内存状态，不向线上任务池写入模拟 Job；同时只允许一次计算，繁忙返回 429，墙钟计算超时返回 503。

页面入口：设备中心 → 调度实验室 → **调度池 · 策略对照演练**。选择场景、规模、seed 与策略，点击“运行策略对照”，查看对照指标、逐机结果和时间线。独立演练不要求先创建十槽机架；已有模拟实验机架后可点击“应用这次报告的策略”，这一步才会更新该机架的持久调度配置，已有在途任务继续原会话。可用“停用机架池策略”恢复原领取策略，已产生的冷却仍保留。

实验调用实际 `claim → beginCommand → completeCommand`，以虚拟时间推进；每批 24–160 个有界任务，最多推进 10 分钟。8 秒时触发扩容或策略替换，能力场景从此时开始逐台等待空闲后补充能力；failure 具体注入首任务的错误身份回执并隔离设备。能力“迁入”只是给空闲模拟设备增加声明，不会安装真实 App 或迁移真实账号。

比较同一 seed、到达流量、每 Job/指令服务时间和输入；不能因为策略改变执行顺序就顺带抽到另一组耗时，造成虚假胜负。本轮基线明确为 `spread`，预算、工作负载及任务排序保持相同，只比较放置；并非 FIFO 或未配置池策略的旧算法。任何策略都可能在某类负载上变差，应保留结果而非只展示获胜样本。

实际报告已有：提交/完成/失败/未完成数、总历时、等待 P50/P95/P99/最大值、完成周转 P95、运行利用率、App 切换、软计划改派、峰值并发、指令数、`realTransportCalls`、设备汇总、时间线及剩余任务阻塞。运行中检查单机指令互斥、执行后设备绑定不变、新会话冷却、次数/预计服务预算、完整指令能力与模拟 realm；失败的硬断言直接中止报告，检查清单以 `invariantChecks` 返回。违规为零只说明这些已检查性质，不证明所有调度或真实设备性质。等待只统计已开始任务，必须与积压一起读；`failed` 汇总包含 unknown，详细语义看事件。时间线有上限，不是无限完整审计日志。

无需数据库或浏览器也可复现：在项目目录执行 `npm run demo:pool -- mixed 10 42`，或 `npm run demo:pool -- scale 100 42 --json` 输出完整报告。`npm run demo:pool -- --help` 列出场景。CLI 与 HTTP 使用同一虚拟时钟模型，均不连接手机。

目标指标：等待 P50/P95/P99、完成时延、吞吐、最大等待、各调用方实际服务份额、设备运行/冷却/空闲时间、能力阻塞、重排次数、unknown/失败、估计误差。报告必须注明实现了哪些指标、是否任务全部完成、剩余队列和停止原因。虚拟耗时不是宿主机性能压测。

额外安全性质：重复幂等键只接收一次；重复回执不重复结算；旧代次不覆盖新结果；派发未知不自动重试；同账号重新绑定不清账；重启保留持久冷却；取消/排空不打断已开始会话；预计收益不突破硬限制。

## 12. 从 2 台到 100 台的演进

虚拟机架可以探索 100 台的排队决策，不等于在线 worker 已能并发控制 100 台。当前在线 Engine 仍以模拟 10、真实 4 个在途工作槽为边界；活动任务池保持 200 的保护。不得只提高设备数就声称吞吐线性增长。

当前 PG 用每 realm 的短事务 advisory lock 串行化决策，并载入该 realm 的设备/App/活动任务等状态。这样便于证明互斥；随着任务和历史增加，要测量锁等待、事务 P95、状态载入大小、每秒领取量和回执写入量。

- 2–10 台：单中心＋PG＋少量 worker，优先完成模型与真实单设备契约。
- 20–50 台：能力索引、分批领取、合理轮询/事件唤醒、输出外置、历史归档；按测量调整 worker 容量。
- 100 台：验证数据规模和峰值；若模式锁成为瓶颈再拆设备/账号行锁，固定锁顺序并保留唯一约束。
- 多主机/HA：独占 owner、设备侧 fencing、故障接管、PG 恢复点、备份/恢复演练分别验收；不能靠启动两个进程推断已获得 HA。

PG 是冷却与预算事实来源，Redis 如后续确需使用，仅作为可重建唤醒/展示缓存，不能用 key 消失作为派发授权。[PostgreSQL 锁机制](https://www.postgresql.org/docs/current/explicit-locking.html)说明了事务与行/咨询锁的边界；应用仍需保证所有领取方遵守同一协议。

## 13. Hub 与 adapter 渐进接入

建议分离外部 Job API 与内部 Command API。外部接收版本化定义、输入、完成标准、幂等键和允许的资源范围；返回 jobId、状态查询地址、接收/拒绝原因。不要将 PoC URL、账号凭据或设备控制端口暴露给浏览器。

结果包含 realm、来源 Job/Attempt、定义版本、采集时间、完成原因、计数、结果引用与证据摘要。重复查询不再次操作手机。Webhook 需要持久 outbox、投递 ID、重试和接收方幂等；这些是目标契约，当前新增实验 API 不等于已完成 Hub 生产接入。

迁移顺序：先由 Hub 调用模拟任务并核对 schema；再对一个明确支持的真实流程做独立验收；灰度切换该接口路由；逐项迁出 Night-All 依赖。每次只切一个物理派发入口，不能同时向新旧系统镜像提交真实副作用。回退仅影响新接收流量，在途任务继续归原调度方。

Adapter 交付清单：能力/版本清单、独占接收、执行身份与代次、明确拒绝忙碌、逐指令回执、停止证明、收尾证据、限制信号、结果关联。不能取消/不能恢复/不能 fence 都要显式声明，并由中心选择保守路径。

## 14. 阶段路线与仍未解决的问题

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| A：模拟决策 | 本轮策略、异构能力、可重复负载与页面实验 | 相同输入可复现；互斥/冷却/能力不被评分突破；真实 I/O 为零 |
| B：持久计划与公平 | 计划修订、调用方配额、有效期、账号/操作预算预留 | 多 worker 竞争、重启、策略更新下账本一致 |
| C：业务完成 | 搜索 N 条、组合结果引用、正文标准、收尾状态 | 数据成功与设备可释放分别有证据，部分失败不冒充完成 |
| D：真实 adapter | 经验证的单设备控制权、代次、停止与故障边界 | 派发/回执各故障点均无静默双执行；缺能力路径明确 |
| E：容量与 HA | 压测、分区/故障切换、恢复演练 | 有实际容量与恢复指标，不能用模拟成功代替 |

主要待优化项包括：耗时估计偏差与长尾；长期公平；亲和导致局部热点；能力/账号随设备状态变化而过期；软计划抖动；长任务越过服务窗口；App 页面恢复不可靠；结果混入旧运行；不完整停止/收尾；数据库与执行端网络分区；未知任务的人工核验；任务/证据历史膨胀。

默认策略是可解释、可比较的起点。先保证单手机任务不串、已发生动作不误重试、任务不静默丢失，再以模拟和真实测量逐阶段优化等待与利用率。
