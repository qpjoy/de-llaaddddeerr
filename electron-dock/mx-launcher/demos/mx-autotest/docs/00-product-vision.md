# 00 · 产品愿景

> 状态：提议。这里定义产品方向与价值判断，不声称已具备所列能力。

## 一句话定义

MX Autotest 是一个可独立安装的桌面测试工作台和多工具测试控制面：使用者从“我要验证什么”出发建立项目、测试目录、套件和任务，由平台选择合适的执行能力，最终得到可复现、可诊断、可评审、可分享的质量证据。

## 为什么不是“另一个测试工具启动器”

团队已经可以分别运行 Cypress、Playwright、pytest 或 k6。真正缺少的是这些工具之间的一致工作方式：

- 谁定义了应该测试的范围；
- 本次结果对应哪个应用版本、测试源码版本和工具链版本；
- 没有执行到的用例为何没有执行；
- 一次失败是产品缺陷、测试缺陷还是环境受阻；
- 开发如何快速定位，项目经理如何判断风险；
- 负责人如何看长期趋势，外部人员如何安全地查看证据。

因此平台不以“集成了多少工具”作为核心价值，而以 **质量意图、执行证据和可追溯决策** 为核心。工具是可替换的 adapter。

## 产品对象，而不是工具菜单

用户的主流程是：

    建立 Project
      → 定义 Catalog 中应该被验证的能力
      → 组织 Suite
      → 保存或调度 Task
      → 产生不可变 Run
      → 查看风险、失败原因和证据
      → 修复、重跑、比较趋势或生成脱敏分享

首页不应先问“你要用 Cypress 还是 Playwright”，而应先问：

1. 你要测试哪个产品和表面；
2. 这是快速反馈、发布前走查还是人工演示；
3. 要回答哪个风险问题；
4. 哪台执行环境具备所需能力。

平台可以推荐工具，新手不必先理解 runner、镜像和 reporter；专家仍可展开高级设置查看命令、版本、分片、重试和原生证据。

## 首要用户与体验目标

### 测试新手

- 用模板建立 Web 冒烟、Electron 冒烟或 API 检查。
- 用自然语言解释 blocked、failed、flaky、notRun，而不是只显示红色退出码。
- 默认选择安全、可复现的工具版本和证据策略。
- 可以从失败报告一键重跑相同输入，不需要重新拼命令。

### 测试专家与 SDET

- 可控制 source ref、工具版本、能力标签、环境变量、并发和保留策略。
- 能查看 JUnit、引擎原生报告、trace、视频、截图和原始日志。
- 可通过 adapter 接入 pytest、k6、WebdriverIO 或未来的 tshark，而不修改平台核心。
- 目录 drift、flaky 历史和执行环境差异均可查询。

### 开发人员

- 报告直接给出应用提交、测试提交、工具链摘要、首个失败步骤和相关证据。
- 能区分产品断言失败与基础设施受阻，减少“在我机器上能跑”的往返。
- 分享链接指向一个不可变证据快照，而不是聊天中的一张孤立截图。

### 产品经理

- 看需求关联、P0/P1 目录完成度、失败范围、受阻原因和时间趋势。
- 查看“哪些风险尚未验证”，而不被一个汇总通过率误导。
- 将人工走查视频作为评审材料，但不把视频观看当作机器验收。

### 负责人、质量负责人

- 看执行可靠性、缺陷逃逸、flaky 债务、环境受阻率、证据留存成本和团队采用率。
- 为不同项目设风险策略，而不是强迫所有项目使用相同框架。
- 通过独立故障域保证测试平台故障不会扩散到 MX-H2I 用户路径。

### 投资与商业决策者

- 看到平台复用率：第二、第三种技术栈接入时是否无需修改核心。
- 看到测试周期缩短、复现时间下降、质量证据可审计等可量化收益。
- 对外叙事聚焦“统一质量工作台和证据链”，不使用未经验证的覆盖率或 AI 替代人工等夸大说法。

## 能力范围

长期能力地图包括：

- 黑盒与白盒测试；
- Web / Electron e2e、冒烟、回归；
- API、契约、数据与 ETL 验证；
- pytest 等语言级测试；
- k6 等性能与容量场景；
- 网络和协议证据，例如未来受控接入 tshark；
- Agent 辅助生成、归纳和诊断，但生成的测试必须进入版本评审。

“长期能力地图”不是首版交付清单。首个可验证闭环只覆盖：

1. standalone launcher 下的 mx-launcher 账号登录；
2. Luopan / Compass Web 的 Cypress 自动化；
3. Luopan / Compass 打包 Electron 的 Playwright 技术验证；
4. 可追溯报告、视频和原生证据；
5. 部署与运行不影响 MX-H2I 现有登录和联网。

## 非目标

- 不替代语言自身的单元测试框架。
- 不把任意脚本编排扩张成通用 CI/CD DSL。
- 不在初期引入 Jenkins 作为强依赖。
- 不接管 mx-launcher Release Center、用户系统、DNS 或网络控制面。
- 不把 MX Autotest 放进 MX-H2I 的启动、登录、联网或发布关键路径。
- 不宣称一个“总覆盖率”代表产品质量。
- 不让运行时 AI 临时操作浏览器成为可重复回归的唯一执行方式。

## 产品原则

1. **风险先于工具**：先定义验证意图，再选择工具。
2. **证据先于结论**：每个状态必须能回到输入、日志和产物。
3. **受阻不等于失败，零用例绝不等于通过**。
4. **版本必须可还原**：应用、测试代码、工具链和配置都有不可变引用。
5. **新手有默认值，专家有逃生舱**。
6. **独立故障域**：测试平台可以停，MX-H2I 用户仍可正常登录和联网。
7. **低流量默认**：不直播视频，不反复下载相同工具，不为静态页面维持常驻连接。
8. **诚实宣传**：只宣传真实验证过的能力，并保留验证环境和日期。

## 产品语言与视觉方向

界面沿用 ui-design-neon-void 的深色优先、高信息密度和操作台语言。它应像一个专业测试工作台，而不是营销首页：

- 左侧以项目、运行、目录、runner、报告和设置组织导航；
- 主区域先展示风险与当前工作，再展示工具细节；
- 右侧 inspector 用于 source、toolchain、环境和 artifact 元数据；
- cyan 表示可操作与当前上下文，danger / warning / success 保留明确语义；
- blocked、failed、flaky 不能只靠颜色区分；
- 新手看到引导和解释，专家可展开原始配置与证据。

Neon Void 是共享 token 和组件体系，正式实现应直接复用 ui-design package，不复制 demo 页面里的局部样式或 Unicode 临时图标。

## Agent 与 MCP 的位置

如果 Cypress、Playwright 或其他工具提供官方 MCP 服务，可以把它作为 Agent 可调用的受控入口或开发辅助；它不替代 Run 合同：

- MCP 调用也要落到明确 Project / Suite / Run；
- 结果仍需 JUnit、sidecar 或可验证 artifact；
- MCP server 版本和权限必须固定；
- 一次探索性工具调用不能自动升级成稳定回归；
- 没有官方 MCP 不阻塞直接使用开源 CLI / library adapter。

## 成功指标

平台不以“工具数量”或“总运行次数”作为唯一成功指标。建议同时观察：

| 方向 | 指标示例 |
| --- | --- |
| 反馈速度 | P50 / P95 从触发到首个可行动失败的时间 |
| 可复现性 | 使用相同 source ref 和 toolchain digest 重跑的一致率 |
| 诊断效率 | 从失败到首次定位或创建缺陷的中位时间 |
| 目录诚实度 | notRun、unmapped、duplicate 的数量与关闭时间 |
| 稳定性 | blocked 率、flaky 率、runner 离线率 |
| 使用价值 | 活跃项目数、复用 adapter 数、人工走查时间节省 |
| 成本 | 单次 run 的计算、存储和网络成本 |
| 安全边界 | 对 MX-H2I 的变更数应为零，部署前后登录回归必须通过 |

这些指标必须按项目、表面、套件和时间窗口拆分，不能压成一个漂亮但不可解释的分数。
